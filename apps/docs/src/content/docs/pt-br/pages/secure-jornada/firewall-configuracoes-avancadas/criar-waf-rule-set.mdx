## Crie o rule set

Um rule set carrega até oito famílias de ameaças, cada uma com a sua própria sensibilidade. Toda família começa em `medium`, o nível de partida até que o seu tráfego mostre um motivo para aumentar alguma. Para o que cada família detecta e o que cada nível muda, consulte [WAF Rule Sets](/pt-br/documentacao/plataforma/firewall/waf/rule-sets/#familias-de-ameacas).

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

O formulário lista as oito famílias, então você define toda sensibilidade em um só lugar. Para criar o rule set no Azion Console:

<DocSteps>
  <DocStep title="Abra a página WAF Rules">

  Acesse [Azion Console](https://console.azion.com/) > **WAF Rules**.

  </DocStep>
  <DocStep title="Selecione WAF Rule" />
  <DocStep title="Dê um nome ao rule set">

  Na seção **General**, insira um **Name**. Por exemplo: `checkout-waf`.

  </DocStep>
  <DocStep title="Defina a sensibilidade de cada família de ameaças">

  A seção **Threat Type Configuration** lista oito famílias, cada uma em _Sensitivity Medium_. Por exemplo, defina **SQL Injection** como _Sensitivity High_ ou deixe toda família em _Sensitivity Medium_.

  </DocStep>
  <DocStep title="Mantenha o switch Active ligado" />
  <DocStep title="Salve o rule set" />
</DocSteps>

O rule set aparece em **WAF Rules**. Ele não pontua nenhuma requisição até que uma regra de um Firewall o aplique.

</Fragment>

<Fragment slot="panel.cli">

### CLI

O `--thresholds` recebe pares `threat=sensitivity` separados por vírgula. Para criar o rule set com a Azion CLI:

<DocSteps>
  <DocStep title="Execute o comando de criação">

  ```bash
  azion create waf --name "checkout-waf" --active true --rulesets 1 \
    --thresholds "sql_injection=medium,cross_site_scripting=medium,directory_traversal=medium,evading_tricks=medium,file_upload=medium,identified_attack=medium,remote_file_inclusion=medium,unwanted_access=medium"
  ```

  </DocStep>
  <DocStep title="Leia a saída">

  O comando imprime o ID do rule set:

  ```text
  Created WAF with ID <waf-id>
  ```

  </DocStep>
</DocSteps>

O rule set está ativo, no ruleset `1`, com toda família na sensibilidade que você enviou. Anote o ID: a regra da próxima seção o usa.

Uma criação que envia apenas `--name` também gera um rule set completo: ativo, no ruleset `1`, com a versão de engine `2021-Q3`, o tipo de engine `score` e as oito famílias em `medium`.

</Fragment>

<Fragment slot="panel.api">

Cada entrada de `thresholds` define uma família de ameaças e a sua sensibilidade. Para criar o rule set com a API:

<DocSteps>
  <DocStep title="Envie a requisição de criação">

  Substitua `[TOKEN VALUE]` pelo seu personal token:

  ```bash
  curl --request POST \
    --url https://api.azion.com/v4/workspace/wafs \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: application/json' \
    --data '{
    "name": "checkout-waf",
    "active": true,
    "engine_settings": {
      "engine_version": "2021-Q3",
      "type": "score",
      "attributes": {
        "rulesets": [1],
        "thresholds": [
          { "threat": "cross_site_scripting", "sensitivity": "medium" },
          { "threat": "directory_traversal", "sensitivity": "medium" },
          { "threat": "evading_tricks", "sensitivity": "medium" },
          { "threat": "file_upload", "sensitivity": "medium" },
          { "threat": "identified_attack", "sensitivity": "medium" },
          { "threat": "remote_file_inclusion", "sensitivity": "medium" },
          { "threat": "sql_injection", "sensitivity": "medium" },
          { "threat": "unwanted_access", "sensitivity": "medium" }
        ]
      }
    }
  }'
  ```

  </DocStep>
  <DocStep title="Leia a resposta">

  A API responde `202`, e `"state": "pending"` significa que o rule set ainda está propagando:

  ```json

      "product_version": "1.0",
      "engine_settings": {
        "engine_version": "2021-Q3",
        "type": "score",
        "attributes": {
          "rulesets": [1],
          "thresholds": [
            { "threat": "cross_site_scripting", "sensitivity": "medium" },
            { "threat": "directory_traversal", "sensitivity": "medium" },
            { "threat": "evading_tricks", "sensitivity": "medium" },
            { "threat": "file_upload", "sensitivity": "medium" },
            { "threat": "identified_attack", "sensitivity": "medium" },
            { "threat": "remote_file_inclusion", "sensitivity": "medium" },
            { "threat": "sql_injection", "sensitivity": "medium" },
            { "threat": "unwanted_access", "sensitivity": "medium" }
          ]
        }
      },
      "version_id": null,
      "version_state": null,
      "is_versioned": false,
      "version": null
    }
  }
  ```

  </DocStep>
</DocSteps>

Anote o `id`. A regra da próxima seção o usa.

:::note[nota]
Um array `thresholds` com menos de oito entradas é aceito, e o rule set então carrega apenas as famílias que você enviou. Um `threat` repetido é recusado com `500` e `10067 Internal Server Error`.
:::

No caso de uso [Proteger aplicações web contra ataques do OWASP Top 10 e zero-day](/pt-br/documentacao/casos-de-uso/proteger-aplicacoes-e-redes/proteger-aplicacoes-web-contra-ataques-do-owasp-top-10-e-zero-day/), esta seção usa estes valores:

| Configuração | Valor |

## Aplique o rule set a toda requisição

Uma regra do [Rules Engine para Firewall](/pt-br/documentacao/plataforma/firewall/rules-engine/) seleciona requisições por critérios, e o seu behavior _Set WAF_ aplica um rule set em um modo. Uma regra carrega no máximo um behavior _Set WAF_. O modo é obrigatório: `logging` registra o que o rule set sinaliza e serve a requisição, e `blocking` recusa a requisição com `400`.

:::caution[Atenção]
Um critério em `${request_args}` corresponde apenas a uma requisição que carrega uma query string. Um `POST` com os seus campos no corpo e sem query string então pula o rule set e chega à sua Application sem ser pontuado. Baseie o critério em `${request_uri}`.
:::

<Fragment slot="panel.console">

### Console

Para aplicar o rule set a toda requisição no Azion Console:

<DocSteps>
  <DocStep title="Abra o Firewall">

  Acesse [Azion Console](https://console.azion.com/) > **Firewalls** e selecione o Firewall.

  </DocStep>
  <DocStep title="Selecione a aba Rules Engine" />
  <DocStep title="Selecione Rule" />
  <DocStep title="Dê um nome à regra">

  Insira um nome. Por exemplo: `Apply checkout-waf`.

  </DocStep>
  <DocStep title="Defina o critério">

  Na seção **Criteria**, selecione a variável `Request Uri`, o operador _starts with_ e `/` como argumento.

  </DocStep>
  <DocStep title="Adicione o behavior Set WAF">

  Na seção **Behaviors**, selecione **Set WAF** e então selecione `checkout-waf` como o rule set e _Blocking_ como o modo.

  </DocStep>
  <DocStep title="Salve a regra" />
</DocSteps>

</Fragment>

<Fragment slot="panel.cli">

### CLI

O `azion create firewall-rule` lê a regra de `--file`, então o behavior e o modo vão no JSON. Para aplicar o rule set com a Azion CLI:

<DocSteps>
  <DocStep title="Escreva a regra em um arquivo">

  Salve o seguinte como `fw-rule.json`, com o ID do seu rule set em `waf_id`:

  ```json
  {
    "name": "Apply checkout-waf",
    "active": true,
    "description": "",
    "criteria": [
      [
        {
          "conditional": "if",
          "variable": "${request_uri}",
          "operator": "starts_with",
          "argument": "/"
        }
      ]
    ],
    "behaviors": [
      {
        "type": "set_waf",
        "attributes": {
          "waf_id": 12350,
          "mode": "blocking"
        }
      }
    ]
  }
  ```

  </DocStep>
  <DocStep title="Crie a regra">

  Substitua `<firewall-id>` pelo ID do seu Firewall:

  ```bash
  azion create firewall-rule --firewall-id <firewall-id> --file fw-rule.json
  ```

  </DocStep>
  <DocStep title="Leia a saída">

  O comando imprime o ID da regra:

  ```text
  Created Firewall Rule with ID <rule-id>
  ```

  </DocStep>
</DocSteps>

</Fragment>

<DocSteps>

  Salve o seguinte como `rule.json`, com o ID do seu rule set em `waf_id`:

  ```json
  {
    "name": "Apply checkout-waf",
    "active": true,
    "criteria": [
      [
        {
          "conditional": "if",
          "variable": "${request_uri}",
          "operator": "starts_with",
          "argument": "/"
        }
      ]
    ],
    "behaviors": [
      {
        "type": "set_waf",
        "attributes": {
          "waf_id": 12349,
          "mode": "blocking"
        }
      }
    ]
  }
  ```

  </DocStep>
  <DocStep title="Envie a requisição de criação">

  Substitua `<firewall-id>` pelo ID do seu Firewall:


  </DocStep>
  <DocStep title="Leia a resposta">

  A API responde `202` com a regra e dois campos que ela acrescenta, `description` e `order`:

  ```json
  {
    "state": "pending",
    "data": {
      "id": 123456,
      "name": "Apply checkout-waf",
      "last_editor": "user@example.com",
      "last_modified": "2026-01-01T12:00:00.000000Z",
      "created_at": "2026-01-01T12:00:00.000000Z",
      "active": true,
      "criteria": [
        [
          {
            "conditional": "if",
            "variable": "${request_uri}",
            "operator": "starts_with",
            "argument": "/"
          }
        ]
      ],
      "behaviors": [
        {
          "type": "set_waf",
          "attributes": {
            "waf_id": 12349,
            "mode": "blocking"
          }
        }
      ],
      "description": "",
      "order": 1
    }
  }
  ```

  </DocStep>
</DocSteps>

Um behavior `set_waf` sem `mode` é recusado com `400`:

```json
{"errors":[{"code":"10059","title":"Required Field","detail":"This field is required.","status":"400","source":{"pointer":"/data/behaviors/0/attributes/mode"}}]}
```

O `mode` aceita `logging` ou `blocking`. Qualquer outro valor é recusado com `400` e `10039 Invalid Choice`, e um segundo behavior `set_waf` em uma regra, com `25011 Duplicated Behavior`.

</Fragment>

</Tabs>

O Firewall aplica o rule set a toda requisição dos Workloads cujo deployment o define e recusa com `400` uma requisição que o rule set bloqueia. Uma nova regra propaga pela infraestrutura distribuída da Azion antes que as requisições a reflitam. Para mais informações, consulte [Propagação](/pt-br/documentacao/plataforma/firewall/como-funciona/#propagacao).

## Aplique um rule set a caminhos selecionados em Logging

Uma regra pode aplicar um rule set apenas aos caminhos que precisam dele, como um formulário de login, em modo _Logging_. Você então lê o que o rule set sinaliza no seu próprio tráfego antes que ele recuse qualquer coisa. A regra corresponde aos caminhos, não à query string, porque um formulário envia os seus campos no corpo.

O exemplo aplica `auth-waf` a `/login`, `/signup` e `/checkout`. Substitua cada valor pelo seu.

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

Para aplicar o rule set aos três caminhos no Azion Console:

<DocSteps>
  <DocStep title="Abra a aba Rules Engine do Firewall">

  Acesse [Azion Console](https://console.azion.com/) > **Firewalls**, selecione o Firewall e vá para a aba **Rules Engine**.

  </DocStep>
  <DocStep title="Selecione Rule" />
  <DocStep title="Dê um nome à regra">

  Insira `auth - apply auth-waf`.

  </DocStep>
  <DocStep title="Corresponda aos três caminhos">

  Na seção **Criteria**, selecione `Request Uri`, _starts with_ e `/login`. Adicione dois critérios unidos por **Or**: `/signup` e `/checkout`.

  </DocStep>
  <DocStep title="Adicione o behavior Set WAF">

  Na seção **Behaviors**, selecione **Set WAF** e então `auth-waf` e _Logging_.

  </DocStep>
  <DocStep title="Salve a regra" />
</DocSteps>

</Fragment>

<Fragment slot="panel.cli">

### CLI

Para aplicar o rule set aos três caminhos com a Azion CLI:

<DocSteps>
  <DocStep title="Escreva a regra em um arquivo">

  Salve o seguinte como `auth-rule.json`, com o ID do seu rule set em `waf_id`:

  ```json
  {
    "name": "auth - apply auth-waf",
    "active": true,
    "criteria": [
      [
        { "variable": "${request_uri}", "conditional": "if", "operator": "starts_with", "argument": "/login" },
        { "variable": "${request_uri}", "conditional": "or", "operator": "starts_with", "argument": "/signup" },
        { "variable": "${request_uri}", "conditional": "or", "operator": "starts_with", "argument": "/checkout" }
      ]
    ],
    "behaviors": [{ "type": "set_waf", "attributes": { "waf_id": 12351, "mode": "logging" } }]
  }
  ```

  </DocStep>
  <DocStep title="Crie a regra">

  ```bash
  azion create firewall-rule --firewall-id <firewall-id> --file auth-rule.json
  ```

  O comando imprime `Created Firewall Rule with ID <rule-id>`.

  </DocStep>
</DocSteps>

</Fragment>

<Fragment slot="panel.api">

### API

Para aplicar o rule set aos três caminhos com a API:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules \
  --header 'Authorization: Token [TOKEN VALUE]' \
  --header 'Content-Type: application/json' \
  --data '{
  "name": "auth - apply auth-waf",
  "active": true,
  "criteria": [
    [
      { "variable": "${request_uri}", "conditional": "if", "operator": "starts_with", "argument": "/login" },
      { "variable": "${request_uri}", "conditional": "or", "operator": "starts_with", "argument": "/signup" },
      { "variable": "${request_uri}", "conditional": "or", "operator": "starts_with", "argument": "/checkout" }
    ]
  ],
  "behaviors": [{ "type": "set_waf", "attributes": { "waf_id": 12351, "mode": "logging" } }]
}'
```

A API responde `202` com um `state` `pending` e a regra como foi armazenada.

</Fragment>
</Tabs>

O rule set pontua as requisições aos três caminhos e registra o que bloquearia, com `wafLearning` em `1` e `wafAttackAction` em `$LEARNING-BLOCK` no Real-Time Events. Mude a regra para _Blocking_ quando os últimos 3 dias de [Tuning](/pt-br/documentacao/guias/seguranca-de-aplicacoes/firewall-e-waf/tune-waf/) não tiverem nenhuma requisição que deveria ter sido servida. Para a mudança, consulte [Altere o modo](/pt-br/documentacao/guias/seguranca-de-aplicacoes/firewall-e-waf/como-verificar-modo-do-seu-waf/#altere-o-modo).

Para confirmar que a regra pontua os caminhos, envie uma query string com formato de injeção a um deles:

```bash
curl -i "https://www.example.com/login?q=1%27%20OR%20%271%27%3D%271"
```

Em modo _Logging_, a requisição chega à sua Application. Depois da mudança para _Blocking_, a mesma requisição recebe:

```text
HTTP/2 400
```

O header `x-azion-request-id` da resposta encontra o registro do WAF da requisição. Para a busca, consulte [Encontre o score do WAF de uma requisição bloqueada](/pt-br/documentacao/guias/seguranca-de-aplicacoes/firewall-e-waf/como-encontrar-score-de-requisicoes-bloqueadas-pelo-waf/).

No caso de uso [Proteger aplicações web contra ataques do OWASP Top 10 e zero-day](/pt-br/documentacao/casos-de-uso/proteger-aplicacoes-e-redes/proteger-aplicacoes-web-contra-ataques-do-owasp-top-10-e-zero-day/), esta seção usa estes valores:

| Configuração | Valor |
| --- | --- |
| Regra | `webapp - apply webapp-waf` |
| Critério | `Request Uri` _starts with_ `/` |
| Behavior | **Set WAF** com `webapp-waf`, em _Logging_, enviado na API como `"mode": "logging"` |

O rule set pontua toda requisição que a regra de rede do caso de uso deixa passar e registra o que bloquearia. Para ler esses registros e transformar um falso positivo em uma exceção, consulte [Ajuste um WAF rule set](/pt-br/documentacao/guias/seguranca-de-aplicacoes/firewall-e-waf/tune-waf/).

No caso de uso [Proteger APIs públicas contra abuso](/pt-br/documentacao/casos-de-uso/proteger-aplicacoes-e-redes/proteger-apis-publicas-contra-abuso/), esta seção usa estes valores:

| Configuração | Valor |
| --- | --- |
| Regra | `api - apply api-waf` |
| Critério | `Request Uri` _starts with_ `/v1/` |
| Behavior | **Set WAF** com `api-waf`, em _Logging_, enviado na API como `"mode": "logging"` |

O rule set pontua toda requisição a `/v1/` contra `api-waf` e registra o que bloquearia.

O caso de uso [Bloquear account takeover em fluxos de login e checkout](/pt-br/documentacao/casos-de-uso/proteger-aplicacoes-e-redes/bloquear-account-takeover-em-fluxos-de-login-e-checkout/) usa os valores deste exemplo.

No caso de uso [Proteger aplicações web contra ataques do OWASP Top 10 e zero-day](/pt-br/documentacao/casos-de-uso/proteger-aplicacoes-e-redes/proteger-aplicacoes-web-contra-ataques-do-owasp-top-10-e-zero-day/), espere:

- **O WAF pontua um padrão de ataque.** A partir de um endereço que não está na lista, uma requisição com uma query string com formato de injeção, `https://www.example.com/?q=1%27%20OR%20%271%27%3D%271`, é respondida normalmente em _Logging_ e recebe `HTTP/2 400` depois da mudança para _Blocking_. O header `x-azion-request-id` da resposta encontra a requisição no dataset `workloadEvents` do Real-Time Events, onde `wafMatch` indica as regras internas que corresponderam, `1009` e `1013` para essa query string. Para a busca, consulte [Encontre o score do WAF de uma requisição bloqueada](/pt-br/documentacao/guias/seguranca-de-aplicacoes/firewall-e-waf/como-encontrar-score-de-requisicoes-bloqueadas-pelo-waf/).

No caso de uso [Proteger APIs públicas contra abuso](/pt-br/documentacao/casos-de-uso/proteger-aplicacoes-e-redes/proteger-apis-publicas-contra-abuso/), espere:

- **O WAF pontua um padrão de ataque.** Com um token válido, uma requisição com uma query string com formato de injeção, `https://api.example.com/v1/orders?q=1%27%20OR%20%271%27%3D%271`, é respondida normalmente em _Logging_ e recebe `HTTP/2 400` depois da mudança para _Blocking_. O `x-azion-request-id` dela encontra o registro no Real-Time Events.

No caso de uso [Bloquear account takeover em fluxos de login e checkout](/pt-br/documentacao/casos-de-uso/proteger-aplicacoes-e-redes/bloquear-account-takeover-em-fluxos-de-login-e-checkout/), espere:

- **O WAF pontua ataques em `/v1/`.** Uma requisição a `/v1/` com uma query string com formato de injeção é respondida normalmente em _Logging_ e recebe `HTTP/2 400` depois da mudança para _Blocking_. O `x-azion-request-id` dela encontra o registro no Real-Time Events.

No caso de uso [Preparar aplicações web reguladas para auditorias de segurança](/pt-br/documentacao/casos-de-uso/proteger-aplicacoes-e-redes/preparar-aplicacoes-web-reguladas-para-auditorias-de-seguranca/), espere:

- **Os padrões de ataque são filtrados.** Envie `https://www.example.com/?q=1%27%20OR%20%271%27%3D%271`. Com a regra do WAF em _Blocking_, a resposta é `400`.
