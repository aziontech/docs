Você pode criar uma regra no [Rules Engine](/pt-br/documentacao/plataforma/firewall/rules-engine/) de um [Firewall](/pt-br/documentacao/plataforma/firewall/) pelo Azion Console, pela Azion CLI ou pela API. A primeira regra desta página nega um caminho de teste, então uma única requisição confirma que o Firewall a aplica. A segunda, criada no Azion Console, recusa um cliente que não apresenta certificado.

Uma Application carrega um Rules Engine próprio. Uma regra que adiciona um header de requisição para a sua origem pertence ao [Rules Engine para Applications](/pt-br/documentacao/plataforma/applications/rules-engine/).

## Negue requisições a um caminho

A regra desta seção corresponde às requisições cujo caminho começa com `/deny-test` e as recusa com `403`. As requisições para qualquer outro caminho continuam chegando à sua Application. O critério também corresponde a caminhos mais longos que começam com os mesmos caracteres, como `/deny-test-old`.

Nem o critério _Request Uri_ nem o comportamento _Deny (403 Forbidden)_ precisam de um switch específico no Firewall. Um Firewall aceita regras apenas enquanto pelo menos um entre [Web Application Firewall (WAF)](/pt-br/documentacao/plataforma/firewall/waf/), [Network Shield](/pt-br/documentacao/plataforma/firewall/network-shield/) e [Functions](/pt-br/documentacao/plataforma/firewall/functions/) está ativado, e um Firewall novo começa com Network Shield e Functions ativados. Outros critérios e comportamentos precisam de um switch específico. Para a lista completa, consulte [Rules Engine para Firewall](/pt-br/documentacao/plataforma/firewall/rules-engine/#criterios).

<Fragment slot="panel.console">

### Console

Para criar a regra no Azion Console:

<DocSteps>
  <DocStep title="Abra o Firewall que o seu Workload define">

  Acesse [Azion Console](https://console.azion.com/) > **Firewalls** e selecione o Firewall.

  </DocStep>
  <DocStep title="Selecione a aba Rules Engine" />
  <DocStep title="Inicie uma nova regra">

  Selecione **Rule**. O drawer **Create Rule** abre.

  </DocStep>
  <DocStep title="Dê um nome à regra">

  Na seção **General**, informe um **Name**, como `deny-test-path`.

  </DocStep>
  <DocStep title="(Opcional) Descreva a regra">

  Em **Description**, informe uma nota curta sobre o que a regra faz.

  </DocStep>
  <DocStep title="Defina o critério">

  Na seção **Criteria**, a primeira condição abre com a variável _Request Uri_ e o operador _starts with_. Informe `/deny-test` como argumento.

  </DocStep>
  <DocStep title="Adicione o comportamento">

  Na seção **Behaviors**, selecione _Deny (403 Forbidden)_.

  </DocStep>
  <DocStep title="Salve a regra">

  Selecione **Save**.

  </DocStep>
</DocSteps>

Azion Console mostra `Rule successfully created`. A regra aparece na aba **Rules Engine** com _Active_ na coluna **Status**.

</Fragment>

<Fragment slot="panel.cli">

### CLI

Para criar a regra pela Azion CLI, salve a definição dela como `rule.json`. O arquivo carrega o `name` da regra, se ela está `active`, os `criteria` e os `behaviors` dela:

```json
{
  "name": "deny-test-path",
  "active": true,
  "criteria": [
    [
      {
        "variable": "${request_uri}",
        "conditional": "if",
        "operator": "starts_with",
        "argument": "/deny-test"
      }
    ]
  ],
  "behaviors": [
    {
      "type": "deny"
    }
  ]
}
```

`criteria` é uma lista de grupos, e cada grupo é uma lista de condições. A primeira condição recebe `"conditional": "if"`, e cada condição seguinte recebe `and` ou `or`.

Depois, crie a regra no seu Firewall, com o ID dele no lugar de `<firewall-id>`:

```bash
azion create firewall-rule --firewall-id <firewall-id> --file rule.json
```

O comando imprime o ID da nova regra:

```text
Created Firewall Rule with ID <rule-id>
```

A regra fica ativa no Firewall, porque o arquivo define `"active": true`. `azion create firewall-rule` aceita apenas `--firewall-id` e `--file`. O arquivo contém o mesmo corpo que a API aceita.

</Fragment>

<Fragment slot="panel.api">

### API

Para criar a regra pela API, envie uma requisição `POST` para o endpoint `request_rules` do seu Firewall. O corpo carrega o `name` da regra, se ela está `active`, os `criteria` e os `behaviors` dela:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules \
  --header 'Accept: application/json' \
  --header 'Authorization: Token [TOKEN VALUE]' \
  --header 'Content-Type: application/json' \
  --data '{
  "name": "deny-test-path",
  "active": true,
  "criteria": [
    [
      {
        "variable": "${request_uri}",
        "conditional": "if",
        "operator": "starts_with",
        "argument": "/deny-test"
      }
    ]
  ],
  "behaviors": [
    {
      "type": "deny"
    }
  ]
}'
```

`criteria` é uma lista de grupos, e cada grupo é uma lista de condições. A primeira condição recebe `"conditional": "if"`, e cada condição seguinte recebe `and` ou `or`. Uma chave opcional `description` contém uma nota sobre a regra.

A API responde `202` e retorna a regra:

```text
{"state":"pending","data":{"id":<rule-id>,…,"behaviors":[{"type":"deny"}],"description":"","order":0}}
```

A resposta acrescenta o `id` da regra, uma `description` vazia e a `order` dela. A `order` é a posição da regra entre as regras do Firewall, contada a partir de `0`. Envie o corpo como `application/json`: qualquer outro `Content-Type` é recusado com `415` e o erro `10009 Unsupported Media Type`.

Para todas as variáveis, operadores e comportamentos que o corpo aceita, consulte [Rules Engine para Firewall](/pt-br/documentacao/plataforma/firewall/rules-engine/#api) e a [referência da Azion API](https://api.azion.com/).

</Fragment>

</Tabs>

O Firewall executa as regras na ordem da lista, e um comportamento `deny` encerra a lista para a requisição que ele recusa. Para mais informações, consulte [Ordem das regras](/pt-br/documentacao/plataforma/firewall/como-funciona/#ordem-das-regras).

## Confirme que a regra nega o caminho

Uma regra nova chega ao tráfego vários minutos depois que você a cria, e nenhuma duração é garantida. Até lá, `/deny-test` responde como antes. Enquanto a alteração se propaga, as requisições podem receber a resposta antiga e a nova, alternadamente. Para as durações observadas, consulte [Propagação](/pt-br/documentacao/plataforma/firewall/como-funciona/#propagacao).

Para confirmar a regra, envie uma requisição para o caminho de teste, com um domínio do seu Workload no lugar de `<your-domain>`:

```bash
curl -i https://<your-domain>/deny-test
```

O Firewall recusa a requisição com `403`. Este trecho da resposta omite o longo header `content-security-policy`:

```text
HTTP/2 403
server: nginx
date: Thu, 01 Jan 2026 12:00:00 GMT
content-type: text/html; charset=utf-8
x-content-type-options: nosniff
x-azion-request-id: 0123456789abcdef0123456789abcdef
x-azion-edge-location: <edge-location>
alt-svc: h3=":443"; ma=86400
```

O corpo é a página de erro padrão da Azion. Ele mostra `Forbidden` e o mesmo ID de requisição do header `x-azion-request-id`. Uma requisição para qualquer outro caminho continua chegando à sua Application.

Se `/deny-test` continuar chegando à sua Application depois de vários minutos de requisições repetidas, consulte [Solucione problemas de Firewall](/pt-br/documentacao/plataforma/firewall/solucao-de-problemas/#uma-regra-ainda-nao-age-sobre-as-requisicoes).

## Exija um certificado de cliente

A regra desta seção corresponde a uma requisição cujo cliente não apresenta certificado e a responde com `401` e um corpo JSON. Use-a para aplicar uma política de mTLS, como a que o compliance do BACEN exige. Como a primeira regra, ela não precisa de nenhum switch específico no Firewall.

Para criar a regra no Azion Console:

<DocSteps>
  <DocStep title="Abra o Firewall que o seu Workload define">

  Acesse [Azion Console](https://console.azion.com/) > **Firewalls** e selecione o Firewall.

  </DocStep>
  <DocStep title="Selecione a aba Rules Engine" />
  <DocStep title="Inicie uma nova regra">

  Selecione **Rule**.

  </DocStep>
  <DocStep title="Dê um nome à regra">

  Na seção **General**, informe um **Name**, como `require-client-certificate`.

  </DocStep>
  <DocStep title="Defina o critério">

  Na seção **Criteria**, selecione _Ssl Verification Status_ como a variável e _is equal_ como o operador. Em **Select an SSL status**, selecione _Missing Client Certificate_.

  </DocStep>
  <DocStep title="Adicione o comportamento">

  Na seção **Behaviors**, selecione _Set Custom Response_ como o comportamento.

  </DocStep>
  <DocStep title="Informe o código de status">

  Em **Status Code**, informe `401`.

  </DocStep>
  <DocStep title="Informe o tipo de conteúdo">

  Em **Content Type**, informe o tipo MIME do corpo da resposta, como `application/json`.

  </DocStep>
  <DocStep title="Informe o corpo da resposta">

  Em **Content Body**, informe a mensagem que o cliente recebe, como `{}`.

  </DocStep>
  <DocStep title="Salve a regra">

  Selecione **Save**.

  </DocStep>
</DocSteps>

Azion Console mostra `Rule successfully created`. Quando a regra chega ao tráfego, uma requisição a que o critério dela corresponde recebe `401` e o corpo que você informou.

Para todas as opções deste critério e deste comportamento, consulte [Rules Engine para Firewall](/pt-br/documentacao/plataforma/firewall/rules-engine/#set-custom-response).

Para encaminhar à sua origem o Common Name (CN) do certificado do cliente, use [Rules Engine para Applications](/pt-br/documentacao/plataforma/applications/rules-engine/) em vez disso. Lá, um comportamento que adiciona um header de requisição, como `client_cn`, envia a variável `${ssl_client_s_dn_parsed}`. Para a configuração completa, consulte [Passe os detalhes do certificado de cliente para a origem](/pt-br/documentacao/guias/seguranca-de-aplicacoes/tls-e-certificados/associar-um-certificado-mtls/#passe-os-detalhes-do-certificado-de-cliente-para-a-origem).
