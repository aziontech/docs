**Applications** é um recurso da plataforma que processa as requisições recebidas pelos seus [Workloads](/pt-br/documentacao/plataforma/workloads/), a partir do data center mais próximo ao seu usuário. Uma Application pode executar funções serverless, atuar como proxy reverso para as suas origens ou combinar os dois. Ela também pode armazenar respostas com [Cache](/pt-br/documentacao/plataforma/applications/cache/), liberar quatro capacidades para o cache e as regras com [Application Accelerator](/pt-br/documentacao/plataforma/applications/application-accelerator/) e transformar imagens com [Image Processor](/pt-br/documentacao/plataforma/applications/image-processor/). Use Applications para executar uma [Function](/pt-br/documentacao/plataforma/functions/), definir o [Connector](/pt-br/documentacao/plataforma/connectors/) que chega a cada origem, adicionar ou remover headers ou reescrever requisições.

Cada Application pode usar estes recursos aninhados e features:

- [Cache](/pt-br/documentacao/plataforma/applications/cache/) permite que uma Application responda a uma requisição com uma cópia de uma resposta anterior da origem. Por exemplo, os seus arquivos estáticos ficam no data center mais próximo ao seu usuário.
- [Application Accelerator](/pt-br/documentacao/plataforma/applications/application-accelerator/) é a escolha certa quando uma URL tem mais de uma resposta correta, como uma página personalizada ou a resposta a um `POST`. Cache então guarda uma cópia separada por valor de argumento de query string, cookie, device group ou método.
- [Image Processor](/pt-br/documentacao/plataforma/applications/image-processor/) atende a uma página que precisa de uma imagem em vários tamanhos, recortes, qualidades ou formatos, como WEBP para navegadores que o aceitam. Cada variante sai de um arquivo único na origem, o único que você armazena e envia.
- [Device Groups](/pt-br/documentacao/plataforma/applications/device-groups/) permite que uma Application diferencie os dispositivos que enviam as suas requisições, para que uma regra ou um cache setting trate cada grupo de forma diferente. Ele precisa de Application Accelerator ativo na Application.
- [Rules Engine para Applications](/pt-br/documentacao/plataforma/applications/rules-engine/) é onde você escreve o que uma Application faz com cada requisição que recebe. Por exemplo, uma regra pode encaminhar `/api/` para uma origem enquanto uma segunda regra encaminha todos os outros paths para outra.
- [WebSocket Proxy](/pt-br/documentacao/plataforma/applications/websocket/) permite que uma Application transporte uma conexão WebSocket entre os seus usuários e a sua origem. A Azion o ativa em uma conta somente mediante solicitação.
- Uma [Function Instance](/pt-br/documentacao/plataforma/applications/functions-instances/) permite que uma Application execute uma das suas Functions. Por exemplo, a mesma Function pode ser executada em mais de uma Application, cada Function Instance com os seus próprios argumentos.

## Caminho da requisição

Criar uma Application não lhe encaminha requisições: elas só chegam a ela depois que o deployment de um Workload define essa Application. A Application então só chega a uma origem por meio de uma regra que define um Connector. No lugar de uma origem, uma regra pode executar uma Function que constrói a resposta sem nenhum Connector.

O diagrama acompanha uma requisição que chega a uma origem. As setas sólidas levam a requisição, e as setas pontilhadas levam a resposta. Cada rótulo começa com o número do seu passo abaixo.

```mermaid
  Client(["Cliente"])
  WL["Workload"]
  FW["Firewall"]
  App["Application"]
  Cache["Cache"]
  Conn["Connector"]
  Origin[["servidor de origem"]]
  Client -->|"1. requisição"| WL
  WL -->|"1. com Firewall"| FW
  WL -->|"1. sem Firewall"| App
  FW -->|"1. permitida"| App
  FW -.->|"1. recusa"| Client
  App -.->|"2. Deny (403)"| Client
  App -->|"3. cache setting"| Cache
  Cache -.->|"3. cópia válida"| App
  App -->|"4. sem cópia válida"| Conn
  Conn -->|"4. requisição"| Origin
  Origin -.->|"4. resposta"| Conn
  Conn -.->|"4. resposta"| App
  App -.->|"5. resposta"| Client
```

1. A requisição chega a um Workload por um dos domínios dele, e o Workload a encaminha para a Application. Quando o deployment do Workload também define um [Firewall](/pt-br/documentacao/plataforma/firewall/), o Firewall executa as suas regras primeiro e pode recusar a requisição.
2. A Application executa as suas regras da Request Phase em ordem. Quando um behavior, a ação que uma regra executa, encerra o processamento, como faz _Deny (403 Forbidden)_, a Application responde ao cliente e nenhuma regra posterior é executada.
3. Uma regra com _Set Cache Policy_ pode aplicar um cache setting, o conjunto de valores que diz ao Cache como armazenar e servir uma resposta. Cache então procura uma cópia válida da resposta da origem. Se Cache tem uma, essa cópia se torna a resposta, e a origem não recebe nenhuma requisição.
4. Caso contrário, o Connector que uma regra com _Set Connector_ define encaminha a requisição à origem. Se várias regras correspondentes carregam _Set Connector_, somente a última delas é executada.
5. A Application executa as suas regras da Response Phase sobre a resposta, e a resposta chega ao cliente.
