Uma Function em um [Firewall](/pt-br/documentacao/plataforma/firewall/) é uma [Function](/pt-br/documentacao/plataforma/functions/) cujo código JavaScript o Firewall executa em uma requisição antes que a [Application](/pt-br/documentacao/plataforma/applications/) a receba. Um comportamento _Run Function_ a executa por meio de uma [Function Instance](/pt-br/documentacao/plataforma/firewall/functions-instances/), e o código dela deixa a requisição seguir ou a nega, a descarta ou a responde. O código que serve uma requisição que o Firewall permitiu é executado em uma Application, a partir de uma Function cujo ambiente de execução é `application`.

---

## Ambiente de execução

Toda Function carrega um ambiente de execução, e um Firewall executa somente uma Function cujo ambiente é `firewall`. Você define o ambiente ao criar a Function em [Functions](/pt-br/documentacao/plataforma/functions/):

| Interface | Configuração | Valor para uma Function em um Firewall |
| --- | --- | --- |
| API | `execution_environment`, um campo da Function | `firewall` |
| Azion CLI | `--execution-environment`, uma flag de `azion create function` | `firewall` |

O campo da API recebe `application` ou `firewall`, e o padrão é `application`. Uma Function criada sem o campo é uma Function `application`, e a API recusa uma Function Instance dela em um Firewall com `29001`. Para a Function Instance que coloca essa Function em uma Application, consulte [Function Instances](/pt-br/documentacao/plataforma/applications/functions-instances/).

A ajuda da CLI diz `Either 'edge_application' or 'edge_firewall'` para a flag. Nenhum dos dois valores está no enum da API, e a API recusa ambos com `10039`. `azion describe function --function-id <function-id> --format json` imprime o campo de uma Function existente, como `"execution_environment": "application"`.

No Azion Console, o campo **Function** de uma Function Instance lista somente as Functions cujo ambiente é `firewall`.

Uma Function com o ambiente `firewall` ainda não é executada em nenhuma requisição até que outras duas entidades apontem para ela. Uma Function Instance coloca a Function em um Firewall, e o comportamento _Run Function_ de uma regra executa essa Function Instance. Para escrever essa regra, consulte [Run Function](/pt-br/documentacao/plataforma/firewall/rules-engine/#run-function).

O Firewall também precisa ter Functions ativado. Até que tenha, o Azion Console oculta a aba **Functions Instances** do Firewall e lista o comportamento como _Run Function - required Functions_, que não pode ser selecionado. O switch **Functions** fica na seção **Modules** da aba **Main Settings** do Firewall. Um Firewall criado pela API, pela CLI ou pela página de criação do Console começa com Functions ativado, e o drawer de criação do Console começa com ele desativado.

## O evento firewall

Uma Function em um Firewall registra um listener para o evento `firewall` com `addEventListener`. O listener recebe o evento, que carrega a requisição em `event.request` e os métodos que decidem o que acontece com ela.

Para ler um header que a requisição já carrega, chame `event.request.headers.get(<name>)`. O exemplo [Functions em um firewall](/pt-br/documentacao/plataforma/functions/general-firewall-example/) lê vários headers da requisição dessa forma para escolher o que o seu handler faz.

Toda Function em um Firewall precisa terminar com um resultado final, como `event.continue()`, `event.deny()` ou `event.drop()`. Um listener que retorna sem um resultado responde à requisição com HTTP 500, e uma chamada a `event.continue()` depois de `event.deny()` ou de `event.drop()` também. Para escrever condicionais que sempre chegam a um resultado, consulte [Boas práticas de Firewall](/pt-br/documentacao/plataforma/firewall/boas-praticas/).

## Métodos do evento

A tabela lista os métodos que uma Function em um Firewall chama no evento `firewall`, e a propriedade `event.args`, em ordem alfabética.

| Método | Argumentos | O que faz |
| --- | --- | --- |
| `event.addRequestHeader()` | Um nome de header e o seu valor | Adiciona o header à requisição que a Application recebe |
| `event.addResponseHeader()` | Um nome de header e o seu valor | Adiciona o header à resposta que o cliente recebe |
| `event.args` | Nenhum. É uma propriedade, não um método | Um objeto com uma chave por argumento dos **Arguments** da Function Instance, lido como `event.args.arg_name` |
| `event.continue()` | Nenhum | Encerra a Function com um resultado final. O Firewall retoma o processamento a partir do comportamento _Run Function_ que executou a Function Instance |
| `event.deny()` | Nenhum | Finaliza a requisição com HTTP `403 Forbidden`. O status, o corpo e o motivo são fixos |
| `event.drop()` | Nenhum | Finaliza a requisição sem resposta ao cliente |
| `event.respondWith()` | Um objeto `Response` | Intercepta a requisição e a responde com uma resposta personalizada, cujo status, headers e conteúdo o objeto define |
| `event.waitUntil()` | Uma promise, como a que um handler `async` retorna | Executa um handler `async` a partir do listener síncrono. Sem ele, um handler que responde depois de um `await` encerra a requisição com HTTP 500 |

No padrão ES Modules, o handler `firewall` chama esses métodos em `ctx`, o terceiro argumento dele. Em [código que o Azion Bundler não empacotou](/pt-br/documentacao/devtools/runtime/api-reference/handlers/#handler-firewall), ele lê os **Arguments** da Function Instance em `ctx.args`. Os métodos são `ctx.addRequestHeader()`, `ctx.addResponseHeader()`, `ctx.continue()`, `ctx.deny()`, `ctx.drop()`, `ctx.respondWith()` e `ctx.waitUntil()`, e cada um se comporta como o método do evento com o mesmo nome. Para o handler e o `ctx` dele, consulte [Handlers](/pt-br/documentacao/devtools/runtime/api-reference/handlers/#handler-firewall).

No padrão ES Modules, o handler `firewall` precisa ser uma função `async`. Em código que o Azion Bundler não empacotou, um handler síncrono responde a toda requisição com HTTP 500. Os logs da Function registram `TypeError: firewall handler must be an async function`. Em uma Function com build feito pela Azion CLI 4.23.0, `ctx` carrega apenas `waitUntil`, então `ctx.deny()` lança um erro e a requisição responde HTTP 500.

### event.addRequestHeader

`event.addRequestHeader()` adiciona um header à requisição que a Application recebe. Ele recebe dois argumentos, o nome do header e o seu valor. Este listener adiciona dois headers e deixa a requisição seguir:

```javascript
  addEventListener("firewall", (event) => {
      event.addRequestHeader("X-Custom-Header-1", "1");
      event.addRequestHeader("X-Custom-Header-2", "2");
      event.continue();
  });
```

### event.addResponseHeader

`event.addResponseHeader()` adiciona um header à resposta que o cliente recebe. Ele recebe os mesmos dois argumentos, o nome do header e o seu valor. Este listener adiciona dois headers de resposta e deixa a requisição seguir:

```javascript
  addEventListener("firewall", (event) => {
      event.addResponseHeader("X-Custom-Header-3", "3");
      event.addResponseHeader("X-Custom-Header-4", "4");
      event.continue();
  });
```

### event.deny

`event.deny()` não recebe argumentos e finaliza a requisição com HTTP `403 Forbidden`, cujo status, corpo e motivo a Function não pode alterar. Um header que `event.addResponseHeader()` adicionou antes não aparece nessa resposta. Para uma resposta que a Function controla, o método a chamar é `event.respondWith()`. Este listener nega toda requisição que recebe:

```javascript
  addEventListener("firewall", (event) => {
      event.deny();
  });
```

### event.drop

`event.drop()` finaliza a requisição sem resposta ao cliente e não recebe argumentos. Este listener descarta toda requisição que recebe:

```javascript
  addEventListener("firewall", (event) => {
      event.drop();
  });
```

### event.respondWith

`event.respondWith()` intercepta a requisição e a responde com uma resposta personalizada. Ele recebe um objeto `Response`, que define o status, os headers e o conteúdo da resposta. A chamada desta seção é executada dentro de um listener `firewall` e responde com um corpo JSON, o status `599` e um `content-type` igual a `application/json`:

```javascript
    event.respondWith(new Response('{"my_custom_response": true}', {
        status: 599,
        headers: { "content-type": "application/json" }
    }));
```

## Metadados

Uma Function em um Firewall lê metadados da requisição para filtrar o acesso à Application e aplicar lógicas diferentes por cenário. Quatro grupos desses metadados descrevem de onde uma requisição vem e como ela chega. A referência [API de metadados](/pt-br/documentacao/devtools/runtime/api-reference/metadata/) lista os campos de cada grupo.

| Grupo | O que contém | Campos |
| --- | --- | --- |
| GeoIP | De onde a requisição vem. Use-o para negar o acesso à Application a partir de certos lugares | [Metadados de GeoIP](/pt-br/documentacao/devtools/runtime/api-reference/metadata/#geoip) |
| Remote | O endereço IP e a porta TCP que o cliente usa | [Metadados de Remote](/pt-br/documentacao/devtools/runtime/api-reference/metadata/#remote) |
| Server | O protocolo que a requisição usa | [Metadados de Server](/pt-br/documentacao/devtools/runtime/api-reference/metadata/#server) |
| TLS | Detalhes disponíveis quando a requisição chega por uma conexão TLS segura | [Metadados de TLS](/pt-br/documentacao/devtools/runtime/api-reference/metadata/#tls) |

## Limites

Uma Function em um Firewall é executada dentro de dois conjuntos de limites. Os limites da própria Function, como tamanho do código, memória, tempo de CPU e sub-requisições, estão em [Limites de Functions](/pt-br/documentacao/plataforma/functions/limites/). Os limites do Firewall e das suas Function Instances estão em [Limites de Firewall](/pt-br/documentacao/plataforma/firewall/limites/).

A API recusa os argumentos de uma Function Instance a partir de 100.000 bytes, com `23000`. Um objeto com uma chave, enviado como JSON compacto, é aceito com 99.999 bytes e recusado com 100.000 bytes. Um handler Service Worker lê os argumentos em `event.args`. Em código que o Azion Bundler não empacotou, um handler ES Modules os lê em `ctx.args`.

## Erros

Três recusas dizem respeito a uma Function em um Firewall, e cada uma responde `400` com um array `errors`. Azion CLI imprime a mensagem entre colchetes, depois de `Error: Failed to create function:` ou de `Error: failed to create the Firewall Function Instance:`. `azion create function` encerra a mensagem com `Check your settings and try again. If the error persists, contact Azion support`.

| Código | Título | Mensagem | Causa | Correção |
| --- | --- | --- | --- | --- |
| `10039` | Invalid Choice | `"<value>" is not a valid choice.` | `execution_environment` contém `edge_firewall` ou `edge_application`, os valores que a ajuda da CLI lista para `--execution-environment`. | Envie `firewall`, ou passe `--execution-environment firewall`. |
| `23000` | JSON Args Size Too Big | `Value size (in bytes) is too big. Maximum size allowed is 100000 bytes.` | Os `args` de uma Function Instance chegam a 100.000 bytes. | Envie argumentos menores. |
| `29001` | Invalid Function Runtime | `Invalid edge function runtime. You should use a function designed for Edge Firewall.` | A Function de uma nova Function Instance tem o ambiente de execução `application`, pela API ou por `azion create firewall-instance`. | Instancie uma Function cujo ambiente de execução é `firewall`. |
