A maior parte do que dá errado com objetos armazenados é decidida antes de qualquer upload. Uma chave que não pode ser substituída com segurança e um content type que ninguém definiu são baratos de corrigir no início. O mesmo vale para um bucket do qual qualquer um exclui objetos e para uma credencial que alcança todos os buckets da conta. Cada um deles é caro de mudar depois que um público passa a depender dele.

As práticas abaixo cobrem, em ordem: nível de acesso, chaves versionadas, content type, prefixo, credencial S3, caminho de entrega e exclusões.

---

## Dê a um bucket o menor nível de acesso de que a Application precisa

Defina `workloads_access` como `read_only`, a menos que uma Function tenha de gravar objetos durante uma requisição, e como `restricted` quando nenhuma Application deva servir o bucket.

O nível decide o que um Connector e uma Function das suas Applications podem fazer com os objetos. A API da Azion e o protocolo S3 ficam fora dele: um pipeline de deploy grava em um bucket `read_only` com um token ou uma credencial com `writeFiles`. Em um bucket `read_write`, um Connector exclui um objeto em qualquer requisição `DELETE` que chega a ele. Não aponte nenhum Connector para um bucket em que uma Function grava.

<Code client:visible lang="bash" code={`curl --request POST \\
\x20 --url https://api.azion.com/v4/workspace/storage/buckets \\
\x20 --header 'Accept: application/json' \\
\x20 --header 'Authorization: Token [TOKEN VALUE]' \\
\x20 --header 'Content-Type: application/json' \\
\x20 --data '{
\x20 "name": "site-assets-ro",
\x20 "workloads_access": "read_only"
}'`} />

Uma resposta `201` devolve o bucket com `workloads_access` definido como `read_only`.

O custo é que uma troca de nível leva até cerca de 90 segundos para chegar ao Connector e à Function, como explica [Níveis de acesso](/pt-br/documentacao/plataforma/object-storage/como-funciona/#niveis-de-acesso). Azion Console não devolve um bucket a `restricted` depois que ele foi aberto a Workloads, mas a API da Azion devolve. Comece baixo e eleve o nível quando uma Function precisar da gravação. Para conferir o nível de um bucket, `azion list storage bucket` o mostra na coluna WORKLOADS ACCESS.

## Versione o nome de um objeto em vez de substituí-lo no lugar

Dê a um objeto uma chave que muda quando o seu conteúdo muda, e envie o novo conteúdo sob a nova chave.

Um upload para uma chave em uso substitui o objeto que a API da Azion devolve, e nenhuma configuração ativa o versionamento. Pelo protocolo S3, uma versão anterior fica legível pelo ID da versão por um prazo que você não define, então um rollback não pode contar com ela. Os leitores da chave recebem o novo conteúdo de imediato, pela API da Azion e por uma Application com as configurações padrão. Durante um deploy que substitui vários objetos um a um, os leitores veem uma mistura de antigo e novo até o último chegar.

```text
assets/app.4f2a9c.js
assets/app.9b71e0.js
assets/styles.4f2a9c.css
```

Uma chave com um identificador de build deixa as duas versões existirem durante um deploy, e um rollback aponta de volta para a chave anterior. Um tempo longo de cache também é seguro, porque a chave nunca serve conteúdo diferente. O custo é que as chaves antigas se acumulam, então um deploy que versiona chaves também precisa de um passo que remova as que nada referencia.

## Defina o cabeçalho Content-Type em todo upload

Envie o cabeçalho `Content-Type` em toda requisição de upload, em vez de contar com a detecção.

O content type é fixado no upload e retornado em toda leitura. Sem o cabeçalho, um upload pela API da Azion recebe o tipo pela extensão da chave. Um texto sob uma chave `.png` é guardado como `image/png`. `curl --data-binary` sem o cabeçalho `Content-Type` envia `application/x-www-form-urlencoded`, e o Object Storage guarda e serve esse tipo. Um objeto armazenado com o content type errado continua servindo esse tipo até ser gravado de novo, e um navegador que recebe o tipo errado pode baixar uma página em vez de renderizá-la.

<Code client:visible lang="bash" code={`curl --request POST \\
\x20 --url https://api.azion.com/v4/workspace/storage/buckets/site-assets-ro/objects/assets/app.4f2a9c.js \\
\x20 --header 'Accept: application/json' \\
\x20 --header 'Authorization: Token [TOKEN VALUE]' \\
\x20 --header 'Content-Type: application/javascript' \\
\x20 --data-binary '@./dist/app.4f2a9c.js'`} />

Uma resposta `201` confirma a chave:

```json
{
  "state": "executed",
  "data": {
    "object_key": "assets/app.4f2a9c.js"
  }
}
```

O cabeçalho `Storage-Content-Type` que a API aceita não define o tipo armazenado, então um script que o envia em vez de `Content-Type` guarda silenciosamente o tipo detectado. Para conferir o tipo armazenado, leia o objeto: o cabeçalho `content-type` da resposta o traz.

## Escolha um prefixo que corresponda ao que a Application serve

Organize as chaves de modo que um prefixo guarde exatamente o que um Connector deve servir.

Um Connector do tipo `storage` pede ao bucket dele a chave formada pelo prefixo, quando ele tem um, seguido do caminho da requisição. Quando o arranjo corresponde, um Connector expõe um conjunto de objetos e nada mais. Quando não corresponde, ou o Connector expõe mais do que se pretendia, ou o mesmo bucket precisa de vários Connectors e regras.

```text
public/index.html
public/assets/app.4f2a9c.js
internal/reports/2026-q3.csv
```

Um Connector com o prefixo `public` serve `public/index.html` em `/index.html`, porque coloca o prefixo antes de todo caminho de requisição. Sem prefixo, um Connector alcança todas as chaves, e uma requisição para `/` as lista, como explicam os [Limites do Object Storage](/pt-br/documentacao/plataforma/object-storage/limites/#escopo). O custo é que mudar um prefixo depois regrava todos os objetos sob ele, com uma cópia e uma exclusão por objeto. Para conferir o arranjo, peça `/internal/reports/2026-q3.csv` pela Application: o Connector pede `public/internal/reports/2026-q3.csv` e responde `404`.

## Limite uma credencial S3 aos buckets e às capabilities de que ela precisa

Nomeie os buckets no array `buckets` e conceda apenas as capabilities que o cliente usa.

Uma credencial criada sem `buckets` alcança todos os buckets da conta, assim como uma enviada com `bucket` no singular, que a API ignora. Uma credencial não muda depois de criada: `PATCH` e `PUT` retornam `405`. Então uma credencial ampla demais é substituída por uma nova. `writeFiles` também permite `DeleteObject`, e `deleteFiles` sozinha não permite nenhuma operação, como mostra [Capabilities](/pt-br/documentacao/plataforma/object-storage/compatibilidade-s3/#capabilities).

<Code client:visible lang="bash" code={`curl --request POST \\
\x20 --url https://api.azion.com/v4/workspace/storage/credentials \\
\x20 --header 'Accept: application/json' \\
\x20 --header 'Authorization: Token [TOKEN VALUE]' \\
\x20 --header 'Content-Type: application/json' \\
\x20 --data '{
\x20 "name": "ci-upload",
\x20 "capabilities": ["listFiles", "readFiles", "writeFiles"],
\x20 "buckets": ["site-assets-ro"],
\x20 "expiration_date": "2027-01-31T23:59:59Z"
}'`} />

Uma resposta `201` devolve a credencial com o `access_key` e o `secret_key` dela, e nenhuma resposta posterior traz o secret key. Confira `buckets` nela: uma lista vazia significa que a credencial alcança todos os buckets.

Definir `expiration_date` limita o estrago de uma chave vazada sem que ninguém tenha de lembrar de revogá-la. Depois dessa data, o endpoint S3 recusa a chave com `403` `InvalidAccessKeyId`. O custo é uma credencial nova antes da data, porque uma expiração não pode ser estendida, então defina a data onde você provisiona a credencial.

## Sirva objetos aos usuários finais por meio de uma Application

Sirva o bucket por uma regra de Application que define um Connector ou executa uma Function, e mantenha os usuários finais fora do endpoint S3.

Os [Termos de Serviço](/pt-br/documentacao/contratos/tds/) dizem que os objetos devem chegar aos usuários finais por uma Application que usa Connectors. Eles também sujeitam o acesso direto aos objetos, fora de uma Application, a rate limits. Uma URL pré-assinada entregue a um navegador é um acesso direto, porque o endpoint S3 entrega o objeto a quem tiver a URL. Servir por uma Application aplica as regras que a Application já tem, como um redirecionamento de `/` que esconde a listagem do bucket.

O custo é a configuração: uma Application não serve nada até que uma regra defina um Connector ou execute uma Function. Guarde o endpoint S3 para enviar, listar e remover objetos.

## Planeje as exclusões considerando o período de carência

Trate uma exclusão como algo em etapas, e não como algo imediato, e não construa um fluxo que cria um bucket, o esvazia e o exclui em uma única passagem.

A API da Azion deixa de listar e de servir um objeto excluído de imediato. O protocolo S3 ainda o lê pelo ID da versão. O objeto é removido em definitivo após um período de carência de 24 horas, e até lá o bucket dele não pode ser excluído. Então uma remoção automatizada que esvazia um bucket e o exclui em seguida falha, enquanto um bucket que nunca guardou um objeto é excluído de imediato.

Exclua antes os Connectors que referenciam o bucket: a API da Azion recusa a exclusão de um bucket referenciado com `409` `17016`.

Tanto reutilizar um único bucket de vida longa quanto aceitar que a remoção termine no dia seguinte evitam a falha. O custo da reutilização é que o nome do bucket continua ocupado, o que importa porque os nomes são únicos entre todas as contas Azion.
