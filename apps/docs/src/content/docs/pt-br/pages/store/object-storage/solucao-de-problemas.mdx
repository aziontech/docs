Esta página lista os sintomas de buckets e objetos no [Object Storage](/pt-br/documentacao/plataforma/object-storage/), cada um com a causa e a correção. As respostas da Azion API vêm primeiro. Depois vêm um objeto que uma Application não serve e dois comandos da Azion CLI.

---

## Um bucket não pode ser excluído e a API retorna 17006

Um `DELETE` no bucket responde HTTP `400`, com o título `Cannot Delete Non Empty Bucket` e o detalhe `Unable to delete a non-empty bucket. Additionally, objects deleted within the last 24 hours are also taken into consideration.`

Duas condições bloqueiam a exclusão, e o detalhe nomeia as duas. Um bucket que guarda um objeto não pode ser excluído. Um bucket esvaziado nas últimas 24 horas também não pode ser excluído, porque Object Storage remove um objeto excluído permanentemente apenas depois de um período de carência de 24 horas. Um bucket que nunca guardou um objeto é excluído na hora.

- **Esvazie o bucket**: liste as chaves com `GET /buckets/{bucket_name}/objects`, depois envie um `DELETE` por chave. Para as operações, consulte [Buckets e objetos](/pt-br/documentacao/plataforma/object-storage/buckets-e-objetos/).
- **Espere o período de carência passar**: envie o `DELETE` de novo 24 horas depois de o último objeto ter sido removido.
- **Exclua com a Azion CLI**: consulte [Uma exclusão forçada com a Azion CLI deixa o bucket no lugar](/pt-br/documentacao/plataforma/object-storage/solucao-de-problemas/#uma-exclusao-forcada-com-a-azion-cli-deixa-o-bucket-no-lugar).

O `DELETE` então responde HTTP `200` com `state` definido como `executed`, e o bucket sai de `GET /buckets`.

## Um bucket não pode ser excluído e a API retorna 17016

Um `DELETE` no bucket responde HTTP `409`, com o título `Cannot Delete Referenced Bucket` e o detalhe `Cannot delete a bucket referenced by another resource. References: <connector-name> (id: <connector-id>)`.

Um [Connector](/pt-br/documentacao/plataforma/connectors/) do tipo `storage` ainda referencia o bucket, então a API recusa a exclusão. O detalhe e `meta.references` informam esse Connector e o ID dele.

- **Libere o Connector das regras**: em cada regra de Application que define o Connector informado no detalhe, defina outro Connector ou exclua a regra. A API recusa excluir um Connector que uma regra ainda define, com `28000`.
- **Exclua o Connector**: para os erros que um Connector retorna, consulte [Configurações de Connector](/pt-br/documentacao/plataforma/connectors/configuracoes/#erros).
- **Exclua o bucket de novo**: envie o mesmo `DELETE` quando nenhum Connector referenciar o bucket.

Quando nenhum Connector referencia o bucket, o `DELETE` responde HTTP `200` com `state` definido como `executed`. Um bucket que guarda objetos, ou que perdeu um nas últimas 24 horas, responde `17006` no lugar.

## Um nome de bucket é recusado e a API retorna 17000, 17001 ou 17002

Um `POST /buckets` responde HTTP `400` sob um de três títulos, e `source.pointer` nomeia `/data/name`.

`Bucket Already Exists` significa que a sua conta ou outra já tem o nome. Um nome de bucket é único em todas as contas da Azion, e o detalhe diz `Bucket name '<name>' is already in use.`

`Bucket Name Not Available` significa que o nome começa ou termina com uma string reservada. Os prefixos reservados são `azion`, `xn--`, `sthree-` e `amzn-s3-demo-`, e os sufixos são `-s3alias` e `--ol-s3`. `Invalid Bucket Name` significa que o nome tem um underscore (`_`), uma letra maiúscula ou um hífen no começo ou no fim.

- **`17000`, `Bucket Already Exists`**: envie outro nome. Um nome que começa com seu projeto ou sua conta colide com menos frequência que um nome genérico.
- **`17001`, `Bucket Name Not Available`**: remova do nome o prefixo ou o sufixo reservado.
- **`17002`, `Invalid Bucket Name`**: remova cada underscore, escreva as letras em minúsculas e comece e termine o nome com uma letra ou um número.
- **Verifique o nome contra as outras regras**: um nome tem de 6 a 63 caracteres entre letras minúsculas, números e hífens. Fora desse tamanho, a API responde `10048` `Min Length` ou `10046` `Max Length`. Para cada limite, consulte [Limites do Object Storage](/pt-br/documentacao/plataforma/object-storage/limites/).

A requisição de criação então responde HTTP `201` com `state` definido como `executed`, e a resposta carrega o bucket.

## O nível de acesso é recusado e a API retorna 10059 ou 10039

Um `POST /buckets` responde HTTP `400` com o título `Required Field` sob o código `10059`, ou com o título `Invalid Choice` sob o código `10039`. Nos dois casos, `source.pointer` nomeia `/data/workloads_access`.

`workloads_access` é obrigatório na criação e aceita exatamente três valores: `read_only`, `read_write` e `restricted`. `10059` significa que o campo está ausente do corpo. Um corpo que envia `edge_access` produz o mesmo erro, porque a API não lê `edge_access` e o schema de criação não armazena um campo desconhecido. `10039` significa que o valor está fora dos três: um corpo carregando `private` responde `"private" is not a valid choice.`

- **Nomeie o campo como `workloads_access`**: a Azion API e a biblioteca `@aziontech/storage` usam esse nome, e a Azion CLI usa a flag `--workloads-access`. Nenhuma delas usa `edge_access`.
- **Troque `private` por `restricted`**: `restricted` fecha o bucket para um Connector e uma Function das suas Applications. A Azion API e o protocolo S3 continuam lendo e gravando nele.
- **Verifique de qual nível o bucket precisa**: para o que cada valor permite, consulte [Níveis de acesso](/pt-br/documentacao/plataforma/object-storage/como-funciona/#niveis-de-acesso).

A requisição de criação então responde HTTP `201`, e ler o bucket de volta mostra `workloads_access` com o valor que você enviou.

## Um objeto é servido com o content type errado

Um download do objeto retorna um `Content-Type` com o qual o objeto não foi enviado. Uma imagem é servida como `text/plain`, um corpo JSON como `application/octet-stream` ou um arquivo enviado com `curl` como `application/x-www-form-urlencoded`.

O content type armazenado vem do header `Content-Type` da requisição de upload. Sem `Content-Type`, um upload pela API da Azion recebe o tipo pela extensão da chave. Uma chave `.txt` recebe `text/plain`, e uma chave sem extensão recebe `application/octet-stream`, qualquer que seja o conteúdo.

Quando o comando não define o header `Content-Type`, `curl --data-binary` adiciona o seu próprio, `application/x-www-form-urlencoded`, e Object Storage armazena esse valor. A especificação da API documenta um header `Storage-Content-Type`, e Object Storage o ignora. Uma requisição que define apenas esse header armazena um tipo detectado, não o que você nomeou.

- **Envie o objeto de novo com `Content-Type`**: o header define o tipo armazenado, e um `POST` para uma chave que já existe substitui o objeto e responde `201`.
- **Tire `Storage-Content-Type` da requisição**: o header não muda nada e esconde a ausência do `Content-Type`.
- **Leia o tipo de volta**: `GET /buckets/{bucket_name}/objects/{object_key}` retorna o objeto com o tipo que ele carrega.

Toda requisição posterior pelo objeto então retorna o tipo que você enviou. Para as operações de upload, consulte [Buckets e objetos](/pt-br/documentacao/plataforma/object-storage/buckets-e-objetos/).

## Um PUT em uma chave de objeto retorna 17013

Um `PUT` em `/buckets/{bucket_name}/objects/{object_key}` responde HTTP `404`, com o título `Object Does Not Exist`. O bucket existe e o corpo da requisição é válido.

`PUT` mapeia para `update_object_key`, que substitui um objeto já armazenado. Ele nunca cria um. `POST` mapeia para `create_object_key`, que é a operação que cria a chave, incluindo todo prefixo dentro dela: um `POST` para `objects/folder/sub/data.json` não precisa de nenhum passo anterior.

- **Faça o `POST` da chave primeiro**: a criação responde `201` com `state` definido como `executed` e `data.object_key` nomeando a chave.
- **Guarde o `PUT` para substituições**: uma vez que a chave existe, `PUT` responde `200` ou `202`.
- **Ou use `POST` sempre**: um `POST` para uma chave que já existe substitui o objeto e responde `201`, então uma operação cobre os dois casos.

O objeto então fica armazenado sob a chave, e `GET /buckets/{bucket_name}/objects` o retorna.

## Uma requisição de listagem não retorna nenhum bucket embora o bucket exista

`GET /buckets` com `name` definido como parte de um nome de bucket responde `200` com `count` igual a `0` e um array `results` vazio. O filtro `bucket` não retorna nada para nenhum valor, inclusive um nome exato.

`name` corresponde ao nome inteiro do bucket e ignora maiúsculas e minúsculas. A especificação da API, porém, o descreve como uma correspondência parcial. O filtro `bucket` não retorna registro nenhum. `search` é o parâmetro que corresponde a parte de um nome, e `workloads_access` filtra corretamente.

- **Corresponda parte de um nome com `search`**: `GET /buckets?search=my-bucket` retorna todo bucket cujo nome contém `my-bucket`.
- **Use `name` apenas com o nome inteiro**: `GET /buckets?name=my-bucket-ro` retorna aquele bucket.
- **Não filtre com `bucket`**: ele não retorna registro nenhum, então uma resposta vazia não prova nada sobre a conta.
- **Pagine a lista em vez de filtrar**: uma página traz 10 buckets, a menos que você defina `page_size`, que aceita até 100. `page` percorre as páginas.

A resposta então carrega o bucket em `results`, e `count` informa quantos buckets corresponderam.

## Um objeto está ausente na Application que serve o bucket

O bucket lista a chave do objeto, mas a Application que serve o bucket não retorna o objeto.

Esta entrada trata de um bucket servido por um [Connector](/pt-br/documentacao/plataforma/connectors/) do tipo `storage` que uma regra de Application define. O Connector pede ao bucket o caminho da requisição, precedido do prefixo do Connector quando ele tem um. Por exemplo, com o prefixo `assets`, uma requisição para `/logo.svg` lê `assets/logo.svg`, e uma requisição para `/assets/logo.svg` lê `assets/assets/logo.svg`. Uma chave que o bucket não guarda responde `404` com um corpo XML `NoSuchKey`.

- **Compare a chave do objeto com o prefixo do Connector**: peça o caminho que vem depois do prefixo na chave, como `/logo.svg` para `assets/logo.svg`. O Connector coloca o prefixo antes do caminho da requisição, então `/assets/logo.svg` pede `assets/assets/logo.svg` e recebe `404`.
- **Confirme que uma regra define o Connector**: sem uma regra que o defina, nenhuma requisição chega ao Connector.
- **Verifique o nível de acesso do bucket**: um bucket `restricted` responde `502` por um Connector, enquanto buckets `read_only` e `read_write` servem os seus objetos.
- **Para a cadeia inteira, consulte [Usar um bucket como origem](/pt-br/documentacao/guias/desenvolvimento-de-aplicacoes/dados/bucket-como-connector/)**: ela carrega os campos do Connector e a regra.

Uma requisição que corresponde à regra então retorna o objeto do bucket.

## Uma exclusão forçada com a Azion CLI deixa o bucket no lugar

`azion delete storage bucket --name <bucket> --force` imprime `Delete all objects from bucket` e `Deleting objects...`, depois remove os objetos. O bucket continua na saída de `azion list storage bucket`, e alguns objetos podem continuar nele.

Um bucket não pode ser excluído enquanto guarda objetos, nem nas 24 horas seguintes à remoção do último objeto: a API o recusa com `17006`. O comando não consegue concluir a exclusão dentro desse prazo.

- **Confira o que sobrou**: `azion list storage object --bucket-name <bucket>` lista os objetos que o comando não removeu. Remova cada um com `azion delete storage object --bucket-name <bucket> --object-key <key>`, que imprime `Object <key> was deleted successfully`.
- **Exclua o bucket depois do período de carência**: 24 horas depois de o último objeto ter sido removido, execute `azion delete storage bucket --name <bucket>`.

Uma exclusão que tem sucesso imprime `Bucket <bucket> was deleted successfully`, e o bucket sai da lista.

:::note[nota]
Com a Azion CLI 4.26.2, o comando pode parar depois de `Deleting objects...` e deixar alguns objetos no bucket. A Azion CLI 4.23.0 imprimia `Bucket deletion was scheduled successfully` no final.
:::

## A Azion CLI relata no such file or directory para um arquivo que existe

`azion create storage object --source` falha em um caminho que você consegue ler. A partir do diretório de trabalho `/tmp`, `--source /tmp/os-cli.txt` responde `Error: open /tmp/tmp/os-cli.txt: no such file or directory`, e o arquivo está lá.

O comando antepõe o diretório de trabalho ao valor de `--source`, mesmo quando o valor é um caminho absoluto. O diretório então aparece duas vezes no caminho que o comando abre.

- **Passe um caminho relativo**: a partir do diretório que guarda o arquivo, `--source os-cli.txt` chega até ele.
- **Execute o comando a partir do diretório que guarda o arquivo**: o caminho relativo é então apenas o nome do arquivo.
- **Faça o upload pela API quando um script precisar de um caminho absoluto**: `POST /buckets/{bucket_name}/objects/{object_key}` recebe o arquivo como corpo da requisição.

O comando então imprime `Object created successfully`. Para os comandos de storage e suas flags, consulte [Azion CLI storage](/pt-br/documentacao/devtools/cli/recursos/storage/).

:::note[nota]
O comportamento da CLI nesta seção corresponde ao da Azion CLI 4.26.2.
:::
