A documentação é uma base de código. Cada página é um arquivo em um repositório público, e uma mudança chega ao site como um pull request. Verificações automáticas rodam no pull request antes do merge.

O site é publicado em dois idiomas: inglês dos EUA (EN) e português do Brasil (PT-BR). O EN é a fonte, e o PT-BR é a tradução.

## Um repositório, uma revisão

O código-fonte fica em [aziontech/docs](https://github.com/aziontech/docs) no GitHub, aberto a contribuições externas. Para mudanças significativas, a issue vem antes do pull request, para que um mantenedor avalie a abordagem antes do trabalho começar. Uma página nova, uma página que muda de lugar ou é excluída, uma mudança de permalink e uma reestruturação da navegação são significativas. Um erro de digitação, um link quebrado ou um ajuste de formatação podem ir direto para um pull request.

Dois times revisam as mudanças. Developer Relations revisa e aprova o conteúdo, e UX Engineering revisa e aprova o código de estrutura. Os [templates de issue](https://github.com/aziontech/docs/issues/new/choose) encaminham cada pedido: reportar um erro, pedir uma adição, atualizar conteúdo ou fazer uma pergunta.

## As verificações de um pull request

As verificações rodam no GitHub Actions em cada pull request para a `main`, em três workflows. A governança do repositório pede que os três passem antes do merge; as regras de branch da `main` exigem o Design system adoption, e os revisores garantem os outros dois.

O **CI gate** agrupa quatro jobs. Um primeiro job lê o diff e roda só os jobs cujos caminhos a mudança toca, então nem todo pull request roda todas as verificações. O job Build roda em todo pull request.

| Job | O que roda | O que ele captura |
| --- | --- | --- |
| Security scans | Uma auditoria de dependências e o TruffleHog sobre o diff | Mais vulnerabilidades altas ou críticas que a baseline, e segredos verificados na mudança |
| Content integrity | `lint:navcheck` e uma verificação de slugs de tradução | Uma linha da navegação que aponta para uma página ou árvore desconhecida, uma página EN fora de qualquer linha da navegação, e mais páginas PT-BR sem página EN de mesmo `namespace` que a baseline |
| Code quality | ESLint, Prettier e Stylelint nos arquivos que o pull request altera, e `astro check` | Um erro de lint ou de formatação em um arquivo alterado, e mais erros de tipo que a baseline |
| Build | `astro build`, depois `test:frontmatter` | Uma página que não compila, e um `permalink` ausente, malformado ou duplicado, ou um `namespace` duplicado |

O **Internal links** faz o build do site e roda o verificador de links. O verificador segue só links internos. Ele aponta um link para uma página ou um fragmento que não existe, um link para uma página de redirect em vez da URL canônica, uma URL absoluta onde cabe uma relativa e um link para uma página no outro idioma. A verificação de texto vago cobre todo link, interno ou externo: ela aponta textos de link como "here" ou "read more".

O **Design system adoption** roda as regras de lint do design system sobre a UI e o conteúdo MDX, e escreve um relatório no resumo da execução.

Cinco verificações são ratchets: a auditoria de dependências, a verificação de slugs de tradução, o `astro check`, o verificador de links e a verificação do design system. Cada uma compara uma contagem com a baseline em [`ci/baselines.json`](https://github.com/aziontech/docs/blob/main/ci/baselines.json) e falha só quando a contagem passa da baseline. Um pull request que reduz uma contagem atualiza a baseline com `pnpm ci:ratchet <check> --update`. As demais verificações falham com qualquer erro.

Rode as verificações localmente antes de abrir o pull request:

```bash
pnpm build:local                  # astro build + test:frontmatter
pnpm lint:navcheck                # árvore de navegação
pnpm ci:ratchet slugcheck         # slugs de tradução
pnpm ci:ratchet linkcheck         # verificador de links, depois de pnpm build:local
pnpm ci:ratchet astro-check       # erros de tipo
pnpm ci:ratchet webkit-adoption   # regras do design system
pnpm exec eslint <arquivos>       # lint dos arquivos alterados
pnpm exec prettier --check <arquivos>
```

## Redirects

Um permalink que muda ou desaparece leva o redirect no mesmo pull request. Sem o redirect, a URL antiga devolve um erro para todo favorito, resultado de busca e link externo que aponta para ela.

### Onde os redirects ficam

Os redirects ficam em quatro arquivos JSON, dois por idioma:

- `apps/docs/redirects/en/00.json` e `apps/docs/redirects/en/01.json` para URLs EN
- `apps/docs/redirects/pt-br/00.json` e `apps/docs/redirects/pt-br/01.json` para URLs PT-BR

Cada arquivo é um array de objetos. Cada objeto liga uma URL de origem completa a uma URL de destino completa:

```json
{
  "from": "https://www.azion.com/pt-br/documentacao/arquiteturas/",
  "moved": "https://www.azion.com/pt-br/documentacao/casos-de-uso/"
}
```

Cada objeto tem exatamente um campo de origem e exatamente um campo de destino:

| Campo | Significado |
| --- | --- |
| `from` | A URL de origem exata |
| `from_regex` | Uma expressão regular que corresponde às URLs de origem |
| `moved` | O destino de um redirect permanente, HTTP 301 |
| `found` | O destino de um redirect temporário, HTTP 302 |

### Adicionar um redirect

1. Adicione o par ao arquivo do idioma da página, no mesmo pull request que muda ou remove o permalink. Adicione os pares novos ao arquivo de maior número desse idioma.
2. Procure a URL antiga como destino nos arquivos de redirect. Aponte essas entradas para a URL nova, para que o leitor nunca passe por uma cadeia de redirects.
3. Declare a mudança no pull request, em URL changes and redirects no [template de pull request](https://github.com/aziontech/docs/blob/main/.github/PULL_REQUEST_TEMPLATE.md): a URL antiga, a URL nova e os redirects adicionados.

### Como um redirect entra no ar

Cada arquivo de redirect é a lista de argumentos de uma instância da função Massive 301 Redirect na aplicação da Azion que serve o site. O `pnpm --filter docs redirects:publish` valida os quatro arquivos, confere cada instância de destino e grava nas instâncias os arquivos que mudaram. A flag `--dry-run` informa o que mudaria e não grava nada. Os dois modos leem as instâncias publicadas, então os dois precisam das variáveis de ambiente `AZION_TOKEN` e `AZION_APPLICATION_ID`.

O workflow de deploy de produção roda a etapa de publicação depois de cada deploy de produção. Um merge na `main` sozinho não publica um redirect: o redirect entra no ar com o próximo deploy de produção.

### Quando um arquivo enche

Uma instância de função aceita no máximo 300 KB de argumentos, e a etapa de publicação rejeita um arquivo acima desse tamanho. Quando um arquivo se aproximar do limite, comece o próximo arquivo numerado, como `en/02.json`. Os arquivos não são ligados às instâncias de forma automática, então um arquivo novo é uma mudança de plataforma em três partes:

1. Crie uma instância da função Massive Redirect na aplicação da Azion.
2. Carregue o arquivo em `apps/docs/redirects/index.js`.
3. Adicione o arquivo como destino em `apps/docs/cicd/massive-redirects/update-function-instances.mjs`, com o ID e o nome da instância.

Nenhuma verificação de pull request valida os arquivos de redirect ainda. A etapa de publicação é a primeira a lê-los, no deploy de produção, então confira o formato e o tamanho do arquivo à mão antes do merge. Um arquivo que o `index.js` não carrega nunca é publicado.

## Metadados

Toda página tem cinco campos de frontmatter: `title`, `description`, `meta_tags`, `namespace` e `permalink`. Dois deles são contratos. O `permalink` é único por idioma, e o `namespace` liga a página EN à sua tradução PT-BR. As regras de cada campo estão em [Frontmatter](/pt-br/documentacao/guia-de-estilo/convencoes/frontmatter/).
