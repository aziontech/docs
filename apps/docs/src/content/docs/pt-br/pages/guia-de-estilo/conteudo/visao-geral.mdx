## Propósito

Uma página de visão geral é a raiz da seção de um recurso da plataforma. Ela diz o que o recurso da plataforma é, o que ele faz e quando o leitor o usaria. Ela aplica a forma base de [referência](/pt-br/documentacao/guia-de-estilo/conteudo/referencia/).

Todo recurso da plataforma tem uma. É a página onde o leitor chega pela busca, pela sidebar e por outro recurso da plataforma que aponta para este.

## Quando usar

- Escreva uma visão geral para cada recurso da plataforma, como a primeira página da seção.
- Escreva-a antes de qualquer outra página da seção. A visão geral define do que a seção trata.

Não escreva uma visão geral quando:

- O assunto é uma feature, como o Tiered Cache ou as regras personalizadas de firewall. Isso vai em uma [página de referência](/pt-br/documentacao/guia-de-estilo/conteudo/referencia/) dentro da seção. Um recurso da plataforma aninhado em outro não é uma feature: ele pode ter uma página de visão geral própria, e a visão geral do recurso pai aponta para ela.
- A página levaria o leitor por uma tarefa. Isso é um [guia how-to](/pt-br/documentacao/guia-de-estilo/conteudo/guias-how-to/), com link a partir daqui.
- A página só listaria links. Isso é um [hub de navegação](/pt-br/documentacao/guia-de-estilo/conteudo/hubs-de-navegacao/).

## Registro

Descritivo: 25 palavras por frase, voz ativa, passiva apenas quando o agente é desconhecido. Tom: acolhedor, factual, direto. [Estrutura de frases](/pt-br/documentacao/guia-de-estilo/escrita/estrutura-de-frases/) tem as regras.

## Estrutura

**Componentes obrigatórios**

- **Bloco de definição**, em três partes. Primeiro o recurso da plataforma: `**<Recurso da plataforma>** é um <classe> que <verbo> <o que faz> <onde e como na Azion>.` Essa frase nomeia o recurso, declara a classe dele e se sustenta sozinha. A classe é `recurso da plataforma`, tanto na visão geral de uma seção quanto na de um recurso da plataforma aninhado, conforme [Terminologia da documentação](/pt-br/documentacao/guia-de-estilo/escrita/terminologia/#declare-a-classe-de-um-elemento-da-azion). A frase nunca depende de um conceito que o leitor ainda não conheceu, como faz "executa esse código". Depois o conceito: uma ou duas frases dizendo o que é a classe da coisa, para um leitor que nunca usou uma, com qualquer termo do mercado definido no próprio texto. Depois uma frase nomeando as tarefas concretas para as quais as pessoas o usam, no vocabulário do leitor, fechando o bloco: `Use <Recurso da plataforma> para fazer A, executar B ou servir C.` Uma lista de benefícios em bullets é a forma mais fraca dessa frase: parece um folheto e custa uma tela.
- **CTAs**: um `DocButton` primário com o rótulo **Primeiros passos** e um secundário com o rótulo `Referência de <Recurso da plataforma>`.
- **O mecanismo**: quando uma requisição, um evento ou um job atravessa mais de dois objetos antes de o recurso da plataforma executar, essa cadeia como um diagrama `mermaid`, seguido de um percurso numerado com no máximo seis itens. Abra com o que o leitor presumiria errado e diga na mesma frase o que acontece no lugar: `Criar uma Function não a expõe: uma requisição só chega a ela por uma Function Instance que uma regra invoca.`
- **A amostra**: quando o recurso da plataforma tem um artefato de código, um objeto de configuração ou uma requisição, um exemplo completo e mínimo dele, inteiro, logo depois do mecanismo, ou logo depois dos CTAs quando a página não tem a seção de mecanismo. Dois a quatro bullets nomeiam as partes, e uma frase diz qual conhecimento prévio se aproveita. Um recurso da plataforma sem esse artefato pula a seção em vez de inventar uma.
- **Os recursos**: somente em um recurso da plataforma que tem outros recursos da plataforma aninhados nele. Para cada aninhado, diga o que ele faz neste recurso e quando o leitor o ativa, em uma ou duas frases, a primeira declarando a classe dele: `<Recurso da plataforma aninhado> é um recurso da plataforma que…`. Depois aponte para onde o leitor vai para usá-lo. É o que o leitor precisa para decidir se abre o recurso da plataforma aninhado, nunca a lista de features.
- **As fronteiras**: um único bloco compacto de bullets com introduções em negrito — linguagens, APIs, frameworks, integrações e os principais limites. Um bloco, não uma seção por feature.
- **Seções de capacidade**: só para uma capacidade que muda o que o leitor construiria, no máximo três. Uma capacidade que cabe em uma frase e um link pertence ao bloco de fronteiras ou ao roteador.
- **Fechamento**: `## Próximos passos`, um `DocCardGroup` indexado pelo que o leitor quer fazer: cada card nomeia o destino, e seu texto é a intenção (`Rode o primeiro agora.`).

As seções mantêm essa ordem.

## Regras

- **Nunca instrua.** Sem passos numerados, sem procedimentos, sem sequências de cliques. A amostra não é um passo a passo: ela aparece uma vez, completa, sem nada para o leitor fazer. Uma visão geral que instrui é uma página de [quickstart](/pt-br/documentacao/guia-de-estilo/conteudo/quickstart/) arquivada no lugar errado. Um caminho do Console dentro de uma frase também conta: declare a configuração no lugar dele, conforme [Escolha de palavras](/pt-br/documentacao/guia-de-estilo/escrita/escolha-de-palavras/#declare-a-configuracao-nao-o-caminho-fora-de-uma-tarefa).
- **Sem adjetivos de qualidade.** Diga o que o recurso da plataforma faz e onde para.
- **O título é o nome do recurso da plataforma, um substantivo.** Não "documentação", não um gerúndio.
- **Coloque o recurso da plataforma antes do conceito.** A primeira frase declara a classe do recurso da plataforma e o que ele faz na Azion; as frases de conceito vêm depois. Cubra o nome do recurso da plataforma nas frases de conceito: o que sobra precisa valer para a versão de qualquer fornecedor.
- **Faça cada palavra de posição concordar com o caminho da requisição.** `para`, `de`, `na frente de`, `atrás de` e `antes de` implicam, cada uma, uma seta. Desenhe as setas que a frase implica e compare com o diagrama da página. Diga a direção com o verbo: `processa as requisições recebidas pelos seus Workloads`. `executa um proxy reverso para os seus Workloads` põe os Workloads atrás do proxy, e a requisição vai no sentido contrário.
- **Escolha um verbo que cubra tudo o que o recurso da plataforma faz.** Quando um recurso da plataforma faz duas ou mais coisas no mesmo nível, a primeira frase declara o papel que elas têm em comum e a frase seguinte as lista: `**Applications** é um recurso da plataforma que processa as requisições recebidas pelos seus Workloads. Uma Application pode executar funções serverless, atuar como proxy reverso para as suas origens ou combinar os dois.` Teste a frase contra a menor configuração que a documentação mostra.
- **Leia a definição como um leitor do mercado.** Um desenvolvedor que conhece o vocabulário de outras plataformas lê workload como aquilo que roda atrás de um ponto de entrada. Quando essa leitura diz algo falso sobre a Azion, reescreva a frase para que ela declare o papel ou a direção. Isto é um modo de ler, não uma lista de palavras a evitar.
- **Conte para a frente a relação entre dois recursos da plataforma.** Quem faz a ligação é o sujeito, e a frase segue a ordem em que as coisas acontecem: `Uma Application recebe as requisições de um Workload depois que o deployment desse Workload define essa Application.` A frase `Uma Application recebe as requisições dos Workloads cujo deployment a define.` começa pelo fim e deixa dois pronomes apontando para trás. O verbo leva o objeto por extenso: `define essa Application`, nunca `a define`.
- **Escolha o conceito com cuidado.** Vários elementos da Azion fazem coisas diferentes sob um mesmo nome. Quando um conceito de mercado cobre tudo o que o recurso da plataforma faz, explique esse conceito. Quando nenhum cobre, explique cada coisa em uma frase.
- **Nomeie o recurso da plataforma que fornece um conceito.** Quando outro recurso da plataforma fornece uma dessas coisas, a frase que explica o termo de mercado nomeia a instância dele logo depois do termo e mantém a explicação: `Uma função serverless é uma Function, um código executado sob demanda a cada requisição, sem um servidor para você provisionar.`
- **Corte do bloco de definição o que o leitor não precisa.** Quatro tipos de frase saem: o contexto que o recurso da plataforma não muda, como a delegação de um domínio a partir do registro; o passo que o leitor já presume, como um proxy abrindo a própria conexão com a origem; um ponto que o bloco já fez; e um contraste com algo que a página não cobre, como `Um log é a visão oposta.`
- **Um uso diz o que este recurso da plataforma acrescenta.** A frase de usos nomeia as tarefas que este recurso da plataforma faz e outro não. Em Functions, o uso é "bloquear requisições com a sua própria lógica", porque o Firewall já bloqueia requisições por regra. Um recurso da plataforma de segurança nomeia o padrão público que as páginas dele documentam, como o OWASP Top 10.
- **Nomeie o recurso da plataforma na primeira frase, e nunca abra com o contexto do problema.** Uma frase de conceito explica um mecanismo. Uma frase sobre a importância do problema não explica nada.
- **Organize pelas perguntas do leitor, não pela sua lista de features.** As seções respondem, na ordem: o que o recurso da plataforma da Azion faz, o que é a classe da coisa, como isso é chamado, o que eu escrevo, quais produtos ele hospeda, o que faz e onde para, para onde vou agora. Um sumário que reproduz a lista de features do recurso da plataforma é um catálogo: responde "o que vendemos" em vez de "o que estou decidindo".
- **As perguntas moldam as seções; elas nunca viram títulos.** Um título é uma expressão nominal curta, nunca uma pergunta: `Estrutura de uma função`, não `Como é uma função`.
- **Desenhe o diagrama a partir da sequência documentada.** Um diagrama de uma sequência que a documentação já descreve em prosa é uma mudança de notação, não um fato novo. Cada nó e cada seta corresponde a um passo que o recurso da plataforma executa, e o percurso numerado carrega o significado se a figura não renderizar.
- **Envie o leitor para o [Quickstart](/pt-br/documentacao/guia-de-estilo/conteudo/quickstart/)**, nos CTAs e de novo no roteador.
- **Nunca encurte a amostra nem tire o diagrama para deixar a página mais curta.** Eles são as duas coisas que o leitor veio buscar. Quando uma página fica longa, o excesso está nas seções de capacidade; comprima-as no bloco de fronteiras.

## Exemplos

Este trecho, em inglês dos EUA, da visão geral de **Functions** mostra o bloco de definição nas suas três partes e a amostra, e deixa o mecanismo de fora. A primeira frase nomeia o recurso da plataforma, declara a classe dele e diz o que ele faz na Azion; as seguintes explicam o que é uma função para um leitor que nunca usou uma; a frase de usos fecha o bloco; a amostra mostra o artefato em vez de descrevê-lo:

```mdx
**Functions** is a Platform Resource that runs JavaScript code on Azion's distributed infrastructure, inside the request path of an application or a firewall. A function is code that runs when a request arrives: you write a handler that receives the request and returns a response, and the platform starts it on demand and stops it when the response is sent, so there is no server to provision or scale. That model is called [serverless](https://www.azion.com/en/learning/serverless/what-is-serverless/). Use Functions to build APIs, manipulate request and response headers, apply logic from request metadata, or block traffic before it reaches your application.

## Function structure

A function exports one default object whose keys are handlers. The `fetch` handler answers an HTTP request:

<Code client:visible lang="javascript" code={`
export default {
  fetch: async (request, env, ctx) => {
    return new Response('Hello World');
  }
};
`} />

- **`export default`** exposes the object Azion Runtime reads. Each key names a handler for one event.
- **`fetch(request, env, ctx)`** runs on an HTTP request.
- **The returned `Response`** answers the request.

If you know the Web `Request` and `Response` objects, you know the code model.
```
