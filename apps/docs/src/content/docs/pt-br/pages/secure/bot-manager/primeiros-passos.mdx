Este guia instrui você a pontuar a sua primeira requisição com [Bot Manager Lite](/pt-br/documentacao/plataforma/firewall/bot-manager/bot-manager-lite/), a edição que você instala por conta própria pelo Marketplace.

- Crie uma Function Instance no seu Firewall, carregando os argumentos com que a Function é executada.
- Execute essa Function Instance por uma regra do Rules Engine, em toda requisição que o Firewall recebe.
- Envie uma requisição com formato de bot e leia o score que a Function deu a ela.

Bot Manager Lite pontua cada requisição contra um conjunto publicado de regras estáticas, que carregam assinaturas de credential stuffing, varredura de vulnerabilidades e scraping de site. [Bot Manager](/pt-br/documentacao/plataforma/firewall/bot-manager/), a edição completa, acrescenta um score dinâmico e o Reputation Intelligence sobre essas regras.

Bot Manager está em Preview, então não vem habilitado na conta por padrão. A Azion o habilita mediante solicitação e depois calibra o perfil dele. Para solicitá-lo, consulte [Diretrizes de suporte](/pt-br/documentacao/suporte/). As duas edições são configuradas do mesmo jeito, então as etapas deste guia não mudam com a edição.

Cinco partes colocam uma requisição sob inspeção, e cada uma liga à seguinte:

1. A **Function** instalada é o código do Bot Manager Lite, instalado uma vez pelo Marketplace na conta.
2. O **Firewall** tem **Functions** ativado, que é o que executa uma Function instalada.
3. A **Function Instance** nesse Firewall guarda os argumentos com que a Function é executada.
4. A **regra** no Rules Engine do mesmo Firewall carrega um comportamento _Run Function_, que executa essa Function Instance.
5. O **deployment** do Workload que atende a sua Application define esse Firewall.

Uma Function instalada não pontua nada sozinha. As cinco partes precisam existir.

## Crie uma instância de Bot Manager Lite no seu Firewall

Uma [Function Instance](/pt-br/documentacao/plataforma/firewall/functions-instances/) carrega toda a sua configuração em um objeto JSON. Quatro argumentos bastam para uma primeira execução:

```json
{
  "threshold": 30,
  "action": "deny",
  "internal_logs": 2,
  "log_tag": "storefront-bots"
}
```

`threshold` e `action` são o par que decide o resultado: a Function aplica `action` a uma requisição cujo score alcança `threshold`, e `30` com `deny` são os valores que Bot Manager Lite entrega. `internal_logs` em `2` escreve uma linha de report para toda requisição, incluindo uma que pontua `0`. `log_tag` identifica esta Function Instance nessas linhas, então substitua `storefront-bots` por uma tag sua. Para cada argumento que uma Function Instance aceita, consulte [Campos](/pt-br/documentacao/plataforma/firewall/bot-manager/argumentos/#campos).

:::caution[Atenção]
A API verifica se os argumentos são um objeto ou um array JSON e não verifica nenhuma chave. Toda chave que você envia é armazenada e lida de volta com o valor inalterado, leia a Function essa chave ou não. Um argumento escrito errado, como `thresold: 5`, é guardado, a API e a Azion CLI não levantam erro e `threshold` fica ausente da Function Instance. Para ver o que a Function faz sem ele, consulte [Threshold](/pt-br/documentacao/plataforma/firewall/bot-manager/argumentos/#threshold).
:::

### Console

Para criar a Function Instance no Azion Console:

<DocSteps>
  <DocStep title="Abra o Firewall que o deployment do seu Workload define">

  Acesse [Azion Console](https://console.azion.com/) > **Firewalls** e selecione esse Firewall.

  </DocStep>
  <DocStep title="Selecione a aba Functions Instances" />
  <DocStep title="Selecione Function">

  Em um Firewall que ainda não carrega nenhuma Function Instance, a mesma ação aparece como **Function Instance**.

  </DocStep>
  <DocStep title="Nomeie a Function Instance">

  Na seção **General**, informe um **Name**. Por exemplo: `bot-manager-lite`.

  </DocStep>
  <DocStep title="Selecione a Function instalada">

  Na seção **Function**, selecione a Function do Bot Manager Lite. O seletor lista apenas as Functions da conta que são executadas em um Firewall.

  </DocStep>
  <DocStep title="Informe os argumentos">

  Na seção **Arguments**, informe o objeto. Bot Manager Lite não carrega esquema de argumentos, então a seção guarda um editor JSON e não constrói formulário a partir dele.

  </DocStep>
  <DocStep title="Selecione Save" />
</DocSteps>

A Function Instance aparece em **Functions Instances**, que lista o seu **Name**, **Function**, **Last Editor** e **Last Modified**. O formulário não carrega um controle **Active** e a lista não carrega uma coluna **Status**: Azion Console cria toda Function Instance ativa.

### CLI

`azion create firewall-instance` lê os argumentos de um arquivo. A flag `--args` dele recebe um caminho, não JSON inline.

<DocSteps>
  <DocStep title="Escreva os argumentos em um arquivo">

  Salve o objeto como `bmargs.json`:

  ```json
  {
    "threshold": 30,
    "action": "deny",
    "internal_logs": 2,
    "log_tag": "storefront-bots"
  }
  ```

  </DocStep>
  <DocStep title="Crie a Function Instance">

  Substitua `<firewall-id>` pelo ID do seu Firewall e `<function-id>` pelo ID da Function do Bot Manager Lite instalada:

  ```bash
  azion create firewall-instance --name bot-manager-lite --firewall-id <firewall-id> \
    --function-id <function-id> --args bmargs.json --active true
  ```

  </DocStep>
  <DocStep title="Leia a saída">

  O comando imprime o ID da nova Function Instance:

  ```text
  Created Firewall Function Instance with ID 12347
  ```

  </DocStep>
</DocSteps>

Guarde esse ID. O comportamento _Run Function_ da próxima etapa executa a Function Instance por esse ID, nunca pelo ID da Function.

</Fragment>

### API

A chamada de criação carrega o nome, o ID da Function e os argumentos em um corpo só.

<DocSteps>
  <DocStep title="Envie a requisição de criação">

  Substitua `<firewall-id>` pelo ID do seu Firewall, `[TOKEN VALUE]` pelo seu personal token e `12345` pelo ID da Function do Bot Manager Lite instalada:

  ```bash
  curl --request POST \
    --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/functions \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: application/json' \
    --data '{
    "name": "bot-manager-lite",
    "function": 12345,
    "active": true,
    "args": {
      "threshold": 30,
      "action": "deny",
      "internal_logs": 2,
      "log_tag": "storefront-bots"
    }
  }'
  ```

  </DocStep>
  <DocStep title="Leia a resposta">

  Uma criação responde `202`, e `"state": "pending"` significa que a mudança ainda está se propagando:

  ```json
      "last_editor": "user@example.com",
      "last_modified": "2026-01-01T12:00:00.000000Z",
      "created_at": "2026-01-01T12:00:00.000000Z"
    }
  }
  ```

  </DocStep>
</DocSteps>

Guarde o `id` da Function Instance, `12348` nesta resposta. O comportamento _Run Function_ da próxima etapa executa a Function Instance por esse ID, nunca pelo ID da Function.

## Execute a instância por uma regra do Rules Engine

Uma regra do [Rules Engine para Firewall](/pt-br/documentacao/plataforma/firewall/rules-engine/) decide quais requisições alcançam a Function Instance. O comportamento _Run Function_ dela executa uma Function Instance, e a regra desta etapa executa a sua em toda requisição que o Firewall recebe.

:::caution[Atenção]
Baseie o critério na URI da requisição. Um critério como `${request_args}` `matches` `.*` não corresponde a uma requisição que não carrega query string, então ele pula todo `POST` cujo payload está no corpo.
:::

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

Para criar a regra no Azion Console:

<DocSteps>
  <DocStep title="Abra a aba Rules Engine">

  Em Azion Console, vá até **Firewalls**, selecione o seu Firewall e depois selecione a aba **Rules Engine**.

  </DocStep>
  <DocStep title="Inicie uma nova regra">

  Selecione **Rule**. O drawer **Create Rule** abre.

  </DocStep>
  <DocStep title="Nomeie a regra">

  Na seção **General**, informe um **Name**. Por exemplo: `Run Bot Manager on every request`. A descrição é opcional.

  </DocStep>
  <DocStep title="Defina o critério">

  Na seção **Criteria**, selecione a variável _Request Uri_, o operador _starts with_ e `/` como argumento.

  </DocStep>
  <DocStep title="Acrescente o comportamento Run Function">

  Na seção **Behaviors**, selecione _Run Function_. Um segundo controle aparece, com o placeholder `Select a Function`: ele lista as Function Instances deste Firewall, então selecione a que você nomeou.

  </DocStep>
  <DocStep title="Selecione Save" />
</DocSteps>

O Firewall executa a Function Instance em toda requisição que recebe. Uma regra carrega no máximo um comportamento _Run Function_.

</Fragment>

<Fragment slot="panel.cli">

### CLI

`azion create firewall-rule` lê a regra inteira de um arquivo JSON. Ele não tem flag para um critério ou um comportamento.

<DocSteps>
  <DocStep title="Escreva a regra em um arquivo">

  Salve o seguinte como `rule.json`, com o ID da sua Function Instance em `value`:

  ```json
  {
    "name": "Run Bot Manager on every request",
    "active": true,
    "criteria": [
      [
        {
          "conditional": "if",
          "variable": "${request_uri}",
          "operator": "starts_with",
          "argument": "/"
        }
      ]
    ],
    "behaviors": [
      {
        "type": "run_function",
        "attributes": {
          "value": 12347
        }
      }
    ]
  }
  ```

  </DocStep>
  <DocStep title="Crie a regra">

  Substitua `<firewall-id>` pelo ID do seu Firewall:

  ```bash
  azion create firewall-rule --firewall-id <firewall-id> --file rule.json
  ```

  </DocStep>
  <DocStep title="Leia a saída">

  O comando imprime o ID da nova regra:

  ```text
  Created Firewall Rule with ID 123458
  ```

  </DocStep>
</DocSteps>

O Firewall executa a Function Instance em toda requisição que recebe. A chave do comportamento é `type`: um arquivo que escreve `name` no lugar é recusado com `Failed to decode the given 'json' file`, que não nomeia nem o campo nem o motivo.

</Fragment>

### API

Os critérios carregam `${request_uri}`, então o corpo é enviado a partir de um arquivo.

<DocSteps>
  <DocStep title="Escreva a regra em um arquivo">

  Salve o seguinte como `rule.json`, com o ID da sua Function Instance em `value`:

  ```json
  {
    "name": "Run Bot Manager on every request",
    "active": true,
    "criteria": [
      [
        {
          "conditional": "if",
          "variable": "${request_uri}",
          "operator": "starts_with",
          "argument": "/"
        }
      ]
    ],
    "behaviors": [
      {
        "type": "run_function",
        "attributes": {
          "value": 12348
        }
      }
    ]
  }
  ```

  </DocStep>
  <DocStep title="Envie a requisição de criação">

  Substitua `<firewall-id>` pelo ID do seu Firewall:

  ```bash
  curl --request POST \
    --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: application/json' \
    --data @rule.json
  ```

  </DocStep>
  <DocStep title="Leia a resposta">

  A chamada responde `202`. A resposta devolve a regra e acrescenta o `order` que a plataforma atribui a ela, que é `0` para a primeira regra do Firewall.

  </DocStep>
</DocSteps>

O Firewall executa a Function Instance em toda requisição que recebe. A chave do comportamento é `type`, e `attributes.value` guarda o ID da Function Instance. O ID da Function é recusado com `400` e `25030 Entity Not Found`.

## Verifique que uma requisição é pontuada

A verificação é a mesma qualquer que seja a interface que construiu a Function Instance. O seu Workload responde em um domínio no formato `<id>.map.azionedge.net`, escrito nesta etapa como `<your-workload-domain>`.

Uma regra nova pode levar vários minutos para alcançar a infraestrutura distribuída da Azion, e nenhuma duração é garantida. Uma mudança nos argumentos de uma Function Instance leva até alguns minutos. Enquanto uma mudança se espalha, as respostas à mesma requisição alternam entre o resultado anterior e o novo, então espere antes de ler qualquer coisa em uma resposta. Para mais informações, consulte [Propagação](/pt-br/documentacao/plataforma/firewall/como-funciona/#propagacao).

Verifique lendo o log de report, não tentando ser recusado. No limite de `30` que este guia define, uma requisição com formato de bot é pontuada e ainda assim servida, então o log é onde o resultado está.

Envie uma requisição sem user agent, que é o que um cliente programado envia:

```bash
curl -A "" https://<your-workload-domain>/
```

Depois leia a linha que a Function escreveu. O log de report é servido pelo dataset `functionConsoleEvents`. Envie a consulta a seguir para `https://api.azion.com/v4/events/graphql` com um cabeçalho `Authorization: Token [TOKEN VALUE]`, e um `tsRange` que cubra o momento da requisição:

```graphql
{
  functionConsoleEvents(
    limit: 200
    filter: { tsRange: { begin: "2026-01-01T11:30:00", end: "2026-01-01T13:00:00" } }
    orderBy: [ts_ASC]
  ) {
    ts
    line
    level
    lineSource
    functionId
    configurationId
  }
}
```

A consulta responde `200` e devolve um registro por linha que a Function escreveu. `functionId` é o ID da Function instalada, não da Function Instance dela. `configurationId` é o ID do Workload em que a requisição chegou, não do Firewall. `line` carrega a linha de report inteira, que abre com o prefixo e continua como um objeto JSON:

```text
[Bot-Protection][storefront-bots] Report:  {"request_id":"0123456789abcdef0123456789abcdef","remote_addr":"203.0.113.42","fingerprint":"ge20cn020000_000000000000_000000000000_000000000000","host":"<your-workload-domain>","http_user_agent":"","request_uri":"/","geoip_country":"DE","geoip_region":"HE","asn":"64496","score":28,"bot_category":"Bad Bot Signatures, Malicious Intent detected","classified":"legitimate","action":"allow","matched_rules":[1,10,18,19,20]}
```

O segundo colchete do prefixo carrega a `log_tag` que você definiu, que é como você separa uma Function Instance de outra. Quatro valores no objeto respondem à pergunta que este guia fez. `score` é `28`. `matched_rules` é `[1, 10, 18, 19, 20]`, as regras que produziram esse score, entre elas a regra `1` pelo user agent vazio. `action` se lê `allow`, e `classified` se lê `legitimate`. Para cada campo que uma linha carrega, consulte [Logs](/pt-br/documentacao/plataforma/firewall/bot-manager/logs/#campos).

Nada foi recusado, e esse é o resultado a esperar: `28` é menor que o limite de `30`, então o score nunca alcançou o valor a partir do qual `deny` é executado. A requisição foi inspecionada, pontuada e servida, que é o que você se propôs a provar.

O que um limite mais baixo muda é a ação, não o score. Uma requisição cujo score alcança o limite recebe `action`, e `deny` responde `HTTP 403` com a página de erro padrão da Azion. A classificação também se move com o limite: `classified` é um veredito relativo ao limite em vigor, então o mesmo score de `28`, das mesmas regras correspondidas, se lê `legitimate` sob um limite de `30` e `bad bot` sob um limite que `28` alcança. Aprenda quanto o seu próprio tráfego pontua antes de reduzi-lo.
