Este guia orienta você a negar a sua primeira requisição com um [Firewall](/pt-br/documentacao/plataforma/firewall/).

- Crie um Firewall que começa com as configurações padrão.
- Adicione uma regra que nega toda requisição para um caminho.
- Defina o Firewall no deployment do [Workload](/pt-br/documentacao/plataforma/workloads/) que serve a sua [Application](/pt-br/documentacao/plataforma/applications/).
- Envie uma requisição para esse caminho e leia o `403` que ela retorna.

Quatro partes transformam uma requisição em uma decisão, e cada parte leva à seguinte:

1. O **Firewall** guarda as regras. Ele fica ativo desde o momento em que você o cria.
2. A **regra** nesse Firewall combina um critério com um comportamento. O critério seleciona requisições, e o comportamento decide o que acontece com elas. Neste guia, o critério seleciona todo caminho que começa com `/deny-test`, e o comportamento nega a requisição.
3. O **deployment** do Workload que serve a sua Application define esse Firewall, ao lado da Application.
4. A **requisição** para o domínio do Workload encontra a regra, e uma requisição negada nunca chega à sua Application.

Um Firewall não inspeciona nada por conta própria. Enquanto o deployment de um Workload não o definir, nenhuma requisição chega às regras dele.

[Network Shield](/pt-br/documentacao/plataforma/firewall/network-shield/), [Web Application Firewall (WAF)](/pt-br/documentacao/plataforma/firewall/waf/) e [Bot Manager](/pt-br/documentacao/plataforma/firewall/bot-manager/) são recursos da plataforma aninhados ao Firewall. Network Shield compara requisições pela origem, WAF detecta ataques e Bot Manager detecta clientes automatizados. Os primeiros passos de cada um partem de um Firewall que o deployment de um Workload define, e este guia deixa um pronto para você.

## Crie o Firewall

Um Firewall novo não tem regras, e ele começa ativo. Um Firewall só aceita uma regra enquanto WAF, Network Shield ou [Functions](/pt-br/documentacao/plataforma/firewall/functions/) está ativado. Um Firewall novo começa com Network Shield e Functions ativados, então as configurações padrão aceitam a regra Deny deste guia.

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

Para criar o Firewall no Azion Console:

<DocSteps>
  <DocStep title="Abra a página Firewalls">

  Acesse [Azion Console](https://console.azion.com/) > **Firewalls**.

  </DocStep>
  <DocStep title="Inicie um Firewall">

  Selecione **Firewall**. A página **Create Firewall** abre.

  </DocStep>
  <DocStep title="Dê um nome ao Firewall">

  Na seção **General**, informe um **Name**. Por exemplo: `storefront-firewall`.

  </DocStep>
  <DocStep title="Deixe as outras seções como abrem">

  Em **Modules**, **Functions** e **Network Shield** abrem ativados, e **Web Application Firewall** abre desativado. Em **Status**, **Active** continua ativado.

  </DocStep>
  <DocStep title="Selecione Create" />
</DocSteps>

Azion Console exibe a mensagem "Your Firewall has been created" e abre o Firewall. As abas dele são **Main Settings**, **Functions Instances** e **Rules Engine**. **Functions Instances** aparece somente enquanto **Functions** está ativado.

</Fragment>

<Fragment slot="panel.cli">

### CLI

Para criar o Firewall pela Azion CLI:

```bash
azion create firewall --name "storefront-firewall" --active true
```

O comando imprime o ID do Firewall novo:

```text
Created Firewall with ID 12352
```

O Firewall fica ativo, com Functions e Network Shield ativados e WAF desativado. Anote o ID. A regra o passa como `--firewall-id`.

</Fragment>

<Fragment slot="panel.api">

### API

Para criar o Firewall pela API, envie uma requisição `POST` para o endpoint de firewalls. Substitua `[TOKEN VALUE]` pelo seu personal token:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/firewalls \
  --header 'Accept: application/json' \
  --header 'Authorization: Token [TOKEN VALUE]' \
  --header 'Content-Type: application/json' \
  --data '{"name": "storefront-firewall"}'
```

A API responde com `202`. Este trecho da resposta mostra o Firewall novo e as configurações com que ele começa:

```json
{
  "state": "pending",
  "data": {
    "id": 12353,
    "name": "storefront-firewall",
    "modules": {
      "ddos_protection": { "enabled": true },
      "functions": { "enabled": true },
      "network_protection": { "enabled": true },
      "waf": { "enabled": false }
    },
    "debug": false,
    "active": true,
    …
    "product_version": "2.0",
    …
    "version": 0
  }
}
```

O Firewall fica ativo, e `waf` é a única entrada de `modules` que começa desativada. Anote o `id`. A regra o passa como `<firewall-id>`.

</Fragment>

</Tabs>

## Adicione uma regra que nega um caminho

Uma regra do [Rules Engine para Firewall](/pt-br/documentacao/plataforma/firewall/rules-engine/) combina critérios com comportamentos. A regra desta etapa carrega um critério, uma URI de requisição que começa com `/deny-test`, e um comportamento, Deny. Deny recusa a requisição com `403 Forbidden`.

O critério corresponde a todo caminho que começa com `/deny-test`, então `/deny-test/page` também corresponde. Para mais informações, consulte [Deny (403 Forbidden)](/pt-br/documentacao/plataforma/firewall/rules-engine/#deny-403-forbidden).

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

Para adicionar a regra no Azion Console:

<DocSteps>
  <DocStep title="Abra o Firewall">

  Acesse [Azion Console](https://console.azion.com/) > **Firewalls** e selecione o Firewall que você criou.

  </DocStep>
  <DocStep title="Selecione a aba Rules Engine" />
  <DocStep title="Inicie uma regra">

  Selecione **Rule**. O drawer **Create Rule** abre.

  </DocStep>
  <DocStep title="Dê um nome à regra">

  Na seção **General**, informe um **Name**. Por exemplo: `Deny the test path`.

  </DocStep>
  <DocStep title="Defina o critério">

  Na seção **Criteria**, o primeiro critério abre com _Request Uri_ e _starts with_. Informe `/deny-test` como argumento dele.

  </DocStep>
  <DocStep title="Selecione o comportamento Deny">

  Na seção **Behaviors**, selecione _Deny (403 Forbidden)_.

  </DocStep>
  <DocStep title="Selecione Save" />
</DocSteps>

Azion Console exibe a mensagem "Rule successfully created". A regra aparece na lista **Rules Engine** com o status _Active_.

</Fragment>

<Fragment slot="panel.cli">

### CLI

`azion create firewall-rule` lê a regra inteira de um arquivo JSON. `criteria` é uma lista de grupos, e o primeiro critério de um grupo carrega a condicional `if`. Salve esta regra como `rule.json`:

```json
{
  "name": "Deny the test path",
  "active": true,
  "criteria": [
    [
      {
        "variable": "${request_uri}",
        "conditional": "if",
        "operator": "starts_with",
        "argument": "/deny-test"
      }
    ]
  ],
  "behaviors": [
    { "type": "deny" }
  ]
}
```

Crie a regra. Substitua `<firewall-id>` pelo ID do seu Firewall:

```bash
azion create firewall-rule --firewall-id <firewall-id> --file rule.json
```

O comando imprime o ID da regra nova:

```text
Created Firewall Rule with ID 123460
```

A regra fica ativa no Firewall.

</Fragment>

<Fragment slot="panel.api">

### API

O corpo da requisição é a própria regra. `criteria` é uma lista de grupos, e o primeiro critério de um grupo carrega a condicional `if`. Salve esta regra como `rule.json`:

```json
{
  "name": "Deny the test path",
  "active": true,
  "criteria": [
    [
      {
        "variable": "${request_uri}",
        "conditional": "if",
        "operator": "starts_with",
        "argument": "/deny-test"
      }
    ]
  ],
  "behaviors": [
    { "type": "deny" }
  ]
}
```

Envie uma requisição `POST` para as regras do seu Firewall. Substitua `<firewall-id>` pelo ID do seu Firewall:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules \
  --header 'Accept: application/json' \
  --header 'Authorization: Token [TOKEN VALUE]' \
  --header 'Content-Type: application/json' \
  --data @rule.json
```

A API responde com `202`. Este trecho da resposta mostra o `id` da regra nova e a `order` dela entre as regras do Firewall:

```json
{
  "state": "pending",
  "data": {
    "id": 123459,
    …
    "behaviors": [{ "type": "deny" }],
    "description": "",
    "order": 0
  }
}
```

A API atribui `order` na ordem de criação, começando em `0`. A regra fica ativa no Firewall.

</Fragment>

</Tabs>

## Defina o Firewall no deployment do seu Workload

Um Firewall não tem domínio próprio, e o Workload carrega o domínio. O deployment de um Workload define três coisas: a Application, o Firewall e a custom page. Mantenha a Application e a custom page que o seu Workload usa hoje e defina o seu Firewall ao lado delas. Enquanto o deployment não definir o seu Firewall, a regra Deny não corresponde a nenhuma requisição.

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

Para definir o Firewall no Azion Console:

<DocSteps>
  <DocStep title="Abra a página Workloads">

  Acesse [Azion Console](https://console.azion.com/) > **Workloads**.

  </DocStep>
  <DocStep title="Abra o seu Workload">

  Selecione o Workload que serve a sua Application. O formulário de edição dele abre.

  </DocStep>
  <DocStep title="Selecione o Firewall">

  No campo **Firewall** de **Deployment Settings**, selecione o Firewall que você criou. **Application** e **Custom Page** mantêm o que o Workload serve hoje.

  </DocStep>
  <DocStep title="Selecione Save" />
</DocSteps>

O deployment do seu Workload define o seu Firewall, ao lado da Application e da custom page dele.

</Fragment>

<Fragment slot="panel.cli">

### CLI

A Azion CLI não tem comando que atualize um deployment, e um Workload guarda somente um deployment. Para definir o Firewall no deployment que o seu Workload já tem, siga o painel do Console. Para criar o deployment de um Workload que não tem nenhum, consulte [Azion CLI workload-deployment](/pt-br/documentacao/devtools/cli/recursos/workload-deployment/).

</Fragment>

<Fragment slot="panel.api">

### API

A referência publicada da Azion API v4 não tem endpoint para o deployment de um Workload. Para definir o Firewall, siga o painel do Console.

</Fragment>

</Tabs>

## Confirme que o caminho responde 403

A verificação é a mesma, qualquer que seja a interface que criou o Firewall. O seu Workload responde no domínio de workload dele, no formato `<id>.map.azionedge.net`, escrito nesta etapa como `<your-workload-domain>`.

Um Workload cujo deployment passa a definir um Firewall pode levar vários minutos para aplicar a primeira regra, e nenhuma duração é garantida. Enquanto a mudança se propaga, as respostas à mesma requisição alternam entre a resposta anterior e a nova. Envie a requisição de novo até ela responder `403`. Para mais informações, consulte [Propagação](/pt-br/documentacao/plataforma/firewall/como-funciona/#propagacao).

Envie uma requisição para o caminho negado:

```bash
curl -i https://<your-workload-domain>/deny-test
```

O Firewall a recusa com `403`:

```text
HTTP/2 403
server: nginx
date: Thu, 01 Jan 2026 12:00:00 GMT
content-type: text/html; charset=utf-8
x-content-type-options: nosniff
x-azion-request-id: 0123456789abcdef0123456789abcdef
x-azion-edge-location: <edge-location>
alt-svc: h3=":443"; ma=86400
```

A resposta também carrega um header `content-security-policy` longo, omitido deste trecho. O corpo é a página de erro padrão da Azion, com o título Forbidden, e ela lista o seu endereço IP e o ID da requisição. Nenhum header nomeia o Firewall ou a regra que recusou a requisição.

Requisições para qualquer outro caminho não correspondem à regra, e a sua Application as responde como antes. O seu Firewall nega toda requisição cujo caminho começa com `/deny-test`.
