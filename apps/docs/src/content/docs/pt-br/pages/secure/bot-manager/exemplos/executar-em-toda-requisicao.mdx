Você pode executar uma Function Instance do Bot Manager em toda requisição que um Firewall recebe com uma regra do [Rules Engine para Firewall](/pt-br/documentacao/plataforma/firewall/rules-engine/), pelo Azion Console, pelo Azion CLI ou pela API. Uma Function Instance não pontua nada até que uma regra a execute. Para saber onde a regra fica no caminho que uma requisição percorre, consulte [Score de bots](/pt-br/documentacao/plataforma/firewall/bot-manager/score-de-bots/).

## Crie a regra

A regra a seguir corresponde a toda requisição que o Firewall dela recebe e executa uma Function Instance em cada uma. O `value` dela contém o ID da Function Instance neste Firewall, então substitua `12347` pelo seu. Ele nunca contém o ID da Function instalada, que é o mesmo para toda Function Instance dela na conta.

```json
{
  "name": "Run Bot Manager on every request",
  "active": true,
  "criteria": [
    [
      {
        "conditional": "if",
        "variable": "${request_uri}",
        "operator": "starts_with",
        "argument": "/"
      }
    ]
  ],
  "behaviors": [
    {
      "type": "run_function",
      "attributes": {
        "value": 12347
      }
    }
  ]
}
```

<Fragment slot="panel.console">

### Console

Para criar a regra pelo Azion Console:

<DocSteps>
  <DocStep title="Abra o Firewall que carrega a Function Instance">

  Acesse [Azion Console](https://console.azion.com/) > **Firewalls** e selecione esse Firewall.

  </DocStep>
  <DocStep title="Selecione a aba Rules Engine" />
  <DocStep title="Selecione Rule" />
  <DocStep title="Dê um nome à regra">

  Informe `Run Bot Manager on every request` como o nome. A descrição é opcional.

  </DocStep>
  <DocStep title="Defina o critério">

  Na seção **Criteria**, selecione `Request Uri` como variável e _starts with_ como operador e, em seguida, informe `/` como argumento.

  </DocStep>
  <DocStep title="Adicione o comportamento Run Function">

  Na seção **Behaviors**, selecione **Run Function**. Um segundo controle aparece, sem rótulo e com o placeholder `Select a Function`. Ele lista as Function Instances deste Firewall, então selecione a que deve ser executada.

  </DocStep>
  <DocStep title="Selecione Save" />
</DocSteps>

O Firewall guarda a regra, e a Function Instance pontua toda requisição que o Firewall recebe. O seletor do comportamento lista Function Instances, e não Functions. Uma regra carrega no máximo um comportamento **Run Function**, e o Azion Console desabilita a opção quando a regra já tem um.

A variável `Request Uri` sempre pode ser selecionada. Enquanto o [WAF](/pt-br/documentacao/plataforma/firewall/waf/) está desativado no Firewall, a lista mostra `Header User Agent - required WAF` e `Request Args - required WAF`, e nenhuma das duas pode ser selecionada.

</Fragment>

<Fragment slot="panel.cli">

### CLI

Para criar a regra com o Azion CLI, salve a regra do exemplo como `rule.json`. `azion create firewall-rule` lê a regra inteira desse arquivo e não tem flag para um critério ou um comportamento:

```bash
azion create firewall-rule --firewall-id <firewall-id> --file rule.json
```

```text
Created Firewall Rule with ID 123458
```

O Azion CLI confirma a regra com o ID que ela recebeu. Ao ler a regra de volta, a plataforma terá adicionado uma chave que ela mesma atribui, `"order": 0`, que é a posição da regra entre as regras daquele Firewall. `criteria` é uma lista de listas, e o comportamento recebe a chave `type`. Um arquivo que escreve `name` no lugar é recusado com `Failed to decode the given 'json' file`, uma mensagem que não informa nem o campo nem o motivo: o arquivo é JSON válido e o defeito está no formato.

</Fragment>

<Fragment slot="panel.api">

### API

Envie uma requisição `POST` para a coleção `request_rules` do Firewall que carrega a Function Instance, com `rule.json` como corpo:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules \
  --header 'Accept: application/json' \
  --header 'Authorization: Token [TOKEN VALUE]' \
  --header 'Content-Type: application/json' \
  --data @rule.json
```

A API responde `202` e retorna a regra com uma chave que ela atribuiu: o `order` da regra entre as regras daquele Firewall, `0` para a primeira. O ID da Function em `value` é recusado com `400` e `25030 Entity Not Found`.

</Fragment>

</Tabs>

:::note[nota]
Baseie o critério na URI da requisição. A variável `${request_args}` com o operador `matches` e `.*` como argumento parece corresponder a tudo e não corresponde: a variável fica vazia sempre que uma requisição não carrega query string, e uma variável vazia não corresponde a nada. Uma regra montada assim ignora silenciosamente todo `POST` cujo payload está no corpo. Executar uma segunda Function Instance na mesma requisição exige uma segunda regra, porque uma regra carrega no máximo um comportamento `run_function`.
:::
