O ponto de entrada de um site decide quem pode alcançá-lo e se uma conexão é confiável. Erros nesse ponto raramente aparecem como um erro no seu código. Uma mudança testada no tráfego real alcança todos os visitantes de uma vez. Um endereço que você esqueceu fica aberto a qualquer pessoa que o encontre. Um certificado que expira deixa de proteger o tráfego no dia em que vence.

Estas práticas se aplicam a um [Workload](/pt-br/documentacao/plataforma/workloads/), aos hostnames e às configurações de Transport Layer Security (TLS) que ele guarda e aos certificados que ele usa. Os mecanismos por trás delas estão em [Como Workloads funciona](/pt-br/documentacao/plataforma/workloads/como-funciona/), e cada campo está em [Configurações de Workload](/pt-br/documentacao/plataforma/workloads/configuracoes/).

Uma mudança em um Workload leva vários minutos para alcançar toda a infraestrutura distribuída da Azion, sem duração garantida. Nesse meio-tempo, as requisições podem receber a configuração antiga ou a nova, como descreve [Propagação](/pt-br/documentacao/plataforma/workloads/como-funciona/#propagacao). Cada verificação desta página só vale quando requisições repetidas concordam.

As quatro primeiras práticas se aplicam a todo Workload: testar uma mudança em um Workload de staging antes da produção, fechar o workload domain quando o seu domínio servir tráfego, usar o TLS mútuo (mTLS) permissive apenas para testes e garantir que toda aplicação cliente envie Server Name Indication (SNI). As práticas para os certificados que um Workload usa vêm em seguida, em Certificate Manager.

## Teste uma mudança em um Workload de staging antes da produção

Um Workload de staging é um Workload criado na infraestrutura de staging, com `infrastructure` definido como `2` na API. Ele roda na rede de staging, separado da rede de produção, então um erro ali não alcança nenhum visitante do seu site. Ele responde apenas no workload domain dele, `<id>.preview.azionedge.net`, porque um Workload de staging não aceita domínio personalizado. O custo é um segundo Workload com o próprio deployment, que você mesmo mantém em sincronia com a produção. A infraestrutura é fixada na criação, então uma configuração testada chega à produção como um novo Workload, não como uma edição do Workload de staging. Para a mesma escolha no Azion Console, consulte [Configurações de Workload](/pt-br/documentacao/plataforma/workloads/configuracoes/#infraestrutura).

Este arquivo, enviado com `azion create workload --file`, cria um Workload de staging por meio de `"infrastructure": 2`. Os outros valores são os padrões de um Workload de produção. Copie os valores do seu próprio Workload de produção, para que o staging teste a mesma configuração.

<Code client:visible lang="json" code={`{
  "name": "my-workload-staging",
  "active": true,
  "infrastructure": 2,
  "tls": { "certificate": null, "ciphers": 7, "minimum_version": "tls_1_3" },
  "protocols": { "http": { "versions": ["http1", "http2", "http3"], "http_ports": [80], "https_ports": [443], "quic_ports": [443] } },
  "domains": [],
  "workload_domain_allow_access": true
}`} />

A CLI responde `Created Workload with ID <workload-id>`, e `azion describe workload --workload-id <workload-id> --format json` retorna um `workload_domain` que termina em `.preview.azionedge.net`. Para testar um hostname de produção antes que os registros de Domain Name System (DNS) dele mudem, liste-o em um Workload de produção. Depois, mapeie o hostname para o endereço do workload domain no seu arquivo hosts, como descreve [Teste uma aplicação pelo arquivo hosts](/pt-br/documentacao/guias/desenvolvimento-de-aplicacoes/primeiros-passos/testar-edge-application-atraves-do-arquivo-hosts/).

## Feche o workload domain quando o seu domínio servir tráfego

Por padrão, um Workload também responde no workload domain dele, o endereço `<id>.map.azionedge.net` que a Azion gera. O campo `workload_domain_allow_access` controla esse acesso, e Azion Console o chama de **Workload Domain Allow Access**, como mostra [Configurações de Workload](/pt-br/documentacao/plataforma/workloads/configuracoes/#dominios). Definir o campo como `false` deixa os hostnames em `domains` como a única entrada, então todo cliente chega por um nome que você escolheu listar. O custo é uma dependência desses hostnames.

:::caution[Atenção]
A API recusa essa mudança em um Workload cuja lista `domains` está vazia. Ela responde `When the workload hostname access is blocked, the workload requires alternate domains or domains.` Adicione um hostname primeiro.
:::

Envie este corpo com `azion update workload --file`, que lê o ID do Workload da chave `"id"`:

<Code client:visible lang="json" code={`{
  "id": <workload-id>,
  "workload_domain_allow_access": false
}`} />

A CLI responde `Updated Workload with ID <workload-id>`. Depois que a mudança se propaga, uma requisição ao workload domain responde `404`, enquanto os seus próprios domínios continuam servindo. Defina o campo como `false` somente depois que os seus próprios hostnames responderem em todos os lugares, para que os clientes sempre tenham um hostname que funcione. Para apontar o seu domínio para o Workload antes, consulte [Aponte um domínio para um workload](/pt-br/documentacao/guias/plataforma/migracao/apontar-dominio-para-a-azion/).

## Use mTLS permissive apenas para testes

TLS mútuo ([mTLS](/pt-br/documentacao/plataforma/workloads/mtls/)) é um handshake TLS no qual o cliente também apresenta um certificado. Depois, o Workload verifica se uma autoridade certificadora (CA) em que você confia assinou esse certificado. No modo `enforce`, um cliente sem esse certificado falha no handshake. No modo `permissive`, o handshake se completa, então uma regra de Firewall que testa a variável Client Certificate Validation precisa recusar o cliente. Sem essa regra, um Workload permissive admite os clientes que o mTLS deveria recusar.

Use `permissive` para testar o acesso em condições específicas e sirva a produção com `enforce`, como neste corpo para `azion update workload --file`:

<Code client:visible lang="json" code={`{
  "id": <workload-id>,
  "mtls": {
    "enabled": true,
    "config": { "certificate": <trusted-ca-id>, "crl": [<crl-id>], "verification": "enforce" }
  }
}`} />

Para verificar o modo em vigor, envie uma requisição sem certificado de cliente. Em `enforce`, o handshake falha e o curl sai com o código `56`:

<Code client:visible lang="bash" code={`curl -skv https://<your-domain>/ -o /dev/null`} />

Para a regra de Firewall de que um Workload permissive precisa, consulte [Modos de verificação](/pt-br/documentacao/plataforma/workloads/mtls/#modos-de-verificacao). Para os passos, consulte [Configure mTLS em um workload](/pt-br/documentacao/guias/seguranca-de-aplicacoes/tls-e-certificados/associar-um-certificado-mtls/).

## Garanta que toda aplicação cliente envie SNI

Server Name Indication (SNI) é a extensão de TLS na qual um cliente nomeia o host que deseja durante o handshake. Todo domínio servido com um certificado vinculado ao Workload, enviado ou do Let's Encrypt, depende dela. Uma conexão sem SNI alcança a configuração padrão da Azion, que apresenta o certificado SAN da Azion em vez do seu. Esse é o certificado da própria Azion, com hostnames da Azion listados como Subject Alternative Names (SAN), como `*.map.azionedge.net` e `*.azion.app`. Em um Workload com mTLS no modo `enforce`, a Azion fecha essa conexão antes que ela chegue à sua aplicação, e o cliente não recebe resposta.

A configuração fica em cada cliente, como o cliente de API de um parceiro ou um serviço que chama o seu Workload, então a Azion não pode adicioná-la por eles. Confirme com o responsável por cada aplicação cliente que a biblioteca TLS dela envia, como nome do servidor, o hostname que ela chama. Se um cliente com um certificado válido nunca alcança a sua aplicação, verifique primeiro se ele envia SNI. Para os demais requisitos do mTLS, consulte [mTLS](/pt-br/documentacao/plataforma/workloads/mtls/#requisitos).

## Certificate Manager

[Certificate Manager](/pt-br/documentacao/plataforma/workloads/#certificate-manager) é um recurso da plataforma que armazena os certificados que um Workload usa para TLS. Ele armazena os certificados de servidor que os Workloads apresentam aos clientes e os certificados de CA confiável que verificam certificados de cliente no mTLS. Ele também solicita e renova certificados Let's Encrypt. As práticas desta seção são substituir um certificado de servidor antes que ele expire, manter o registro de desafio de um domínio hospedado fora do [Edge DNS](/pt-br/documentacao/plataforma/edge-dns/), escolher um certificado validado por domínio a menos que precise de mais, limitar as credenciais de DNS-01 aos registros de desafio e manter certificados wildcard fora de sistemas críticos de produção.

### Substitua um certificado de servidor antes que ele expire

Um certificado de servidor que você envia não se renova sozinho e, depois que a data em `validity` passa, ele deixa de proteger o tráfego. Trocar enquanto o certificado antigo ainda é válido deixa tempo para confirmar que o novo funciona e para voltar ao antigo se ele não funcionar. A entrada antiga permanece em Certificate Manager depois da troca, então o custo é mais um certificado para excluir. A Azion renova os certificados Let's Encrypt que gerencia, como descreve [Emissão e renovação](/pt-br/documentacao/plataforma/workloads/certificate-manager/emissao-e-renovacao/).

Envie o novo certificado e, depois, aponte `tls.certificate` para o ID dele com `azion update workload --file`. Mantenha `ciphers` e `minimum_version` nos valores que o Workload já tem, para que o certificado seja o único valor que muda:

<Code client:visible lang="json" code={`{
  "id": <workload-id>,
  "tls": { "certificate": <new-certificate-id>, "ciphers": 7, "minimum_version": "tls_1_3" }
}`} />

A CLI responde `Updated Workload with ID <workload-id>`. Em seguida, `azion list digital-certificate --details` mostra o novo certificado como `active` e o antigo como `inactive` quando nenhum Workload o usa mais. Quando o novo certificado estiver `active` e a mudança tiver se propagado, exclua a entrada antiga. Para o envio em si, consulte [Envie um certificado digital](/pt-br/documentacao/guias/seguranca-de-aplicacoes/tls-e-certificados/certificado-digital/).

### Mantenha o registro de desafio de um domínio hospedado fora do Edge DNS

A Azion renova um certificado Let's Encrypt gerenciado antes que ele expire, executando o desafio dele novamente. Quando a zona do domínio de um certificado DNS-01 está no [Edge DNS](/pt-br/documentacao/plataforma/edge-dns/), a própria Azion escreve o registro `_acme-challenge`. Quando a zona está hospedada em outro provedor de DNS, você adiciona um registro canonical name (CNAME), `_acme-challenge.<your-domain>`, que aponta para `<your-domain>.letsencrypt.azion.com`. Excluir esse CNAME depois faz a próxima renovação falhar, e o certificado então expira.

Mantenha o CNAME no seu provedor enquanto um Workload usar o certificado. A renovação começa 30 dias antes do fim da validade de 90 dias. Para verificar, confirme antes disso que o CNAME ainda existe e que o status do certificado em Certificate Manager não é `failed`. Para o registro a criar, consulte [Solicite um certificado Let's Encrypt](/pt-br/documentacao/guias/seguranca-de-aplicacoes/tls-e-certificados/como-gerar-um-certificado-lets-encrypt/).

### Escolha um certificado validado por domínio, a menos que precise de mais

A autoridade certificadora que emite um certificado que você envia valida a solicitação em um de três níveis. Domain Validation (DV) confirma o seu direito de usar o domínio. Organization Validation (OV) acrescenta verificações sobre a organização solicitante, e Extended Validation (EV) pede documentos que comprovem a existência física, jurídica e operacional dela.

Use DV na maioria dos casos. OV e EV são mais complexos de obter, e as verificações extras dão garantias sobre a sua organização, não sobre o domínio. Peça OV ou EV somente quando um requisito que você consiga nomear exigir essas verificações. Para os três níveis, consulte [Níveis de validação](/pt-br/documentacao/plataforma/workloads/certificate-manager/certificados/#niveis-de-validacao).

### Limite as credenciais de DNS-01 aos registros de desafio

Esta prática vale quando você mesmo obtém um certificado, com um cliente Automatic Certificate Management Environment (ACME) como o Certbot, para uma zona hospedada fora do Edge DNS. Um certificado Let's Encrypt que a Azion gerencia não precisa dela: basta o CNAME de [Mantenha o registro de desafio de um domínio hospedado fora do Edge DNS](#mantenha-o-registro-de-desafio-de-um-dominio-hospedado-fora-do-edge-dns). O seu cliente escreve o registro `_acme-challenge` no provedor de DNS, então guarda as credenciais de API do provedor. Credenciais que alcançam todos os registros dão a quem as obtiver o controle do domínio e de todos os registros dele.

Restrinja essas credenciais a registros `_acme-challenge`, para que um vazamento exponha apenas o desafio. O custo é uma credencial separada para criar e manter só para esse cliente. Para verificar, confirme no seu provedor que as permissões da credencial nomeiam apenas registros `_acme-challenge`.

### Mantenha certificados wildcard fora de sistemas críticos de produção

Um certificado wildcard, como um para `*.example.com`, cobre os subdomínios de `example.com`, como `blog.example.com`, com uma única chave privada. Se essa chave vazar, ou se o certificado for revogado, todos os subdomínios que ele cobre são afetados de uma vez. Um certificado wildcard é adequado quando:

- A gestão centralizada é uma prioridade.
- A mesma equipe gerencia os subdomínios.
- Existe uma arquitetura de proxy reverso bem definida.
- As suas políticas de segurança permitem o compartilhamento controlado de chaves.

Sob requisitos mais rígidos, dê a cada sistema crítico de produção o seu próprio certificado, mantenha certificados separados para ambientes de desenvolvimento e deixe o wildcard para serviços de menor criticidade. O custo é uma substituição por certificado em vez de uma para todos. Mantenha a chave privada de um wildcard em Certificate Manager, vinculada a Workloads, em vez de espalhada por servidores: depois de salva, a chave não pode ser lida de volta pelo Azion Console nem pela API. Para verificar, liste os Workloads que usam cada certificado wildcard com `GET /v4/workspace/workloads?digital_certificate_id=<certificate-id>` e dê a qualquer Workload crítico de produção um certificado próprio.
