Esta página cobre os sintomas de um [Workload](/pt-br/documentacao/plataforma/workloads/) no tráfego real ou em uma requisição recusada, incluindo os de [Certificate Manager](/pt-br/documentacao/plataforma/workloads/#certificate-manager) e de [Custom Pages](/pt-br/documentacao/plataforma/workloads/#custom-pages). Uma recusa citada é a mensagem da API, a menos que a entrada nomeie outra fonte. Azion CLI imprime a mesma mensagem dentro de `Error: Failed to ... [...]`.

---

## Um Workload responde 404 com a página de erro da Azion

As requisições ao workload domain retornam `HTTP/2 404` e a página de erro HTML da Azion em vez da resposta da sua aplicação.

O Workload não tem uma Application para a qual encaminhar a requisição: nenhum deployment define uma ainda, ou o deployment ainda não se propagou, como [O deployment](/pt-br/documentacao/plataforma/workloads/como-funciona/#o-deployment) explica. Um Workload com `workload_domain_allow_access` definido como `false` também responde `404` no workload domain dele, enquanto os seus próprios domínios continuam servindo.

- **Defina a Application no deployment**: no Azion Console, selecione-a no campo **Application** de **Deployment Settings**. Para as outras interfaces, siga [Primeiros passos com Workloads](/pt-br/documentacao/plataforma/workloads/primeiros-passos/).
- **Repita a requisição depois de vários minutos**: um deployment só alcança o tráfego quando se [propaga](/pt-br/documentacao/plataforma/workloads/como-funciona/#propagacao).
- **Verifique o acesso ao workload domain**: o workload domain serve apenas enquanto `workload_domain_allow_access` é `true`. No Azion Console, esse é o switch **Workload Domain Allow Access** da seção **Domains**.
- **Leia os headers**: `curl -sI https://<your-workload-domain>/` imprime a linha de status e o header `x-azion-request-id`, que identifica a requisição.

Quando o deployment se propaga, a mesma requisição retorna a resposta da sua aplicação.

---

## Uma requisição recebe a configuração antiga depois de uma mudança

Depois que você salva uma mudança em um Workload ou no deployment dele, algumas requisições ainda recebem o comportamento anterior, ou as respostas alternam entre o antigo e o novo.

A mudança se espalha pela infraestrutura distribuída da Azion um data center por vez. Isso leva vários minutos, sem duração garantida. Cada data center serve a configuração antiga ou a nova até que todos concordem, como [Propagação](/pt-br/documentacao/plataforma/workloads/como-funciona/#propagacao) detalha.

- **Espere vários minutos antes de testar**: uma requisição antecipada mede a propagação, não a configuração.
- **Envie várias requisições, não uma**: repita a requisição até que as respostas concordem.
- **Confirme que a API armazenou a mudança**: `azion describe workload --workload-id <workload-id> --format json` imprime o Workload como a API o guarda.

Quando todo data center serve a nova configuração, cada requisição recebe a resposta que essa configuração define.

## Um domínio personalizado não alcança o Workload

As requisições a um hostname seu não alcançam o Workload, enquanto o workload domain dele responde.

Um Workload responde apenas aos hostnames listados nos domínios dele, e um cliente só o alcança depois que o DNS envia o hostname para a Azion. As duas partes são necessárias, como [Workload domain e domínios personalizados](/pt-br/documentacao/plataforma/workloads/como-funciona/#workload-domain-e-dominios-personalizados) explica.

- **Liste o hostname no Workload**: adicione-o a `domains` ou, no Azion Console, como uma linha de **Subdomain** e **Domain** da seção **Domains**, como [Adicione um domínio a um workload](/pt-br/documentacao/guias/plataforma/migracao/configurar-dominio/) mostra.
- **Aponte o hostname para o workload domain**: adicione um registro CNAME no seu provedor de DNS, ou hospede a zona no [Edge DNS](/pt-br/documentacao/plataforma/edge-dns/), como [Aponte um domínio para um workload](/pt-br/documentacao/guias/plataforma/migracao/apontar-dominio-para-a-azion/) mostra.
- **Dê tempo aos resolvers**: os visitantes alcançam o Workload quando os seus resolvers obtêm o novo registro.
- **Use um Workload de produção**: um Workload de staging não aceita domínio personalizado.

O hostname então responde com o mesmo conteúdo do workload domain, e por HTTPS quando um certificado o cobre.

## O HTTPS de um domínio personalizado falha com erro de certificado

As requisições HTTPS a um domínio personalizado falham porque o cliente recusa o certificado, enquanto o workload domain serve HTTPS.

Com `tls.certificate` em `null`, o Workload apresenta o certificado SAN da própria Azion, que cobre nomes da Azion como o workload domain, não os seus. Um certificado vinculado também pode não cobrir o hostname, porque a API não compara os nomes dele com os domínios do Workload, como explica [O certificado](/pt-br/documentacao/plataforma/workloads/como-funciona/#o-certificado).

- **Solicite um certificado Let's Encrypt**: no Azion Console, selecione uma opção _New Let's Encrypt Certificate_ no campo **Digital Certificate** do Workload. Essa opção solicita um certificado para os **Domains** do Workload, como mostra [Solicite um certificado Let's Encrypt](/pt-br/documentacao/guias/seguranca-de-aplicacoes/tls-e-certificados/como-gerar-um-certificado-lets-encrypt/).
- **Envie um certificado que cubra o hostname**: envie-o com a chave privada dele e defina o ID dele em `tls.certificate`. Para o envio, consulte [Envie um certificado digital](/pt-br/documentacao/guias/seguranca-de-aplicacoes/tls-e-certificados/certificado-digital/).
- **Verifique os nomes antes de vincular**: os nomes do certificado precisam cobrir o hostname, porque a API não os compara.
- **Espere a mudança se propagar**: vincular um certificado é uma mudança do Workload, e ela só alcança o tráfego quando se [propaga](/pt-br/documentacao/plataforma/workloads/como-funciona/#propagacao).

O cliente então aceita o certificado, e o domínio personalizado serve HTTPS.

## Um domínio é recusado com This account is not allowed to use the following CNAMEs

Salvar os domínios do Workload falha com `This account is not allowed to use the following CNAMEs: example.com.`, em que a mensagem nomeia cada domínio recusado.

A conta não tem permissão para um domínio em `domains`, e a API recusa a requisição inteira, como os erros de [Configurações de Workload](/pt-br/documentacao/plataforma/workloads/configuracoes/#erros) mostram. No Azion Console, uma opção _New Let's Encrypt Certificate_ solicita um certificado primeiro, e essa solicitação falha como [Uma solicitação de certificado é recusada](#uma-solicitacao-de-certificado-e-recusada-com-this-account-cannot-use-certain-common-or-alternative-names) descreve.

- **Remova o domínio que a mensagem nomeia** e salve o restante da lista.
- **Liste apenas domínios para os quais a sua conta tem permissão**.

Azion CLI então imprime `Updated Workload with ID <workload-id>`, e o Workload responde nos domínios que manteve.

## Um hostname personalizado é recusado em um Workload de staging

Adicionar um domínio a um Workload falha com `Custom hostname is not available in the environment 'Staging Infrastructure'.`

Um Workload de staging, com `infrastructure` definido como `2`, não aceita hostname personalizado, incluindo um hostname `azion.app`. Ele responde apenas no workload domain dele, `<id>.preview.azionedge.net`.

- **Teste no workload domain**: envie `"domains": []` e alcance o Workload de staging pelo workload domain dele.
- **Use um Workload de produção para o seu hostname**: um Workload com `infrastructure` definido como `1` o aceita.
- **Visualize o seu hostname antes que o DNS dele mude**: mapeie-o para um Workload de produção no arquivo hosts do seu dispositivo, como [Teste uma aplicação pelo arquivo hosts](/pt-br/documentacao/guias/desenvolvimento-de-aplicacoes/primeiros-passos/testar-edge-application-atraves-do-arquivo-hosts/) mostra.

O Workload de produção então aceita o hostname, e o Workload de staging continua servindo no workload domain dele.

## Um domínio azion.app é recusado

Adicionar um hostname `azion.app`, que Azion Console chama de **Azion Custom Domain**, falha com uma de três mensagens.

Um Workload contém no máximo um hostname `azion.app`, um nome pertence a um Workload por vez e toda entrada precisa estar em conformidade com a RFC 1035, como os erros de [Configurações de Workload](/pt-br/documentacao/plataforma/workloads/configuracoes/#erros) mostram.

- **Mantenha um hostname `azion.app` por Workload**: `Duplicated usage of suffix in alternate_domains: 'azion.app'.` recusa um segundo, mesmo com outro nome.
- **Escolha um nome que nenhum outro Workload tenha**: `The custom hostname is not available.` significa que outro Workload o tem, então escolha outro nome ou remova-o de lá primeiro.
- **Liste o hostname completo, nunca um wildcard**: `The domain does not conform to the format defined in RFC 1035.` recusa `*.azion.app`.

A Azion então serve o hostname por HTTPS com o certificado SAN da própria Azion, como [Crie um Azion custom domain](/pt-br/documentacao/guias/desenvolvimento-de-aplicacoes/primeiros-passos/criar-dominio-personalizado-azion/) mostra.

## O workload domain não pode ser fechado

Definir `workload_domain_allow_access` como `false` falha com `When the workload hostname access is blocked, the workload requires alternate domains or domains.` No Azion Console, essa configuração é o switch **Workload Domain Allow Access**.

Um Workload precisa de um hostname no qual responder, então `workload_domain_allow_access` só pode ser `false` enquanto `domains` contiver pelo menos uma entrada.

- **Adicione primeiro o seu próprio hostname ou um hostname `azion.app`**.
- **Feche o workload domain depois que os seus hostnames responderem em todos os lugares**, como [Boas práticas de Workloads](/pt-br/documentacao/plataforma/workloads/boas-praticas/#feche-o-workload-domain-quando-o-seu-dominio-servir-trafego) explica.

O workload domain então responde `404`, enquanto os seus hostnames continuam servindo.

## A infraestrutura não pode ser alterada

Uma atualização que move um Workload entre staging e produção falha com `The infrastructure cannot be changed after Workload creation.`

O valor de `infrastructure` é fixado quando o Workload é criado, e o texto de ajuda do Azion Console para **Infrastructure** diz "Once this option is saved, it cannot be modified."

- **Crie um segundo Workload na outra infraestrutura**, com `infrastructure` definido como `1` para produção, e dê a ele um deployment próprio.
- **Deixe `infrastructure` fora das atualizações** do Workload existente.

O novo Workload recebe o sufixo de workload domain da infraestrutura dele, `.map.azionedge.net` em produção, como [Infraestrutura](/pt-br/documentacao/plataforma/workloads/como-funciona/#infraestrutura) explica.

---

## Um segundo deployment é recusado

Criar um deployment falha com `The maximum number of deployments allowed per workload is 1.`

Um Workload contém no máximo um deployment, que define a Application e também pode definir um Firewall e um conjunto de custom pages. Uma mudança vai para esse deployment, como [O deployment](/pt-br/documentacao/plataforma/workloads/como-funciona/#o-deployment) explica.

Para editar o deployment existente no Azion Console:

1. Acesse [Azion Console](https://console.azion.com/) > **Workloads** > **o seu Workload**.
2. Em **Deployment Settings**, altere **Application**, **Firewall** ou **Custom Page**.
3. Selecione **Save**.

A mudança salva alcança todo hostname do Workload quando se propaga.

## Uma mudança de porta ou de versão HTTP é recusada

Uma atualização dos protocolos do Workload falha com `Invalid choices for multiple choices field: [80, 8008, 8080, 8880].` ou `Missing required choices for multiple choices field: ['http1', 'http2'].`

A primeira mensagem lista as quatro portas HTTP que um Workload aceita. A segunda significa que `versions` contém `http3` sem `http1` e `http2`.

- **Use apenas `80`, `8008`, `8080` ou `8880` em `http_ports`**, e as portas HTTPS que [Protocolos e portas](/pt-br/documentacao/plataforma/workloads/configuracoes/#protocolos-e-portas) lista.
- **Envie `["http1", "http2", "http3"]` ou remova `http3`**.
- **Ative o suporte a HTTPS antes do suporte a HTTP/3** no Azion Console: **HTTP/3 support** exige **HTTPS support**.

Azion CLI então imprime `Updated Workload with ID <workload-id>`. Para as outras recusas de configuração, como um conjunto de cifras fora do intervalo de `1` a `8`, consulte os erros de [Configurações de Workload](/pt-br/documentacao/plataforma/workloads/configuracoes/#erros).

## Um cliente falha no handshake TLS em um Workload com mTLS

Um cliente não recebe resposta: o curl termina com o código `56` depois da solicitação de certificado do servidor, e o LibreSSL reporta `reason(1116)`, certificate required.

O Workload tem TLS mútuo (mTLS) no modo `enforce`, e o cliente não apresentou certificado, ou apresentou um que uma autoridade certificadora (CA) em que você não confia assinou. Uma conexão sem Server Name Indication (SNI) também é encerrada antes que chegue à sua aplicação.

- **Apresente um certificado que a sua CA confiável assinou**: o certificado de CA confiável é o certificado da CA que assina os certificados dos seus clientes. O Workload o lê de `mtls.config.certificate`, e o curl envia um certificado de cliente com `--cert` e `--key`.
- **Envie SNI de todo cliente**: em um Workload `enforce`, uma conexão sem ele nunca alcança a sua aplicação, como [mTLS](/pt-br/documentacao/plataforma/workloads/mtls/#requisitos) lista.
- **Admita clientes enquanto testa**: `permissive` completa o handshake e deixa a decisão para uma regra de Firewall, como [Modos de verificação](/pt-br/documentacao/plataforma/workloads/mtls/#modos-de-verificacao) descreve.
- **Espere uma mudança de modo se propagar**: até lá, alguns data centers respondem com o modo anterior.

O handshake então se completa, e a requisição alcança a Application. Para a saída detalhada do curl de um handshake recusado, consulte os erros de [mTLS](/pt-br/documentacao/plataforma/workloads/mtls/#erros).

## O mTLS continua ativo depois que uma atualização o desativa

Uma atualização que envia `"enabled": false` em `mtls` é aceita, mas o Workload continua com `"enabled": true` e segue solicitando certificados de cliente.

Enquanto `mtls.config.certificate` guarda um certificado de CA confiável, o Workload mantém o mTLS ativo e ignora `enabled` enviado sozinho. Azion CLI ainda imprime `Updated Workload with ID <workload-id>`, como [mTLS](/pt-br/documentacao/plataforma/workloads/mtls/#campos) observa.

- **Defina todos os campos de `config` como `null`**: envie `null` em `certificate`, `crl` e `verification`, com `false` em `enabled`. Azion Console envia os mesmos valores quando você desliga **Mutual Authentication**. Mantenha o próprio objeto `config`.
- **Espere a mudança se propagar**: até lá, alguns data centers ainda solicitam um certificado de cliente, como [Propagação](/pt-br/documentacao/plataforma/workloads/como-funciona/#propagacao) descreve.

Com a CLI, envie este corpo com `azion update workload --file`:

<Code client:visible lang="json" code={`{
  "id": <workload-id>,
  "mtls": {
    "enabled": false,
    "config": { "certificate": null, "crl": null, "verification": null }
  }
}`} />

`azion describe workload --workload-id <workload-id> --format json` então mostra `"enabled": false` com todos os campos de `config` em `null`. A partir daí, os clientes se conectam sem certificado.

## Um certificado é recusado em uma configuração do Workload

Vincular um certificado a um Workload falha com `Invalid certificate type, MUST be an Edge Certificate.` ou `Invalid certificate type, MUST be a Trusted CA.`

`tls.certificate` aceita somente um certificado de servidor, do tipo `edge_certificate`. `mtls.config.certificate` aceita somente um certificado de CA confiável, do tipo `trusted_ca_certificate`, como os erros de [mTLS](/pt-br/documentacao/plataforma/workloads/mtls/#erros) mostram.

- **Verifique o tipo**: a coluna `TYPE` de `azion list digital-certificate --details` o mostra.
- **Coloque o certificado de servidor em `tls.certificate`**, ou `null` para o certificado SAN da Azion.
- **Coloque o certificado de CA confiável em `mtls.config.certificate`**.

Azion CLI então imprime `Updated Workload with ID <workload-id>`, e o certificado vinculado aparece como `active` em Certificate Manager.

## Certificate Manager

[Certificate Manager](/pt-br/documentacao/plataforma/workloads/#certificate-manager) é um recurso da plataforma que armazena os certificados que um Workload usa para TLS. Ele solicita certificados Let's Encrypt para os domínios de um Workload, guarda os que você envia e mostra o estado de cada um em `status`. Para saber onde ele age sobre uma requisição, consulte [Como Workloads funciona](/pt-br/documentacao/plataforma/workloads/como-funciona/#certificate-manager).

### Um certificado fica pendente

Um certificado Let's Encrypt mantém o status `pending` ou `challenge_verification`, e, no Azion Console, o campo **Digital Certificate** do Workload avisa "This certificate is pending validation and HTTPS may not work until it’s validated".

O desafio não valida um dos nomes: no HTTP-01, o Let's Encrypt busca um arquivo no hostname, então todo nome precisa apontar para a Azion. No DNS-01, ele lê um registro `_acme-challenge` no DNS do domínio, como [Validação de domínio](/pt-br/documentacao/plataforma/workloads/certificate-manager/emissao-e-renovacao/#validacao-de-dominio) explica.

- **Verifique os nomes**: um certificado solicitado pelo formulário do Workload no Azion Console cobre os **Domains** do Workload, então confirme que cada um está correto.
- **Para o HTTP-01, aponte todo nome para a Azion**, incluindo os nomes alternativos.
- **Para o DNS-01 em outro provedor de DNS, adicione o CNAME**: `_acme-challenge.<your-domain>` com o valor `<your-domain>.letsencrypt.azion.com`. No Edge DNS, a Azion grava o registro ela mesma.
- **Depois de 48 horas pendente, verifique os registros CNAME de novo**: as novas tentativas passam então a ocorrer a cada 3 horas, e uma vez por dia depois de 7 dias, como [Tempo de emissão e novas tentativas](/pt-br/documentacao/plataforma/workloads/certificate-manager/emissao-e-renovacao/#tempo-de-emissao-e-novas-tentativas) lista.

Depois que uma tentativa posterior valida, o certificado aparece como `active` enquanto um Workload o usa, ou `inactive` até lá. Para os registros passo a passo, consulte [Solicite um certificado Let's Encrypt](/pt-br/documentacao/guias/seguranca-de-aplicacoes/tls-e-certificados/como-gerar-um-certificado-lets-encrypt/).

### Uma solicitação de certificado é recusada com This account cannot use certain common or alternative names

Uma solicitação Let's Encrypt, uma solicitação de assinatura de certificado (CSR) ou o salvamento de um domínio novo no Azion Console falha com `This account cannot use certain common or alternative names because it does not have permission for their domain names.`

Um nome da solicitação pertence a um domínio para o qual a conta não tem permissão. Um hostname `azion.app` também é recusado, mesmo um que um Workload da conta tenha, como os erros de [Certificados](/pt-br/documentacao/plataforma/workloads/certificate-manager/certificados/#erros) mostram.

- **Nomeie apenas hostnames em domínios para os quais a sua conta tem permissão**, em `common_name` e `alternative_names`.
- **Não solicite certificado para um hostname `azion.app`**: com `tls.certificate` definido como `null`, o Workload apresenta o certificado SAN da Azion, que cobre o hostname `azion.app` e o workload domain.
- **No Azion Console, remova o domínio recusado de Domains**: adicionar um domínio troca **Digital Certificate** de _Azion (SAN)_ para _New Let's Encrypt Certificate (DNS-01)_. **Save** então solicita esse certificado antes de salvar o Workload, e não salva nada quando a solicitação é recusada.

Uma solicitação aceita retorna o `id` do certificado com o status `pending`, e Azion Console mostra "Your workload has been updated".

### A emissão de um certificado falha

Um certificado Let's Encrypt aparece como `failed`, e, no Azion Console, o campo **Digital Certificate** do Workload avisa "This digital certificate failed and HTTPS cannot be used until the issue is resolved".

A validação falhou, e a Azion registra o motivo no campo `status_detail` do certificado. Um valor nomeia o hostname cujo registro deve ser verificado:

```text
An error has occurred while issuing the requested certificate. Please verify the following domains CNAME: www.example.com
```

Outro não nomeia hostname, então verifique todos os nomes do certificado, como [Um certificado fica pendente](#um-certificado-fica-pendente) lista:

```text
domain ownership validation failed - verify DNS records or HTTP challenge accessibility
```

Leia `status_detail` em qualquer interface e corrija o registro ou o nome para o qual ele aponta:

- **Azion Console**: em **Certificate Manager**, o ícone de erro do certificado o mostra.
- **Azion CLI**: `azion describe digital-certificate --digital-certificate-id <certificate-id> --format json` o imprime ao lado de `status`.
- **API**: `GET /v4/workspace/tls/certificates/<certificate-id>` o retorna com o certificado.

Uma tentativa posterior no [cronograma de novas tentativas](/pt-br/documentacao/plataforma/workloads/certificate-manager/emissao-e-renovacao/#tempo-de-emissao-e-novas-tentativas) pode então emitir o certificado, e um certificado emitido em uso aparece como `active`, com `status_detail` em `""`.

### Uma chave privada enviada é recusada

O envio de um certificado de servidor falha com `The provided private key is invalid. Please check the key and try again.`

A API não consegue ler a `private_key` enviada com o certificado, como os erros de [Certificados](/pt-br/documentacao/plataforma/workloads/certificate-manager/certificados/#erros) mostram.

- **Envie a chave que corresponde ao certificado**.
- **Envie-a em PEM**, com as suas linhas `-----BEGIN` e `-----END` e sem passphrase, como [Algoritmos e formatos de chave](/pt-br/documentacao/plataforma/workloads/certificate-manager/certificados/#algoritmos-de-chave-e-formatos) lista.
- **Mantenha a chave como uma única string JSON em um corpo de API**, com cada quebra de linha escrita como `\n`.

Azion CLI então imprime `Created Digital Certificate with ID <certificate-id>`, e o certificado aparece como `inactive` até que um Workload o use.

## Custom Pages

[Custom Pages](/pt-br/documentacao/plataforma/workloads/#custom-pages) é um recurso da plataforma que substitui por uma página sua a resposta de erro retornada por um Connector, uma página por status code de erro. As páginas ficam em um conjunto de custom pages. Para saber onde ele age sobre uma requisição, consulte [Como Workloads funciona](/pt-br/documentacao/plataforma/workloads/como-funciona/#custom-pages).

### Um conjunto de custom pages é recusado com Ensure this field has at least 1 elements

Criar um conjunto de custom pages falha com `Ensure this field has at least 1 elements.`, ou Azion Console se recusa a salvá-lo com `You must have at least one custom page code`.

Um conjunto contém pelo menos uma página, e a requisição enviou `"pages": []`, como os erros de [Configurações de custom page](/pt-br/documentacao/plataforma/workloads/custom-pages/configuracoes/#erros) mostram.

- **Adicione uma página a `pages`**: uma página substitui um status code de erro por um conteúdo de um Connector, como mostra [Corpo da requisição](/pt-br/documentacao/plataforma/workloads/custom-pages/configuracoes/#corpo-da-requisicao).
- **Adicione um código de página no Azion Console**: a tabela **Page Codes** precisa de uma linha antes que você salve o conjunto.

Azion CLI então imprime `Created Custom Page with ID <custom-page-id>`.

### Uma página de erro não aparece

A resposta de erro do Connector chega ao cliente sem alteração, mesmo que um conjunto de custom pages contenha uma página para o status code dela.

Um Workload usa um conjunto de custom pages somente depois que o deployment desse Workload define esse conjunto.

- **Defina o conjunto de custom pages no deployment**: no Azion Console, selecione-o no campo **Custom Page** de **Deployment Settings**, ou passe `--custom-page` para `azion create workload-deployment` ao criar o deployment. A Azion CLI não tem comando que altere um deployment que já existe. Para os passos, consulte [Personalize uma página de erro](/pt-br/documentacao/guias/desenvolvimento-de-aplicacoes/primeiros-passos/personalizar-pagina-resposta-erro/#atribua-o-conjunto-no-deployment-do-workload).
- **Verifique o status code que o Connector retorna**: uma página age apenas sobre o código que lista, como `"404"`.
- **Espere a mudança se propagar**, e o `ttl` de uma página editada expirar.

O cliente então recebe o conteúdo da página no próprio lugar, com o `custom_status_code` da página quando definido, e sem header `Location`.
