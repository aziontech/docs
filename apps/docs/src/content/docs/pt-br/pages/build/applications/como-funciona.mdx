Entre um cliente e o servidor que guarda o seu conteúdo, uma camada pode ler cada requisição antes desse servidor, seja ela para uma página, um arquivo ou uma rota de API. A camada então decide o que acontece com a requisição. Ela pode responder com uma cópia de uma resposta que o servidor enviou antes, adicionar ou remover um header ou escolher o servidor que recebe a requisição. Quando a resposta volta, a mesma camada pode alterá-la antes que o cliente a receba.

Na Azion, essa camada é uma Application. [Applications](/pt-br/documentacao/plataforma/applications/) é um recurso da plataforma que executa cada Application na infraestrutura distribuída da Azion, a partir do data center mais próximo ao seu usuário. Cada requisição chega a uma Application por meio de um [Workload](/pt-br/documentacao/plataforma/workloads/), que recebe a requisição em um dos seus domínios. O deployment do Workload define a Application que trata a requisição.

A Application age sobre a requisição por meio das suas regras, que você escreve em [Rules Engine para Applications](/pt-br/documentacao/plataforma/applications/rules-engine/). Cada regra pertence a uma de duas fases: as regras da Request Phase agem sobre a requisição, e as regras da Response Phase agem sobre a resposta que o usuário recebe. Para enviar a requisição à origem, uma regra da Request Phase usa o behavior _Set Connector_, que define o [Connector](/pt-br/documentacao/plataforma/connectors/) que encaminha a requisição até lá.

Três recursos da plataforma aninhados em Applications agem no caminho do Workload até a origem, cada um com o seu próprio switch na Application. [Cache](/pt-br/documentacao/plataforma/applications/cache/) responde com uma cópia armazenada de uma resposta da origem. [Application Accelerator](/pt-br/documentacao/plataforma/applications/application-accelerator/) acrescenta mais partes da requisição, como um cookie ou um argumento de query string, à cache key, o índice sob o qual Cache arquiva cada cópia. [Image Processor](/pt-br/documentacao/plataforma/applications/image-processor/) constrói uma imagem redimensionada ou convertida a partir de uma imagem na origem.

Esta página explica os mecanismos, e outras duas páginas guardam os campos: Rules Engine para Applications lista cada variável, operador e behavior, e [Limites de Applications](/pt-br/documentacao/plataforma/applications/limites/) lista cada limite. As seções acompanham uma requisição pelo seu caminho e depois cobrem as duas fases, como as regras são executadas, o que uma Application nova tem e a propagação. Depois delas, uma seção para cada um cobre Cache, Application Accelerator e Image Processor. [WebSocket Proxy](/pt-br/documentacao/plataforma/applications/websocket/) cobre, em uma página própria, as conexões WebSocket que uma Application repassa à origem.

## O caminho que uma requisição percorre

Criar uma Application não a coloca no caminho de nenhuma requisição: uma requisição só chega à Application depois que o deployment de um Workload a define. A relação fica guardada no deployment, não na Application, e no Azion Console você a define no campo **Application** das **Deployment Settings** do Workload. O deployment também pode definir um [Firewall](/pt-br/documentacao/plataforma/firewall/), e a requisição então passa pelo Firewall antes que a Application a receba. Os domínios, os protocolos e os certificados também ficam no Workload, então você configura a entrega no Workload, não na Application.

A Application também não guarda uma origem: uma requisição só chega a uma origem quando uma regra da Request Phase a envia para lá com o behavior _Set Connector_. Esse behavior define um Connector, e o Connector guarda o endereço da origem. A API mostra isso: uma Application criada só com `name` e `active` volta com `modules`, `active` e `debug`, e sem nenhum campo que aponte para um servidor. Os Connectors substituem as origens que as versões anteriores de Applications configuravam na Application.

O diagrama acompanha uma requisição do cliente até a resposta que ele recebe. As setas sólidas levam a requisição, e as setas pontilhadas levam a resposta. Cada rótulo começa com o número do seu passo abaixo.

```mermaid

flowchart TD
  Client(["Cliente"])
  WL["Workload"]
  FW["Firewall"]
  App["Application"]
  Cache["Cache"]
  Conn["Connector"]
  Origin[["servidor de origem"]]
  Client -->|"1. requisição"| WL
  WL -->|"1. com Firewall"| FW
  WL -->|"1. sem Firewall"| App
  FW -->|"1. permitida"| App
  FW -.->|"1. recusa"| Client
  App -.->|"2. Deny (403)"| Client
  App -->|"3. cache setting"| Cache
  Cache -.->|"3. cópia válida"| App
  App -->|"4. sem cópia válida"| Conn
  Conn -->|"4. requisição"| Origin
  Origin -.->|"4. resposta"| Conn
  Conn -.->|"4. resposta"| App
  App -.->|"5. resposta"| Client
```

1. O cliente envia a requisição para um dos domínios do Workload. Quando o deployment do Workload também define um Firewall, o Firewall executa as suas regras primeiro e pode recusar a requisição.
2. A Application que o deployment define executa as suas regras da Request Phase, em ordem. Quando um behavior encerra o processamento, como faz _Deny (403 Forbidden)_, a Application responde ao cliente e nenhum behavior ou regra posterior é executado.
3. Quando uma regra com _Set Cache Policy_ aplicou um cache setting, Cache procura uma cópia válida da resposta da origem. Se encontra uma, essa cópia se torna a resposta, e a origem não recebe nenhuma requisição.
4. Caso contrário, o Connector que uma regra com _Set Connector_ definiu encaminha a requisição à origem, e a resposta da origem volta por esse Connector.
5. A Application executa as suas regras da Response Phase sobre a resposta, e o cliente recebe o resultado.

Como uma regra escolhe a origem de cada requisição, uma Application pode encaminhar `/api/` para um servidor e todos os outros paths para outro, com duas regras e dois Connectors. O custo é que nenhuma requisição chega a uma origem por padrão: uma Application nova não tem regras, então nenhum Connector é definido para as suas requisições. Para criar a primeira regra que encaminha as requisições de uma Application a uma origem, consulte [Primeiros passos com Applications](/pt-br/documentacao/plataforma/applications/primeiros-passos/).

## Fases de requisição e de resposta

Cada regra de uma Application pertence a uma fase, e as duas fases são executadas em uma ordem fixa: a Request Phase antes que exista uma resposta, depois a Response Phase sobre a resposta que a Application entrega. Você define a fase de uma regra quando a cria e não pode mudá-la depois. Na API, o endpoint que recebe a regra define a fase dela: `request_rules` ou `response_rules`. Para executar a mesma lógica na outra fase, adicione uma segunda regra nessa fase.

As setas sólidas levam a requisição, e as setas pontilhadas levam a resposta. Cada rótulo começa com o número do seu passo abaixo.

```mermaid
%%{init: {"layout": "elk", "elk": {"cycleBreakingStrategy": "MODEL_ORDER"}, "themeVariables": {"fontSize": "13px"}, "flowchart": {"nodeSpacing": 24, "rankSpacing": 36, "padding": 8, "wrappingWidth": 150, "useMaxWidth": true}, "sequence": {"width": 120, "actorMargin": 30, "useMaxWidth": true}}}%%
flowchart TD
  Client(["Cliente"])
  ReqRules["Application: regras da Request Phase"]
  RespRules["Application: regras da Response Phase"]
  Cache["Cache"]
  Conn["Connector"]
  Origin[["servidor de origem"]]
  Client -->|"1. requisição"| ReqRules
  ReqRules -->|"2. Set Cache Policy"| Cache
  ReqRules -->|"2. Set Connector, Bypass Cache"| Conn
  Conn -->|"2. requisição"| Origin
  Cache -.->|"3. cópia armazenada"| RespRules
  Origin -.->|"3. resposta"| Conn
  Conn -.->|"3. resposta"| RespRules
  RespRules -.->|"4. resposta"| Client
```

1. A requisição chega, e as regras da Request Phase são executadas sobre ela primeiro. Elas podem ler o que a requisição carrega, como a sua URI, os seus headers e os seus cookies, mas nada sobre a resposta, que ainda não existe.
2. Essas regras decidem o cache e a origem. _Set Cache Policy_ aplica um cache setting, _Bypass Cache_ faz a requisição ignorar o cache e _Set Connector_ define o Connector que encaminha a requisição à origem. Esses três behaviors e _Optimize Images_ só são executados na Request Phase. Nessa fase, _Add Request Header_ adiciona um header à requisição que a origem recebe.
3. A resposta volta: ou uma cópia de uma resposta da origem que Cache armazenou, ou a resposta da origem pelo Connector.
4. As regras da Response Phase são executadas sobre essa resposta, uma vez para cada entrega ao usuário. Elas também podem ler o que voltou, como `${status}` e os headers que a origem enviou. Nessa fase, _Add Response Header_ adiciona um header à resposta que o usuário recebe.

Como a Request Phase é executada primeiro, o cache é decidido antes que a resposta exista. Uma regra não pode aplicar um cache setting com base no status code que a origem retorna, porque `${status}` só pode ser lido na Response Phase e _Set Cache Policy_ só é executado na Request Phase.

Alguns behaviors funcionam nas duas fases, e a fase limita o que eles fazem. Em uma regra da Response Phase, _Redirect To_ só é executado quando a origem retorna `404`. Então, um redirecionamento nessa fase pode enviar o usuário para outra página quando a origem não tem nada no path e deixar intactas as requisições para paths que existem. _Run Function_ também funciona nas duas fases, mas a Response Phase só aceita Functions escritas em Lua. O formulário da Function Instance no Azion Console informa esse limite: `Only Lua functions can be used in the Response phase.` [Fases](/pt-br/documentacao/plataforma/applications/rules-engine/#fases) lista as variáveis e os behaviors que cada fase aceita.

## Como as regras são executadas

Dentro de uma fase, a Application pega as suas regras uma de cada vez, em ordem. Ela para quando todas as regras da fase foram executadas ou quando um behavior encerra o processamento.

As setas sólidas acompanham uma requisição pelas regras de uma fase. Cada rótulo começa com o número do seu passo abaixo.

```mermaid
%%{init: {"layout": "elk", "elk": {"cycleBreakingStrategy": "MODEL_ORDER"}, "themeVariables": {"fontSize": "13px"}, "flowchart": {"nodeSpacing": 24, "rankSpacing": 36, "padding": 8, "wrappingWidth": 150, "useMaxWidth": true}, "sequence": {"width": 120, "actorMargin": 30, "useMaxWidth": true}}}%%
flowchart TD
  Req(["requisição"])
  Next["Application: próxima regra, em ordem"]
  Match{"os critérios correspondem?"}
  Run["Application: behaviors da regra, em ordem"]
  Stop["Application: processamento encerrado"]
  Done["Application: fase concluída"]
  Req -->|"1. entra na fase"| Next
  Next -->|"2. regra encontrada"| Match
  Match -->|"2. não"| Next
  Match -->|"3. sim"| Run
  Run -->|"4. um behavior o encerra"| Stop
  Run -->|"5. nenhum behavior o encerra"| Next
  Next -->|"5. nenhuma regra restante"| Done
```

1. A requisição entra em uma fase, e a Application pega a primeira regra dessa fase.
2. A Application compara os critérios da regra com a requisição. Se eles não correspondem, a regra não executa nada, e a Application passa para a próxima regra.
3. Se correspondem, a regra executa os seus behaviors um após o outro, na ordem em que você os organizou.
4. Quando um desses behaviors encerra o processamento, nada depois dele é executado na fase.
5. Caso contrário, a Application passa para a próxima regra, até que não reste nenhuma regra da fase.

[Rules Engine para Applications](/pt-br/documentacao/plataforma/applications/rules-engine/#criterios) lista as variáveis, os operadores e os condicionais que os critérios combinam.

A posição de uma regra é o seu `order`. A plataforma o atribui quando você cria a regra, a partir de `0` para a primeira regra de cada fase. Você pode mudar a ordem das regras no Azion Console ou reordenar uma fase com uma única chamada à API.

Alguns behaviors não podem ficar juntos na mesma regra ou só podem ficar juntos sob algumas condições, e o Console recusa essas combinações.

### Behaviors que se repetem

Quando várias regras correspondem a uma requisição e carregam o mesmo behavior, o tipo do behavior decide o resultado. Com um behavior do tipo Set, como _Set Connector_, não há acúmulo: só o da última regra correspondente é executado. Por exemplo, uma primeira regra define um Connector para todos os paths, e uma segunda regra define outro Connector para `/api/`. Uma requisição para `/api/` corresponde às duas regras, então o Connector da segunda regra a encaminha.

Um behavior do tipo Add, ao contrário, se acumula. _Add Request Cookie_ e _Add Request Header_ são executados uma vez em cada regra correspondente que os carrega, então duas regras que adicionam o mesmo nome e o mesmo valor produzem duas entradas idênticas.

Então, a ordem das regras molda o resultado tanto quanto o conteúdo delas. Uma regra ampla perto do topo define um padrão, e uma regra mais específica mais abaixo substitui esse padrão para as requisições às quais ela corresponde. O mesmo mecanismo tem um custo: mover uma regra na lista pode mudar o Connector a que um path chega, mesmo sem nenhuma regra alterada.

### Behaviors que encerram o processamento

Alguns behaviors interrompem o processamento de uma requisição, e nada depois deles é executado: nenhum behavior posterior na regra deles e nenhuma regra posterior. _Deny (403 Forbidden)_ responde com uma página `403 Forbidden`, _Deliver_ entrega o conteúdo ao usuário e _Redirect To_ envia o usuário para outra URL com um status `301` ou `302`. _Finish Request Phase_ encerra a Request Phase no ponto em que é executado, então o restante da sua regra e todas as regras posteriores dessa fase são ignorados.

Um behavior que encerra o processamento economiza trabalho e também pode esconder uma regra. No início da lista, ele resolve a requisição antes que as regras seguintes gastem tempo com ela. Colocado antes de uma regra de que você ainda precisa, ele impede que essa regra seja executada em cada requisição à qual a regra anterior corresponde. Com Debug Rules ativo, [Real-Time Events](/pt-br/documentacao/plataforma/real-time-events/) e [Data Stream](/pt-br/documentacao/plataforma/data-stream/) mostram quais regras cada requisição executou. Debug Rules é o campo `debug` da Application na API, e [Main Settings](/pt-br/documentacao/plataforma/applications/main-settings/#debug-rules) mostra onde ativá-lo no Azion Console.

## O que uma Application nova tem

Uma Application nova tem dois switches ativos, Cache e Functions, e nenhuma regra. Quando você cria uma Application pela API só com `name` e `active`, a resposta traz estes campos:

```json
{
  "modules": {
    "cache": { "enabled": true },
    "functions": { "enabled": true },
    "application_accelerator": { "enabled": false },
    "image_processor": { "enabled": false }
  },
  "active": true,
  "debug": false
}
```

A lista das suas regras de requisição vem vazia, com `count` em `0`. As quatro chaves de `modules` são os quatro switches de uma Application, e [Main Settings](/pt-br/documentacao/plataforma/applications/main-settings/#recursos-da-plataforma) mostra cada um no Azion Console e na API. No Azion Console, a nota sobre Cache diz `Automatically enabled in all accounts.` [Tiered Cache](/pt-br/documentacao/plataforma/applications/cache/tiered-cache/) não é um desses switches: é uma feature de Cache, e cada cache setting a ativa no seu campo `modules.cache.tiered_cache.enabled`.

Cache está ativo, mas só armazena cópias depois que uma regra aplica um cache setting, e uma Application nova não tem cache settings nem regras. Cache começa a armazenar cópias quando você cria um cache setting e uma regra com _Set Cache Policy_ que o aplica.

Enquanto um switch está desativado, as opções de regra que dependem dele ficam indisponíveis. O formulário do **Rules Engine** no Azion Console marca cada uma dessas opções com _- Required Application Accelerator_, _- Required Image Processor_ ou _- Required Function_, e a API recusa uma regra que usa uma delas. Por exemplo, em uma Application com Application Accelerator desativado, uma regra de requisição com um critério sobre `${request_uri}` retorna `400` com este corpo:

```json
{
  "errors": [
    {
      "code": "25047",
      "title": "Missing Required Modules",
      "detail": " It requires any of the following modules to be enabled: ['application_accelerator'].",
      "status": "400",
      "source": { "pointer": "/data/criteria/0/0/variable" },
      "meta": {
        "message_prefix": "",
        "owner_modules": "any",
        "missing_required_modules": ["application_accelerator"]
      }
    }
  ]
}
```

A API aceita a mesma regra com `${uri}` no lugar de `${request_uri}`, porque `${uri}` não depende de nenhum recurso da plataforma. Essa verificação impede que uma regra dependa de um recurso da plataforma que está desativado na Application. A contrapartida é escolher entre duas variáveis: `${uri}` guarda a URI decodificada sem a query string, enquanto `${request_uri}` mantém a query string e precisa de Application Accelerator. [Rules Engine para Applications](/pt-br/documentacao/plataforma/applications/rules-engine/#behaviors) lista as variáveis e os behaviors que cada recurso da plataforma acrescenta.

## Propagação

Uma alteração em uma Application só chega ao tráfego depois de se propagar pela infraestrutura distribuída da Azion, e a Azion não garante nenhum tempo de propagação. Uma regra nova em uma Application que já atende tráfego pode levar alguns minutos para valer. O deployment de um Workload novo pode levar vários minutos para se propagar e, até lá, o Workload responde com o `404` de placeholder da Azion.

Enquanto uma alteração se propaga, as respostas se alternam, porque cada requisição pode chegar a um data center diferente. Uma requisição retorna o `404` de placeholder, e a seguinte retorna a resposta da Application. Uma resposta correta depois de uma alteração não prova que a alteração está no ar, porque a requisição seguinte ainda pode retornar o placeholder. Repita a requisição até que todas as respostas sejam a que você espera.

Um Firewall que o mesmo deployment define pode entrar no caminho bem depois da Application. Então, um domínio que já responde ainda pode atender requisições que não passam pelo Firewall. Para ver como um Firewall age sobre as requisições, consulte [Firewall](/pt-br/documentacao/plataforma/firewall/).

## Cache

Um cache armazena uma cópia de uma resposta da origem no data center que a buscou. As requisições seguintes pelo mesmo objeto recebem essa cópia, e a origem não recebe nenhuma requisição por elas. Cada cópia é arquivada sob uma cache key, construída a partir da requisição, e mantida pelo seu tempo de vida (TTL). Quando o TTL termina, a cópia expira, e a próxima requisição por esse objeto consulta a origem.

Em uma Application, Cache armazena essas cópias, e ele está ativo em toda Application que você cria. Um cache setting pertence a uma Application e guarda os TTLs e as entradas que tornam duas requisições diferentes. Um cache setting só age por meio de uma regra da Request Phase, que o aplica com _Set Cache Policy_ às requisições às quais a regra corresponde. _Bypass Cache_ faz o contrário e faz a requisição ignorar o cache.

[Cache settings](/pt-br/documentacao/plataforma/applications/cache/cache-settings/) lista cada campo e o seu padrão, e [Cache keys](/pt-br/documentacao/plataforma/applications/cache/cache-keys/) traz o formato completo da key. Para variar o cache por query string, cookie, device group ou método, você precisa de [Application Accelerator](/pt-br/documentacao/plataforma/applications/application-accelerator/). [Primeiros passos com Cache](/pt-br/documentacao/plataforma/applications/cache/primeiros-passos/) cria um primeiro cache setting e a regra que o aplica.

A [visão geral do Cache](/pt-br/documentacao/plataforma/applications/cache/#caminho-da-requisicao) mostra onde Cache age sobre uma requisição, e [Expiração e atualização](/pt-br/documentacao/plataforma/applications/cache/expiracao-e-atualizacao/) explica quanto tempo uma cópia dura e o que a encerra.

## Application Accelerator

Uma cache key construída só a partir da URL supõe que cada URL tem uma única resposta correta. O conteúdo dinâmico quebra essa suposição: sob uma única URL, um visitante autenticado vê o próprio carrinho, uma listagem se reordena quando um filtro muda e o layout difere em um celular. Com uma key construída só a partir da URL, o cache ou entrega a resposta de um visitante a outro, ou não consegue armazenar o path em cache.

Em uma Application, Application Accelerator remove essa suposição. Ele vem desativado em uma Application nova, e cada Application o ativa separadamente, no seu campo `modules.application_accelerator.enabled` na API. Cada cache setting guarda, então, as suas próprias variações, no seu próprio objeto `modules.application_accelerator`. Se você já escreveu um header `Vary` ou uma regra de cache key, o modelo é o mesmo: você lista as entradas que tornam duas requisições diferentes. [Configurações do Application Accelerator](/pt-br/documentacao/plataforma/applications/application-accelerator/configuracoes/) lista cada campo, o seu tipo e o seu padrão, e [Limites de Applications](/pt-br/documentacao/plataforma/applications/limites/#application-accelerator) traz os limites de TTL. Para ativar Application Accelerator e acrescentar uma primeira variação a um cache setting, consulte [Primeiros passos com Application Accelerator](/pt-br/documentacao/plataforma/applications/application-accelerator/primeiros-passos/).

A [visão geral do Application Accelerator](/pt-br/documentacao/plataforma/applications/application-accelerator/#caminho-da-requisicao) mostra como uma variação muda a cache key, e [Variação de cache](/pt-br/documentacao/plataforma/applications/application-accelerator/variacao-de-cache/) explica o que ativá-lo libera e quanto custa cada variação.

## Image Processor

Uma página costuma precisar da mesma imagem em vários tamanhos, recortes e formatos, um para cada layout e browser. Preparar cada variante com antecedência significa um arquivo armazenado por variante e a reconstrução de todos eles sempre que o original muda. Transformar a imagem no momento da requisição evita as duas coisas: a URL descreve a variante, e a plataforma a constrói a partir de um único original quando uma requisição a pede.

Em uma Application, Image Processor constrói essas variantes. A URL da requisição descreve a variante na sua query string `ims`, e Image Processor aplica essa descrição à imagem original, que fica na origem. O resultado, a imagem derivada, é o que o cliente recebe. Image Processor lê a imagem original sem alterá-la e retorna a imagem derivada sem salvá-la como um ativo da conta. Então, um único arquivo na origem atende a cada tamanho, recorte, qualidade e formato que uma página pede.

Image Processor vem desativado em uma Application nova, e cada Application o ativa separadamente, no seu campo `modules.image_processor.enabled` na API. Mesmo ativo, Image Processor só age sobre as requisições às quais uma regra da Request Phase com _Optimize Images_ corresponde. [Parâmetros de URL do Image Processor](/pt-br/documentacao/plataforma/applications/image-processor/parametros-de-url/) lista as operações que `ims` aceita, e [Configurações do Image Processor](/pt-br/documentacao/plataforma/applications/image-processor/configuracoes/) cobre os headers e os behaviors. Para ativar Image Processor e pedir uma primeira imagem derivada, siga [Primeiros passos com Image Processor](/pt-br/documentacao/plataforma/applications/image-processor/primeiros-passos/).

A [visão geral do Image Processor](/pt-br/documentacao/plataforma/applications/image-processor/#caminho-da-requisicao) mostra onde Image Processor age sobre uma requisição, e [Entrega de imagens](/pt-br/documentacao/plataforma/applications/image-processor/entrega-de-imagens/) explica como o formato entregue é escolhido e onde Image Processor para.
