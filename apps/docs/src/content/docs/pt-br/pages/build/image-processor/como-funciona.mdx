Uma imagem construída sob demanda ainda precisa chegar ao navegador em um formato que ele lê, e ser construída uma vez, e não para cada leitor. Em uma [Application](/pt-br/documentacao/plataforma/applications/), [Image Processor](/pt-br/documentacao/plataforma/applications/image-processor/) é o recurso da plataforma que constrói essa imagem, a imagem derivada, a partir da imagem de origem que está no servidor de origem. Como uma requisição se torna uma imagem derivada, com o diagrama dessa cadeia, está na [visão geral do Image Processor](/pt-br/documentacao/plataforma/applications/image-processor/#caminho-da-requisicao).

As seções cobrem como o formato entregue é escolhido, como o cache diferencia uma imagem derivada de outra e onde Image Processor para.

---

## Negociação de formato

O formato entregue pode ser diferente do formato da imagem de origem. Dois mecanismos o alteram, e eles se comportam de forma diferente.

O primeiro é explícito. Um filtro `filters:format()` na string `ims` pede um formato de saída nomeado. Converter para WEBP também exige que a requisição carregue `Accept: image/webp`, e o behavior [Add Request Header](/pt-br/documentacao/plataforma/applications/rules-engine/#add-request-header) adiciona esse header a toda requisição à qual a regra dele corresponde.

O segundo é automático e não precisa de nenhum parâmetro `ims`. Image Processor detecta quais formatos o navegador aceita e, quando possível, converte a imagem para um deles, como WEBP ou AVIF. Uma imagem BMP é convertida para JPEG ou WEBP dependendo do mesmo suporte. Por exemplo, uma requisição cujo header `Accept` lista `image/webp`, sem query string, pode receber `image/webp` para uma imagem de origem armazenada como PNG. Uma resposta pode carregar um formato diferente do que está na origem mesmo quando a URL não tem filtro.

Então, os bytes na origem e os bytes transmitidos são duas medidas diferentes, e a resposta informa isso. Uma resposta processada carrega `x-ims: Enabled`, e `x-original-image-size` carrega o tamanho da imagem de origem antes da transformação. Leia esses headers antes de comparar uma resposta com o arquivo na origem. Para os headers, consulte [Configurações do Image Processor](/pt-br/documentacao/plataforma/applications/image-processor/configuracoes/#headers-de-resposta).

## Uma entrada de cache por transformação

Uma imagem derivada só vale a pena ser construída uma vez. A prática para o cache setting que serve imagens é variar o cache por `ims`: o seu campo `cache_vary_by_querystring` recebe o behavior `allowlist`, com `ims` em `fields`. Cada string `ims` distinta tem então uma cache key própria. Esse campo fica em `modules.application_accelerator` no cache setting, então variar o cache por `ims` exige Application Accelerator, enquanto processar uma imagem não exige. [Configurações do Image Processor](/pt-br/documentacao/plataforma/applications/image-processor/configuracoes/#variacao-de-cache) relaciona cada um desses campos ao seu controle no Azion Console.

Um cache setting criado com essa allowlist é lido de volta com este objeto `modules`:

```json
{
  "modules": {
    "application_accelerator": {
      "cache_vary_by_querystring": {
        "behavior": "allowlist",
        "fields": ["ims"],
        "sort_enabled": false
      },
      "cache_vary_by_cookies": { "behavior": "ignore", "cookie_names": [] },
      "cache_vary_by_devices": { "behavior": "ignore", "device_group": [] },
      "cache_vary_by_method": []
    },
    "cache": {
      "behavior": "honor",
      "max_age": 60,
      "stale_cache": { "enabled": false },
      "large_file_cache": { "enabled": false, "offset": 1024 },
      "tiered_cache": { "enabled": false }
    }
  }
}
```

A cache key de uma imagem derivada convertida para outro formato também carrega o formato depois do separador `@@`, como em `httpsstatic.example.com/static/images/image_1.jpg?ims=880x@@webp`.

Essa key tem um custo, e o custo é a cardinalidade. Cada string `ims` distinta, em cada formato entregue, é um objeto armazenado distinto. Uma página que pede larguras arbitrárias armazena um objeto por largura e formato, enquanto uma página que pede quatro larguras fixas armazena quatro por formato. Então, escolher um conjunto pequeno de tamanhos é tanto uma decisão de cache quanto uma decisão de layout.

Também é uma decisão de cobrança, porque o medidor mensal de Images conta as imagens que Image Processor processa, e não as imagens que o cache serve. Então, uma imagem derivada que permanece em cache é contada quando Image Processor a constrói, e não cada vez que um leitor a recebe. O cache pode remover um objeto pouco acessado antes do fim da idade máxima dele, e a próxima requisição por essa imagem é processada e contada de novo. Para a tarifa, consulte [Preços](/pt-br/documentacao/fundamentos/precos/#image-processor).

## Onde Image Processor para

Image Processor lê uma imagem de origem a partir da origem e retorna uma derivada sem salvá-la como um ativo da conta. Não é possível fazer upload de imagens para Image Processor: a imagem de origem permanece onde já está, e o cache guarda as imagens derivadas. Um workflow que precisa manter um arquivo transformado precisa salvar a resposta por conta própria.

O que a string `ims` pode expressar e o tamanho da imagem limitam a transformação. As operações que a string aceita estão em [Parâmetros de URL do Image Processor](/pt-br/documentacao/plataforma/applications/image-processor/parametros-de-url/), e o tamanho e as dimensões máximas estão em [Limites de Applications](/pt-br/documentacao/plataforma/applications/limites/#image-processor).

Vale nomear uma distinção, porque duas superfícies compartilham um nome. [WASM Image Processor](/pt-br/documentacao/devtools/azion-lib/wasm-image-processor/) é uma biblioteca WebAssembly que processa imagens dentro de uma [Function](/pt-br/documentacao/plataforma/functions/). Ela é executada no código dessa Function, separada do recurso da plataforma Image Processor e de tudo o que esta página descreve.
