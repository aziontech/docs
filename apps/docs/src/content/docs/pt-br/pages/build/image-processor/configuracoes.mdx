[Image Processor](/pt-br/documentacao/plataforma/applications/image-processor/) é um recurso da plataforma que constrói uma imagem derivada a partir da imagem de origem no servidor de origem de uma [Application](/pt-br/documentacao/plataforma/applications/). Ele vem desativado em uma Application nova, e cada Application o ativa separadamente. Com Image Processor ativado, uma requisição de imagem pode carregar um parâmetro de query string `ims` que descreve uma transformação.

---

## Ativação

Cinco interfaces definem o mesmo switch, e o switch pertence à Application: uma Application pode ter Image Processor ativado enquanto outra não.

| Interface | Onde você define | Campo ou flag |
| --- | --- | --- |
| Azion Console | Aba **Main Settings** › **Modules** › **Default Modules** de uma Application | O switch **Image Processor** |
| Azion API v4 | `PATCH /v4/workspace/applications/<id>` | `modules.image_processor.enabled` |
| Azion API v3 | `PATCH https://api.azionapi.net/edge_applications/<id>` | `image_optimization` |
| [Azion CLI](/pt-br/documentacao/devtools/cli/) | `azion create application` e `azion update application` | `--image-processor` |
| [`azion.config.js`](/pt-br/documentacao/devtools/cli/azion-config-js/) e [Azion Lib](/pt-br/documentacao/devtools/azion-lib/) | Uma entrada de `applications`, uma por Application | `imageProcessorEnabled` |

`modules.image_processor.enabled` e `imageProcessorEnabled` são booleanos, e os dois assumem `false` por padrão. A flag da Azion CLI recebe uma string: `--image-processor true`. Em Azion Console, o switch carrega o texto de ajuda "Enable dynamic image editing options." e é salvo com **Save**.

API v4 carrega o switch no objeto `modules` da Application:

```json
{
  "modules": {
    "image_processor": {
      "enabled": true
    }
  }
}
```

O mesmo objeto `modules` carrega `application_accelerator`, `cache` e `functions`, cada um com seu próprio booleano `enabled`. API v3 nomeia o switch `image_optimization` e o recebe no nível superior do corpo. Em uma Application criada pela API v4, API v3 lê `websocket` como `true`, e o `PATCH` retorna `400` até o corpo também carregar `"websocket": false`.

## Behaviors do Rules Engine

Uma regra para imagens pode carregar três behaviors do [Rules Engine](/pt-br/documentacao/plataforma/applications/rules-engine/). Só _Optimize Images_ é necessário para processar uma imagem, e ele exige Image Processor ativado na Application que executa a regra.

| Behavior | Fase | Tipo na API | O que faz |
| --- | --- | --- | --- |
| _Optimize Images_ | **Request Phase** | `optimize_images` | Aplica Image Processor à requisição correspondente. Não recebe atributos. |
| _Set Cache Policy_ | **Request Phase** | `set_cache_policy` | Aplica um cache setting à requisição correspondente. |
| _Add Request Header_ | **Request Phase** | `add_request_header` | Adiciona um header à requisição. |

Em _Set Cache Policy_, `attributes.value` carrega o id do cache setting, e no Azion Console você o seleciona em um segundo dropdown. Em _Add Request Header_, `attributes.value` assume o formato `Field: value`, como `Accept: image/webp` ou `Accept: image/avif`.

Um critério da mesma regra carrega `variable`, `operator`, `conditional` e `argument`. Uma regra que corresponde a requisições de imagem lê `${request_uri}` ou `${uri}` com o operador `matches`, usando um argumento como `\.(jpg|jpeg|gif|bmp|png|ico|webp|avif)`. `${request_uri}` exige Application Accelerator na Application: enquanto Application Accelerator está desativado, a API recusa uma regra que o lê e retorna o erro `25047`. `${uri}` não depende de nenhum recurso da plataforma.

Para processar cada requisição por um path de imagem e armazenar em cache cada imagem derivada, envie esta regra como corpo de `POST /v4/workspace/applications/{application_id}/request_rules`:

```json
{
  "name": "Optimize images",
  "description": "Apply the cache setting and optimize images",
  "active": true,
  "criteria": [
    [
      {
        "conditional": "if",
        "variable": "${request_uri}",
        "operator": "matches",
        "argument": "\\.(jpg|jpeg|gif|bmp|png|ico|webp|avif)"
      }
    ]
  ],
  "behaviors": [
    { "type": "set_cache_policy", "attributes": { "value": <cache-setting-id> } },
    { "type": "optimize_images" }
  ]
}
```

Substitua `<cache-setting-id>` pelo id do cache setting que guarda as imagens derivadas.

## Variação de cache

Uma imagem derivada recebe uma cache key própria quando o cache setting dela varia o cache por `ims`. A key passa a carregar o valor de `ims` depois de `@@`, e uma cópia com um formato convertido também carrega o formato do arquivo no fim da key, sem separador, como em `httpsstatic.example.com/static/images/image_1.jpg@@?ims=880xwebp`.

Variar o cache por query string usa um campo do [Application Accelerator](/pt-br/documentacao/plataforma/applications/application-accelerator/): `cache_vary_by_querystring`, sob `modules.application_accelerator` em um cache setting. Então, variar o cache por `ims` exige Application Accelerator, enquanto processar uma imagem não o exige.

No Azion Console, cada campo corresponde a um controle do painel **Cache vary by Query String**, na seção **Application Accelerator** de um cache setting:

| Campo | Controle no Console | O que define |
| --- | --- | --- |
| `cache_vary_by_querystring.behavior` | **Behavior** | O modo que decide como a query string varia a key: _Allowlist_, _Denylist_, _Ignore_ ou _All_. |
| `cache_vary_by_querystring.fields` | **Fields** | Os argumentos de query string aos quais o modo se aplica, um por linha. |
| `cache_vary_by_querystring.sort_enabled` | **Sort** | Se toda ordem dos argumentos se agrupa sob uma única key, em ordem alfabética. |

Um cache setting para imagens carrega `ims` em `fields`. Para o restante dos campos que um cache setting carrega, incluindo a idade máxima do objeto em cache, consulte [Cache settings](/pt-br/documentacao/plataforma/applications/cache/cache-settings/). Para os demais campos que Application Accelerator libera, consulte [Configurações do Application Accelerator](/pt-br/documentacao/plataforma/applications/application-accelerator/configuracoes/).

## Headers de resposta

Dois headers de resposta descrevem a imagem que Image Processor entrega.

| Header | O que carrega |
| --- | --- |
| `x-ims` | A marca de uma resposta em que Image Processor entrega uma imagem. O valor é `Enabled`. |
| `x-original-image-size` | O tamanho em bytes da imagem de origem, antes da transformação. |

Uma resposta carrega `x-ims: Enabled` ou não tem o header `x-ims`. O header está presente sempre que Image Processor entrega uma imagem, em cada um destes casos:

- A imagem é transformada.
- A requisição não carrega o parâmetro `ims`.
- A requisição carrega um valor de `ims` que Image Processor não interpreta.
- A requisição usa o método `HEAD`.
- A resposta é um `304`.

O header está ausente quando nenhuma regra com _Optimize Images_ corresponde à requisição. Ele também está ausente quando Image Processor responde com um status de erro, como `400`, `404`, `500` ou `504`. Essa resposta de erro carrega `server: Azion IMS`. Para um arquivo que não é imagem e para um erro da origem, consulte [Solucione problemas de Applications](/pt-br/documentacao/plataforma/applications/solucao-de-problemas/#image-processor).

## Dados de uso e eventos

Azion reporta a atividade de Image Processor em seis superfícies: duas em Real-Time Metrics e duas em Real-Time Events, no Console, e duas em GraphQL.

| Superfície | O que carrega |
| --- | --- |
| A aba **Image Processor** de [Real-Time Metrics](/pt-br/documentacao/plataforma/real-time-metrics/) | Os gráficos Total Requests e Total Requests per Second das imagens que Image Processor processou na sua conta. |
| O dashboard **Bandwidth Saving** na aba **Applications** de Real-Time Metrics | Os bytes que Image Processor economizou nas imagens que processou e entregou. |
| O dataset **Image Processor** de [Real-Time Events](/pt-br/documentacao/plataforma/real-time-events/) | Os registros de eventos das requisições feitas a Applications que usam Image Processor. |
| O campo **Proxy Upstream** da fonte de dados Tiered Cache de Real-Time Events | `ims_http`, o valor que o campo assume quando Image Processor é o upstream da camada de Tiered Cache. |
| O dataset de consumo de [GraphQL](/pt-br/documentacao/devtools/graphql/campos-gql-consumption/) | `productId` `1441110021` e a métrica `images_processed`, o número total de imagens processadas por Image Processor. |
| Os [datasets de métricas](/pt-br/documentacao/devtools/graphql/campos-gql-real-time-metrics/) de GraphQL | O dataset `imagesProcessedMetrics` e seus campos. |

No Azion Console, o dataset **Image Processor** de Real-Time Events exige Image Processor ativado, e em GraphQL ele é o dataset `imagesProcessedEvents`. Os dados de consumo ficam disponíveis por até 24 meses, e um registro de Real-Time Events é mantido por 7 dias. Para criar a consulta de consumo e ler sua resposta, consulte [Consultar dados de uso do Image Processor](/pt-br/documentacao/guias/plataforma/observabilidade/consultar-dados-de-uso-image-processor-com-graphql/).

## Biblioteca WASM Image Processor

WASM Image Processor é uma biblioteca WebAssembly que processa imagens dentro de uma [Function](/pt-br/documentacao/plataforma/functions/). Ela fornece `loadImage`, `resize`, `getImageResponse` e `clean`, e grava `webp`, `jpeg` e `png`. Ela é executada no código dessa Function, separada do recurso da plataforma Image Processor e dos campos desta página. Para mais informações, consulte [WASM Image Processor](/pt-br/documentacao/devtools/azion-lib/wasm-image-processor/).
