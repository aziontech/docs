Quando a resposta de uma URL depende de um cookie, de um dispositivo ou do corpo de uma requisição, o cache precisa distinguir essas requisições. Em uma [Application](/pt-br/documentacao/plataforma/applications/), [Application Accelerator](/pt-br/documentacao/plataforma/applications/application-accelerator/) é um recurso da plataforma que acrescenta essas entradas à cache key. Ele vem desativado em uma Application nova, e cada Application o ativa separadamente, no campo `modules.application_accelerator.enabled` da Application na API. Cada [cache setting](/pt-br/documentacao/plataforma/applications/cache/cache-settings/) da Application guarda por quanto tempo uma resposta fica em cache. Ele define então as entradas que tornam duas requisições diferentes, no seu próprio objeto `modules.application_accelerator`. Como uma variação altera a cache key, com o diagrama correspondente, está na [visão geral do Application Accelerator](/pt-br/documentacao/plataforma/applications/application-accelerator/#caminho-da-requisicao).

As seções cobrem o que ativar Application Accelerator libera, o que uma variação custa e como os purges alcançam as variações. A última seção compara _Bypass Cache_ com um tempo de vida (TTL) de 0.

---

## O que Application Accelerator libera

Ativar Application Accelerator libera quatro capacidades que parecem não ter relação entre si até você ver o que elas têm em comum:

- Variação de cache além da URL, por query string, por cookie, por device group e por método de requisição. A funcionalidade se chama [Advanced Cache Key](/pt-br/documentacao/plataforma/applications/cache/cache-settings/#application-accelerator).
- Cache de respostas `POST` e `OPTIONS`, além das respostas `GET` e `HEAD` que uma Application armazena em cache sem ele.
- Um Max Age que pode chegar a 0 segundos, no campo `modules.cache.max_age` de um cache setting, menor que o piso de 60 segundos que vale sem ele.
- Mais behaviors do [Rules Engine](/pt-br/documentacao/plataforma/applications/rules-engine/) e as variáveis `${request_uri}` e `${device_group}` nos critérios das regras. Os behaviors são _Add Request Cookie_ e _Add Response Cookie_, _Bypass Cache_, _Capture Match Groups_, _Filter Request Cookie_ e _Filter Response Cookie_, _Forward Cookies_ e _Rewrite Request_.

O que as quatro têm em comum é o conteúdo dinâmico. A variação de cache dá à cache key a entrada extra de que ela precisa para distinguir duas respostas corretas. O cache de `POST` e `OPTIONS` traz os métodos que carregam essa entrada no corpo da requisição. Um TTL menor que um minuto serve ao conteúdo que deixa de ser correto antes de um minuto passar. Vários dos behaviors liberados agem justamente sobre os cookies e os paths que carregam a diferença.

Application Accelerator entrega as quatro capacidades ou nenhuma. Uma Application recebe a variação de cache só junto com os métodos e os behaviors extras. A API recusa um cache setting que define uma variação em uma Application com Application Accelerator desativado. Para o erro que a API retorna, consulte [Cache settings](/pt-br/documentacao/plataforma/applications/cache/cache-settings/#erros).

Ativar Application Accelerator mantém o tráfego como estava: os controles de query string, de cookie e de dispositivo de um cache setting começam em `ignore`, e a lista de métodos começa vazia. Um cache setting só alcança uma requisição quando um behavior [Set Cache Policy](/pt-br/documentacao/plataforma/applications/rules-engine/#set-cache-policy) o aplica.

Ativar Application Accelerator pode gerar custos relacionados ao uso. Para mais informações, consulte [Preços](/pt-br/documentacao/fundamentos/precos/#application-accelerator).

## O custo de uma variação

A variação de cache custa primeiro em armazenamento. O custo decorre de como a key é montada: cada valor distinto de um atributo que varia produz um objeto em cache separado. Isso torna a escolha do atributo pelo qual variar mais consequente do que a decisão de variar. Um cookie cujo valor é único para cada visitante dá a cada visitante uma cópia do objeto. O cache ainda funciona, mas cada resposta armazenada passa a servir um único visitante. O número de objetos cresce com a audiência, e não com o conteúdo.

Uma allowlist é o controle desse custo. O behavior `allowlist` nomeia os argumentos de query string ou os cookies que alteram a resposta, então só um atributo que ele nomeia pode criar outro objeto. O behavior `all` varia por todo argumento de query string ou cookie que a requisição carrega. Por exemplo, um link que chega com um argumento de campanha ganha o próprio objeto em cache sob `all`. Sob uma allowlist que não nomeia esse argumento, o mesmo link aponta para o objeto compartilhado.

A ordenação aplica a mesma economia à ordem dos argumentos. Os argumentos escolhidos entram na key na ordem em que a requisição os enviou, então `?a=1&b=2` e `?b=2&a=1` são dois objetos que guardam uma única resposta. Com `sort_enabled` ativo, essas variações se agrupam sob uma única key, em ordem alfabética. Por exemplo, uma listagem de produtos que muda com os argumentos `category` e `page` nomeia os dois em uma allowlist. Com `sort_enabled` ativo, toda ordem dos dois argumentos chega a um único objeto. O custo da ordenação é que a key passa a diferir da URL como o cliente a escreveu, o que importa na hora do purge. Para os passos no Console que definem esses controles, consulte [Configure a Advanced Cache Key para uma aplicação](/pt-br/documentacao/guias/performance-e-confiabilidade/cache-e-purge/advanced-cache-key/).

## Variação de cache e purges

Um purge é uma requisição que remove um objeto do cache e encontra esse objeto pela sua cache key. Um purge por URL converte a URL que recebe em uma cache key sem considerar a variação de conteúdo. Então toda variação que a URL não carrega sobrevive a ele, como uma variação por cookie ou por device group, e as cópias dela permanecem no cache.

Dois tipos de purge alcançam essas cópias. Um purge por cache key nomeia cada variação, e um purge por wildcard termina a key com `@@*`. As variações por query string são a exceção, porque a query string faz parte da URL. Um purge por URL alcança essas variações quando os argumentos são enviados na ordem em que foram apresentados, ou em ordem alfabética quando `sort_enabled` está ativo.

As variações que você configura são também os objetos que um purge precisa alcançar. Então uma variação com muitos valores distintos custa tanto na hora do purge quanto em armazenamento. Para os tipos de purge e os passos para executar cada um, consulte [Real-Time Purge](/pt-br/documentacao/plataforma/applications/cache/real-time-purge/#purgue-conteudo-que-varia).

## Bypass Cache e um TTL de 0

Sem Application Accelerator, o Max Age mais curto que um cache setting aceita, no seu campo `modules.cache.max_age`, é de 60 segundos, e a API recusa um valor menor. Para o erro, consulte [Cache settings](/pt-br/documentacao/plataforma/applications/cache/cache-settings/#erros). Application Accelerator remove esse piso e permite 0 segundos, ou 3 segundos quando o cache setting também tem [Tiered Cache](/pt-br/documentacao/plataforma/applications/cache/tiered-cache/) ativo. Um TTL de 0 difere de não armazenar em cache, e essa diferença é a razão de ambos existirem. Os dois precisam de Application Accelerator, porque _Bypass Cache_ é um dos behaviors que ele libera.

O behavior [Bypass Cache](/pt-br/documentacao/plataforma/applications/rules-engine/#bypass-cache) envia à origem cada requisição HTTP e HTTPS que corresponde à sua regra, e a resposta contorna o próprio cache da Azion. Ele mantém as otimizações de protocolo e, quando possível, uma conexão keep-alive com a origem. Ele deixa o browser cache como um behavior _Set Cache Policy_ o define. O efeito dele também para no próprio cache da Azion: uma Application com cache settings de Tiered Cache ativos continua a armazenar objetos em cache na camada do Tiered Cache pelo TTL mínimo. Use-o quando cada requisição precisa receber conteúdo diferente.

Um Max Age de 0 segundos mantém a requisição no caminho do cache. Requisições paralelas pelo mesmo objeto chegam à origem como uma única requisição, e a Azion valida o objeto com uma requisição `If-Modified-Since`. Um objeto que não mudou não é transferido de novo, e a resposta pode ser um `304 Not Modified`. Um Max Age de 0 ainda cria um objeto em cache, que vive por 999 milissegundos. Use-o quando o conteúdo dinâmico pode ser entregue de forma idêntica a todos que o requisitam no mesmo momento.

A troca é entre a atualidade de cada requisição e a carga na origem. _Bypass Cache_ dá a cada requisição a sua própria resposta. Em troca, abre mão da requisição única à origem para requisições paralelas e da revalidação que evita a transferência de um objeto inalterado. Um TTL de 0 mantém as duas coisas, e abre mão da capacidade de responder de forma diferente a duas requisições simultâneas.
