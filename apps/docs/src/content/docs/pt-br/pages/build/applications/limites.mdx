Uma [Application](/pt-br/documentacao/plataforma/applications/) processa as requisições recebidas pelos seus [Workloads](/pt-br/documentacao/plataforma/workloads/): ela executa as suas [regras](/pt-br/documentacao/plataforma/applications/rules-engine/) de requisição e de resposta em cada requisição.

Cada recurso da plataforma ativado na Application acrescenta limites próprios. [Cache](/pt-br/documentacao/plataforma/applications/cache/) limita os [cache settings](/pt-br/documentacao/plataforma/applications/cache/cache-settings/) e os objetos que armazena, e [Real-Time Purge](/pt-br/documentacao/plataforma/applications/cache/real-time-purge/) limita as requisições de purge. [Application Accelerator](/pt-br/documentacao/plataforma/applications/application-accelerator/) move o piso do time to live (TTL) de cache, e [Image Processor](/pt-br/documentacao/plataforma/applications/image-processor/) limita o tamanho, a largura e a altura de uma imagem. Esta página informa cada limite e a resposta que uma chamada recebe quando a API o recusa.

Um recurso da plataforma que você ativa pode gerar custos que dependem do uso, e um plano de serviço inclui uma quantidade de uso antes que uma tarifa se aplique. Essa quantidade é um valor de cobrança: ultrapassá-la muda o valor cobrado da conta, e não o que a chamada retorna. A página [Preços da Azion](https://www.azion.com/pt-br/precos/) lista os planos e o uso que cada um inclui. Para as tarifas, consulte [Preços](/pt-br/documentacao/fundamentos/precos/#applications).

## Escopo

Estas restrições valem para toda Application, quaisquer que sejam os recursos da plataforma ativados nela. As restrições de cada recurso da plataforma aninhado abrem a seção desse recurso nesta página.

- **Fases**: toda regra pertence a uma de duas fases, que você escolhe quando cria a regra e não pode mudar depois. A Request Phase age sobre a requisição antes que exista uma resposta, e a Response Phase age sobre a resposta que o usuário recebe. Somente as regras da Request Phase podem escolher a origem e o cache setting. [Rules Engine para Applications](/pt-br/documentacao/plataforma/applications/rules-engine/#fases) lista as variáveis e os behaviors de cada fase e o recurso da plataforma de que cada um precisa.
- **Origens**: uma Application chega a cada origem por meio de um [Connector](/pt-br/documentacao/plataforma/connectors/) que uma regra define, então duas regras com dois Connectors podem encaminhar `/api/` para um servidor e todos os outros paths para outro. A origem por trás de um Connector pode ser um servidor web na sua infraestrutura, um serviço em cloud ou um bucket do [Object Storage](/pt-br/documentacao/plataforma/object-storage/), como mostra [Use um bucket como origem de uma aplicação](/pt-br/documentacao/guias/desenvolvimento-de-aplicacoes/dados/bucket-como-connector/). Com [Load Balancer](/pt-br/documentacao/plataforma/connectors/load-balancer/) ativado, um Connector do tipo `http` pode distribuir o tráfego entre várias origens. Os Connectors substituem as origens que as versões anteriores de Applications configuravam na Application.
- **Functions**: uma [Function Instance](/pt-br/documentacao/plataforma/applications/functions-instances/) pertence a uma Application, e ela só é executada quando uma regra com _Run Function_ a invoca. Functions começa ativo em uma Application nova, no campo `modules.functions.enabled` dela na API. Somente Functions escritas em Lua são executadas na Response Phase, como informa o formulário da Function Instance no Azion Console: `Only Lua functions can be used in the Response phase.` Para os passos de adicionar a sua primeira Function, consulte [Instancie uma função em uma aplicação](/pt-br/documentacao/guias/desenvolvimento-de-aplicacoes/primeiros-passos/instanciar-functions/).
- **Dispositivos**: um [device group](/pt-br/documentacao/plataforma/applications/device-groups/) é um nome e uma expressão regular que a Application compara com o header `User-Agent` de cada requisição. Os dois usos de um grupo precisam de Application Accelerator ativo: uma regra testa o grupo por meio de `${device_group}`, e um cache setting pode manter uma cópia por grupo. [Boas práticas de Applications](/pt-br/documentacao/plataforma/applications/boas-praticas/#defina-um-device-group-pelas-palavras-que-so-esse-dispositivo-envia) mostra como escrever uma expressão que corresponda somente aos dispositivos que você pretende alcançar.
- **WebSocket**: a Azion ativa [WebSocket Proxy](/pt-br/documentacao/plataforma/applications/websocket/) em uma conta somente mediante solicitação, e [Diretrizes de suporte](/pt-br/documentacao/suporte/) explica como pedir. Uma conexão WebSocket abre com os headers `Upgrade: websocket` e `Connection: upgrade`. A Azion recicla as conexões keepalive dos seus servidores aproximadamente a cada 15 minutos, então uma conexão ativa que precisa de mais tempo pode ser encerrada. Quando uma conexão WebSocket se fecha dessa forma, o código do seu cliente precisa detectar a conexão fechada e abri-la de novo.
- **Arquivos grandes**: o mesmo ciclo de keepalive pode encerrar uma transferência longa, e qualquer uma de duas opções permite que cada transferência termine antes que a conexão seja reciclada. Com `modules.cache.large_file_cache.enabled` definido como `true` em um cache setting, Cache armazena o arquivo em fragmentos, como mostra [Cache settings](/pt-br/documentacao/plataforma/applications/cache/cache-settings/#cache). A outra opção, a compressão, reduz o arquivo, como mostra [Comprima as respostas de uma aplicação com gzip](/pt-br/documentacao/guias/performance-e-confiabilidade/otimizacao-de-entrega/gzip-compression/).
- **Workloads**: um Workload guarda os domínios, os protocolos e os certificados que servem a Application, então você configura a entrega no Workload, não na Application. _Redirect HTTP to HTTPS_ só funciona quando o Workload tem HTTPS. Quando o Connector recebe uma resposta 4xx ou 5xx da sua origem, o cliente vê a página de erro do conjunto de custom pages que o deployment do Workload define, em [Custom Pages](/pt-br/documentacao/plataforma/custom-pages/). Para requisitar uma Application no seu próprio domínio a partir de um dispositivo antes de alterar os registros DNS dele, consulte [Teste uma aplicação pelo arquivo hosts](/pt-br/documentacao/guias/desenvolvimento-de-aplicacoes/primeiros-passos/testar-edge-application-atraves-do-arquivo-hosts/).

## Applications, regras e conexões

Estes limites se aplicam a toda Application, quaisquer que sejam os recursos da plataforma ativados nela. Eles cobrem as regras do seu Rules Engine, o log de [Debug Rules](/pt-br/documentacao/plataforma/applications/main-settings/#debug-rules) e as conexões que ela mantém abertas.

### Limites padrão

Sete limites se aplicam a toda Application.

| Escopo | Limite |
| --- | --- |
| Regras em uma Application, fases de requisição e de resposta somadas | 200 regras |
| Grupos de critérios por regra | 1 a 5 grupos |
| Critérios por grupo | 1 a 10 critérios |
| Behaviors por regra | 1 a 10 behaviors |
| Argumento de behavior | 1.600 caracteres |
| Tamanho do log de Debug Rules | 1,5 kB |
| Tempo de conexão WebSocket | 15 minutos |

Outros três limites se aplicam a nomes: o nome de uma Application aceita de 1 a 100 caracteres, o nome de um device group aceita de 1 a 250 e a expressão `user_agent` de um device group aceita de 1 a 512.

As 200 regras são um único total que a fase de requisição e a fase de resposta compartilham. Por exemplo, uma Application pode ter 150 regras de requisição e 50 regras de resposta, mas não 200 de cada.

## Cache

Cache limita um cache setting e um objeto que ele armazena, e Real-Time Purge limita uma requisição de purge. A API valida os limites de TTL em todo cache setting e, quando um valor ultrapassa um limite que ela verifica, a chamada retorna HTTP `400` com um código de erro e um título. [Tiered Cache](/pt-br/documentacao/plataforma/applications/cache/tiered-cache/) altera dois limites de um cache setting: o menor TTL que ele aceita e o comportamento de cache que ele permite.

Para as tarifas de Cache, consulte [Preços](/pt-br/documentacao/fundamentos/precos/#cache). Para obter os dados que Tiered Cache transferiu, use o guia [Consulte dados de uso do Tiered Cache](/pt-br/documentacao/guias/plataforma/observabilidade/consultar-dados-de-uso-tiered-cache-com-graphql/).

### Escopo

Estas restrições valem para Cache em toda Application, a partir de qualquer interface.

- **Sempre ativo**: Cache fica ativo em toda Application, e a API recusa `false` no campo `modules.cache.enabled` dela com o erro `31001`. No Azion Console, o switch **Cache** de **Main Settings** fica travado como ativo, com a nota `Automatically enabled in all accounts.` Uma Application nova não tem cache settings nem regras, então Cache só armazena cópias quando uma regra com _Set Cache Policy_ aplica um cache setting.
- **Cópias expiradas**: com o stale cache ativado em `modules.cache.stale_cache.enabled` de um cache setting, a Azion pode servir uma cópia expirada quando não consegue confirmar a cópia com a origem, e a resposta então informa `STALE`. Um setting criado pela Azion API ou pela Azion CLI vem com o stale cache desativado, enquanto Azion Console o ativa em um setting novo, como mostra [Cache settings](/pt-br/documentacao/plataforma/applications/cache/cache-settings/#cache). Para saber quando uma página antiga é melhor que um erro, consulte [Boas práticas de Applications](/pt-br/documentacao/plataforma/applications/boas-praticas/#cache).
- **Arquivos grandes**: a Large File Optimization vem desativada em um cache setting novo, e um cache setting a ativa em `modules.cache.large_file_cache.enabled`. Cada fragmento de um arquivo grande é buscado quando um usuário chega a ele e armazenado sob uma key própria, então um purge do arquivo precisa nomear cada fragmento ou usar um wildcard.
- **Tiered Cache**: [Tiered Cache](/pt-br/documentacao/plataforma/applications/cache/tiered-cache/) adiciona uma segunda camada de cache entre o data center que responde a uma requisição e a origem, e exige o behavior `override` e um TTL mínimo. Cada cache setting ativa o Tiered Cache no seu campo `modules.cache.tiered_cache.enabled`, e todos os planos o incluem. Uma regra com _Bypass Cache_ age apenas sobre o cache da Azion, então a camada do Tiered Cache continua a armazenar objetos pelo Max Age do cache setting.
- **Cache keys e variação**: a Azion monta a [cache key](/pt-br/documentacao/plataforma/applications/cache/cache-keys/) padrão a partir do esquema, do host e do path, então um path é um objeto armazenado, e a query string fica fora da key. [Application Accelerator](/pt-br/documentacao/plataforma/applications/application-accelerator/) permite que um cache setting mantenha uma cópia separada para cada valor de um argumento de query string, de um cookie, do device group ou do método. [Image Processor](/pt-br/documentacao/plataforma/applications/image-processor/) acrescenta à key o formato de uma imagem convertida.
- **Purge**: [Real-Time Purge](/pt-br/documentacao/plataforma/applications/cache/real-time-purge/) coloca um purge em fila depois que você o confirma, porque o resultado leva tempo para se propagar, e o purge aparece no histórico de purges quando termina. Uma cópia que varia por cookie, device group ou formato de imagem sobrevive a um purge por URL, e um purge por cache key ou por wildcard a alcança.
- **Código**: Cache não pode executar código, então o código que lê e grava entradas em cache é executado em uma [Function](/pt-br/documentacao/plataforma/functions/) e chama [Cache API](/pt-br/documentacao/devtools/runtime/api-reference/cache/).

### Cache settings

Cada limite desta tabela se aplica a um cache setting, qualquer que seja a interface que o escreve. A coluna Escopo nomeia o campo da API e, quando existe, o rótulo do Console. A coluna Além do limite traz o código e o título da resposta `400`. Os títulos dos erros mantêm nomes antigos: `Edge Cache` corresponde a Cache, e `Module` corresponde a um recurso da plataforma ativado na Application.

| Escopo | Limite | Além do limite |
| --- | --- | --- |
| TTL mínimo de cache, **Max Age** (`modules.cache.max_age`) | 60 segundos; 0 segundos com Application Accelerator ativo na Application | Erro `21021`, `Edge Cache Max Age Lower Than The Minimum Allowed By Application's Application Accelerator Module`, com `meta.min_value` definido como `60`. |
| TTL mínimo de cache com Tiered Cache ativo | 3 segundos, com Application Accelerator ativo; sem ele, o mínimo de 60 segundos continua valendo | Erro `21020`, `Edge Cache Max Age Lower Than The Minimum Allowed By The Tiered Cache Module`, com `meta.min_value` definido como `3`. |
| TTL máximo de cache | 31.536.000 segundos, um ano | Erro `10068`, `Max Value`, com o detalhe `Ensure this value is less than or equal to 31536000.` |
| Comportamento de cache com Tiered Cache ativo (`modules.cache.behavior`) | Apenas `override` | Erro `21001`, `It's Not Possible To Use This Edge Cache Behavior.` |
| TTL do cache do navegador (`browser_cache.max_age`) | 0 a 31.536.000 segundos | Erro `10068`, `Max Value`. |
| Nome do cache setting, **Name** (`name`) | 250 caracteres | Erro `10046`, `Max Length`, com o detalhe `Ensure this field has no more than 250 characters.` |

Outro limite se aplica a um cache setting: o seu array `cache_vary_by_method` aceita no máximo 2 valores, `post` e `options`.

Com `modules.cache.stale_cache.enabled` definido como `true` em um cache setting, Cache pode servir uma cópia expirada de um objeto durante uma janela limitada. Sob o comportamento `honor`, a janela é o valor da diretiva `stale-while-revalidate=<ttl>` da origem. Sob `override`, ou quando a origem omite a diretiva, a janela é de 300 segundos.

### Objetos em cache

Dois limites se aplicam a um objeto em cache: o seu tamanho e o tamanho de cada fragmento de um arquivo grande. A API verifica o tamanho do fragmento em todo cache setting.

| Escopo | Limite | Além do limite |
| --- | --- | --- |
| Tamanho do fragmento de um arquivo grande (`modules.cache.large_file_cache.offset`) | 1.024 kB por fragmento, fixo | Erro `10068`, `Max Value`, com o detalhe `Ensure this value is less than or equal to 1024.` |

Um objeto único em cache aceita até 10 GB.

### Real-Time Purge

Cada limite desta tabela se aplica a uma requisição de purge, qualquer que seja a interface que a envia. A coluna Além do limite traz o que a API retorna além do limite.

| Escopo | Limite | Além do limite |
| --- | --- | --- |
| Objetos em uma requisição de purge por URL ou por cache key | 50 objetos | Erro `10065`, `List Field Max Length`, com o detalhe `Ensure this field has no more than 50 elements.` |
| Wildcards em uma requisição de purge | 1 wildcard | Erro `10065`, `List Field Max Length`, com o detalhe `Ensure this field has no more than 1 elements.` |

Uma URL ou uma cache key em um purge aceita até 4.096 caracteres.

Outros seis limites definem a taxa de requisições de purge, o tamanho de um wildcard e quanto histórico de purges a Azion mantém.

| Escopo | Limite |
| --- | --- |
| Requisições de purge por URL e por cache key por cliente | 200 requisições, de 50 objetos cada |
| Objetos purgados por URL e por cache key a cada 60 segundos | 10.000 objetos |
| Requisições de purge por wildcard por dia, em um intervalo de 24 horas | 2.000 requisições |
| Tamanho de um wildcard | 256 caracteres |
| Requisições mantidas no histórico de purges | 1.000.000 de requisições |
| Tempo de permanência de uma requisição no histórico de purges | 6 meses |

## Application Accelerator

Application Accelerator altera um limite de um cache setting: o menor tempo que Cache mantém um objeto. O Max Age de um cache setting, o seu campo `modules.cache.max_age`, define em segundos por quanto tempo Cache mantém um objeto. O campo aceita um inteiro de 0 a 31.536.000 e recusa qualquer valor fora dessa faixa. O estado de Application Accelerator e de Tiered Cache, ativos ou não, decide até onde um cache setting desce dentro da faixa.

Para as tarifas de Application Accelerator, consulte [Preços](/pt-br/documentacao/fundamentos/precos/#application-accelerator).

### Escopo

Estas restrições valem para Application Accelerator em toda Application, a partir de qualquer interface.

- **Uma Application de cada vez**: Application Accelerator vem desativado em uma Application nova e pertence à Application, então uma Application pode tê-lo ativo enquanto outra o tem desativado. Ativá-lo mantém o tráfego como estava: os controles de variação de um cache setting começam em `ignore`, e um cache setting só alcança uma requisição por meio de uma regra com [Set Cache Policy](/pt-br/documentacao/plataforma/applications/rules-engine/#set-cache-policy). [Main Settings](/pt-br/documentacao/plataforma/applications/main-settings/#recursos-da-plataforma) mostra onde ativá-lo no Azion Console e na API.
- **Tudo ou nada**: uma Application recebe todas as capacidades que Application Accelerator libera, ou nenhuma delas. Elas são a variação de cache, o cache de respostas `POST` e `OPTIONS`, um piso mais baixo para o Max Age, as variáveis `${request_uri}` e `${device_group}` e os behaviors do Rules Engine que [Configurações do Application Accelerator](/pt-br/documentacao/plataforma/applications/application-accelerator/configuracoes/) lista.
- **Métodos**: uma Application repassa requisições `POST`, `PUT`, `PATCH`, `DELETE` e `OPTIONS` à origem com ou sem Application Accelerator. Desses métodos, Application Accelerator permite armazenar em cache só as respostas `POST` e `OPTIONS`. Um `POST` informa `-` em `x-cache` até que o campo `cache_vary_by_method` do cache setting traga `post`.
- **Tamanho da variação**: cada valor distinto de uma entrada variada é um objeto em cache separado. Um cookie único para cada visitante dá uma cópia a cada visitante, então o número de objetos cresce com a audiência, e não com o conteúdo. Uma allowlist e a ordenação, o campo `sort_enabled`, limitam esse número, como explica [Variação de cache](/pt-br/documentacao/plataforma/applications/application-accelerator/variacao-de-cache/#o-custo-de-uma-variacao). Para as práticas, consulte [Boas práticas de Applications](/pt-br/documentacao/plataforma/applications/boas-praticas/#application-accelerator).
- **Purges**: as cópias que variam por cookie ou por device group sobrevivem a um purge por URL, e um purge por cache key ou um purge por wildcard que termina a key com `@@*` as alcança. As cópias que variam por query string são a exceção: um purge por URL as alcança quando envia os argumentos na ordem em que foram apresentados, ou em ordem alfabética com `sort_enabled` ativo. Para os tipos de purge, consulte [Real-Time Purge](/pt-br/documentacao/plataforma/applications/cache/real-time-purge/#purgue-conteudo-que-varia).
- **Bypass Cache e um TTL de 0**: [Bypass Cache](/pt-br/documentacao/plataforma/applications/rules-engine/#bypass-cache) envia à origem cada requisição que corresponde à sua regra e mantém a resposta fora do cache da Azion, mas não fora da camada do Tiered Cache de um cache setting que ativa o Tiered Cache. Um Max Age de 0 segundos mantém a requisição no caminho do cache, e toda requisição ainda chega à origem. [Bypass Cache e um TTL de 0](/pt-br/documentacao/plataforma/applications/application-accelerator/variacao-de-cache/#bypass-cache-e-um-ttl-de-0) compara como os dois tratam uma requisição.
- **Image Processor**: para variar o cache pela string `ims` do [Image Processor](/pt-br/documentacao/plataforma/applications/image-processor/), acrescente `ims` à allowlist de query string do cache setting que entrega as imagens.

### Limites padrão

Cada linha nomeia um limite de TTL de cache e a condição que o coloca em vigor.

| Escopo | Limite | Aplica-se quando |
| --- | --- | --- |
| TTL mínimo de cache | 60 segundos | Application Accelerator está desativado na Application, com Tiered Cache ativo ou desativado. |
| TTL mínimo de cache | 0 segundos | Application Accelerator está ativo e Tiered Cache está desativado. |
| TTL mínimo de cache | 3 segundos | Application Accelerator está ativo e Tiered Cache está ativo. |
| TTL máximo de cache | 31.536.000 segundos, um ano | Todo cache setting, quaisquer que sejam os recursos da plataforma ativos. |

Um Max Age menor que o mínimo em vigor retorna HTTP `400`. O erro é `21021` enquanto Application Accelerator está desativado, e `21020` enquanto Application Accelerator e Tiered Cache estão ambos ativos. Um valor maior que o máximo retorna o erro `10068`. Para os títulos dos erros, consulte [Cache settings](#cache-settings).

Uma requisição que Application Accelerator varia continua limitada pelos recursos da plataforma que armazenam o objeto e executam código sobre ele. Cache limita o próprio objeto: o tamanho de um objeto em cache e o tamanho de cada fragmento de um arquivo grande. Para esses valores, consulte [Objetos em cache](#objetos-em-cache).

Uma [Function](/pt-br/documentacao/plataforma/functions/) que a Application executa tem os seus próprios limites de código e de cada invocação. Para esses valores, consulte [Limites de Functions](/pt-br/documentacao/plataforma/functions/limites/).

## Image Processor

Image Processor limita uma única imagem com três limites padrão: o seu tamanho, a sua largura e a sua altura.

Para as tarifas da métrica Images, consulte [Preços](/pt-br/documentacao/fundamentos/precos/#image-processor). Para obter o número de imagens que a conta processou, use o guia [Consulte dados de uso do Image Processor](/pt-br/documentacao/guias/plataforma/observabilidade/consultar-dados-de-uso-image-processor-com-graphql/).

### Escopo

Estas restrições valem para Image Processor em toda Application, a partir de qualquer interface.

- **Uma Application de cada vez**: Image Processor vem desativado em uma Application nova, e cada Application o ativa separadamente, no seu campo `modules.image_processor.enabled` na API. Mesmo ativo, Image Processor processa somente as requisições às quais uma regra com _Optimize Images_ corresponde. [Main Settings](/pt-br/documentacao/plataforma/applications/main-settings/#recursos-da-plataforma) mostra onde ativá-lo no Azion Console e na API.
- **Parâmetros que ele não interpreta**: um valor de `ims` que Image Processor não consegue interpretar retorna a imagem de origem sem transformação. Para a sintaxe que cada operação aceita, consulte [Parâmetros de URL](/pt-br/documentacao/plataforma/applications/image-processor/parametros-de-url/).
- **Armazenamento**: Image Processor retorna cada imagem derivada sem salvá-la como um ativo da conta, e não é possível fazer upload de imagens para Image Processor. O cache guarda as imagens derivadas, e a imagem de origem permanece onde já está. Um workflow que precisa manter um arquivo transformado salva a resposta por conta própria.
- **Código**: [WASM Image Processor](/pt-br/documentacao/devtools/azion-lib/wasm-image-processor/) é uma biblioteca WebAssembly que processa imagens dentro de uma [Function](/pt-br/documentacao/plataforma/functions/). Ela é executada no código dessa Function, separada de Image Processor e das configurações dele, como explica [Onde Image Processor para](/pt-br/documentacao/plataforma/applications/image-processor/entrega-de-imagens/#onde-image-processor-para).

### Limites padrão

Uma imagem aceita no máximo 150 MB, 3.840 pixels de largura e 2.160 pixels de altura.

Cada parâmetro `ims` também aceita uma faixa de valores própria. Para a faixa de cada parâmetro, consulte [Parâmetros de URL](/pt-br/documentacao/plataforma/applications/image-processor/parametros-de-url/).
