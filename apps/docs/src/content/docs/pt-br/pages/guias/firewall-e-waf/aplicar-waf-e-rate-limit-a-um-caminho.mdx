Você pode aplicar um rule set do WAF e um rate limit a um caminho de um Workload, como `/api/`, com uma regra do [Firewall](/pt-br/documentacao/plataforma/firewall/), pelo Azion Console, pela Azion CLI ou pela API. Para aplicar um rule set a toda requisição, consulte [Crie e aplique um WAF rule set](/pt-br/documentacao/guias/seguranca-de-aplicacoes/firewall-e-waf/criar-waf-rule-set/).

## Crie a regra para o caminho

O critério é `Request Uri` _starts with_ `/api/`, que também corresponde a caminhos mais profundos, como `/api/v1/orders`. _Set WAF_ vem antes de _Set Rate Limit_, porque só _Run Function_ e _Set WAF_ podem ser seguidos por outro comportamento. Para entender o motivo, consulte [Comportamentos que encerram a lista](/pt-br/documentacao/plataforma/firewall/como-funciona/#comportamentos-que-encerram-a-lista).

_Set WAF_ começa em _Logging_, então o rule set registra o que sinaliza no seu tráfego e não recusa nada. A taxa é de `10` requisições por segundo por endereço IP de cliente, com um burst de `10`. Para saber como o burst coloca requisições em fila, consulte [Rate limits](/pt-br/documentacao/plataforma/firewall/como-funciona/#rate-limits).

<Fragment slot="panel.console">

### Console

Para criar a regra no Azion Console:

<DocSteps>
  <DocStep title="Abra o Firewall que o deployment do seu Workload define">

  Acesse [Azion Console](https://console.azion.com/) > **Firewalls** e selecione o Firewall.

  </DocStep>
  <DocStep title="Selecione a aba Rules Engine" />
  <DocStep title="Selecione + Rule" />
  <DocStep title="Dê um nome à regra">

  Insira `api - waf and rate limit`.

  </DocStep>
  <DocStep title="Defina o critério">

  Na seção **Criteria**, selecione a variável `Request Uri`, o operador _starts with_ e `/api/` como argumento.

  </DocStep>
  <DocStep title="Adicione o comportamento Set WAF">

  Na seção **Behaviors**, selecione **Set WAF**, depois o seu rule set e _Logging_ como modo.

  </DocStep>
  <DocStep title="Adicione o comportamento Set Rate Limit">

  Selecione **Add Behavior** e depois **Set Rate Limit**. Defina **Rate Limit Type** como _Req/s_ e **Limit By** como _Client IP address_. Insira `10` em **Average Rate Limit** e `10` em **Maximum Burst Size**.

  </DocStep>
  <DocStep title="Selecione Save" />
</DocSteps>

A regra aparece na aba **Rules Engine**, abaixo das regras criadas antes dela.

</Fragment>

<Fragment slot="panel.cli">

### CLI

Para criar a regra com a Azion CLI, salve-a como `rule.json`, com o ID do seu rule set em `waf_id`:

```json
{
  "name": "api - waf and rate limit",
  "active": true,
  "criteria": [
    [
      { "variable": "${request_uri}", "conditional": "if", "operator": "starts_with", "argument": "/api/" }
    ]
  ],
  "behaviors": [
    { "type": "set_waf", "attributes": { "waf_id": <waf-id>, "mode": "logging" } },
    { "type": "set_rate_limit", "attributes": { "type": "second", "limit_by": "client_ip", "average_rate_limit": 10, "maximum_burst_size": 10 } }
  ]
}
```

Depois crie a regra a partir do arquivo:

```bash
azion create firewall-rule --firewall-id <firewall-id> --file rule.json
```

O comando imprime o ID da nova regra:

```text
Created Firewall Rule with ID <rule-id>
```

</Fragment>

<Fragment slot="panel.api">

### API

Para criar a regra com a API, envie os dois comportamentos em ordem, com o ID do seu rule set em `waf_id`:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules \
  --header 'Authorization: Token <personal-token>' \
  --header 'Content-Type: application/json' \
  --data '{
  "name": "api - waf and rate limit",
  "active": true,
  "criteria": [
    [{ "variable": "${request_uri}", "conditional": "if", "operator": "starts_with", "argument": "/api/" }]
  ],
  "behaviors": [
    { "type": "set_waf", "attributes": { "waf_id": <waf-id>, "mode": "logging" } },
    { "type": "set_rate_limit", "attributes": { "type": "second", "limit_by": "client_ip", "average_rate_limit": 10, "maximum_burst_size": 10 } }
  ]
}'
```

A API responde `202` com `state` igual a `pending` e acrescenta a `order` que a regra ocupa entre as regras do Firewall:

```text
{"state":"pending","data":{"id":<rule-id>,…,"description":"","order":<order>}}
```

Um comportamento `set_waf` enviado sem `mode` é recusado com `400` e `10059 Required Field`, e um `waf_id` que não corresponde a nenhum rule set, com `25036 Invalid Informed WAF`.

</Fragment>
</Tabs>

A regra aplica o rule set e o rate limit a toda requisição a `/api/` e a nenhuma requisição a outro caminho. Para recusar o que o rule set sinaliza, mude o modo para _Blocking_ quando **Tuning** não tiver nenhuma requisição que deveria ter sido servida, como descreve [Verifique ou altere o modo do WAF](/pt-br/documentacao/guias/seguranca-de-aplicacoes/firewall-e-waf/como-verificar-modo-do-seu-waf/).

:::note[nota]
Uma regra mantém um rate limit para tudo o que os critérios dela correspondem, então uma regra que corresponde a dois caminhos por `or` compartilha um limite entre eles, e um limite separado por caminho exige uma regra por caminho. Quando o caminho já tem uma regra com _Set WAF_, ou outra regra precisa ser executada antes do limite, coloque _Set Rate Limit_ em uma regra própria com o mesmo critério, na última posição. Um Firewall executa as regras em ordem, e uma regra nova ocupa a última posição. Para mover uma regra, consulte [Altere a ordem das regras de Firewall](/pt-br/documentacao/guias/seguranca-de-aplicacoes/bots-e-rede/alterar-a-ordem-das-regras-de-firewall/).
:::

No caso de uso [Implantar servidores MCP remotos](/pt-br/documentacao/casos-de-uso/construir-e-executar-workloads-de-ai/implantar-servidores-mcp-remotos/), esta seção usa estes valores:

| Configuração | Valor |
| --- | --- |
| Nome | `mcp - waf and rate limit` |
| Critério | `Request Uri` _starts with_ `/mcp` |
| Set WAF | O rule set `mcp-waf` em modo _Blocking_ |
| Set Rate Limit | _Req/s_, _Client IP address_, um **Average Rate Limit** de `10` e um **Maximum Burst Size** de `20` |
| Ordem dos comportamentos na API | `set_waf` primeiro, depois `set_rate_limit` |

Toda requisição a `/mcp` é pontuada pelo `mcp-waf` e contada contra a taxa antes de chegar à Function. Uma requisição que o rule set bloqueia responde `400` com a página padrão Bad Request, e uma requisição acima da taxa responde `429` com a página padrão Too Many Requests e um header `retry-after: 1`. Nenhuma das respostas indica o Firewall.

No caso de uso [Proteger APIs públicas contra abuso](/pt-br/documentacao/casos-de-uso/proteger-aplicacoes-e-redes/proteger-apis-publicas-contra-abuso/), esta seção usa estes valores:

| Configuração | Valor |
| --- | --- |
| Nome | `api - rate limit per client` |
| Critério | `Request Uri` _starts with_ `/v1/` |
| Comportamento | _Set Rate Limit_ sozinho, com _Req/s_, _Client IP address_, um **Average Rate Limit** de `10` e um **Maximum Burst Size** de `10`. Na API, `set_rate_limit` com `type` `second`, `limit_by` `client_ip`, `average_rate_limit` `10` e `maximum_burst_size` `10` |

Cada endereço IP de cliente pode enviar 10 requisições por segundo a `/v1/`, com um pico de mais 10 em fila. Uma requisição recusada carrega `retry-after: 1` e nenhum outro header de rate limit.

## Confirme que a regra age no caminho

Uma regra que você adiciona ou altera chega ao tráfego vários minutos depois de salva, e nenhuma duração é garantida. Em testes, uma regra nova ou alterada agiu nas requisições pela primeira vez de cerca de 4 minutos a mais de 9 minutos depois de salva, e as respostas alternaram por até 12 minutos. Até lá, as requisições alternam entre a resposta anterior e a nova, então repita cada verificação até que as respostas concordem. Para mais informações, consulte [Propagação](/pt-br/documentacao/plataforma/firewall/como-funciona/#propagacao).

Para confirmar os dois comportamentos:

1. Envie 30 requisições simultâneas ao caminho a partir de um endereço:

   ```bash
   seq 30 | xargs -P 30 -I{} curl -s -o /dev/null -w '%{http_code}\n' https://www.example.com/api/
   ```

   Algumas das respostas imprimem `429`: as requisições simultâneas além do burst de `10`. Uma requisição recusada recebe a página de erro padrão da Azion, com o título **Too Many Requests**, e um header `retry-after`:

   ```text
   HTTP/2 429
   content-type: text/html; charset=utf-8
   retry-after: 1
   x-azion-request-id: <request-id>
   ```

2. Envie as mesmas 30 requisições a um caminho fora de `/api/`. Nenhuma delas imprime `429`, porque a regra não corresponde a esse caminho.

3. Envie ao caminho uma requisição com uma query string em formato de injeção:

   ```bash
   curl -i "https://www.example.com/api/?q=1%27%20OR%20%271%27%3D%271"
   ```

   Em _Logging_, a Application responde normalmente, e o registro da requisição mostra `$LEARNING-BLOCK`. Depois da mudança para _Blocking_, a mesma requisição recebe:

   ```text
   HTTP/2 400
   ```

A regra recusa com `429` as requisições a `/api/` além do burst e registra o que o rule set sinaliza no caminho. Nenhuma resposta indica o Firewall, então o `x-azion-request-id` de uma requisição recusada é o que leva ao registro dela. Para lê-lo, consulte [Leia o score de uma requisição bloqueada](/pt-br/documentacao/guias/seguranca-de-aplicacoes/firewall-e-waf/ler-score-do-bloqueio/). Em testes, o WAF não inspecionou toda requisição: para as condições observadas, consulte [Modos](/pt-br/documentacao/plataforma/firewall/waf/score-e-modos/#modos).

No caso de uso [Implantar servidores MCP remotos](/pt-br/documentacao/casos-de-uso/construir-e-executar-workloads-de-ai/implantar-servidores-mcp-remotos/), espere:

- **O rate limit recusa um loop.** Sessenta requisições `tools/list` enviadas 30 de cada vez, para que cheguem mais rápido que 10 por segundo, respondem com `200` e `429`: a taxa e o burst admitem algumas das requisições, e o Firewall recusa as outras.

No caso de uso [Proteger APIs públicas contra abuso](/pt-br/documentacao/casos-de-uso/proteger-aplicacoes-e-redes/proteger-apis-publicas-contra-abuso/), espere:

- **O caminho da API recusa uma inundação.** As requisições a `/api/` além do burst respondem `429`, e as mesmas requisições a um caminho fora de `/api/` não.
- **O WAF registra ataques no caminho.** Uma requisição em formato de injeção para `/api/` tem um registro do WAF e, depois da mudança para _Blocking_, responde `400`.
