Em Azion Console ou pela API, você define por quanto tempo um objeto fica em cache, ignora o cache em um path e encaminha o header `Set-Cookie` da origem. Um cache setting carrega a política de cache, e uma regra do [Rules Engine](/pt-br/documentacao/plataforma/applications/rules-engine/) a aplica às requisições que você escolher.

Para variar um objeto em cache por um argumento de query string ou por um cookie, consulte [Configure a Advanced Cache Key para uma aplicação](/pt-br/documentacao/guias/performance-e-confiabilidade/cache-e-purge/advanced-cache-key/).

---

## Pré-requisitos

- Uma aplicação. Para criar uma, consulte [Primeiros passos com Applications](/pt-br/documentacao/plataforma/applications/primeiros-passos/).
- Acesso a Azion Console. Consulte [Como acessar o Azion Console](/pt-br/documentacao/guias/plataforma/conta-e-billing/como-acessar-o-azion-console/).
- Um personal token, para os painéis de API. Para criar um, consulte [Personal tokens](/pt-br/documentacao/guias/plataforma/conta-e-billing/personal-tokens/).
- Application Accelerator pode gerar custos relacionados ao uso. Para as tarifas, consulte [Preços](/pt-br/documentacao/fundamentos/precos/#application-accelerator).

## Ative Application Accelerator

Um cache setting não exige módulo algum, e qualquer aplicação pode carregar um. [Application Accelerator](/pt-br/documentacao/plataforma/applications/#application-accelerator) é exigido para um **Max Age** abaixo de 60 segundos, para a variação de cache e para os behaviors **Bypass Cache** e **Forward Cookies**. O módulo vem desativado por padrão. Para ativá-lo:

<DocSteps>
  <DocStep title="Abra a aplicação">

  Acesse [Azion Console](https://console.azion.com/) > **Applications** > **sua aplicação**.

  </DocStep>
  <DocStep title="Ative o módulo">

  Na aba **Main Settings**, na seção **Modules**, ative **Application Accelerator**.

  </DocStep>
  <DocStep title="Selecione Save" />
</DocSteps>

A aplicação roda com Application Accelerator. Os cache settings dela aceitam um **Max Age** abaixo de 60 segundos, e **Bypass Cache** e **Forward Cookies** ficam disponíveis no **Rules Engine**.

## Defina o cache TTL de um path

Um cache setting guarda o time-to-live (TTL) que o navegador aplica e o TTL que a Azion aplica. Para criar um:

<DocSteps>
  <DocStep title="Abra a aba Cache Settings">

  Acesse [Azion Console](https://console.azion.com/) > **Applications** > **sua aplicação** e vá para a aba **Cache Settings**.

  </DocStep>
  <DocStep title="Selecione + Cache" />
  <DocStep title="Nomeie o cache setting">

  Em **Name**, digite um nome que identifique o cache setting. Por exemplo: `/target-uri - Cache TTL`.

  </DocStep>
  <DocStep title="Defina o cache do navegador">

  Em **Browser Cache**, selecione _Override cache settings_ e defina a idade máxima em segundos.

  </DocStep>
  <DocStep title="Defina o Max Age">

  Em **Cache**, selecione _Override cache behavior_ e defina **Max Age** como o número de segundos que a Azion mantém o objeto.

  </DocStep>
  <DocStep title="Selecione Save" />
</DocSteps>

O cache setting aparece na aba **Cache Settings**. O mesmo cache setting também pode variar o objeto em cache por query string ou por cookie, que é o recurso [Advanced Cache Key](/pt-br/documentacao/plataforma/applications/cache/cache-settings/#application-accelerator).

Um cache setting entra em vigor apenas quando uma regra o aplica. Para aplicar este ao path `/target-uri`:

<DocSteps>
  <DocStep title="Vá para a aba Rules Engine" />
  <DocStep title="Selecione + Rule" />
  <DocStep title="Nomeie a regra">

  Digite um nome para a regra. Por exemplo: `/target-uri - Cache TTL`.

  </DocStep>
  <DocStep title="Selecione Request Phase" />
  <DocStep title="Selecione a variável na seção Criteria">

  Na seção **Criteria**, selecione a variável `${uri}`.

  </DocStep>
  <DocStep title="Selecione starts with como operador de comparação" />
  <DocStep title="Digite o argumento">

  Digite `/target-uri` como argumento.

  </DocStep>
  <DocStep title="Na seção Behaviors, selecione Set Cache Policy" />
  <DocStep title="Selecione o cache setting que você criou" />
  <DocStep title="Selecione Save" />
</DocSteps>

As requisições cuja URI começa com `/target-uri` carregam o cache setting, tanto no TTL do navegador quanto no TTL da Azion que você definiu. Uma nova regra leva alguns minutos para propagar.

## Ignore o cache em um path

**Bypass Cache** impede que a Azion armazene em cache a resposta da origem para as requisições que correspondem a uma regra. Para criar a regra:

<DocSteps>
  <DocStep title="Vá para a aba Rules Engine">

  Acesse [Azion Console](https://console.azion.com/) > **Applications** > **sua aplicação** e vá para a aba **Rules Engine**.

  </DocStep>
  <DocStep title="Selecione + Rule" />
  <DocStep title="Nomeie a regra">

  Digite um nome para a regra. Por exemplo: `/target-uri - Bypass Cache`.

  </DocStep>
  <DocStep title="Selecione Request Phase" />
  <DocStep title="Selecione a variável na seção Criteria">

  Na seção **Criteria**, selecione a variável `${uri}`.

  </DocStep>
  <DocStep title="Selecione starts with como operador de comparação" />
  <DocStep title="Digite o argumento">

  Digite `/target-uri` como argumento.

  </DocStep>
  <DocStep title="Na seção Behaviors, selecione Bypass Cache" />
  <DocStep title="Selecione Save" />
</DocSteps>

As requisições cuja URI começa com `/target-uri` chegam à origem, e a Azion não armazena nenhuma resposta delas. Uma nova regra leva alguns minutos para propagar.

:::note[nota]
**Bypass Cache** afeta apenas o cache na Azion, não o cache do navegador. O cache do navegador vem do cache setting que **Set Cache Policy** aplica.
:::

Para mais informações, consulte [Bypass Cache](/pt-br/documentacao/plataforma/applications/rules-engine/#bypass-cache). Para a diferença entre **Bypass Cache** e um **Max Age** de `0` segundos, consulte [Variação de cache](/pt-br/documentacao/plataforma/applications/application-accelerator/variacao-de-cache/).

## Ignore o cache em um path pela API

**Bypass Cache** também pode ser definido pela API, com uma regra que tem o behavior `bypass_cache`. O exemplo faz bypass do cache em `/api/`, com uma regra chamada `cdn - api pass-through`. Substitua cada valor pelo seu. Para criar a regra de bypass:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/applications/<application-id>/request_rules \
  --header 'Authorization: Token <personal-token>' \
  --header 'Content-Type: application/json' \
  --data '{
  "name": "cdn - api pass-through",
  "active": true,
  "criteria": [[{ "variable": "${uri}", "conditional": "if", "operator": "starts_with", "argument": "/api/" }]],
  "behaviors": [{ "type": "bypass_cache" }]
}'
```

A API responde `202` com um `state` igual a `pending` e a regra como foi guardada.

As requisições cuja URI começa com `/api/` chegam à origem, e a Azion não armazena nenhuma resposta delas. Uma nova regra leva alguns minutos para propagar.

Para confirmar a regra, solicite um caminho que ela corresponde com o header `Pragma: azion-debug-cache`:

```bash
curl -sI -H "Pragma: azion-debug-cache" https://www.example.com/api/status
```

A resposta carrega `x-cache: BYPASS`. Para saber como ler o header, consulte [Verifique o status de cache de uma resposta](/pt-br/documentacao/guias/performance-e-confiabilidade/cache-e-purge/verificar-tempo-de-cache-da-pagina/).

O caso de uso [Acelerar sites e APIs com uma CDN](/pt-br/documentacao/casos-de-uso/melhorar-performance-e-confiabilidade/acelerar-sites-e-apis-com-uma-cdn/) usa os valores deste exemplo.

Estas verificações confirmam o caso de uso [Acelerar sites e APIs com uma CDN](/pt-br/documentacao/casos-de-uso/melhorar-performance-e-confiabilidade/acelerar-sites-e-apis-com-uma-cdn/).

## Encaminhe cookies da origem ao usuário

**Forward Cookies** envia aos usuários o header `Set-Cookie` da origem, inclusive em um cache hit. Para criar a regra:

<DocSteps>
  <DocStep title="Vá para a aba Rules Engine">

  Acesse [Azion Console](https://console.azion.com/) > **Applications** > **sua aplicação** e vá para a aba **Rules Engine**.

  </DocStep>
  <DocStep title="Selecione + Rule" />
  <DocStep title="Nomeie a regra">

  Digite um nome para a regra. Por exemplo: `/target-uri - Forward Cookies`.

  </DocStep>
  <DocStep title="Selecione Request Phase" />
  <DocStep title="Selecione a variável na seção Criteria">

  Na seção **Criteria**, selecione a variável `${uri}`.

  </DocStep>
  <DocStep title="Selecione starts with como operador de comparação" />
  <DocStep title="Digite o argumento">

  Digite `/target-uri` como argumento.

  </DocStep>
  <DocStep title="Na seção Behaviors, selecione Forward Cookies" />
  <DocStep title="Selecione Save" />
</DocSteps>

As requisições cuja URI começa com `/target-uri` retornam ao usuário o header `Set-Cookie` da origem.

O header encaminhado pode carregar cookies de sessão. Para impedir que um usuário receba os cookies de sessão de outro usuário:

<DocSteps>
  <DocStep title="Vá para a aba Cache Settings" />
  <DocStep title="Selecione + Cache" />
  <DocStep title="Nomeie o cache setting">

  Em **Name**, digite um nome que identifique o cache setting. Por exemplo: `/target-uri - Private cookies`.

  </DocStep>
  <DocStep title="Aplique denylist aos cookies de sessão">

  Em **Application Accelerator**, abra **Cache vary by Cookies** e defina **Behavior** como _Denylist_.

  </DocStep>
  <DocStep title="Digite os nomes dos cookies">

  Adicione cada cookie de sessão à lista de nomes de cookies.

  </DocStep>
  <DocStep title="Selecione Save" />
</DocSteps>

O cache setting aparece na aba **Cache Settings**, e ele mantém os cookies listados fora da cache key.

Para aplicar esse cache setting à regra que encaminha os cookies:

<DocSteps>
  <DocStep title="Vá para a aba Rules Engine" />
  <DocStep title="Selecione a regra">

  Selecione a regra `/target-uri - Forward Cookies`.

  </DocStep>
  <DocStep title="Na seção Behaviors, selecione + Behavior" />
  <DocStep title="Selecione Set Cache Policy" />
  <DocStep title="Selecione o cache setting">

  Selecione o cache setting `/target-uri - Private cookies`.

  </DocStep>
  <DocStep title="Selecione Save" />
</DocSteps>

A regra encaminha o header `Set-Cookie` da origem e aplica o cache setting. Uma alteração em uma regra leva alguns minutos para propagar. A mesma regra também pode carregar o behavior **Bypass Cache**.

## Coloque em cache um conjunto de caminhos só para visitantes sem sessão

Uma regra pode ter vários critérios. Em um grupo, cada critério depois do primeiro se une ao anterior por **And** ou **Or**, e os grupos se unem por **And**, então uma requisição só casa quando atende a todos os grupos. A regra desta seção une seus dois caminhos por **Or** em um grupo e verifica o cookie em um segundo grupo. Ela coloca em cache dois caminhos de catálogo só para requisições que não carregam cookie de sessão, então um visitante autenticado nunca recebe uma cópia compartilhada. O exemplo usa `/products/` e `/category/` para os caminhos e `session_id` para o cookie que a origem define quando uma sessão começa. Substitua cada um pelo seu.

O cache setting guarda uma página por 600 segundos na Azion e sobrescreve o cache do navegador para `0` segundos, porque uma cópia no navegador não pode ser purgada.

<Fragment slot="panel.console">

Crie um cache setting chamado `storefront-catalog`, como mostra [Defina o cache TTL de um path](#defina-o-cache-ttl-de-um-path), com idade máxima do navegador de `0` e **Max Age** de `600`. Para criar a regra que o aplica:

<DocSteps>
  <DocStep title="Vá para a aba Rules Engine">

  Acesse [Azion Console](https://console.azion.com/) > **Applications** > **sua aplicação** e vá para a aba **Rules Engine**.

  </DocStep>
  <DocStep title="Selecione + Rule" />
  <DocStep title="Dê um nome à regra">

  Insira `storefront - catalog cache`.

  </DocStep>
  <DocStep title="Selecione Request Phase" />
  <DocStep title="Case os caminhos do catálogo">

  Na seção **Criteria**, defina o primeiro critério como `${uri}` _starts with_ `/products/`. Adicione um segundo critério unido por **Or**: `${uri}` _starts with_ `/category/`.

  </DocStep>
  <DocStep title="Exclua visitantes com sessão">

  Adicione um segundo grupo de critérios com um critério: `${cookie_session_id}` _does not exist_.

  </DocStep>
  <DocStep title="Na seção Behaviors, selecione Set Cache Policy" />
  <DocStep title="Selecione o cache setting storefront-catalog" />
  <DocStep title="Selecione Save" />
</DocSteps>

</Fragment>

<Fragment slot="panel.api">

Para criar o cache setting, envie o corpo dele para os cache settings da aplicação:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/applications/<application-id>/cache_settings \
  --header 'Authorization: Token <personal-token>' \
  --header 'Content-Type: application/json' \
  --data '{
  "name": "storefront-catalog",
  "browser_cache": { "behavior": "override", "max_age": 0 },
  "modules": { "cache": { "behavior": "override", "max_age": 600 } }
}'
```

A API responde `201` com o novo setting. Guarde o `id` dele para a regra:

```json
{"state":"executed","data":{"id":<cache-setting-id>,"name":"storefront-catalog",...}}
```

Para criar a regra, envie dois grupos de critérios. Os grupos se unem com `and`, então uma requisição só casa quando o caminho dela é um caminho de catálogo e ela não carrega cookie de sessão:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/applications/<application-id>/request_rules \
  --header 'Authorization: Token <personal-token>' \
  --header 'Content-Type: application/json' \
  --data '{
  "name": "storefront - catalog cache",
  "active": true,
  "criteria": [
    [
      { "variable": "${uri}", "conditional": "if", "operator": "starts_with", "argument": "/products/" },
      { "variable": "${uri}", "conditional": "or", "operator": "starts_with", "argument": "/category/" }
    ],
    [
      { "variable": "${cookie_session_id}", "conditional": "if", "operator": "does_not_exist" }
    ]
  ],
  "behaviors": [{ "type": "set_cache_policy", "attributes": { "value": <cache-setting-id> } }]
}'
```

A API responde `202` com um `state` igual a `pending` e a regra como foi armazenada.

</Fragment>
</Tabs>

As páginas de catálogo e de produto requisitadas sem cookie de sessão ficam em cache por 600 segundos, e os navegadores as revalidam a cada visita. Uma regra nova leva alguns minutos para se propagar.

O caso de uso [Criar vitrines de e-commerce](/pt-br/documentacao/casos-de-uso/construir-e-executar-aplicacoes/criar-vitrines-de-e-commerce/) usa os valores deste exemplo.

## Ignore o cache em vários caminhos e em um cookie de sessão

Uma única regra pode enviar toda requisição por visitante para a origem. A regra desta seção casa com os caminhos de carrinho, checkout e conta e com qualquer requisição que carregue o cookie de sessão, então um visitante com sessão ignora o cache em todos os caminhos. Ela também carrega **Forward Cookies**, para que o cookie de sessão que a origem define chegue ao visitante. Nada que essa regra casa fica em cache, então o cache setting de denylist de [Encaminhe cookies da origem ao usuário](#encaminhe-cookies-da-origem-ao-usuario) não é necessário aqui. O exemplo usa `/cart`, `/checkout`, `/account` e `session_id`. Substitua cada um pelo seu.

  Insira `storefront - bypass per-visitor pages`.

<Fragment slot="panel.api">

Para criar a regra de bypass, envie os quatro critérios em um grupo unido por `or` e os dois behaviors:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/applications/<application-id>/request_rules \
  --header 'Authorization: Token <personal-token>' \
  --header 'Content-Type: application/json' \
  --data '{
  "name": "storefront - bypass per-visitor pages",
  "active": true,
  "criteria": [
    [
      { "variable": "${uri}", "conditional": "if", "operator": "starts_with", "argument": "/cart" },
      { "variable": "${uri}", "conditional": "or", "operator": "starts_with", "argument": "/checkout" },
      { "variable": "${uri}", "conditional": "or", "operator": "starts_with", "argument": "/account" },
      { "variable": "${cookie_session_id}", "conditional": "or", "operator": "exists" }
    ]
  ],
  "behaviors": [{ "type": "bypass_cache" }, { "type": "forward_cookies" }]
}'
```

A API responde `202` com um `state` igual a `pending` e a regra como foi armazenada.

</Fragment>
</Tabs>

As requisições de carrinho, checkout e conta, e toda requisição com sessão, chegam à origem, e a Azion não guarda nenhuma das respostas delas. Uma regra nova leva alguns minutos para se propagar.

Para confirmar as duas regras, requisite uma página de catálogo duas vezes sem cookie, depois o carrinho, depois uma página de catálogo com o cookie de sessão, cada uma com o header `Pragma: azion-debug-cache`:

```bash
curl -sI -H "Pragma: azion-debug-cache" https://www.example.com/products/blue-shirt
curl -sI -H "Pragma: azion-debug-cache" https://www.example.com/cart
curl -sI -H "Pragma: azion-debug-cache" -H "Cookie: session_id=test" https://www.example.com/products/blue-shirt
```

A segunda requisição de catálogo carrega `x-cache: HIT`. O carrinho e a requisição com o cookie carregam `x-cache: BYPASS`. Para saber como ler o header, consulte [Verifique o status de cache de uma resposta](/pt-br/documentacao/guias/performance-e-confiabilidade/cache-e-purge/verificar-tempo-de-cache-da-pagina/).

O caso de uso [Criar vitrines de e-commerce](/pt-br/documentacao/casos-de-uso/construir-e-executar-aplicacoes/criar-vitrines-de-e-commerce/) usa os valores deste exemplo.

Estas verificações confirmam o caso de uso [Criar vitrines de e-commerce](/pt-br/documentacao/casos-de-uso/construir-e-executar-aplicacoes/criar-vitrines-de-e-commerce/).
