Você pode ler e alterar o modo em que um [Firewall](/pt-br/documentacao/plataforma/firewall/) aplica um rule set do [Web Application Firewall (WAF)](/pt-br/documentacao/plataforma/firewall/waf/), pelo Azion Console ou pela API. O modo pertence ao comportamento _Set WAF_ de uma regra, não ao rule set, então um mesmo rule set pode rodar em _Logging_ em uma regra e em _Blocking_ em outra. Para aplicar um rule set pela primeira vez, consulte [Crie e aplique um WAF rule set](/pt-br/documentacao/guias/seguranca-de-aplicacoes/firewall-e-waf/criar-waf-rule-set/).

## Verifique o modo

Um Firewall contém várias regras, e o modo fica na regra que carrega _Set WAF_.

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

Para ler o modo no Azion Console:

<DocSteps>
  <DocStep title="Abra a aba Rules Engine do Firewall">

  Acesse [Azion Console](https://console.azion.com/) > **Firewalls**, selecione o Firewall e vá para a aba **Rules Engine**.

  </DocStep>
  <DocStep title="Selecione a regra que aplica o rule set">

  A seção **Behaviors** dela carrega **Set WAF**.

  </DocStep>
  <DocStep title="Leia o modo">

  Ao lado do rule set, o comportamento **Set WAF** mostra _Logging_ ou _Blocking_.

  </DocStep>
</DocSteps>

O Firewall aplica o rule set nesse modo a toda requisição a que a regra corresponde.

</Fragment>

<Fragment slot="panel.api">

### API

Para ler o modo com a API:

<DocSteps>
  <DocStep title="Liste as regras do Firewall">

  Substitua `<firewall-id>` pelo ID do seu Firewall e `[TOKEN VALUE]` pelo seu personal token:

  ```bash
  curl --request GET \
    --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]'
  ```

  </DocStep>
  <DocStep title="Encontre o comportamento set_waf">

  A API responde `200`. A regra que aplica o rule set carrega este comportamento:

  ```json
  "behaviors": [
    { "type": "set_waf", "attributes": { "waf_id": 12345, "mode": "blocking" } }
  ]
  ```

  </DocStep>
</DocSteps>

`mode` mostra `logging` ou `blocking`, que o Azion Console exibe como _Logging_ e _Blocking_. Anote o `id` da regra para alterar o modo dela.

</Fragment>

</Tabs>

## Altere o modo

`mode` aceita `logging` ou `blocking`. Em _Logging_, o WAF registra o que o rule set sinaliza e serve a requisição; em _Blocking_, ele recusa a requisição com `400`. Para saber o que cada modo faz, consulte [Score e modos](/pt-br/documentacao/plataforma/firewall/waf/score-e-modos/#modos).

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

Para alterar o modo no Azion Console:

<DocSteps>
  <DocStep title="Abra a regra">

  Abra a regra como em [Verifique o modo](#verifique-o-modo).

  </DocStep>
  <DocStep title="Selecione o novo modo no comportamento Set WAF">

  Selecione _Logging_ ou _Blocking_.

  </DocStep>
  <DocStep title="Selecione Save" />
</DocSteps>

</Fragment>

<Fragment slot="panel.api">

### API

Um `PATCH` substitui o array `behaviors` inteiro da regra e mantém os critérios dela, então envie todo comportamento que a regra carrega. Para alterar o modo com um `PATCH`:

<DocSteps>
  <DocStep title="Envie a alteração">

  Substitua `<firewall-id>` e `<rule-id>` pelos seus IDs e `waf_id` pelo ID do seu rule set:

  ```bash
  curl --request PATCH \
    --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules/<rule-id> \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: application/json' \
    --data '{
    "behaviors": [
      {
        "type": "set_waf",
        "attributes": {
          "waf_id": 12345,
          "mode": "blocking"
        }
      }
    ]
  }'
  ```

  </DocStep>
  <DocStep title="Leia a resposta">

  A API responde `202`, com `"state": "pending"` e a regra inteira, que carrega o novo modo:

  ```json
  "behaviors": [{ "type": "set_waf", "attributes": { "waf_id": 12345, "mode": "blocking" } }]
  ```

  </DocStep>
</DocSteps>

Um `PUT`, por sua vez, substitui a regra inteira, então o corpo dele carrega também o nome e os critérios. Um `PUT` sem `criteria` é recusado com `10059 Required Field` em `/data/criteria`. Para alterar o modo com um `PUT`:

<DocSteps>
  <DocStep title="Escreva a regra inteira em um arquivo">

  Salve a regra como `rule.json`, com `mode` definido com o novo valor:

  ```json
  {
    "name": "Apply storefront-waf",
    "active": true,
    "criteria": [
      [
        {
          "conditional": "if",
          "variable": "${request_uri}",
          "operator": "starts_with",
          "argument": "/"
        }
      ]
    ],
    "behaviors": [
      {
        "type": "set_waf",
        "attributes": {
          "waf_id": 12345,
          "mode": "blocking"
        }
      }
    ]
  }
  ```

  </DocStep>
  <DocStep title="Envie a substituição">

  ```bash
  curl --request PUT \
    --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules/<rule-id> \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: application/json' \
    --data @rule.json
  ```

  </DocStep>
  <DocStep title="Leia a resposta">

  A API responde `202`, com `"state": "pending"` e a regra como foi armazenada:

  ```text
  {"state":"pending","data":{"id":<rule-id>,"name":"Apply storefront-waf",…,"behaviors":[{"type":"set_waf","attributes":{"waf_id":12345,"mode":"blocking"}}],"description":"","order":<order>}}
  ```

  </DocStep>
</DocSteps>

Um comportamento `set_waf` sem `mode` é recusado com `10059 Required Field` em `/data/behaviors/0/attributes/mode`. Qualquer outro valor também é recusado. O Real-Time Events registra uma requisição pontuada em _Logging_ com `wafLearning` igual a `1`, mas a API recusa `learning` como modo:

```json
{
  "errors": [
    {
      "code": "10039",
      "title": "Invalid Choice",
      "detail": "\"learning\" is not a valid choice.",
      "status": "400",
      "source": { "pointer": "/data/behaviors/0/attributes/mode" }
    }
  ]
}
```

</Fragment>

</Tabs>

Depois da mudança para _Blocking_, uma requisição que o rule set sinaliza recebe `400` em vez de chegar à sua Application. O novo modo se propaga antes que as requisições o reflitam, e as respostas podem alternar entre os dois modos nesse meio-tempo. Em uma mudança observada, o primeiro `400` veio 323 segundos depois de salvar, e uma requisição posterior ainda foi servida. Para mais informações, consulte [Propagação](/pt-br/documentacao/plataforma/firewall/como-funciona/#propagacao).
