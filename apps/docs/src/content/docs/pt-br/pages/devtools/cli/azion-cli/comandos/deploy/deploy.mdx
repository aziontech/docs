O comando `deploy` da Azion CLI faz o build do projeto no diretório atual e o deploy dele na Azion. Ele cria ou atualiza a [Application](/pt-br/documentacao/plataforma/applications/) do projeto, o [Workload](/pt-br/documentacao/plataforma/workloads/) dele e, para um site estático, o bucket do [Object Storage](/pt-br/documentacao/plataforma/object-storage/) que guarda os arquivos. Por padrão, o build é executado na Azion; com `--local`, ele é executado na sua máquina. As opções que todo comando aceita, como `--format`, `--out` e `-y`, estão em [Opções globais](/pt-br/documentacao/devtools/cli/globals/).

---

## Uso

`azion deploy` lê as configurações do projeto na pasta `azion` do diretório atual e faz o deploy do projeto.

Este comando faz o deploy do projeto:

```bash
azion deploy
```

Com `--local`, o deploy envia a pasta que o campo `dir` da entrada `storage` indica no arquivo `azion.config` do projeto. Essa pasta é `./.edge/assets` com o preset `vue` e `./www` com o preset `html`. Com `--local --debug`, a saída mostra essa pasta, como em `Path to be uploaded: ./.edge/assets`. Para enviar outra pasta, defina o caminho dela em `dir`.

Para verificar quais arquivos um deploy com `--local` enviou, liste os objetos do bucket com `azion list storage object`. Depois de um deploy bem-sucedido, as chaves dele começam com o campo `prefix` do `azion/azion.json`. Para o comando e as flags `--page-size` e `--next-page`, consulte [Azion CLI storage](/pt-br/documentacao/devtools/cli/recursos/storage/#listar).

### Flags

| Flag | Curta | Tipo | Padrão | Descrição |
| --- | --- | --- | --- | --- |
| `--alias-env` | — | — | — | Passa `--alias-env` para a fase de build do deploy, para que as variáveis lidas dos arquivos `.env` do projeto recebam um prefixo formado a partir do nome do projeto. Para mais informações, consulte [Azion CLI build](/pt-br/documentacao/devtools/cli/build/). |
| `--auto` | — | — | — | Executa o comando inteiro sem parar para uma pergunta. |
| `--config-dir` | — | string | `"azion"` | Caminho relativo para a pasta que guarda os seus arquivos `azion.json` e `args.json`. |
| `--config-file` | — | string | — | Caminho para o arquivo `azion.config` usado no deploy, como `azion.staging.config.cjs`. Sem ela, o deploy usa o arquivo `azion.config.*` do diretório atual. Em um deploy remoto, o padrão, o arquivo precisa estar dentro do diretório do projeto, porque só esse diretório é enviado. Com `--local`, o deploy grava o prefixo de storage nesse arquivo e faz o build a partir dele. Um arquivo inexistente, ou um arquivo fora do projeto em um deploy remoto, é rejeitado antes que o deploy altere qualquer coisa na sua máquina ou na Azion. |
| `--dry-run` | — | — | — | Lista as etapas que o deploy executaria, sem executá-las. O dry run não cria nem altera nenhum recurso e não altera `azion/azion.json`, e `--format json` imprime a lista em JSON. As etapas são as do fluxo `--local`, também quando você executa `azion deploy --dry-run` sem `--local`. |
| `--env` | — | string | `".edge/.env"` | Caminho relativo para o seu arquivo `.env`. |
| `--local` | — | — | — | Executa o build e o deploy na sua máquina em vez de na Azion. Use-a quando você precisa do seu próprio ambiente de build ou de mais controle sobre o build. |
| `--no-prompt` | — | — | — | Retorna o erro em vez de fazer uma pergunta quando uma etapa falha. |
| `--path` | — | string | — | Obsoleta. O deploy a ignora e envia a pasta que o `azion.config` define. |
| `--skip-build` | — | — | — | Em um deploy seguinte com `--local`, pula o build e o envio dos arquivos estáticos. |
| `--skip-framework-build` | — | — | — | Em um deploy seguinte com `--local`, pula o build do framework, como o `vite build`. |
| `--sync` | — | — | — | Sincroniza o arquivo `azion.json` local com os recursos remotos. |
| `--workers` | — | int | auto-calculated based on CPU cores, max `20` | Número de workers de upload que enviam arquivos ao mesmo tempo. |
| `--writable-bucket` | — | — | — | Cria o bucket do projeto com acesso de leitura e gravação. |

A CLI gerencia as credenciais de storage que cada rota precisa, então nenhum envio pede uma credencial sua. Um deploy padrão envia os arquivos-fonte para o build remoto, com as credenciais em `~/.azion/<profile>/settings.toml`. Com `--local`, a própria CLI envia os arquivos estáticos já construídos e guarda um conjunto de credenciais por bucket em `~/.azion/<profile>/credentials.toml`.

:::note[nota]
O comportamento de `--path`, `--skip-build` e `--skip-framework-build` nesta página é o da Azion CLI 4.27.0 e das versões seguintes. Para ver a versão instalada, execute `azion --version`. Para atualizar a CLI, consulte [Instalar a Azion CLI](/pt-br/documentacao/devtools/cli/#instalar-a-azion-cli).
:::

O deploy ignora `--path` e imprime este aviso:

```text
Flag --path has been deprecated, it is ignored and will be removed in a future release; set the storage directory in azion.config instead
```

O que `--skip-build` e `--skip-framework-build` fazem depende de o projeto já ter passado por um deploy e de onde o build é executado:

| Flag | Primeiro deploy | Deploy seguinte com `--local` | Deploy sem `--local` |
| --- | --- | --- | --- |
| `--skip-framework-build` | Ignorada: o build do framework é executado | Pula o build do framework e envia a saída que já existe | Ignorada: a Azion executa o build do framework |
| `--skip-build` | Ignorada: o build é executado | Pula o build e o envio, sem trocar o prefixo de storage | Ignorada: a Azion executa o build |

Quando você passa uma das flags para o primeiro deploy com `--local`, o comando imprime `This is the project's first deploy, so --skip-build and --skip-framework-build are ignored: the project is built and its static files are generated and uploaded`. O primeiro deploy executa o build do framework, como o `vite build`, então a pasta do projeto precisa ter o `package.json` e o código-fonte do app. Um primeiro deploy que para no build não conta, então o deploy seguinte também é um primeiro deploy.

Em um deploy seguinte com `--local`, `--skip-framework-build` executa o build da Azion sem o build do framework. O preset `vue` copia a pasta de saída do Vite que já existe, a `dist` por padrão, para `./.edge/assets`, e o deploy envia essa pasta com um novo prefixo de storage. Sem essa pasta, o deploy para com o erro da pasta de storage descrito em [Erros](/pt-br/documentacao/devtools/cli/deploy/#erros).

Com `--skip-build` no lugar dessa flag, o deploy não envia nenhum arquivo e imprime `Skipping the upload of static files: --skip-build was passed, so no new static files were generated`. Ele mantém o prefixo de storage do deploy anterior e atualiza cada recurso a partir do `.edge/manifest.json`. A pasta que `dir` indica ainda precisa ter arquivos, ou o deploy para com o mesmo erro da pasta de storage.

Sem `--local`, o deploy executa o build na Azion e ignora as duas flags, sem nenhum aviso. A Azion executa o build do framework de novo e envia a saída dele em vez da pasta do build que você fez.

## Exemplos

Cada exemplo mostra o comando e a saída que ele imprime.

### Fazer o deploy com um build remoto

Este comando faz o primeiro deploy de um site estático. A CLI envia os arquivos de código-fonte, e o build é executado na Azion:

```bash
azion deploy
```

O comando imprime um link para a página **Deploy** do Azion Console, onde **Deploy Log** mostra o progresso do deploy, e depois o domínio do site:

```text

Uploading source files

Upload completed successfully!
Please visit https://console.azion.com/create/deploy/00000000-0000-0000-0000-000000000002 in case it did not open automatically, to follow up the full deploy process
Your Application was deployed successfully

To visualize your application access the Domain: https://xxxxxxxxxx.map.azionedge.net
Your application is being deployed to all Azion Locations and it might take a few minutes.
```

O primeiro deploy pode levar vários minutos para responder a partir de todas as localidades; os deploys seguintes levam cerca de dois minutos.

Um projeto que declara os dois carrega os dois conjuntos de IDs.

### Fazer o deploy com um build local

Este comando faz o deploy de uma alteração no mesmo site. A CLI faz o build do projeto na sua máquina, envia os arquivos e atualiza cada recurso pelo ID em `azion/azion.json`:

```bash
azion deploy --local
```

O comando executa o build por conta própria, exista ou não uma pasta `.edge` de um `azion build` anterior. Em um deploy seguinte, `--skip-build` pula o build, e `--skip-framework-build` pula só o build do framework. Antes do build, o comando grava um novo prefixo de storage em `azion.config.cjs`, ou em `azion.config.mjs` quando o projeto tem os dois arquivos:

### Pré-visualizar um deploy

Este comando simula um deploy local do mesmo site:

```bash
azion deploy --local --dry-run
```

O comando termina sem alterar nenhum recurso, e `azion/azion.json` mantém o mesmo conteúdo.

## Erros

| Erro | Causa | O que fazer |
| --- | --- | --- |
| `Failed to capture deploy logs: <reason>. Please check your account to verify if the resources were successfully created.` | O upload terminou, e a CLI não conseguiu acompanhar o build e o deploy que rodam na Azion. O deploy pode ter criado apenas parte dos recursos do projeto. | Execute de novo com `--debug` para imprimir o log do build que roda na Azion. Para todas as correções, consulte [Failed to capture deploy logs](/pt-br/documentacao/devtools/cli/solucao-de-problemas/#azion-deploy-falha-com-failed-to-capture-deploy-logs). |
| `Error: Storage folder './.edge/assets' is missing or empty.` | A pasta que `dir` indica não tem nenhum arquivo, como quando falta a `dist` com `--skip-framework-build`. | Faça o build do app, como com `npm run build`, e faça o deploy de novo com `--local`, com ou sem `--skip-framework-build`. `--skip-build` não preenche a pasta de novo. Se o projeto não serve nenhum arquivo estático, remova a entrada `storage` do `azion.config`. |
