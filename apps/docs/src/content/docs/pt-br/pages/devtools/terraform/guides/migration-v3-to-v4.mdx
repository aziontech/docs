Você pode mover uma configuração Terraform e o state dela do [Azion Terraform Provider](/pt-br/documentacao/devtools/terraform/) v1.x, que chama a Azion API v3, para o v2.0, que chama a Azion API v4. Para manter uma configuração na v1.x, consulte [Azion Terraform Provider v1.x (API v3)](/pt-br/documentacao/devtools/terraform/terraform-provider-v3/).

O provider v2.0 é uma versão major. Ele adiciona recursos e remove os descontinuados para corresponder à Azion API v4, então uma configuração v1.x não roda na v2.0 sem mudanças. Os exemplos da v2.0 nesta página foram escritos para o provider 2.10.0.

---

## Pré-requisitos

- Terraform 1.0 ou posterior.
- Uma conta Azion com acesso à Azion API v4.
- Um [personal token](/pt-br/documentacao/fundamentos/personal-tokens/) com as permissões de que a sua configuração precisa.
- Uma lista dos recursos que a sua configuração gerencia, com os que a v2.0 remove ou renomeia marcados. As tabelas em Mudanças de recursos na v2.0, nesta página, indicam esses recursos.

---

## Faça backup da configuração e do state

A migração remove recursos do state do Terraform e os importa novamente com outros tipos. Guarde uma cópia dos arquivos de configuração e do state para poder voltar à configuração da v1.x.

Para fazer backup do projeto e do state:

```bash
# Create a backup directory
mkdir -p ~/terraform-backup

# Copy your configuration files
cp -r ./your-terraform-project ~/terraform-backup/

# Back up the state file (if using local state)
cp terraform.tfstate ~/terraform-backup/
cp terraform.tfstate.backup ~/terraform-backup/ 2>/dev/null || true

# If using remote state, download a local copy
terraform state pull > ~/terraform-backup/terraform.tfstate
```

O diretório `~/terraform-backup` contém os arquivos de configuração e uma cópia do state.

## Fixe o provider na v1.x

Cada linha de versões do provider chama uma versão da Azion API:

| Versão do provider | Versão da API | Status |
| --- | --- | --- |
| 1.41.0 e anteriores | API v3 | Descontinuado |
| 2.0.0 e posteriores | API v4 | Atual |

A versão 1.41.0 é a última versão v1.x. Para continuar usando a v1.x enquanto prepara a migração, fixe o provider nessa versão:

{/* terraform-validate: skip */}
```hcl
terraform {
  required_providers {
    azion = {
      source  = "aziontech/azion"
      version = "1.41.0"
    }
  }
}
```

O próximo `terraform init` mantém o provider na versão 1.41.0.

:::caution[Atenção]
O provider 1.41.0 e as versões anteriores não recebem atualizações nem correções de bugs. Planeje a migração para a v2.0.
:::

## Mudanças de recursos na v2.0

O provider v2.0 remove, renomeia e adiciona recursos. As quatro tabelas desta seção listam cada recurso e data source da v1.x com a contraparte dele na v2.0, e os recursos que a v2 adiciona. Para todos os argumentos de um recurso da v2.0, consulte [Terraform Registry](https://registry.terraform.io/providers/aziontech/azion/latest/docs).

Todo recurso da v2.0 que tem contraparte na v1.x, inclusive os que mantêm o nome da v1.x, recebe as configurações em um único bloco aninhado, como `workload = {}`, `connector = {}`, `application = {}`, `function = {}`, `data = {}` ou `results = {}`. Um bloco da v1.x com os argumentos no nível superior falha no `terraform validate` da v2.0, então todo bloco de recurso precisa ser reescrito.

### Recursos removidos

O provider v2.0 não tem recurso nem data source com estes nomes da v1.x:

| Nome na v1.x (API v3) | Substituto na v2.0 |
| --- | --- |
| `azion_domain` | `azion_workload` e `azion_workload_deployment` |
| `azion_domains` (data source) | `azion_workloads` (data source) |
| `azion_edge_application_origin` | `azion_connector` |
| `azion_edge_applications_origins` (data source) | `azion_connectors` (data source) |
| `azion_environment_variable` | Nenhum. O provider v2.0 não tem recurso para variáveis de ambiente, então gerencie-as fora do Terraform, por exemplo no Azion Console. |
| `azion_environment_variables` (data source) | Nenhum |
| `azion_waf_domains` (data source) | Nenhum |

### Recursos renomeados

Estes recursos da v1.x mantêm a mesma função na v2.0 com outro nome. Os nomes da v2.0 seguem os nomes atuais dos produtos:

| Nome na v1.x (API v3) | Nome na v2.0 |
| --- | --- |
| `azion_edge_function` | `azion_function` |
| `azion_edge_functions` (data source) | `azion_functions` (data source) |
| `azion_edge_application_main_setting` | `azion_application_main_setting` |
| `azion_edge_application_cache_setting` | `azion_application_cache_setting` |
| `azion_edge_application_rule_engine` | `azion_application_rule_engine` |
| `azion_edge_application_edge_functions_instance` | `azion_application_function_instance` |
| `azion_edge_firewall_main_setting` | `azion_firewall_main_setting` |
| `azion_edge_firewall_edge_functions_instance` | `azion_firewall_functions_instance` |
| `azion_waf_rule_set` | `azion_waf` |
| `azion_waf_rule_sets` (data source) | `azion_wafs` (data source) |

O `azion_waf_rule_set` da v1.x gerencia um WAF rule set, com a sensibilidade de cada família de ameaças. Na v2.0, esse objeto é o `azion_waf`, então um bloco de rule set da v1.x vira um bloco `azion_waf`. O modo do WAF passa para o behavior `set_waf` da regra de firewall que executa o WAF, onde recebe `logging` ou `blocking`. Os data sources seguem o mesmo mapeamento, e os nomes `azion_waf_rule_set` e `azion_waf_rule_sets` continuam na v2.0 para outro objeto, uma exceção do WAF.

### Recursos adicionados na v2

Estes recursos da v2 não têm contraparte na v1.x. Alguns deles chegaram depois da 2.0.0, em versões 2.x posteriores, e o provider 2.10.0 inclui todos:

| Recurso | O que gerencia |
| --- | --- |
| `azion_workload` | Workloads. Substitui `azion_domain` em conjunto com `azion_workload_deployment`. |
| `azion_workload_deployment` | Deployments de workloads, que vinculam uma aplicação e, opcionalmente, um firewall e uma custom page a um workload. |
| `azion_connector` | Connectors. Substitui `azion_edge_application_origin`. |
| `azion_custom_page` | Custom pages. O provider v1.x não tem recurso para elas. |
| `azion_application_device_group` | Device groups de uma aplicação. |
| `azion_application_rule_engine_order` | A ordem das regras em uma fase do Rules Engine de uma aplicação. |
| `azion_firewall_rule_engine` | Regras do Rules Engine de um firewall. |
| `azion_firewall_rule_engine_order` | A ordem das regras no Rules Engine de um firewall. |
| `azion_waf_rule_set` | Exceções do WAF. Cada uma pertence ao rule set que o seu `waf_id` indica. O recurso da v1.x com esse nome corresponde ao `azion_waf`. |
| `azion_bucket` | Buckets do Object Storage. |
| `azion_certificate_request` | Solicitações de certificado da Let's Encrypt. |
| `azion_certificate_signing_request` | Solicitações de assinatura de certificado (CSRs). |
| `azion_crl` | Listas de revogação de certificados. |
| `azion_data_stream` | Streams do Data Stream. |
| `azion_data_stream_template` | Templates do Data Stream. |

### Recursos inalterados

Estes recursos mantêm os nomes da v1.x na v2.0. Os argumentos deles também passam para um bloco aninhado, então reescreva cada um como descrito em [Mudanças de recursos na v2.0](#mudancas-de-recursos-na-v20):

| Recurso | O que gerencia |
| --- | --- |
| `azion_intelligent_dns_zone` | Zonas DNS |
| `azion_intelligent_dns_record` | Registros DNS |
| `azion_intelligent_dns_dnssec` | Configurações de DNSSEC |
| `azion_network_list` | Network lists |
| `azion_digital_certificate` | Certificados digitais |

## Atualize o provider para a v2.0

A atualização exige duas mudanças: a restrição de versão na configuração e o provider instalado no projeto.

Para mudar a restrição de versão, defina `version` como `2.10.0` no bloco `required_providers`:

```hcl
terraform {
  required_providers {
    azion = {
      source  = "aziontech/azion"
      version = "2.10.0"
    }
  }
}
```

Para baixar o provider 2.10.0, execute:

```bash
terraform init -upgrade
```

O Terraform instala o provider 2.10.0 no projeto.

## Remova os recursos da v1.x do state

Remova os recursos descontinuados da v1.x do state do Terraform antes de importá-los com os tipos da v2.0.

Para remover as entradas de domínio, origin, function e WAF rule set do state do Terraform:

```bash
# Remove domain resources
terraform state rm azion_domain.example

# Remove origin resources
terraform state rm azion_edge_application_origin.example

# Remove function resources (will be recreated as azion_function)
terraform state rm azion_edge_function.example

# Remove WAF rule set resources (will be imported as azion_waf)
terraform state rm azion_waf_rule_set.example
```

Substitua `example` pelo nome que cada recurso tem na sua configuração. O state deixa de listar esses recursos, que continuam na sua conta Azion.

## Atualize os arquivos de configuração

Reescreva cada recurso removido ou renomeado nos seus arquivos `.tf` com o tipo da v2.0. Os pares abaixo mostram um bloco da v1.x e o bloco da v2.0 que o substitui.

### Substitua um domínio por um workload

Na v1.x, um recurso `azion_domain` gerenciava todo o ciclo de vida do domínio. Na v2.0, `azion_workload` contém a definição e `azion_workload_deployment` contém o deployment. Para todos os argumentos dos dois recursos, consulte [Recursos de Workloads](/pt-br/documentacao/devtools/terraform/workloads/).

A configuração da v1.x:

{/* terraform-validate: skip */}
```hcl
terraform {
  required_providers {
    azion = {
      source  = "aziontech/azion"
      version = "1.41.0"
    }
  }
}

provider "azion" {
  api_token = var.api_token
}

# Domain resource (v1.x)
resource "azion_domain" "example" {
  name                = "my-domain"
  cname_access_only   = false
  digital_certificate = var.certificate_id
  edge_application    = var.application_id
  is_active           = true

  # Domain name binding
  domain_name = "example.com"
}
```

A configuração da v2.0:

```hcl
terraform {
  required_providers {
    azion = {
      source  = "aziontech/azion"
      version = "2.10.0"
    }
  }
}

variable "api_token" {
  type      = string
  sensitive = true
}

variable "certificate_id" {
  type = number
}

variable "application_id" {
  type = number
}

provider "azion" {
  api_token = var.api_token
}

# Workload resource (v2.0)
resource "azion_workload" "example" {
  workload = {
    name                         = "my-workload"
    active                       = true
    domains                      = ["example.com"]
    workload_domain_allow_access = true

    tls = {
      certificate = var.certificate_id
    }
  }
}

# Workload deployment (v2.0)
resource "azion_workload_deployment" "example" {
  workload_id = azion_workload.example.workload.id

  deployment = {
    name    = "my-deployment"
    active  = true
    current = true

    strategy = {
      type = "default"
      attributes = {
        application = var.application_id
      }
    }
  }
}
```

Os dois blocos leem os IDs do certificado e da aplicação das variáveis `certificate_id` e `application_id`. Cada argumento da v1.x tem um lugar na v2.0. O domínio passa para `workload.domains`, o certificado para `workload.tls.certificate` e `is_active` para `workload.active`. `workload_domain_allow_access = true` mantém acessível o domínio que a Azion atribui ao workload, como fazia `cname_access_only = false`. A aplicação que a v1.x definia em `edge_application` passa para o deployment, em `deployment.strategy.attributes.application`.

### Substitua uma origin por um connector

Na v1.x, uma origin pertencia a uma aplicação e recebia o `edge_application_id` dela. Na v2.0, um connector é um recurso independente. Para todos os argumentos de `azion_connector`, consulte [Recursos de Connectors](/pt-br/documentacao/devtools/terraform/connectors/).

A configuração da v1.x:

{/* terraform-validate: skip */}
```hcl
# Origin (v1.x)
resource "azion_edge_application_origin" "example" {
  edge_application_id = azion_edge_application_main_setting.example.id

  name               = "my-origin"
  origin_type        = "single_origin"
  origin_address     = "origin.example.com"
  origin_protocol    = "https"
  origin_path        = "/api"
  host_header        = "origin.example.com"

  # Connection settings
  connection_timeout = 30
  read_timeout       = 60
}
```

A configuração da v2.0:

```hcl
# Connector (v2.0)
resource "azion_connector" "example" {
  connector = {
    name   = "my-connector"
    type   = "http"
    active = true

    http_attributes = {
      addresses = [
        {
          endpoint = {
            address    = "origin.example.com"
            https_port = 443
          }
        }
      ]

      connection_options = {
        host             = "origin.example.com"
        path_prefix      = "/api"
        transport_policy = "force_https"
      }
    }
  }
}
```

Um connector `http` lista os servidores de origem em `http_attributes.addresses`. Os argumentos `host_header`, `origin_path` e `origin_protocol` da v1.x passam para `http_attributes.connection_options` como `host`, `path_prefix` e `transport_policy`. Os timeouts da v1.x não têm argumento nesse nível: na v2.0, `connection_timeout` e `read_write_timeout` pertencem ao módulo de load balancer, em `http_attributes.modules.load_balancer.config`. Como um connector não recebe o ID de uma aplicação, a aplicação envia requisições para ele por uma regra do Rules Engine com o behavior `set_connector`, como mostra [Migre uma configuração completa](#migre-uma-configuracao-completa).

### Renomeie um recurso de function

O recurso de function muda de tipo, de `azion_edge_function` para `azion_function`, e muda a forma dos argumentos. Na v2.0, eles ficam em um bloco `function`: `name`, `code`, `active`, `default_args`, `execution_environment` e `runtime`. O argumento `json_args` da v1.x não existe com esse nome na v2.0: passe o mesmo valor de `jsonencode()` em `default_args`.

A configuração da v1.x:

{/* terraform-validate: skip */}
```hcl
# Function (v1.x)
resource "azion_edge_function" "example" {
  name    = "my-function"
  active  = true
  code    = file("${path.module}/function.js")

  # Function arguments
  json_args = jsonencode({
    key = "value"
  })
}
```

A configuração da v2.0:

```hcl
# Function (v2.0)
resource "azion_function" "example" {
  function = {
    name   = "my-function"
    active = true
    code = trimspace(<<-EOT
      addEventListener("fetch", (event) => {
        event.respondWith(new Response("Hello from my-function"));
      });
    EOT
    )
    execution_environment = "application"
    runtime               = "azion_js"

    # Function arguments
    default_args = jsonencode({
      key = "value"
    })
  }
}
```

O exemplo mantém o código inline. Para lê-lo de um arquivo do módulo, como faz o bloco da v1.x, defina `code = trimspace(file("${path.module}/function.js"))`. O provider recomenda envolver `code` em `trimspace()`.

### Migre uma configuração completa

Uma configuração com uma aplicação, uma origin, um domínio e uma function muda em cinco pontos: o main setting da aplicação recebe o nome da v2.0, um connector substitui a origin, uma regra do Rules Engine encaminha as requisições da aplicação para o connector, um workload e um deployment substituem o domínio e a function recebe o tipo da v2.0. Para os recursos de aplicação, consulte [Recursos de Applications](/pt-br/documentacao/devtools/terraform/applications/).

A configuração da v1.x:

{/* terraform-validate: skip */}
```hcl
terraform {
  required_providers {
    azion = {
      source  = "aziontech/azion"
      version = "1.41.0"
    }
  }
}

provider "azion" {
  api_token = var.api_token
}

# Application (v1.x)
resource "azion_edge_application_main_setting" "app" {
  name = "my-application"
}

# Origin
resource "azion_edge_application_origin" "origin" {
  edge_application_id = azion_edge_application_main_setting.app.id
  name                = "my-origin"
  origin_type         = "single_origin"
  origin_address      = "origin.example.com"
}

# Domain
resource "azion_domain" "domain" {
  name             = "my-domain"
  edge_application = azion_edge_application_main_setting.app.id
  domain_name      = "example.com"
}

# Function (v1.x)
resource "azion_edge_function" "func" {
  name   = "my-function"
  active = true
  code   = file("${path.module}/function.js")
}
```

A configuração da v2.0:

```hcl
terraform {
  required_providers {
    azion = {
      source  = "aziontech/azion"
      version = "2.10.0"
    }
  }
}

variable "api_token" {
  type      = string
  sensitive = true
}

provider "azion" {
  api_token = var.api_token
}

# Application
resource "azion_application_main_setting" "app" {
  application = {
    name = "my-application"
  }
}

# Connector (replaces origin)
resource "azion_connector" "connector" {
  connector = {
    name = "my-connector"
    type = "http"
    http_attributes = {
      addresses = [
        {
          endpoint = {
            address = "origin.example.com"
          }
        }
      ]
    }
  }
}

# Rule that routes the application's requests to the connector
resource "azion_application_rule_engine" "route_to_connector" {
  application_id = azion_application_main_setting.app.application.application_id
  results = {
    name  = "Route to my-connector"
    phase = "request"
    behaviors = [
      {
        behavior = {
          type = "set_connector"
          attributes = {
            value = azion_connector.connector.connector.id
          }
        }
      }
    ]
    criteria = [
      {
        entries = [
          {
            criterion = {
              variable    = "$${uri}"
              operator    = "starts_with"
              conditional = "if"
              argument    = "/"
            }
          }
        ]
      }
    ]
  }
}

# Workload (replaces domain)
resource "azion_workload" "workload" {
  workload = {
    name    = "my-workload"
    active  = true
    domains = ["example.com"]
  }
}

# Workload deployment (binds the application to the workload)
resource "azion_workload_deployment" "deployment" {
  workload_id = azion_workload.workload.workload.id
  deployment = {
    name    = "my-deployment"
    active  = true
    current = true
    strategy = {
      type = "default"
      attributes = {
        application = azion_application_main_setting.app.application.application_id
      }
    }
  }
}

# Function (renamed)
resource "azion_function" "func" {
  function = {
    name   = "my-function"
    active = true
    code = trimspace(<<-EOT
      addEventListener("fetch", (event) => {
        event.respondWith(new Response("Hello from my-function"));
      });
    EOT
    )
    execution_environment = "application"
    runtime               = "azion_js"
  }
}
```

## Importe os recursos com os tipos da v2.0

Os recursos que você removeu do state continuam na sua conta Azion. Importe cada um com o tipo de recurso da v2.0 usando `terraform import <type>.<name> <id>`.

Para importar o workload, o connector, a function e o WAF rule set:

```bash
# Import workloads
terraform import azion_workload.example <workload_id>

# Import connectors
terraform import azion_connector.example <connector_id>

# Import functions
terraform import azion_function.example <function_id>

# Import WAF rule sets
terraform import azion_waf.example <waf_id>
```

Substitua cada ID pelo ID do recurso na Azion API v4. Um recurso da API v3 pode ter outro ID na API v4, então consulte os IDs no [Azion Console](https://console.azion.com/). O state lista os recursos importados com os tipos da v2.0.

## Revise e aplique o plano

Um plano mostra o que o Terraform muda antes que qualquer mudança aconteça na sua conta.

Para visualizar as mudanças, execute:

```bash
terraform plan
```

Na saída do plano, confirme três pontos:

- Nenhum recurso que você espera manter é destruído.
- Os recursos que você espera criar aparecem no plano.
- Os atributos correspondem aos argumentos da v2.0 que você definiu na configuração.

Para aplicar as mudanças, execute o comando primeiro em um ambiente de teste:

```bash
terraform apply
```

O Terraform gerencia os recursos pelo provider 2.10.0 e pela Azion API v4. Para erros durante a migração, consulte [Solucionar problemas do Terraform Provider](/pt-br/documentacao/devtools/terraform/solucao-de-problemas/).

---

## Faça a limpeza após a migração

Depois do apply, conclua a migração no seu projeto:

- Confirme que os recursos migrados funcionam na sua conta Azion.
- Atualize os pipelines de CI/CD que executam o Terraform.
- Remova o código da v1.x que a configuração não usa mais.
- Atualize a documentação do projeto e informe a sua equipe sobre a mudança.
- Arquive os backups quando a migração estiver confirmada.

O projeto roda no provider v2.0, sem nenhum recurso da v1.x na configuração ou no state.
