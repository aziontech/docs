You can create the [Rules Engine for Firewall](/en/documentation/platform/firewall/rules-engine/) rule that applies a rule set to every request from Azion Console, the Azion CLI, or the API. A rule set scores nothing until a rule names it, and the criterion below skips no request.

---

## Prerequisites

- A firewall bound to your workload, with WAF turned on in its main settings.
- A rule set to apply, such as `storefront-waf`. To create one, refer to [Create a rule set at medium sensitivity](/en/documentation/guides/application-security/firewall-and-waf/rule-set-medium/).
- The [Azion CLI](/en/documentation/devtools/cli/) installed and a configured personal token, for the CLI procedure.
- A personal token, for the API request.

## Create the rule

<Tabs client:visible sharedStore="interface">
<Fragment slot="tab.console">Console</Fragment>
<Fragment slot="tab.cli">CLI</Fragment>
<Fragment slot="tab.api">API</Fragment>

<Fragment slot="panel.console">

To create the rule from Azion Console:

<DocSteps>
  <DocStep title="Open the firewall bound to your workload">

  Access [Azion Console](https://console.azion.com/) > **Firewalls**, then select that firewall.

  </DocStep>
  <DocStep title="Select the Rules Engine tab" />
  <DocStep title="Select + Rule" />
  <DocStep title="Name the rule">

  Enter `Apply storefront-waf` as the name.

  </DocStep>
  <DocStep title="Set the criterion">

  In the **Criteria** section, select the `Request Uri` variable, the _starts with_ operator, and `/` as the argument.

  </DocStep>
  <DocStep title="Add the Set WAF behavior">

  In the **Behaviors** section, select **Set WAF**, then `storefront-waf` as the rule set and _Blocking_ as the mode.

  </DocStep>
  <DocStep title="Save the rule" />
</DocSteps>

The rule hands every request the firewall receives to `storefront-waf` in blocking mode.

For the same rule with the threat families and the mode left open, refer to [Create and apply a WAF rule set](/en/documentation/guides/application-security/firewall-and-waf/create-waf-rule-set/).

</Fragment>

<Fragment slot="panel.cli">

To create the rule with the Azion CLI, save it as `rule.json`, with the id of your rule set in `waf_id`:

```json
{
  "name": "Apply storefront-waf",
  "active": true,
  "criteria": [
    [
      {
        "conditional": "if",
        "variable": "${request_uri}",
        "operator": "starts_with",
        "argument": "/"
      }
    ]
  ],
  "behaviors": [
    {
      "type": "set_waf",
      "attributes": {
        "waf_id": 12349,
        "mode": "blocking"
      }
    }
  ]
}
```

Then create the rule from the file:

```bash
azion create firewall-rule --firewall-id <firewall-id> --file rule.json
```

```text
Created Firewall Rule with ID 123457
```

The output reports the id of the new rule.

</Fragment>

<Fragment slot="panel.api">

Save the rule as `rule.json`, with the id of your rule set in `waf_id`:

```json
{
  "name": "Apply storefront-waf",
  "active": true,
  "criteria": [
    [
      {
        "conditional": "if",
        "variable": "${request_uri}",
        "operator": "starts_with",
        "argument": "/"
      }
    ]
  ],
  "behaviors": [
    {
      "type": "set_waf",
      "attributes": {
        "waf_id": 12349,
        "mode": "blocking"
      }
    }
  ]
}
```

Send a `POST` request to the firewall's request rules endpoint, with the file as the body:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules \
  --header 'Accept: application/json' \
  --header 'Authorization: Token [TOKEN VALUE]' \
  --header 'Content-Type: application/json' \
  --data @rule.json
```

The API answers `202` and returns the rule with two keys it assigned: an empty `description` and the `order` the rule holds among the rules of that firewall.

</Fragment>

</Tabs>

:::note[Note]
`criteria` is a list of lists, and a rule carries at most one `Set WAF` behavior. `mode` is required on that behavior: a `set_waf` behavior sent without it is refused with `400` and the error `10059 Required Field`, pointing at `/data/behaviors/0/attributes/mode`. Key the criterion on `${request_uri}`, not on the query string. An empty variable does not match, so `${request_args}` with the `matches` operator and `.*` skips every request carrying no query string, including a `POST` whose payload sits entirely in the body.
:::

## Apply a rule set to selected paths in Logging

A rule set can score only the paths that need it, such as a login form or an API, and start in _Logging_. _Logging_ scores, records, and serves each request, so the records show what the rule set flags on your own traffic before it refuses anything. The rule matches the paths, not the query string, because a form posts its fields in the body. The example creates the rule set `auth-waf`, with every threat family at `medium`, and applies it to `/login`, `/signup`, and `/checkout`. A single criterion on `/` matches every request. Replace each value with your own.

<Tabs client:visible sharedStore="interface">
<Fragment slot="tab.console">Console</Fragment>
<Fragment slot="tab.api">API</Fragment>

<Fragment slot="panel.console">

To create the rule set and apply it:

<DocSteps>
  <DocStep title="Create the rule set">

  Access [Azion Console](https://console.azion.com/) > **Edge Libraries** > **WAF Rules**, select **+ WAF Rule**, enter `auth-waf` as the **Name**, keep every family at _Sensitivity Medium_, and select **Save**.

  </DocStep>
  <DocStep title="Create the rule">

  In the firewall's **Rules Engine** tab, select **+ Rule** and enter `auth - apply auth-waf`.

  </DocStep>
  <DocStep title="Match the three paths">

  In the **Criteria** section, select `Request Uri`, _starts with_, and `/login`. Add two criteria joined by **Or**: `/signup` and `/checkout`.

  </DocStep>
  <DocStep title="Add the Set WAF behavior">

  In the **Behaviors** section, select **Set WAF**, then `auth-waf` and _Logging_.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

</Fragment>

<Fragment slot="panel.api">

To create the rule set, send the body of the [WAF quickstart](/en/documentation/platform/firewall/waf/quickstart/) with `"name": "auth-waf"`, to `POST https://api.azion.com/v4/workspace/wafs`. The API answers `202` with the rule set's `id`. To apply it:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules \
  --header 'Authorization: Token <personal-token>' \
  --header 'Content-Type: application/json' \
  --data '{
  "name": "auth - apply auth-waf",
  "active": true,
  "criteria": [
    [
      { "variable": "${request_uri}", "conditional": "if", "operator": "starts_with", "argument": "/login" },
      { "variable": "${request_uri}", "conditional": "or", "operator": "starts_with", "argument": "/signup" },
      { "variable": "${request_uri}", "conditional": "or", "operator": "starts_with", "argument": "/checkout" }
    ]
  ],
  "behaviors": [{ "type": "set_waf", "attributes": { "waf_id": <waf-id>, "mode": "logging" } }]
}'
```

The API answers `202` with a `state` of `pending` and the rule as it was stored.

</Fragment>
</Tabs>

Requests to the three paths are scored for attack payloads, and what would be blocked is recorded. Move the rule to _Blocking_ once 3 days of **Tuning** hold no request that should have been served, as [Switch a rule set to blocking](/en/documentation/guides/application-security/firewall-and-waf/switch-to-blocking/) describes.

To confirm the rule scores the paths, send an injection-shaped query string to one of them:

```bash
curl -i "https://www.example.com/login?q=1%27%20OR%20%271%27%3D%271"
```

In _Logging_, the page loads. After the switch to _Blocking_, the same request receives:

```text
HTTP/2 400
```

The response's `x-azion-request-id` finds the request's WAF record. For the lookup, refer to [Find the WAF score of a blocked request](/en/documentation/guides/application-security/firewall-and-waf/how-to-find-waf-score/).

In the [Protect web applications from OWASP Top 10 and zero-day attacks](/en/documentation/use-cases/secure-applications-and-networks/protect-web-applications-from-owasp-top-10-and-zero-day-attacks/) use case, this section takes these values:

| Setting | Value |
| --- | --- |
| Rule | `webapp - apply webapp-waf` |
| Criterion | `Request Uri` _starts with_ `/` |
| Behavior | **Set WAF** with `webapp-waf`, in _Logging_. The API requires the mode, sent as `"mode": "logging"` |

The rule set scores every request the use case's network rule lets through, and records what would have been blocked. To read those records and turn a false positive into an exception, refer to [Tune a WAF rule set](/en/documentation/guides/application-security/firewall-and-waf/tune-waf/).

In the [Protect public APIs from abuse](/en/documentation/use-cases/secure-applications-and-networks/protect-public-apis-from-abuse/) use case, this section takes these values:

| Setting | Value |
| --- | --- |
| Rule | `api - apply api-waf` |
| Criterion | `Request Uri` _starts with_ `/v1/` |
| Behavior | **Set WAF** with `api-waf`, in _Logging_, sent in the API as `"mode": "logging"` |

Every request to `/v1/` is scored against `api-waf`, and what would be blocked is recorded.

The [Block account takeover on login and checkout flows](/en/documentation/use-cases/secure-applications-and-networks/block-account-takeover-on-login-and-checkout-flows/) use case uses the values of this example.

In the [Protect web applications from OWASP Top 10 and zero-day attacks](/en/documentation/use-cases/secure-applications-and-networks/protect-web-applications-from-owasp-top-10-and-zero-day-attacks/) use case, expect:

- **WAF scores an attack pattern.** From an address that is not listed, a request with an injection-shaped query string, `https://www.example.com/?q=1%27%20OR%20%271%27%3D%271`, is answered as usual in _Logging_, and receives `HTTP/2 400` after the switch to _Blocking_. The response's `x-azion-request-id` finds the request in the `workloadEvents` dataset of Real-Time Events, where `wafMatch` names the internal rules that matched, `1009` and `1013` for this query string. For the lookup, refer to [Find the WAF score of a blocked request](/en/documentation/guides/application-security/firewall-and-waf/how-to-find-waf-score/).

In the [Protect public APIs from abuse](/en/documentation/use-cases/secure-applications-and-networks/protect-public-apis-from-abuse/) use case, expect:

- **WAF scores an attack pattern.** With a valid token, a request with an injection-shaped query string, `https://api.example.com/v1/orders?q=1%27%20OR%20%271%27%3D%271`, is answered as usual in _Logging_, and receives `HTTP/2 400` after the switch to _Blocking_. Its `x-azion-request-id` finds the record in Real-Time Events.

These checks confirm the [Block account takeover on login and checkout flows](/en/documentation/use-cases/secure-applications-and-networks/block-account-takeover-on-login-and-checkout-flows/) use case.

In the [Prepare regulated web applications for security audits](/en/documentation/use-cases/secure-applications-and-networks/prepare-regulated-web-applications-for-security-audits/) use case, expect:

- **Attack patterns are filtered.** Send `https://www.example.com/?q=1%27%20OR%20%271%27%3D%271`. With the WAF rule in _Blocking_, the response is `400`.
