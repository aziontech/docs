An HTTPS connection starts with a handshake in which the server presents a certificate whose names cover the hostname the client asked for. A server that also checks its clients needs the certificate of the authority that signs their certificates.

[Certificate Manager](/en/documentation/platform/certificate-manager/) is a Platform Resource that stores the certificates a [Workload](/en/documentation/platform/workloads/) uses for Transport Layer Security (TLS). The handshake, step by step, is under [Request path](/en/documentation/platform/certificate-manager/#request-path), and how Azion obtains a Let's Encrypt certificate is on [Issuance and renewal](/en/documentation/platform/certificate-manager/issuance-and-renewal/). The sections cover what Certificate Manager stores, how a Workload binds a certificate, and the cost of storing certificates apart from the Workload.

---

## What Certificate Manager stores

Certificate Manager stores two kinds of certificate, server and Trusted CA, plus certificate revocation lists, and it creates certificate signing requests.

A server certificate is a TLS certificate for your own domains. The Workload presents it in the handshake to prove it holds a hostname. You upload it with its private key, or Azion requests it from Let's Encrypt and renews it for you.

A domain of your own needs a server certificate, because the Azion SAN certificate, Azion's own, covers only the workload domain and the `azion.app` hostname. For example, a Workload reached only on its workload domain serves HTTPS with nothing stored in Certificate Manager. Once `www.example.com` joins that Workload's domains, it needs a server certificate that covers it.

A Trusted CA certificate is the certificate of a certificate authority (CA) that you trust to sign client certificates. A Workload with mutual TLS (mTLS) on checks each client certificate against it, and [mTLS](/en/documentation/platform/workloads/mtls/#verification-modes) describes how the `enforce` and `permissive` modes treat each client. A certificate revocation list (CRL) is the list of certificates that a CA revoked before their expiration date, signed by that CA.

A certificate signing request (CSR) is the request you submit to a CA to obtain a certificate of your own. Certificate Manager creates the CSR and generates its private key, which Azion keeps and the API never returns. For the fields of each object, refer to [Certificates](/en/documentation/platform/certificate-manager/certificates/).

## Certificate binding

A certificate in Certificate Manager reaches no traffic until you bind it to a Workload, in the Workload field meant for its kind:

- A server certificate goes in [`tls.certificate`](/en/documentation/platform/workloads/settings/#tls).
- A Trusted CA certificate goes in [`mtls.config.certificate`](/en/documentation/platform/workloads/settings/#mtls).
- CRLs go in `mtls.config.crl`.

The API refuses a certificate sent in the field meant for the other kind. With `tls.certificate` set to `null`, the Workload presents the Azion SAN certificate instead. Once bound, a certificate acts during the TLS handshake, before a Firewall or an Application sees the request. For the refusal and its fix, refer to [Troubleshoot Workloads](/en/documentation/platform/workloads/troubleshooting/#a-certificate-is-refused-in-a-workload-setting).

The status of an uploaded certificate shows whether any Workload uses it. It reads `inactive` until you bind it to a Workload, and `active` from then on. For every status value, refer to [Statuses](/en/documentation/platform/certificate-manager/certificates/#statuses).

## Certificates stored apart from the Workload

Certificate Manager keeps each certificate apart from the Workload, so replacing one leaves the Workload's other settings untouched. For example, swapping an uploaded certificate before it expires changes one value, `tls.certificate`, and the old entry stays in Certificate Manager until you delete it.

The price of that split is two separate checks, one per entity. The API does not compare a certificate's names with the Workload's domains, so it accepts a certificate that does not cover them. That mismatch surfaces only when a client checks the names, as a failed handshake.

Binding a certificate is also a Workload change, and it takes several minutes to reach all of Azion's distributed infrastructure. Until then, some data centers serve the old configuration and others the new one, as [Propagation](/en/documentation/platform/workloads/how-it-works/#propagation) describes.
