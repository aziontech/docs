A DNS change reaches your users only after every cache that holds the old answer lets it go. The order of your changes decides how long that takes.

A domain delegated before its records exist is unavailable to every user at once. A name looked up before it answers, even a few seconds after its record is saved, is answered `NXDOMAIN` for up to 1 hour. A long time to live (TTL) keeps an old address in resolvers after you replace it.

These practices apply to the zones and records of [Edge DNS](/en/documentation/platform/edge-dns/) in Azion Console, the Azion CLI, and the Azion API. A saved record needs no deployment step. A new name can take about a minute to answer on every nameserver, and a changed record can take a few minutes. The cache behind that delay is on [How Edge DNS works](/en/documentation/platform/edge-dns/how-it-works/#caching-and-propagation), and every field is on [Zones and records](/en/documentation/platform/edge-dns/zones-and-records/).

In order, the practices cover the records to check, the nameservers to delegate to, and the TTL before a change. They then cover the first query for a name, the apex record, retiring a weighted record, and CNAME targets. Last, they cover DNSSEC support at the top-level domain (TLD) and turning DNSSEC off.

---

## Query every record at Azion's nameservers before you delegate

Delegation sends every resolver on the internet to Azion's nameservers at once. A record missing from the zone at that moment is missing for every user, and the service it points to becomes unavailable. Azion's nameservers answer a zone before any registrar delegates it.

Before you delegate, create the zone and add every record the domain serves. Then ask `ns1.aziondns.net` for each one:

<Code client:visible lang="bash" code={`dig +short @ns1.aziondns.net www.example.com A`} />

```text
192.0.2.1
```

Run the same query for each name and type the domain uses, such as the MX and TXT records of `example.com`. Send each first query about a minute after the save, as [Wait about a minute after you create a name before you query it](#wait-about-a-minute-after-you-create-a-name-before-you-query-it) explains. The cost is lead time: a new zone also takes about a minute to answer, so create it well before the registrar change. For the steps, refer to [Create, edit, or delete a zone](/en/documentation/guides/application-security/dns/edge-dns-configure-main-settings/).

To check it, compare each answer with what the domain's current nameservers return for the same query.

## Delegate the domain to all three nameservers

A delegation lists the nameservers that a resolver may ask for the domain. A resolver never asks a nameserver that the registrar does not list, so each Edge DNS nameserver left out is one server fewer to ask.

Each name sits under its own TLD, so copy the names instead of typing them. Enter each one as its own nameserver at your registrar:

```text
ns1.aziondns.net
ns2.aziondns.com
ns3.aziondns.org
```

The API returns the three names in the zone's `nameservers` field, and [Zones and records](/en/documentation/platform/edge-dns/zones-and-records/#nameservers-and-soa) shows where Azion Console lists them. The cost is a step outside Azion: public resolvers reach the zone only after the registrar publishes the delegation, on the registrar's schedule. For the full migration, refer to [Migrate nameservers to Azion](/en/documentation/guides/platform/migration/migrate-ns-to-azion/).

To check it, ask a public resolver such as `8.8.8.8` for a name in the zone. Once the delegation is published, it returns what `ns1.aziondns.net` returns.

## Lower the TTL a few days before a planned change

A resolver keeps an answer for the TTL that the answer carried. After a change, it can serve the old value until that TTL runs out. A lower TTL shortens the window in which outdated answers are served.

For a zone that still runs at another provider, lower the TTL there a few days before you delegate. In Edge DNS, a few days before a planned change, such as another address, lower the TTL of the records it touches:

<Code client:visible lang="bash" code={`azion update dns-record --zone-id <zone-id> --record-id <record-id> --ttl 300`} />

```text
DNS record 100214 was updated
```

The lower TTL is itself a change, and Azion's nameservers serve it within about 5 minutes. Resolvers pick it up only once the old TTL, 3,600 seconds by default, runs out. The cost is query volume: resolvers ask more often, and each query counts toward your Edge DNS usage, as [Pricing](/en/documentation/fundamentals/pricing/#edge-dns) shows. Raise the TTL again once the change is done.

To check it, run `dig @ns1.aziondns.net www.example.com A` 5 minutes after the change: the answer carries a TTL of `300` or less.

## Wait about a minute after you create a name before you query it

Each Azion nameserver answers a new name within about a minute of the save, and a query that reaches it earlier is answered `NXDOMAIN`. That nameserver keeps the `NXDOMAIN` for 1 hour, the start of authority (SOA) minimum, unlike a cached value, which refreshes within about 5 minutes.

A new type on an existing name, such as an MX record at the apex, gets an empty `NOERROR` for the same hour. Resolvers that asked keep their own negative answer for up to the same hour.

Wait about a minute after you save a new name, or a new type on an existing name, before its first query. Keep monitoring tools and scripts from polling the name during that minute. The cost is that wait in every setup that creates a name. For how the negative answer is cached, refer to [How Edge DNS works](/en/documentation/platform/edge-dns/how-it-works/#caching-and-propagation).

To check it, confirm that each name's first query comes a minute or more after its save.

## Use an ANAME record at the apex, not a CNAME

The apex of a zone, `@`, already holds the SOA and NS records that Azion writes. A CNAME blocks every other type on its name, so the API refuses a CNAME named `@` with `19005`. An ANAME record points the apex at an Azion hostname and is answered with the target's addresses.

The apex keeps its MX and TXT records next to the ANAME record. A `POST` to `/v4/workspace/dns/zones/<zone-id>/records` with this body serves `example.com` from a [Workload](/en/documentation/platform/workloads/):

```json
{
  "name": "@",
  "type": "ANAME",
  "rdata": ["<your-workload>.map.azionedge.net"],
  "ttl": 20
}
```

Keep `ttl` at `20`: any other value, including the default of `3600`, is refused with `19011`. The cost is reach: an ANAME target is a name under `azioncdn.net`, `azionedge.net`, or `azionedge.com` only. For its rules, refer to [Record types](/en/documentation/platform/edge-dns/record-types/#aname), and for the steps, to [Point an apex domain with ANAME](/en/documentation/guides/application-security/dns/access-root-domain/).

To check it, run `dig @ns1.aziondns.net example.com A`: the answer holds A records with a TTL of `20` and no CNAME.

## Set a weight of 0 before you delete a weighted record

Weighted records share one name and type, and each answer carries the value of one record, chosen in proportion to its weight. A weight of `0` keeps a record in the zone and never answers it. That takes the value out of rotation and lets you bring it back by restoring the weight. The same weights let you send a small share of answers to a value you introduce before it takes all of them.

Before you delete a weighted record, set its weight to `0`. The record keeps its *Weighted* policy, so the flag needs no `--policy`:

<Code client:visible lang="bash" code={`azion update dns-record --zone-id <zone-id> --record-id <record-id> --weight 0`} />

```text
DNS record 100189 was updated
```

In the API, the same change is a `PATCH` with `{"weight":0}`. Delete the record once the other values carry the traffic.

The cost is time: Azion's nameservers apply the new weight within the record's TTL or about 5 minutes, whichever is shorter. Resolvers that cached the record's value then keep it for the TTL they received. For how the weights choose an answer, refer to [How Edge DNS works](/en/documentation/platform/edge-dns/how-it-works/#record-policies), and for the steps, to [Weight records to balance traffic](/en/documentation/guides/application-security/dns/load-balance-dns/).

To check it, wait 5 minutes after the change, then run `dig +short @ns1.aziondns.net lb.example.com A` across several minutes: the value with weight `0` never appears.

## Point each CNAME at the final hostname

A resolver that gets a CNAME repeats the lookup with the hostname the CNAME points to. When that hostname is another CNAME, each alias in the chain adds a step before the resolver reaches an address.

When the target is a name in the same zone, Edge DNS returns the CNAME and the target's records in one response. For example, a query for `blog`, a CNAME with the value `www.example.com`, gets the CNAME and the A record of `www`. A target outside the zone costs the resolver another lookup for each alias.

Point each CNAME at the hostname that holds the address, not at another alias. The cost is upkeep: when that hostname changes, every CNAME that names it changes too, where a chain needed one edit. For the rules of a CNAME, refer to [Record types](/en/documentation/platform/edge-dns/record-types/#cname).

To check it, run `dig @ns1.aziondns.net blog.example.com A`: the answer holds one CNAME followed by the address.

## Confirm that the TLD supports DNSSEC before you turn it on

DNSSEC signatures protect a domain only when validating resolvers trust the zone's keys. That trust comes from the delegation signer (DS) record that your registrar and the domain's TLD registry publish. A TLD registry that does not support DNSSEC cannot publish the DS record, so no resolver validates a signed zone under that TLD.

Before you plan on DNSSEC for a domain, confirm that its TLD registry supports it. The cost is an inquiry outside Azion, because the API does not check whether the TLD supports DNSSEC. The DNSSEC status of a zone reads `ready` once Azion signs it, whether or not any registry can publish the DS record. For the four values of the DS record, refer to [DNSSEC](/en/documentation/platform/edge-dns/dnssec/#ds-record).

To check it, confirm with your registrar that it accepts a DS record for the domain.

## Remove the DS record before you turn DNSSEC off

While the registrar publishes a DS record for the domain, or resolvers still cache it, validating resolvers expect signed answers. Turning DNSSEC off first removes the signatures within about 5 minutes, while that DS record is still trusted, and the domain can fail validation. Turning it back on does not end the failures at once, as [How Edge DNS works](/en/documentation/platform/edge-dns/how-it-works/#dnssec) explains.

Before you turn DNSSEC off, remove the DS record at your registrar and wait for it to expire from resolver caches. Only then turn DNSSEC off for the zone:

<Code client:visible lang="bash" code={`azion update dnssec --zone-id <zone-id> --enabled=false`} />

```text
DNSSEC of DNS zone 1234 was updated
```

The cost is time: the zone stays signed during the wait, with no DS record to validate it. For the steps in every interface, refer to [Turn on DNSSEC for a zone](/en/documentation/guides/application-security/dns/activate-dnssec/#turn-dnssec-off).

To check it, run `azion describe dnssec --zone-id <zone-id>`: it prints `Enabled: false`, while `Status` keeps reading `ready`.
