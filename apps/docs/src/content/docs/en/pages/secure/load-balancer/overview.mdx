**Load Balancer** is a Platform Resource that balances requests across the addresses of a [Connector](/en/documentation/platform/connectors/) of type `http`, on Azion's distributed infrastructure. A [load balancer](https://www.azion.com/en/learning/performance/what-is-load-balancing/) is a proxy in front of servers with the same content, and its balancing method picks the server for each request. Use Load Balancer to stay available when an origin fails, favor larger servers, keep a standby origin, or pin each client IP to one server.

## Request path

Turning on Load Balancer changes no rule: a Connector still receives only the requests of the [Application](/en/documentation/platform/applications/) rules that set it. Load Balancer then chooses which address of that Connector receives each one.

The diagram follows a request that a rule sends to a Connector of type `http` with Load Balancer on. Solid arrows carry the request, and dotted arrows carry the response. Each label starts with the number of its step in the list after the diagram.

```mermaid
flowchart TD
  Client(["Client"])
  App["Application"]
  Conn["Connector"]
  LB["Load Balancer"]
  Primary[["primary origin server"]]
  Backup[["backup origin server"]]
  Client -->|"1. request"| App
  App -->|"1. Set Connector"| Conn
  Conn -->|"2. request"| LB
  LB -->|"3. chosen address"| Primary
  LB -->|"4. every primary fails"| Backup
  Primary -.->|"5. response"| Conn
  Backup -.->|"5. response"| Conn
  Conn -.->|"5. response"| App
  App -.->|"5. response"| Client
```

1. An Application receives the client request, which goes to the Connector that a _Set Connector_ rule sets. The criteria of that rule, such as the path, decide which requests are balanced.
2. Load Balancer takes the request and considers only the active addresses of the Connector. An inactive address, with `active` set to `false`, stays on the Connector and leaves the rotation.
3. The balancing method, _Round Robin_, _Least Connections_, or _IP Hash_, chooses a primary address, and the weight of each address shapes that choice. The Connector sends the request there with the same `Host` header, path prefix, and protocol as for every address.
4. When the connection fails, the Connector tries again as many times as `max_retries` allows. A backup address receives requests only when every primary address fails.
5. The origin server answers the Connector, and the response returns through the Application to the client.

For how each method chooses an address, and how the weight and the server role change the result, refer to [Balancing methods](/en/documentation/platform/connectors/load-balancer/balancing-methods/).
