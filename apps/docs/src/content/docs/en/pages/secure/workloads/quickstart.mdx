This guide instructs you through forwarding requests to your [Application](/en/documentation/platform/applications/) from your first [Workload](/en/documentation/platform/workloads/).

- Create a Workload on the production infrastructure.
- Set the Application you already have in the Workload's deployment.
- Send a request to the workload domain and get your Application's response.

You create a Workload and its deployment:

1. **Workloads** is a Platform Resource that receives the requests sent to your domains, as their entry point, on Azion's distributed infrastructure. Azion gives each Workload a workload domain, a hostname of the form `<id>.map.azionedge.net`. The Workload answers on that hostname once its deployment propagates, before you own or point any domain.
2. The **deployment** of the Workload sets your Application. A Workload holds at most one deployment.

After it receives a request, the Workload forwards the request to the Application that this Workload's deployment sets. That Application runs its rules on the request. Your Application already exists, and the Workload adds nothing to it.

This guide keeps the defaults of a new Workload: the production infrastructure, the default Transport Layer Security (TLS) settings, ports `80` and `443`, and no domain of your own.

The Workload this guide leaves you with is the starting point for two more quickstarts. With [Certificate Manager](/en/documentation/platform/workloads/#certificate-manager), you bind a certificate to the Workload. With [Custom Pages](/en/documentation/platform/workloads/#custom-pages), you set a custom page set in the Workload's deployment to replace error responses.

[DDoS Protection](/en/documentation/platform/workloads/#ddos-protection) is a Feature of the Azion Platform that mitigates denial-of-service attacks on every Workload. It is always on, and it needs no activation or configuration.

## Create the Workload

A new Workload runs on the production infrastructure, and Azion generates its workload domain at creation. The infrastructure cannot change after creation, so a Workload created on staging cannot move to production later. The workload domain stays reachable while `workload_domain_allow_access` is `true`, the default. In Azion Console, that setting is the **Workload Domain Allow Access** switch.

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

In Azion Console, one form creates the Workload and its deployment together. The **Application** field of **Deployment Settings** sets your Application in the deployment, and **Save** requires it.

To create the Workload in Azion Console:

<DocSteps>
  <DocStep title="Open the Workloads page">

  Access [Azion Console](https://console.azion.com/) > **Workloads**.

  </DocStep>
  <DocStep title="Start a new Workload">

  Select **+ Workload**. The **Create Workload** page opens.

  </DocStep>
  <DocStep title="Name the Workload">

  Enter a name for the Workload, such as `my-workload`.

  </DocStep>
  <DocStep title="Select the production infrastructure">

  In **Infrastructure**, select _Production Infrastructure (All Edge Locations)_.

  </DocStep>
  <DocStep title="Keep the workload domain open">

  In **Domains**, keep **Workload Domain Allow Access** turned on.

  </DocStep>
  <DocStep title="Select your Application">

  In **Deployment Settings**, select your Application in **Application**. Leave **Firewall** and **Custom Page** empty.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

Azion Console shows the message "Your Workload has been created. After propagation the domain will be available in the Workload URL. You also can add a custom domain." To copy the workload domain that you send the request to, select **Copy Workload URL**. The message closes after a few seconds, and the **Workload Domain** column of the Workloads list also shows the workload domain. The Workload exists, and its deployment sets your Application.

</Fragment>

<Fragment slot="panel.api">

### API

To create the Workload with the API, send a `POST` request to the workloads endpoint. `infrastructure` set to `1` selects the production infrastructure, and `workload_domain_allow_access` set to `true` keeps the workload domain open. Replace `[TOKEN VALUE]` with your personal token:

<Code client:visible lang="bash" code={`curl --request POST \\
  --url https://api.azion.com/v4/workspace/workloads \\
  --header 'Accept: application/json' \\
  --header 'Authorization: Token [TOKEN VALUE]' \\
  --header 'Content-Type: application/json' \\
  --data '{
  "name": "my-workload",
  "active": true,
  "infrastructure": 1,
  "workload_domain_allow_access": true
}'`} />

The API answers with `202`. The response carries the defaults of the new Workload and the workload domain Azion assigned to it:


## Set your Application in the deployment

After it receives a request, the Workload forwards the request to the Application that this Workload's deployment sets. The deployment can also set the [Firewall](/en/documentation/platform/firewall/) that inspects requests first and the custom page set that replaces error responses. A Workload holds at most one deployment, and a second one is refused. Until the Workload has a deployment that sets an Application, its workload domain answers `404`.

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

The **Create Workload** form already created the deployment, so **Application** shows your Application. A Workload created with the API or Azion CLI has no deployment yet, and **Application** stays empty until you select your Application and save the Workload.

To check or set the Application in Azion Console:

<DocSteps>
  <DocStep title="Open the Workloads page">

  Access [Azion Console](https://console.azion.com/) > **Workloads**.

  </DocStep>
  <DocStep title="Open your Workload">

  Select the Workload you created. The **Edit Workload** page opens.

  </DocStep>
  <DocStep title="Select your Application">

  In **Deployment Settings**, if **Application** is empty, select your Application in it.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

Azion Console shows the message "Your workload has been updated". The deployment of the Workload sets your Application.

</Fragment>

<Fragment slot="panel.cli">

### CLI

To set your Application, create the Workload's deployment with the Azion CLI. Replace `<workload-id>` with the ID of the Workload and `<application-id>` with the ID of your Application:

<Code client:visible lang="bash" code={`azion create workload-deployment --workload-id <workload-id> --name my-deployment --application-id <application-id>`} />

The command prints the ID of the new deployment:

```text
Created Workload Deployment with ID <deployment-id>
```

To check which Application the deployment sets, list the deployments of the Workload with their details:

<Code client:visible lang="bash" code={`azion list workload-deployment --workload-id <workload-id> --details`} />

The `EDGE APPLICATION` column shows the ID of your Application:

```text
ID              CURRENT  EDGE APPLICATION  EDGE FIREWALL
<deployment-id> true     <application-id>  0
```

The deployment of the Workload sets your Application. A project that declares the Workload in `azion.config.js` gets its deployment from `azion deploy` instead, through the [`deployments`](/en/documentation/devtools/cli/azion-config-js/#workload-deployments) entry.

</Fragment>

<Fragment slot="panel.api">

### API

The published Azion API v4 reference has no deployment endpoint, so you create the deployment with the Azion CLI. In Azion Console, the **Application** field of the Workload's **Deployment Settings** also sets your Application.

Replace `<workload-id>` with the ID of the Workload and `<application-id>` with the ID of your Application:

<Code client:visible lang="bash" code={`azion create workload-deployment --workload-id <workload-id> --name my-deployment --application-id <application-id>`} />

The command prints the ID of the new deployment:

```text
Created Workload Deployment with ID <deployment-id>
```

The deployment of the Workload sets your Application.

</Fragment>

</Tabs>

## Send a request to the workload domain

The check is the same whichever interface created the Workload. In the commands, replace `<your-workload-domain>` with the workload domain of the Workload you created, of the form `<id>.map.azionedge.net`.

A new Workload answers with your Application only once its deployment propagates across Azion's distributed infrastructure. That takes several minutes, with no guaranteed duration. Until then, the workload domain answers `404` with Azion's HTML error page. While the deployment propagates, answers to the same request can alternate between that `404` and your Application's response. Repeat the request until your Application answers. For more information, refer to [Propagation](/en/documentation/platform/workloads/how-it-works/#propagation).

Before the deployment propagates, a `HEAD` request receives `404` and the headers of Azion's error page:

<Code client:visible lang="bash" code={`curl -sI https://<your-workload-domain>/`} />

```text
HTTP/2 404
server: nginx
date: <date>
content-type: text/html
x-azion-request-id: <request-id>
x-azion-edge-location: <edge-location>
```

The `x-azion-request-id` header identifies the request. Once the deployment propagates, send a request to the root path of your workload domain:

<Code client:visible lang="bash" code={`curl -i https://<your-workload-domain>/`} />

The response is the one your Application returns for `/`: its status, its headers, and its body. Your Workload receives the requests sent to its workload domain and forwards them to your Application.
