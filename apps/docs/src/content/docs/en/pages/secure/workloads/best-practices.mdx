The entry point of a site decides who can reach it and whether a connection is trusted. Mistakes there rarely surface as an error in your code. A change tried on live traffic reaches every visitor at once. An address you forgot stays open to anyone who finds it. A certificate that expires stops protecting traffic on the day it lapses.

These practices apply to a [Workload](/en/documentation/platform/workloads/), the hostnames and Transport Layer Security (TLS) settings it holds, and the certificates it uses. The mechanisms behind them are on [How Workloads works](/en/documentation/platform/workloads/how-it-works/), and every field is on [Workload settings](/en/documentation/platform/workloads/settings/).

A change to a Workload takes several minutes to reach all of Azion's distributed infrastructure, with no guaranteed duration. Meanwhile, requests can receive the old or the new configuration, as [Propagation](/en/documentation/platform/workloads/how-it-works/#propagation) describes. Every check on this page holds only once repeated requests agree.

The first four practices apply to every Workload: test a change on a staging Workload before production, close the workload domain once your own domain serves traffic, use permissive mutual TLS (mTLS) only to test, and make sure every client application sends Server Name Indication (SNI). The practices for the certificates a Workload uses follow, under Certificate Manager.

## Test a change on a staging Workload before production

A staging Workload is a Workload created on the staging infrastructure, with `infrastructure` set to `2` in the API. It runs on the staging network, apart from the production network, so a mistake there reaches no visitor of your site. It answers only on its workload domain, `<id>.preview.azionedge.net`, because a staging Workload takes no custom domain. The cost is a second Workload with its own deployment, which you keep in step with production yourself. The infrastructure is fixed at creation, so a tested configuration reaches production as a new Workload, not as an edit of the staging one. For the same choice in Azion Console, refer to [Workload settings](/en/documentation/platform/workloads/settings/#infrastructure).

This file, sent with `azion create workload --file`, creates a staging Workload through `"infrastructure": 2`. Its other values are the defaults of a production Workload. Copy the values of your own production Workload instead, so that staging tests the same configuration.

<Code client:visible lang="json" code={`{
  "name": "my-workload-staging",
  "active": true,
  "infrastructure": 2,
  "tls": { "certificate": null, "ciphers": 7, "minimum_version": "tls_1_3" },
  "protocols": { "http": { "versions": ["http1", "http2", "http3"], "http_ports": [80], "https_ports": [443], "quic_ports": [443] } },
  "domains": [],
  "workload_domain_allow_access": true
}`} />

The CLI answers `Created Workload with ID <workload-id>`, and `azion describe workload --workload-id <workload-id> --format json` reads back a `workload_domain` that ends in `.preview.azionedge.net`. To try a production hostname before its Domain Name System (DNS) records change, list it on a production Workload. Then map the hostname to the workload domain's address in your hosts file, as [Test an application through the hosts file](/en/documentation/guides/application-development/getting-started/stage-applications-through-hosts-file/) describes.

## Close the workload domain once your own domain serves traffic

By default, a Workload also answers on its workload domain, the `<id>.map.azionedge.net` address Azion generates. The `workload_domain_allow_access` field controls that access, and Azion Console calls it **Workload Domain Allow Access**, as [Workload settings](/en/documentation/platform/workloads/settings/#domains) shows. Setting it to `false` leaves the hostnames in `domains` as the only way in, so every client arrives by a name you chose to list. The cost is a dependency on those hostnames.

:::caution
The API refuses this change on a Workload whose `domains` list is empty. It answers `When the workload hostname access is blocked, the workload requires alternate domains or domains.` Add a hostname first.
:::

Send this body with `azion update workload --file`, which reads the Workload ID from the `"id"` key:

<Code client:visible lang="json" code={`{
  "id": <workload-id>,
  "workload_domain_allow_access": false
}`} />

The CLI answers `Updated Workload with ID <workload-id>`. Once the change propagates, a request to the workload domain answers `404`, while your own domains keep serving. Set the field to `false` only after your own hostnames answer everywhere, so that clients always have a hostname that works. To point your domain at the Workload first, refer to [Point a domain to a workload](/en/documentation/guides/platform/migration/point-domain-to-azion/).

## Use permissive mTLS only to test

Mutual TLS ([mTLS](/en/documentation/platform/workloads/mtls/)) is a TLS handshake in which the client also presents a certificate. The Workload then checks that a certificate authority (CA) you trust signed that certificate. In `enforce` mode, a client without such a certificate fails the handshake. In `permissive` mode, the handshake completes, so a Firewall rule that tests the Client Certificate Validation variable must refuse the client. Without that rule, a permissive Workload admits the clients that mTLS was meant to refuse.

Use `permissive` to test access under specific conditions, and serve production with `enforce`, as in this body for `azion update workload --file`:

<Code client:visible lang="json" code={`{
  "id": <workload-id>,
  "mtls": {
    "enabled": true,
    "config": { "certificate": <trusted-ca-id>, "crl": [<crl-id>], "verification": "enforce" }
  }
}`} />

To check the mode in force, send a request with no client certificate. In `enforce`, the handshake fails and curl exits with code `56`:

<Code client:visible lang="bash" code={`curl -skv https://<your-domain>/ -o /dev/null`} />

For the Firewall rule a permissive Workload needs, refer to [Verification modes](/en/documentation/platform/workloads/mtls/#verification-modes). For the steps, refer to [Configure mTLS on a workload](/en/documentation/guides/application-security/tls-and-certificates/associate-an-mtls-certificate/).

## Make sure every client application sends SNI

Server Name Indication (SNI) is the TLS extension in which a client names the host it wants during the handshake. Every domain served with a certificate bound to the Workload, uploaded or from Let's Encrypt, relies on it. A connection without SNI reaches Azion's default configuration, which presents the Azion SAN certificate instead of yours. That is Azion's own certificate, with Azion hostnames listed as Subject Alternative Names (SAN), such as `*.map.azionedge.net` and `*.azion.app`. On a Workload with mTLS in `enforce` mode, Azion closes such a connection before it reaches your application, and the client receives no response.

The setting lives in each client, such as a partner's API client or a service that calls your Workload, so Azion cannot add it for them. Confirm with the owner of every client application that its TLS library sends the hostname it calls as the server name. If a client with a valid certificate never reaches your application, check first whether it sends SNI. For the rest of the mTLS requirements, refer to [mTLS](/en/documentation/platform/workloads/mtls/#requirements).

## Certificate Manager

[Certificate Manager](/en/documentation/platform/workloads/#certificate-manager) is a Platform Resource that stores the certificates a Workload uses for TLS. It stores the server certificates that Workloads present to clients and the Trusted CA certificates that verify client certificates in mTLS. It also requests and renews Let's Encrypt certificates. The practices in this section are to replace a server certificate before it expires, keep the challenge record of a domain hosted outside [Edge DNS](/en/documentation/platform/edge-dns/), choose a domain-validated certificate unless you need more, limit DNS-01 credentials to the challenge records, and keep wildcard certificates off critical production systems.

### Replace a server certificate before it expires

A server certificate you upload does not renew itself, and once its `validity` date passes, it no longer protects traffic. Switching while the old certificate is still valid leaves time to confirm that the new one works, and to switch back if it does not. The old entry stays in Certificate Manager after the switch, so the cost is one more certificate to delete. Azion renews the Let's Encrypt certificates it manages, as [Issuance and renewal](/en/documentation/platform/workloads/certificate-manager/issuance-and-renewal/) describes.

Upload the new certificate, then point `tls.certificate` at its ID with `azion update workload --file`. Keep `ciphers` and `minimum_version` at the values the Workload already holds, so the certificate is the only value that changes:

<Code client:visible lang="json" code={`{
  "id": <workload-id>,
  "tls": { "certificate": <new-certificate-id>, "ciphers": 7, "minimum_version": "tls_1_3" }
}`} />

The CLI answers `Updated Workload with ID <workload-id>`. `azion list digital-certificate --details` then shows the new certificate as `active`, and the old one as `inactive` once no Workload uses it. When the new certificate is `active` and the change has propagated, delete the old entry. For the upload itself, refer to [Upload a digital certificate](/en/documentation/guides/application-security/tls-and-certificates/digital-certificates/).

### Keep the challenge record of a domain hosted outside Edge DNS

Azion renews a managed Let's Encrypt certificate before it expires by running its challenge again. When the zone of a DNS-01 certificate's domain is in [Edge DNS](/en/documentation/platform/edge-dns/), Azion writes the `_acme-challenge` record itself. When the zone is hosted at another DNS provider, you add a canonical name (CNAME) record, `_acme-challenge.<your-domain>`, that points to `<your-domain>.letsencrypt.azion.com`. Deleting that CNAME later makes the next renewal fail, and the certificate then expires.

Keep the CNAME at your provider for as long as a Workload uses the certificate. Renewal starts 30 days before the 90-day validity ends. To check, confirm before then that the CNAME still exists, and that the certificate's status in Certificate Manager is not `failed`. For the record to create, refer to [Request a Let's Encrypt certificate](/en/documentation/guides/application-security/tls-and-certificates/how-to-generate-a-lets-encrypt-certificate/).

### Choose a domain-validated certificate unless you need more

The certificate authority that issues a certificate you upload validates the request at one of three levels. Domain Validation (DV) confirms your right to use the domain. Organization Validation (OV) adds checks on the requesting organization, and Extended Validation (EV) asks for documents that prove its physical, legal, and operational existence.

Use DV in most cases. OV and EV are more complex to obtain, and the extra checks buy assurance about your organization, not about the domain. Order OV or EV only when a requirement you can name asks for those checks. For the three levels, refer to [Validation levels](/en/documentation/platform/workloads/certificate-manager/certificates/#validation-levels).

### Limit DNS-01 credentials to the challenge records

This practice applies when you obtain a certificate yourself, with an Automatic Certificate Management Environment (ACME) client such as Certbot, for a zone hosted outside Edge DNS. A Let's Encrypt certificate that Azion manages needs none of it: the one CNAME of [Keep the challenge record of a domain hosted outside Edge DNS](#keep-the-challenge-record-of-a-domain-hosted-outside-edge-dns) is enough. Your client writes the `_acme-challenge` record at the DNS provider, so it holds the provider's API credentials. Credentials that reach every record give whoever obtains them control of the domain and all of its records.

Restrict those credentials to `_acme-challenge` records, so that a leak exposes only the challenge. The cost is a separate credential to create and keep for that client alone. To check, confirm at your provider that the credential's permissions name only `_acme-challenge` records.

### Keep wildcard certificates off critical production systems

A wildcard certificate, such as one for `*.example.com`, covers the subdomains of `example.com`, such as `blog.example.com`, with one private key. If that key leaks, or the certificate is revoked, every subdomain it covers is affected at once. A wildcard certificate fits when:

- Centralized management is a priority.
- The same team manages the subdomains.
- A well-defined reverse proxy architecture exists.
- Your security policies allow controlled key sharing.

Under stricter requirements, give each critical production system its own certificate, keep separate certificates for development environments, and leave the wildcard to lower-criticality services. The cost is one replacement per certificate instead of one for all. Keep a wildcard's private key in Certificate Manager, bound to Workloads, rather than spread across servers: once saved, the key cannot be read back from Azion Console or the API. To check, list the Workloads that use each wildcard certificate with `GET /v4/workspace/workloads?digital_certificate_id=<certificate-id>`, and give any critical production Workload a certificate of its own.
