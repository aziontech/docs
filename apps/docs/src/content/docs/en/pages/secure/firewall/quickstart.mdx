This guide instructs you through denying your first request with a [Firewall](/en/documentation/platform/firewall/).

- Create a Firewall that starts with its default settings.
- Add a rule that denies every request to one path.
- Set the Firewall on the deployment of the [Workload](/en/documentation/platform/workloads/) that serves your [Application](/en/documentation/platform/applications/).
- Send a request to that path and read the `403` it returns.

Four parts turn a request into a decision, and each part leads to the next:

1. The **Firewall** holds the rules. It is active from the moment you create it.
2. The **rule** on that Firewall pairs a criterion with a behavior. The criterion selects requests, and the behavior decides what happens to them. In this guide, the criterion selects every path that starts with `/deny-test`, and the behavior denies the request.
3. The **deployment** of the Workload that serves your Application sets that Firewall, beside the Application.
4. The **request** to the Workload's domain meets the rule, and a denied request never reaches your Application.

A Firewall inspects nothing on its own. Until a Workload's deployment sets it, no request reaches its rules.

[Network Shield](/en/documentation/platform/firewall/network-shield/), [Web Application Firewall (WAF)](/en/documentation/platform/firewall/waf/), and [Bot Manager](/en/documentation/platform/firewall/bot-manager/) are nested Platform Resources of Firewall. Network Shield matches requests by source, WAF detects attacks, and Bot Manager detects automated clients. The quickstart of each one starts from a Firewall that a Workload's deployment sets, and this guide leaves you with one.

## Create the Firewall

A new Firewall holds no rules, and it starts active. A Firewall accepts a rule only while WAF, Network Shield, or [Functions](/en/documentation/platform/firewall/functions/) is turned on. A new Firewall starts with Network Shield and Functions turned on, so the default settings accept the Deny rule of this guide.

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

To create the Firewall in Azion Console:

<DocSteps>
  <DocStep title="Open the Firewalls page">

  Access [Azion Console](https://console.azion.com/) > **Firewalls**.

  </DocStep>
  <DocStep title="Start a new Firewall">

  Select **Firewall**. The **Create Firewall** page opens.

  </DocStep>
  <DocStep title="Name the Firewall">

  In the **General** section, enter a **Name**. For example: `storefront-firewall`.

  </DocStep>
  <DocStep title="Leave the other sections as they open">

  In **Modules**, **Functions** and **Network Shield** open turned on, and **Web Application Firewall** opens turned off. In **Status**, **Active** stays turned on.

  </DocStep>
  <DocStep title="Select Create" />
</DocSteps>

Azion Console shows the message "Your Firewall has been created" and opens the Firewall. Its tabs are **Main Settings**, **Functions Instances**, and **Rules Engine**. **Functions Instances** appears only while **Functions** is turned on.

</Fragment>

<Fragment slot="panel.cli">

### CLI

To create the Firewall with the Azion CLI:

```bash
azion create firewall --name "storefront-firewall" --active true
```

The command prints the ID of the new Firewall:

```text
Created Firewall with ID 12352
```

The Firewall is active, with Functions and Network Shield turned on and WAF turned off. Record the ID. The rule passes it as `--firewall-id`.

</Fragment>

<Fragment slot="panel.api">

### API

To create the Firewall with the API, send a `POST` request to the firewalls endpoint. Replace `[TOKEN VALUE]` with your personal token:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/firewalls \
  --header 'Accept: application/json' \
  --header 'Authorization: Token [TOKEN VALUE]' \
  --header 'Content-Type: application/json' \
  --data '{"name": "storefront-firewall"}'
```

The API answers with `202`. This excerpt of the response shows the new Firewall and the settings it starts with:

```json
{
  "state": "pending",
  "data": {
    "id": 12353,
    "name": "storefront-firewall",
    "modules": {
      "ddos_protection": { "enabled": true },
      "functions": { "enabled": true },
      "network_protection": { "enabled": true },
      "waf": { "enabled": false }
    },
    "debug": false,
    "active": true,
    …
    "product_version": "2.0",
    …
    "version": 0
  }
}
```

The Firewall is active, and `waf` is the one entry in `modules` that starts turned off. Record the `id`. The rule passes it as `<firewall-id>`.

</Fragment>

</Tabs>

## Add a rule that denies one path

A [Rules Engine for Firewall](/en/documentation/platform/firewall/rules-engine/) rule pairs criteria with behaviors. The rule in this stage carries one criterion, a request URI that starts with `/deny-test`, and one behavior, Deny. Deny refuses the request with `403 Forbidden`.

The criterion matches every path that begins with `/deny-test`, so `/deny-test/page` matches too. For more information, refer to [Deny (403 Forbidden)](/en/documentation/platform/firewall/rules-engine/#deny-403-forbidden).

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

To add the rule in Azion Console:

<DocSteps>
  <DocStep title="Open the Firewall">

  Access [Azion Console](https://console.azion.com/) > **Firewalls**, and select the Firewall you created.

  </DocStep>
  <DocStep title="Select the Rules Engine tab" />
  <DocStep title="Start a new rule">

  Select **Rule**. The **Create Rule** drawer opens.

  </DocStep>
  <DocStep title="Name the rule">

  In the **General** section, enter a **Name**. For example: `Deny the test path`.

  </DocStep>
  <DocStep title="Set the criterion">

  In the **Criteria** section, the first criterion opens on _Request Uri_ and _starts with_. Enter `/deny-test` as its argument.

  </DocStep>
  <DocStep title="Select the Deny behavior">

  In the **Behaviors** section, select _Deny (403 Forbidden)_.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

Azion Console shows the message "Rule successfully created". The rule appears in the **Rules Engine** list with the status _Active_.

</Fragment>

<Fragment slot="panel.cli">

### CLI

`azion create firewall-rule` reads the whole rule from a JSON file. `criteria` is a list of groups, and the first criterion of a group carries the conditional `if`. Save this rule as `rule.json`:

```json
{
  "name": "Deny the test path",
  "active": true,
  "criteria": [
    [
      {
        "variable": "${request_uri}",
        "conditional": "if",
        "operator": "starts_with",
        "argument": "/deny-test"
      }
    ]
  ],
  "behaviors": [
    { "type": "deny" }
  ]
}
```

Create the rule. Replace `<firewall-id>` with the ID of your Firewall:

```bash
azion create firewall-rule --firewall-id <firewall-id> --file rule.json
```

The command prints the ID of the new rule:

```text
Created Firewall Rule with ID 123460
```

The rule is active on the Firewall.

</Fragment>

<Fragment slot="panel.api">

### API

The request body is the rule itself. `criteria` is a list of groups, and the first criterion of a group carries the conditional `if`. Save this rule as `rule.json`:

```json
{
  "name": "Deny the test path",
  "active": true,
  "criteria": [
    [
      {
        "variable": "${request_uri}",
        "conditional": "if",
        "operator": "starts_with",
        "argument": "/deny-test"
      }
    ]
  ],
  "behaviors": [
    { "type": "deny" }
  ]
}
```

Send a `POST` request to the rules of your Firewall. Replace `<firewall-id>` with the ID of your Firewall:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules \
  --header 'Accept: application/json' \
  --header 'Authorization: Token [TOKEN VALUE]' \
  --header 'Content-Type: application/json' \
  --data @rule.json
```

The API answers with `202`. This excerpt of the response shows the new rule's `id` and its `order` among the rules of the Firewall:

```json
{
  "state": "pending",
  "data": {
    "id": 123459,
    …
    "behaviors": [{ "type": "deny" }],
    "description": "",
    "order": 0
  }
}
```

The API assigns `order` in creation order, starting at `0`. The rule is active on the Firewall.

</Fragment>

</Tabs>

## Set the Firewall on your Workload's deployment

A Firewall has no domain of its own, and the Workload carries the domain. The deployment of a Workload sets three things: the Application, the Firewall, and the custom page. Keep the Application and the custom page your Workload uses today, and set your Firewall beside them. Until the deployment sets your Firewall, the Deny rule matches no request.

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

To set the Firewall in Azion Console:

<DocSteps>
  <DocStep title="Open the Workloads page">

  Access [Azion Console](https://console.azion.com/) > **Workloads**.

  </DocStep>
  <DocStep title="Open your Workload">

  Select the Workload that serves your Application. Its edit form opens.

  </DocStep>
  <DocStep title="Select the Firewall">

  In the **Firewall** field of **Deployment Settings**, select the Firewall you created. **Application** and **Custom Page** keep what the Workload serves today.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

The deployment of your Workload sets your Firewall, beside its Application and its custom page.

</Fragment>

<Fragment slot="panel.cli">

### CLI

The Azion CLI has no command that updates a deployment, and a Workload holds one deployment only. To set the Firewall on the deployment your Workload already has, follow the Console panel. To create the deployment of a Workload that has none, refer to [Azion CLI workload-deployment](/en/documentation/devtools/cli/resources/workload-deployment/).

</Fragment>

<Fragment slot="panel.api">

### API

The published Azion API v4 reference has no endpoint for the deployment of a Workload. To set the Firewall, follow the Console panel.

</Fragment>

</Tabs>

## Confirm that the path answers 403

The check is the same whichever interface built the Firewall. Your Workload answers on its workload domain, of the form `<id>.map.azionedge.net`, written in this stage as `<your-workload-domain>`.

A Workload whose deployment newly sets a Firewall can take several minutes to enforce its first rule, and no duration is guaranteed. While the change spreads, answers to the same request alternate between the earlier response and the new one. Send the request again until it answers `403`. For more information, refer to [Propagation](/en/documentation/platform/firewall/how-it-works/#propagation).

Send a request to the denied path:

```bash
curl -i https://<your-workload-domain>/deny-test
```

The Firewall refuses it with `403`:

```text
HTTP/2 403
server: nginx
date: Thu, 01 Jan 2026 12:00:00 GMT
content-type: text/html; charset=utf-8
x-content-type-options: nosniff
x-azion-request-id: 0123456789abcdef0123456789abcdef
x-azion-edge-location: <edge-location>
alt-svc: h3=":443"; ma=86400
```

The response also carries a long `content-security-policy` header, omitted from this excerpt. The body is Azion's default error page, headed Forbidden, and it lists your IP address and the request ID. No header names the Firewall or the rule that refused the request.

Requests to every other path do not match the rule, and your Application answers them as before. Your Firewall denies every request whose path starts with `/deny-test`.
