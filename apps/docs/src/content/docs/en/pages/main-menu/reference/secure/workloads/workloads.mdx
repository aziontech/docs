**Workloads** is a Platform Resource that receives the requests sent to your domains, as their entry point, on Azion's distributed infrastructure. An entry point is the configuration that answers a site's hostnames, holds a certificate for each, and terminates their HTTPS connections. Use Workloads to put an [Application](/en/documentation/platform/applications/) on your own domain, serve that domain over HTTPS, or try a configuration on staging before production.

Each Workload has these features:

- [DDoS Protection](/en/documentation/platform/workloads/ddos-protection/ddos-mitigation/) mitigates floods of attack traffic before they reach your Workloads and the Applications behind them. For a defense aimed at one specific attack, you add custom rules to a Firewall.
- [Mutual TLS (mTLS)](/en/documentation/platform/workloads/mtls/) lets a Workload refuse, in `enforce` mode, every client without a certificate from a certificate authority you trust. It suits an API that partner systems call, such as one that must meet Open Banking requirements.

## Request path

Creating a Workload serves no request: a request reaches an Application only once that Workload's deployment sets that Application. A deployment is the part of a Workload that sets the Application and, optionally, a [Firewall](/en/documentation/platform/firewall/) and a custom page set. Until the deployment propagates, the workload domain, the hostname Azion generates for the Workload, answers `404` with Azion's HTML error page.

Solid arrows carry the request, and dotted arrows carry what goes back to the client. Each label starts with the number of the step it belongs to.

```mermaid
  DNS -.->|"1. Azion address"| Client
  Client -->|"2. traffic"| DDoS
  DDoS -->|"2. identified as an attack"| Blocked
  DDoS -->|"2, 3. request and TLS handshake"| WL
  WL -.->|"3. handshake refused"| Client
  WL -->|"4. deployment sets a Firewall"| FW
  WL -->|"4. no Firewall"| App
  FW -->|"4. allowed"| App
  FW -.->|"4. blocked"| Client
  App -->|"5. request"| Conn
  Conn -->|"5. fetch"| Origin
  Origin -.->|"5. response"| Conn
  Conn -.->|"5. response"| App
  App -.->|"5. response"| Client
  Conn -.->|"6. covered status code"| CP
  CP -.->|"6. custom page"| Client
```

1. The client looks up the hostname, and DNS returns an address of Azion's distributed infrastructure. A custom domain, a domain of your own listed on the Workload, reaches that address through a CNAME record that points at the workload domain.
2. In the data center the client reaches, DDoS Protection inspects the traffic before the Workload sees it, and Azion mitigates the traffic it identifies as an attack. The Workload that lists the hostname receives the rest.
3. On an HTTPS connection, the Workload completes the Transport Layer Security (TLS) handshake with its certificate, its minimum TLS version, and its cipher suite. The certificate is Azion's own or one you bind from [Certificate Manager](/en/documentation/platform/certificate-manager/). With mTLS on, the Workload also checks the client certificate in this handshake and can refuse it.
4. When the deployment sets a Firewall, the Firewall's rules evaluate the request before the Application and can block that request. With no Firewall, the request goes straight to the Application.
5. The Application that the deployment sets runs its rules on the request. When a rule sets a [Connector](/en/documentation/platform/connectors/), that Connector routes the request to your origin. The response returns through the Application to the client.
6. When the Connector answers with an error status code that the deployment's custom page set covers, the client receives the custom page from [Custom Pages](/en/documentation/platform/custom-pages/) in place of that response.

Every hostname of a Workload reaches the Application, Firewall, and custom page set that its deployment sets. For each step of the path and its tradeoff, refer to [How Workloads works](/en/documentation/platform/workloads/how-it-works/).
