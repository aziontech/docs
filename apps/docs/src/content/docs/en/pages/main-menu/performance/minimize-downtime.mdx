Downtime comes from two places: the switch that brings traffic to Azion, and an origin that stops answering later. You avoid the first by finishing the setup before the DNS change. You limit the second with a backup origin, an expired copy from cache, and your own error page.

---

## Prerequisites

- A workload, an application, and a connector on Azion. To set them up, refer to [Migrate an application to Azion](/en/documentation/fundamentals/migrate-to-azion/).
- Access to the DNS records of the domain at your DNS provider.

---

## Go live without a gap

Users notice only the DNS change, so everything else comes first:

<DocSteps>
  <DocStep title="Bind a certificate to the workload">

  In the workload's **Digital Certificate** field, select a certificate that covers the custom domain. Without it, HTTPS fails as soon as the domain resolves to Azion.

  </DocStep>
  <DocStep title="Enter the custom domain on the workload">

  In **Subdomain** and **Domain**, enter the host name users type.

  </DocStep>
  <DocStep title="Test through the hosts file">

  Load the application from your own computer before any user does. For the steps, refer to [Test an application through the hosts file](/en/documentation/guides/application-development/getting-started/stage-applications-through-hosts-file/).

  </DocStep>
  <DocStep title="Point the domain last">

  At your DNS provider, point the CNAME record at the workload domain. For the steps, refer to [Point a domain to a workload](/en/documentation/guides/platform/migration/point-domain-to-azion/).

  </DocStep>
</DocSteps>

Users reach the application on Azion as their resolvers pick up the change. Until then, the previous provider keeps answering them, so keep it running through the propagation.

## Keep answering when an origin fails

[Load Balancer](/en/documentation/platform/connectors/load-balancer/), a module of the connector, spreads requests across several origin addresses. A connector holds one address until Load Balancer is on. An address with the _Backup_ server role stands by, and it receives requests only when every _Primary_ address fails. To add a backup origin:

<DocSteps>
  <DocStep title="Open the connector">

  Access [Azion Console](https://console.azion.com/) > **Connectors** > **your connector**.

  </DocStep>
  <DocStep title="Turn on Load Balancer">

  In **Modules**, turn on **Load Balancer**.

  </DocStep>
  <DocStep title="Choose the balancing method">

  In **Load Balancer Configuration**, set **Method** to _Round Robin_ or _Least Connections_. _IP Hash_ refuses a backup address.

  </DocStep>
  <DocStep title="Select Add Address" />
  <DocStep title="Enter the backup address">

  In the new **Address**, enter the address of the backup origin.

  </DocStep>
  <DocStep title="Set its role">

  Set its **Server Role** to _Backup_.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

When every primary address fails, requests go to the backup address. The connector retries a failed connection as many times as **Max Retries** allows, and the Console fills in `3` when you turn on Load Balancer. With Load Balancer on, a connector holds up to 15 addresses. For every bound, refer to [Connectors limits](/en/documentation/platform/connectors/limits/#load-balancer).

:::note
To take an origin out for maintenance, turn off **Active** on its address in **Address Management**. The address keeps its role and weight, and it stops receiving requests as the change reaches each data center. For more information, refer to [Active addresses](/en/documentation/platform/connectors/load-balancer/balancing-methods/#active-addresses).
:::

## Answer from cache while the origin recovers

A cache setting with **Stale cache** on lets Azion serve an expired copy when the origin fails, instead of an error. The Console turns it on when you create a setting; the API and the CLI leave it off. To check it:

<DocSteps>
  <DocStep title="Open the cache settings">

  Access [Azion Console](https://console.azion.com/) > **Applications** > **your application** > **Cache Settings** tab.

  </DocStep>
  <DocStep title="Open the cache setting the application uses, or select + Cache to create one" />
  <DocStep title="Turn on Stale cache" />
  <DocStep title="Select Save" />
</DocSteps>

While the origin is down, requests for content Azion has already cached are answered with the last copy.

## Show your own page instead of an error

When the origin fails for content that is not in cache, a custom page set replaces the 5xx response with a page you host. Serve that page from a connector that stays up when the origin fails, such as an [Object Storage](/en/documentation/platform/object-storage/) bucket. To create the set:

<DocSteps>
  <DocStep title="Open Custom Pages">

  Access [Azion Console](https://console.azion.com/) > **Custom Pages**.

  </DocStep>
  <DocStep title="Select + Custom Page" />
  <DocStep title="Add the page code">

  Select **+ Custom Page Code** and, in **Page Code**, select _503_.

  </DocStep>
  <DocStep title="Point it at your page">

  Select the **Connector** that serves the page and, in **Page Path**, enter its path. For example: `/errors/503.html`.

  </DocStep>
  <DocStep title="Set how long Azion keeps it">

  In **Response TTL**, enter the seconds the page stays in cache.

  </DocStep>
  <DocStep title="Select Save" />
  <DocStep title="Bind the set to the workload">

  Access **Workloads** > **your workload**. In **Deployment Settings**, select the custom page set, then select **Save**.

  </DocStep>
</DocSteps>

A 503 from the origin now returns your page. The status code stays 503 unless you set **Response Custom Status Code**.
