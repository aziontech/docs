**Firewall** is a Platform Resource that inspects the requests to your [Workloads](/en/documentation/platform/workloads/) before your [Application](/en/documentation/platform/applications/) receives them, on Azion's distributed infrastructure. A web firewall is a checkpoint in front of an application: it compares each request with rules and stops the requests they catch. A Firewall can match requests by source with [Network Shield](/en/documentation/platform/firewall/network-shield/), detect attacks with [Web Application Firewall (WAF)](/en/documentation/platform/firewall/waf/), and detect automated clients with [Bot Manager](/en/documentation/platform/firewall/bot-manager/). Use Firewall to deny a path or a hostname, limit each client's request rate, answer with a custom response, or run your own [Function](/en/documentation/platform/functions/).

Firewall offers these nested resources and features:

- [Network Shield](/en/documentation/platform/firewall/network-shield/) lets a rule decide by where a request comes from: a list of IP addresses and ranges, Autonomous System Numbers (ASNs), or countries. Use it to block known abusive networks, allow only your own networks, or block Tor exit nodes.
- [WAF](/en/documentation/platform/firewall/waf/) is a good fit when your Application takes input an attacker can abuse, such as a form or an API body. A rule applies it to the paths you choose, where it can log threats before it blocks them.
- [Bot Manager](/en/documentation/platform/firewall/bot-manager/) is a good fit when automation such as credential stuffing or scraping reaches an Application that also serves people. It runs as a Function on the Firewall, so a rule decides which requests it checks.
- [Functions for Firewall](/en/documentation/platform/firewall/functions/) lets a rule run your own JavaScript on a request, to deny it, drop it, answer it, or add headers. Use it when your protection logic needs more than the criteria and behaviors of a rule.

## Request path

Creating a Firewall protects nothing: a Firewall inspects only the requests of a Workload whose deployment sets it. A Firewall has no domain of its own, so several Workloads can share one, and each change to its rules reaches all of them.

```mermaid
flowchart TD
  Client(["Client"])
  WL["Workload"]
  FW["Firewall"]
  App["Application"]
  Client -->|"1. request"| WL
  WL -->|"1. request"| FW
  FW -.->|"3. Firewall answer"| Client
  FW -->|"4. request"| App
  App -.->|"5. response"| Client
```

1. A client requests a domain of a [Workload](/en/documentation/platform/workloads/), and the Workload's deployment sets the Firewall and the Application that serve it. The Firewall receives the request first.
2. The Firewall runs its rules in order. Each rule compares its criteria with the request, and a rule whose criteria do not match applies nothing.
3. A rule whose criteria match applies its behaviors. A behavior that stops the request, such as _Deny (403 Forbidden)_, answers the client or closes the connection, and no later rule runs. _Set WAF_ and _Run Function_ hand the request to WAF or to a [Function Instance](/en/documentation/platform/firewall/functions-instances/), and either one can stop it too.
4. A request that no rule stops reaches the Application, which never receives a request that a rule stopped.
5. The Application processes the request, and its response reaches the client.
