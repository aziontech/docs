The documentation covers two versions of the Azion Platform: API v4, the current version, and API v3, which is deprecated. These rules decide which pages exist in each version and how to name and link the page of an earlier version. They also set how a version leaves the documentation. The version select, the banner, and the frontmatter fields that render them are in [Components](/en/documentation/style-guide/components/#version-notices).

## Decide which versions a page covers

Most pages hold for every version and declare no version. Write one page per version only when the content differs between the versions.

| The content | Pages | Frontmatter |
| --- | --- | --- |
| Holds for every version, such as a concept, a Functions code sample, or a Platform Resource that did not change | One page | No `versions` field |
| Differs between versions for the same resource: the API model, a Console path, a field, or a name | One page per version | `versions` on each page, and `counterpart` naming the page of the other version |
| Exists in only one version, such as Workloads in API v4 or Domains in API v3 | One page | `versions` with that version, and `counterpart` naming the closest page of the other version |

- Never copy a page into an earlier version so that each version has one. A page that holds for both versions stays one page.
- Declare `versions` on the navigation tree when every page of a product shares it, as the Domains tree does. A page then declares only what differs from its tree.
- When only some steps of a guide differ, keep one guide that holds the steps for both versions. The `versionDualSteps` snippet goes at the end of its introduction.

## Name and place a page of an earlier version

A page of API v3 that has an API v4 counterpart takes the identity of that counterpart, with a version marker:

| Field | Rule | Example |
| --- | --- | --- |
| `permalink` | The permalink of the API v4 page, followed by `v3/` | `/documentation/platform/applications/v3/` |
| `namespace` | The namespace of the API v4 page, followed by `_v3` | `documentation_products_edge_applications_v3` |
| `title` | The title of the API v4 page, with no version suffix | `Applications` |
| File | Next to the API v4 page, in its folder or in a `v3/` folder inside it | `edge-application/v3/edge-application-v3.mdx` |

The Brazilian Portuguese page follows the same rules: its permalink is the permalink of the Brazilian Portuguese API v4 page followed by `v3/`, and its `namespace` is identical to the US English page.

- Give the page of an earlier version a different title only when that version names the resource differently. Domains in API v3 and Workloads in API v4 are an example. A deprecated name from [Documentation terminology](/en/documentation/style-guide/writing/terminology/#keep-deprecated-names-out-of-current-pages) stays out of the title in every version: an API v3 page about applications is titled Applications, not Edge Application.
- A resource that exists only in API v3 under its own name keeps its own permalink, with no marker. Domains is at `/documentation/platform/domains/`.
- Register the page in the navigation tree of its API v4 counterpart, in a row with `"hidden": true`. The page declares `versions: [v3]`, `stage: deprecated`, and `counterpart`.
- Some API v3 pages end in `-v3/` instead of `/v3/`. Write `/v3/` on every page you create. Moving an existing page to `/v3/` changes its URL, so it needs a redirect in the same change, as [Frontmatter](/en/documentation/style-guide/conventions/frontmatter/#set-the-permalink) requires.

## Link between versions

Each version reads as documentation of its own. The `counterpart` field is the only link from a page to its equivalent in the other version. The version select and the banner render it.

- Never write an aside, a sentence, or a snippet that announces the other version, such as "An earlier version of this page exists".
- Link inside the version. A page of API v3 links to pages of API v3 or to pages that hold for every version. A page of API v4 never links to a page of API v3.
- A page about the move between versions is the exception: [API v4 Migration](/en/documentation/fundamentals/api-v4-migration/) and [Migrate from provider v1.x to v2.0](/en/documentation/devtools/terraform/terraform-migration-v3-to-v4/) link to both versions in prose.
- To open a page that holds for every version in a given version, add `?api=v3` or `?api=v4` to the link. The select switches to that version and keeps it as the reader's choice. A page of a single version needs no parameter, because it opens in its own version.

## Mark deprecated content

The stage of a version or a feature comes from the `stage` field, never from the body. The stages and what each one commits Azion to are in [section 1.3 of the Terms of Service](/en/documentation/agreements/tos/#13-product-release-stages).

- **A deprecated version.** Every page of the version carries `stage: deprecated`, from its navigation tree or from its own frontmatter when it sits in a tree of another version.
- **A deprecated feature inside the current version.** When the feature has its own page, that page carries `stage: deprecated`. When the feature is a field or an option on a reference page, its entry names the replacement in one sentence, with no date.
- **The content of a deprecated page.** Correct what is wrong on it, and document no addition to it. A deprecated version receives no updates.
- **The shutdown date.** The date when a version shuts down appears only on [API v4 Migration](/en/documentation/fundamentals/api-v4-migration/), as [Numbers](/en/documentation/style-guide/formatting/numbers/) sets out.

## End support for a version

When a version reaches its end of life, its pages leave the documentation in one change, in US English and in Brazilian Portuguese:

- Remove every page of the version.
- Add a redirect for each removed permalink in the highest-numbered file of `apps/docs/redirects/en/` and `apps/docs/redirects/pt-br/`. The redirect goes to the page that `counterpart` names. A page without `counterpart` redirects to the page of the same resource in the remaining version, or to its parent page. Never redirect to the documentation home.
- Remove the steps of the version from every guide that holds steps for both versions, together with the `versionDualSteps` snippet.
- Remove the version from the list of platform versions in the code. Remove it also from every `versions` and `counterpart` field in the navigation trees and the frontmatter.
- Leave changelog entries and dated agreements as they are. They keep the version they shipped with, as [Documentation terminology](/en/documentation/style-guide/writing/terminology/#keep-historical-names-in-historical-documents) explains.

## Add a version before General Availability

A version that the documentation covers before it reaches General Availability follows the same rules. Its pages carry `stage: experimental` or `stage: preview`, and the pages of the current version keep their permalinks with no marker. The version select lists only the versions that the code declares, so adding a version is a code change before it is a content change.
