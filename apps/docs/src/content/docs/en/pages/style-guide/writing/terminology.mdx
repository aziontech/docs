## Use the official names

Every offering has one official name, and every page uses that name. The names come from Azion's official naming catalog, which Product Marketing maintains for all Azion content: documentation, the website, and sales material. The Overview page of each Platform Resource, the root of its section, reflects that catalog. This guide does not restate the current names, because a copy is wrong the day a name changes.

The catalog gives one name per offering. There is no separate marketing name and documentation name. The first mention can carry the full name with the abbreviation in parentheses, and every mention after it uses the abbreviation alone:

- Correct: `Web Application Firewall (WAF) inspects HTTP and HTTPS requests. Apply a WAF rule set to the firewall.`
- Incorrect: a second `Web Application Firewall (WAF)` on the same page.

Name the platform **Azion Platform**, or **Azion Web Platform** where the context calls for it. Never write `Azion Edge Platform`. In a possessive, the platform is a common noun, in lowercase: `Azion's platform`, never `Azion's Platform`.

## Keep deprecated names out of current pages

Azion renamed its offerings over time. The old names still appear in old pages, URLs, and directory names, so they can look current. Treat them as history, not as synonyms. A deprecated name does not change again, so this list does not go out of date the way a list of current names does:

| --- | --- |
| Edge Application | Applications |
| Edge Firewall | Firewall |
| Edge Connector | Connectors |
| Real-Time Manager | Console |
| Edge AI | AI Inference |

**Edge DNS** and **Edge Pulse** are current official names. The word *Edge* in them is not a sign of a deprecated name.

## Name the resource the reader works on

Azion describes what it offers with four terms. They are related concepts, not four levels of one hierarchy: a Platform Resource may or may not be a Product, and a Feature can belong to the Platform or to a Platform Resource.

| Term | Answers | Definition |
| --- | --- | --- |
| Platform | What is the integrated Azion experience? | Azion's distributed infrastructure, its integrated technology, and the interfaces to build, secure, and scale workloads, such as Console, the API, and the CLI |
| Product | What offering does Azion take to market? | A market offering made of one or more Platform Resources and Features that solves a customer problem, such as WAF or Object Storage |
| Platform Resource | What does the reader create or manage? | An identifiable entity that the customer creates, configures, operates, or manages, and that Console, the API, the CLI, or the documentation can reference, such as an application, a firewall, a function, or a bucket |
| Feature | What can the reader do or turn on? | A user-visible functionality of the Platform or of a Platform Resource, which a Product can include, such as custom firewall rules or DNSSEC |

Documentation uses the Platform Resource nomenclature. Product is a go-to-market term, used mainly in marketing and sales material, and the table defines it so the reader recognizes it there. A documentation page calls each section by its official name and calls the offering at the root of a section a Platform Resource, never a product: it names what the reader creates or manages, and it joins one Platform Resource to another with a verb. A page writes Product only as the class of a Product nested in a Platform Resource, per [State the class of an Azion element](#state-the-class-of-an-azion-element).

A Feature is always scoped, so state whether it applies to the Platform or to a Platform Resource. A field or an option on a Platform Resource is a setting, not a Feature.

**Applications**, **Firewall**, **Connectors**, **Workloads**, **Custom Pages**, and **Certificate Manager** are examples of Platform Resource types; the naming catalog holds the complete list. The thing the reader creates is an instance, lowercase: an application, a firewall, a connector.

Azion Console, the API, the CLI, the Terraform Provider, and Copilot are also Platform Resources. They are the ones the reader uses to reach the Platform, so a page can call them its interfaces: `Create the application in Console or with the API.`

- Correct: `Configure a firewall to protect the application.`
- Correct: the sidebar row that opens WAF inside Firewall reads `WAF`, never `Firewall WAF` or `Web Application Firewall`, because a label never repeats its parent.

## State the class of an Azion element

The sentence that defines an Azion element states its class: Platform Resource, Product, or Feature. `**Functions** is a Platform Resource that runs JavaScript code on Azion's distributed infrastructure.` A Feature carries its scope: `Tiered Cache is a Feature of Cache that…`.

The class follows the documentation's nomenclature, not the naming catalog's list of Products:

| The element | Its class on a page | Examples |
| --- | --- | --- |
| The root of a documentation section | Platform Resource, even when the catalog also lists it as a Product | Applications, Firewall, Functions, Object Storage, Workloads |
| Nested in a Platform Resource, and listed in the catalog as a Product | Product | WAF, Network Shield, Cache, Application Accelerator, Image Processor |
| Nested in a Platform Resource, and listed in the catalog as a Platform Resource | Platform Resource | Certificate Manager, Custom Pages, DDoS Protection |
| A functionality of the Platform or of a Platform Resource, in neither list | Feature, with its scope | Tiered Cache, custom firewall rules, DNSSEC |

- **Once per page, at the element's first definition.** That is the first sentence of an Overview, each entry of its resources section, the sentence of a concept page that introduces the element, a glossary row that defines it, and the first sentence of any other page that says what the element is.
- **A mention in passing carries no class.** `Create a firewall` and `Open the application` stay as they are. A changelog entry describes a change, not the element, and keeps the opening that [Changelog pages](/en/documentation/style-guide/content/changelog/) sets.
- **The class does not replace the concept.** The class says what the element is within Azion. The concept sentences after it still say what the class of thing is with any vendor: a reverse proxy is a server in front of your origins.
- **Brazilian Portuguese** writes the classes as `recurso da plataforma`, `produto`, and `feature`: `**Functions** é um recurso da plataforma que executa código JavaScript na infraestrutura distribuída da Azion.`

- Correct: `**Applications** is a Platform Resource that runs a reverse proxy on Azion's distributed infrastructure.`
- Incorrect: `Applications is a product.` The class is wrong.
- Incorrect: `Functions is a serverless product.` A market category replaces the class.

## Classify what lives inside a resource

The words *module* and *add-on* are retired. What a page used to call a module is a Product enabled on a resource, such as Application Accelerator, Image Processor, WAF, or Network Shield. It can also be a feature of a resource, such as Tiered Cache, or a function instantiated on an application or a firewall. The retirement covers the classification of an Azion offering, nothing else.

- Correct: `Web Application Firewall (WAF) is a Product that inspects the requests that reach a firewall. Apply a WAF rule set to the firewall.`
- Incorrect: `Firewall is a product that includes WAF.`
- Incorrect: `WAF is a Firewall module.`

*Modules* stays where the Console renders it, inside a click path: `In the **Modules** section, turn on Application Accelerator.` A JavaScript module, an ES module, and an API field such as `modules.application_accelerator` keep their names.

## Give a plural-form name a singular verb

A Platform Resource name names one thing, whatever its form. Applications, Functions, and Connectors each take a singular verb: `Applications caches content`, `Functions runs your code` — never `Applications cache`. Brazilian Portuguese agrees the same way: `Functions executa suas functions`, never `executam`.

## Lowercase the thing the customer builds

A Platform Resource name is capitalized. The thing a customer creates with them is a common noun, and it stays lowercase.

- Correct: `Use **Applications** to build your own applications.`
- Correct: `**Functions** runs your functions on Azion's distributed infrastructure.`
- Incorrect: `Deploy your first Application.`

The distinction keeps the type name meaningful. A page that capitalizes both leaves the reader unable to tell the type from the instance.

Tie the instance to its Platform Resource where it first appears. A page that moves from the Platform Resource to the thing the reader creates says so once, with a class noun, and then uses the lowercase instance alone. Without that sentence, *application* also reads as the customer's own app, the one on the origin.

- Correct: `An application is the object you create in Applications.`

## Keep historical names in historical documents

Changelogs, release notes, and dated agreements record what was true on the day of publication. These documents keep the names they shipped with. A Terms of Service from 2020 keeps the names that were correct in 2020.

Do not rename an offering in a historical document. An updated name rewrites the record and detaches the text from its date.

## Leave these terms in US English

The names of the Platform, Products, and Platform Resources are never translated. In Brazilian Portuguese, the instance the customer creates with a Platform Resource also keeps its US English name, in lowercase. That covers every instance whose name is the singular of its Platform Resource's name, such as an application, a function, a workload, a connector, or a firewall, and two objects with no Platform Resource of that name, the deployment and the bucket: `Functions executa suas functions`. Application and function take the feminine article, and the others the masculine: `a application`, `o workload`. A generic noun, such as rule, instance, certificate, or zone, is translated: `Crie uma regra na application`.

These terms are generic technical vocabulary, not Platform Resource names. They stay in US English in both languages:

`data center` · `serverless` · `on-premise` · `template` · `compliance` · `e-commerce` · `e-mail` · `keywords` · `meta description`

A translation creates a second name for a concept the reader already knows in US English. The documentation uses one term for one concept, on every page.

The strings `edge` and `edge computing` also stay untranslated where they already appear. That is guidance for translation, not permission to use them. New text names Azion's distributed infrastructure instead.

## Name the infrastructure

The platform runs on Azion's distributed infrastructure, never "on the global network". The physical site is a `data center`, never an edge location or a PoP. The unit of infrastructure inside a data center has no official name: write `the infrastructure in the data center`, never `node` or `edge node`. The network itself appears only as the Platform Resource **Our Network**.

Name the data center that serves the request, not a distance: `from the data center nearest to your user`, never `close to your users` or `near your users`. The nearest data center is chosen by latency, network conditions, and load, so never write `geographically closest`.
