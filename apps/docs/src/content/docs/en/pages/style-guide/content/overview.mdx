## Purpose

An Overview page is the root of a Platform Resource section. It states what the Platform Resource is, what it offers, and how a request reaches it, in that order and nothing else. It applies the [reference](/en/documentation/style-guide/content/reference/) base form.

Every Platform Resource has one. It is the page a reader lands on from search, from the sidebar, and from another Platform Resource that links to this one.

## When to use

- Write one Overview for every Platform Resource, as the first page of its section.
- Write it before any other page in that section. The Overview decides what the section is about.

Do not write an Overview when:

- The subject is a feature, such as Tiered Cache or custom firewall rules. That belongs in a [reference page](/en/documentation/style-guide/content/reference/) inside the Platform Resource section. A Platform Resource nested in another is not a feature: it can have an Overview page of its own, and the parent resource's Overview links it.
- The page would walk the reader through a task. That is a [how-to guide](/en/documentation/style-guide/content/how-to-guides/), linked from here.
- The page would only list links. That is a [navigation hub](/en/documentation/style-guide/content/navigation-hubs/).

## Register

Descriptive: 25 words per sentence, active voice, passive only when the actor is unknown. Tone: objective, factual, direct. [Sentence structure](/en/documentation/style-guide/writing/sentence-structure/) holds the rules.

## Structure

**Required components**

- **Definition block**: one paragraph of at most four sentences, each within the 25-word cap. First the Platform Resource: `**<Platform Resource>** is a <class> that <verb>s <what it does> <where it runs>.` That sentence names the resource, states its class, says where it runs in one phrase, and stands on its own. The class is `Platform Resource`, on the Overview of a section and on the Overview of a nested Platform Resource alike, per [Documentation terminology](/en/documentation/style-guide/writing/terminology/#state-the-class-of-an-azion-element). The sentence never leans on a concept the reader has not met yet, as "runs that code" does. Then the concept: one sentence saying what the class of thing is, for a reader who has never used one. When the Platform Resource does two or more things at the same level, the sentence that lists them takes this place. Then, only where other Platform Resources are nested in it, one sentence naming each of them, with its link and the job it does here. Last, one sentence naming the concrete jobs people use it for, in the reader's vocabulary, closing the block: `Use <Platform Resource> to handle A, run B, or serve C.` A bulleted benefit list is the weaker form of that sentence: it reads as a brochure and costs a screen.
- **The list**: what the Platform Resource offers, as part of the opening prose, right after the definition block and with no heading. One lead-in sentence names the Platform Resource and ends in a colon. Then one bullet per nested Platform Resource, then one per Feature or entity that has a page of its own in the section, such as Device Groups or a Function Instance.
- **CTAs**: a primary `DocButton` labeled **Quickstart**, on the left, and one with `kind="outlined"` labeled `<Platform Resource> reference`, on its right.
- **The mechanism**: where a request, an event, or a job crosses more than two objects before the Platform Resource runs, that chain as a `mermaid` diagram. A numbered walk of at most six items follows the diagram. Open with what the reader would otherwise assume wrong, and say in the same sentence what happens instead: `Creating a Function does not expose it: a request reaches it only through a Function Instance that a rule invokes.`
- **Closing**: `## Next steps`, a `DocCardGroup` indexed by what the reader wants to do: each card names the destination, and its copy is the intent (`Run your first one now.`). One card leads to the Limits page. With the list, the router links every page of the section.

The page keeps this order, and an Overview has no other section. It shows no code: the artifact lives on the Quickstart and on the reference page that documents it. The scope of the Platform Resource and its limits live on its Limits page, under `## Scope`, per [Reference pages](/en/documentation/style-guide/content/reference/).

## Rules

- **Never instruct.** No numbered steps, no procedures, no click-throughs, no code. An overview that instructs is a [quickstart page](/en/documentation/style-guide/content/quickstart/) filed wrong. A Console path inside a sentence counts too: state the setting instead, per [Word choice](/en/documentation/style-guide/writing/word-choice/#state-the-setting-not-the-path-outside-a-task).
- **No quality adjectives.** Say what the Platform Resource does and what it offers.
- **The title is the Platform Resource name, a noun.** Not "documentation", not a gerund.
- **Put the Platform Resource before the concept.** The first sentence states the class of the Platform Resource and what it does on Azion; the concept sentence follows it. Cover the Platform Resource name in the concept sentence: what remains must be true of any vendor's version of the thing.
- **Keep the definition block to four sentences.** It is where the reader decides whether to read on, and every sentence the decision does not need delays it. A fix inside the block replaces words. When it needs a new sentence, another one leaves.
- **Make every word of position agree with the request path.** `for`, `of`, `in front of`, `behind`, and `before` each imply an arrow. Draw the arrows the sentence implies and compare them with the diagram of the page. Say the direction with the verb: `processes the requests received by your Workloads`. `runs a reverse proxy for your Workloads` puts the Workloads behind the proxy, and the request goes the other way.
- **Choose a verb that covers everything the Platform Resource does.** When a Platform Resource does two or more things at the same level, the first sentence states the role they share and the next sentence lists them: `**Applications** is a Platform Resource that processes the requests received by your Workloads, from the data center nearest to your user. An Application can run serverless functions, act as a reverse proxy for your origins, or combine the two.` Test the sentence against the smallest configuration the documentation shows.
- **Name every nested Platform Resource in the block.** Where other Platform Resources are nested in it, one sentence of the definition block names each of them, with its link and its job here: `It can also store responses with Cache, unlock four capabilities for the cache and the rules with Application Accelerator, and transform images with Image Processor.` The names in that sentence are the nested Platform Resources of the list, with none missing. A job said with no name, such as `cache responses`, never tells the reader that Cache exists. A Feature is named in the list only.
- **List what the Platform Resource offers, in the opening prose.** The list continues the introduction: it has no heading, and the CTAs come after it. It always carries every nested Platform Resource, then every Feature or entity that has a page of its own in the section. A Feature of a nested Platform Resource is listed on that resource's Overview. A setting with no page of its own stays on the reference page.
- **Say what the reader uses each item for, not what it is.** The item's own page holds its definition and its class, and the list never repeats them. The first sentence opens on the item's name, linked to its page, and says what it lets the reader do in this Platform Resource, or when it is the right choice. Read side by side, the items name different jobs.
- **Keep each item to two sentences, about 40 words.** The first says what the reader uses it for here. The second says what the reader gets, a condition to meet first, or one example. How the item works, such as a parameter, a header, or a phase, stays on its own page. An item carries no class, no default state, no limit value, no Console path, no code block, and no second link. A literal in inline code, such as `POST`, is fine.
- **Read the definition as a reader from the market.** A developer who knows the vocabulary of other platforms reads a workload as what runs behind an entry point. When that reading says something untrue about Azion, reword the sentence so that it states the role or the direction. This is a way of reading, not a list of words to avoid.
- **Tell a relation between two Platform Resources forward.** The one that makes the connection is the subject, and the sentence runs in the order things happen: `An Application receives the requests of a Workload once that Workload's deployment sets that Application.` The sentence `An Application receives the requests of the Workloads whose deployment sets it.` starts at the end and leaves two pronouns that point backwards. In Brazilian Portuguese, the verb takes its object in full: `define essa Application`, never `a define`. On an Overview, the relation that invokes the Platform Resource is told once, at the start of the mechanism section, not in the definition block.
- **Choose the concept with care.** Several Azion elements do different things under one name. When one market concept fits everything the Platform Resource does, explain that concept. When none does, list the things in the market's words, and explain none of them in a sentence of its own.
- **Name the Platform Resource that provides a capability.** When another Platform Resource provides one of the things the block lists, the uses sentence names its instance, with its link: `Use Applications to run a Function, set the Connector that reaches each origin, add or remove headers, or rewrite requests.` The reader meets the market term in the list and the Azion name in the uses sentence.
- **Cut from the definition block what the reader does not need.** Four kinds of sentence go. The first is background the Platform Resource does not change, such as how a registry delegates a domain. The second is a step the reader already assumes, such as a proxy that opens its own connection to the origin. The third is a point the block already made. The fourth is a contrast with something the page does not cover, such as `A log is the opposite view.` Four more go too. A market term defined in a sentence of its own, such as `A reverse proxy is a server in front of your origin.`, goes to the Overview of the Platform Resource that provides it. The consequence of the generic concept, such as clients reaching a single domain, holds for any vendor. What the next section tells belongs to the mechanism, such as the relation that invokes the Platform Resource and the order of its rules. And a job named twice keeps one place. The uses sentence naming the Azion element that provides or carries a capability the list named, as `run a Function` after `run serverless functions`, is not a second naming.
- **A use says what this Platform Resource adds.** The uses sentence names the jobs this Platform Resource does that another one does not, and none that a nested Platform Resource does. On Functions, the use is "block requests with your own logic", because Firewall already blocks requests by rule. A security Platform Resource names the public standard its pages document, such as the OWASP Top 10.
- **Name the Platform Resource in the first sentence, and never open on the problem space.** A concept sentence explains a mechanism. A sentence about how important the problem is explains nothing.
- **Organize by the reader's questions.** The sections answer four questions, in order: what the Platform Resource is, what it offers, how a request reaches it, and where to go now. The list is the one place the offer is enumerated. An outline with one section per feature is a catalog: it answers "what do we sell" instead of "what am I deciding".
- **Keep the scope and the limits on the Limits page.** What the Platform Resource does not do, where one capability stops, and every limit value go under `## Scope` and the tables of its Limits page. The router links that page.
- **The questions shape the sections; they never become the headings.** A heading is a short noun phrase, never a question: `Request path`, not `How a request reaches your Application`.
- **Draw the diagram from the documented sequence.** A diagram of a sequence the documentation already states in prose is a change of notation, not a new fact. Every node and every arrow matches a step the Platform Resource performs, and the numbered walk carries the meaning if the figure does not render.
- **Send the reader to the [Quickstart](/en/documentation/style-guide/content/quickstart/)**, in the CTAs and again in the router.
- **Never drop the diagram to make the page shorter.** A page that runs long has grown a section the structure does not have: move its facts to the page that owns them.

## Examples

This excerpt of the **Applications** overview shows the opening prose, the definition block and the list, and leaves out the CTAs that follow it, the mechanism, and the router. Applications does two things at the same level and hosts three nested Platform Resources. The second sentence of the block lists the two things, and the third names the three. The list then says what the reader uses each nested Platform Resource and each Feature for, and leaves their definitions to their own pages:

```mdx
**Applications** is a Platform Resource that processes the requests received by your [Workloads](/en/documentation/platform/workloads/), from the data center nearest to your user. An Application can run serverless functions, act as a reverse proxy for your origins, or combine the two. It can also store responses with [Cache](/en/documentation/platform/applications/cache/), unlock four capabilities for the cache and the rules with [Application Accelerator](/en/documentation/platform/applications/application-accelerator/), and transform images with [Image Processor](/en/documentation/platform/applications/image-processor/). Use Applications to run a [Function](/en/documentation/platform/functions/), set the [Connector](/en/documentation/platform/connectors/) that reaches each origin, add or remove headers, or rewrite requests.

Each Application can use these nested resources and features:

- [Cache](/en/documentation/platform/applications/cache/) lets an Application answer a request with a copy of an earlier origin response, so the origin receives no request for it. For example, with stale cache on in the cache setting, an expired copy answers when your origin fails to.
- [Application Accelerator](/en/documentation/platform/applications/application-accelerator/) fits when one URL has more than one correct response, such as a personalized page or a `POST` response. With cache variation, Cache keeps one copy per value of a query-string argument, a cookie, the device group, or the request method.
- [Image Processor](/en/documentation/platform/applications/image-processor/) lets one image on your origin serve every size, crop, and format your pages request, such as WEBP. You store and upload only that one file.
- [Device Groups](/en/documentation/platform/applications/device-groups/) let an Application tell client devices apart, so a rule or a cache setting can treat each group differently. They need Application Accelerator on in the Application.
- [Rules Engine for Applications](/en/documentation/platform/applications/rules-engine/) is where you write what an Application does with each request. For example, two rules with two Connectors can route `/api/` to one server and every other path to another.
- [WebSocket Proxy](/en/documentation/platform/applications/websocket/) lets an Application carry a WebSocket connection between your users and your origin, for real-time applications such as chat. Azion turns it on for an account only on request.
- [Function Instances](/en/documentation/platform/applications/functions-instances/) let a rule run one of your Functions in an Application. The same Function can run in several Applications, each with arguments of its own.
```

A Platform Resource with one role and nothing nested has a definition block of three sentences. The first names the Platform Resource, states its class, and says what it does on Azion. The next one explains what a function is to a reader who has never used one, and the uses sentence closes the block:

```mdx
**Functions** is a Platform Resource that runs JavaScript code on Azion's distributed infrastructure, inside the request path of an [Application](/en/documentation/platform/applications/) or a [Firewall](/en/documentation/platform/firewall/). A function is [serverless](https://www.azion.com/en/learning/serverless/what-is-serverless/) code: a handler that the platform runs at each request, with no server for you to provision. Use Functions to build APIs, manipulate request and response headers, apply logic from request metadata, or block requests with your own logic.
```
