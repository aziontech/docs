You can score the requests that carry a chosen cookie against a second [Web Application Firewall (WAF)](/en/documentation/platform/firewall/waf/) rule set, which holds an exception, from Azion Console. Use it when signed-in users, or an integrated third-party tool, need a policy that the rest of your traffic does not. For one exception on a single rule set, refer to [Create a WAF exception](/en/documentation/guides/application-security/firewall-and-waf/configure-waf-allowed-rules/).

---

## Prerequisites

- A Firewall with WAF turned on. Refer to [Set a Firewall's main settings](/en/documentation/guides/application-security/firewall-and-waf/firewall-configure-main-settings/).
- A Workload whose deployment sets the Firewall and an Application that sends its requests to a Connector. WAF inspected requests only when the Application sent them to a Connector. Refer to [Set a Firewall on a Workload](/en/documentation/guides/application-security/firewall-and-waf/firewall-protect-your-domain/).
- The name and value of the cookie your origin issues.
- Access to [Azion Console](https://console.azion.com/). Refer to [Access Azion Console](/en/documentation/guides/platform/account-and-billing/how-to-access-azion-console/).

---

## Create the primary rule set

The primary rule set scores the requests that do not carry the cookie. To create it in Azion Console:

<DocSteps>
  <DocStep title="Open the WAF Rules page">

  Access [Azion Console](https://console.azion.com/) > **WAF Rules**.

  </DocStep>
  <DocStep title="Select WAF Rule" />
  <DocStep title="Name the rule set">

  In the **General** section, enter a **Name**. For example: `storefront-primary`.

  </DocStep>
  <DocStep title="Set the threat families">

  In the **Threat Type Configuration** section, set the sensitivity of each threat family.

  </DocStep>
  <DocStep title="Keep the Active switch turned on" />
  <DocStep title="Save the rule set" />
</DocSteps>

The rule set appears in **WAF Rules**. It scores no request until a rule of a Firewall applies it.

---

## Create the secondary rule set

The secondary rule set scores the requests that carry the cookie, with the same sensitivities as the primary one. To create it in Azion Console:

<DocSteps>
  <DocStep title="Select WAF Rule">

  On the **WAF Rules** page, start a second rule set.

  </DocStep>
  <DocStep title="Name the rule set">

  In the **General** section, enter a **Name**. For example: `storefront-cookie`.

  </DocStep>
  <DocStep title="Repeat the threat families of the primary rule set">

  In the **Threat Type Configuration** section, set each family to the sensitivity of the primary rule set.

  </DocStep>
  <DocStep title="Keep the Active switch turned on" />
  <DocStep title="Save the rule set" />
</DocSteps>

The two rule sets carry the same policy. The exception of the next section makes them differ.

---

## Add the cookie exception

An exception stops one internal rule from scoring one part of a request, and leaves the rule scoring everything else. Azion Console calls an exception an allowed rule. To add one to the secondary rule set:

<DocSteps>
  <DocStep title="Open the secondary rule set">

  In **WAF Rules**, select the rule set you created in the previous section.

  </DocStep>
  <DocStep title="Select the Allowed Rules tab" />
  <DocStep title="Select Allowed Rule" />
  <DocStep title="Select the rule to allow">

  In **Rule ID**, select the internal rule that your cookie trips. This example uses `1005`, `Possible SQL Injection attack: MySQL keyword (|) found in Body, Path, Query String or Cookies`.

  </DocStep>
  <DocStep title="Describe the exception">

  In **Description**, enter why this rule is allowed.

  </DocStep>
  <DocStep title="Leave the Path field empty">

  An empty **Path** covers every path. A **Path** of `/` did not cover requests to other paths in the observed runs.

  </DocStep>
  <DocStep title="Scope the exception to the Cookie header">

  In **Condition**, select _Specific HTTP Header Value_, then enter `cookie`, the name of the header, in the **Value** field.

  </DocStep>
  <DocStep title="Leave the Active switch of the Regex section off" />
  <DocStep title="Save the allowed rule" />
</DocSteps>

The allowed rule appears in **Allowed Rules**, with its **Rule ID**, **Description**, **Path**, **Conditions**, and **Status**. Every other internal rule of the secondary rule set still scores the requests.

:::caution
Reopen the allowed rule and confirm that **Condition** reads _Specific HTTP Header Value_ with `cookie`. A _Specific HTTP Header Name_ condition with `cookie` did not clear a match in the `Cookie` header in the observed runs, and the allowed rule saves either way.
:::

A cookie comes from the client and can be forged. Anyone who learns the name and value of the cookie sends the same header and reaches the secondary rule set. Hold the exception to one **Rule ID**.

## Apply the primary rule set to every request

A rule of [Rules Engine for Firewall](/en/documentation/platform/firewall/rules-engine/) selects requests with its criteria, and its _Set WAF_ behavior applies one rule set in one mode. A rule carries at most one _Set WAF_ behavior, so this setup takes two rules.

:::caution
Key the criterion on the request URI, not on the query string. A criterion such as `Request Args` _matches_ `.*` does not match a request without a query string, so a `POST` with its fields in the body skips the rule set.
:::

To create the first rule in Azion Console:

<DocSteps>
  <DocStep title="Open the Rules Engine tab of the Firewall">

  Access [Azion Console](https://console.azion.com/) > **Firewalls**, select the Firewall, then go to the **Rules Engine** tab.

  </DocStep>
  <DocStep title="Select Rule" />
  <DocStep title="Name the rule">

  Enter a name. For example: `Apply storefront-primary`.

  </DocStep>
  <DocStep title="Set the criterion">

  In the **Criteria** section, select the `Request Uri` variable, the _starts with_ operator, and `/` as the argument.

  </DocStep>
  <DocStep title="Add the Set WAF behavior">

  In the **Behaviors** section, select **Set WAF**, then select the primary rule set and _Blocking_ as the mode.

  </DocStep>
  <DocStep title="Save the rule" />
</DocSteps>

The Firewall applies the primary rule set to every request of the Workloads whose deployment sets it.

---

## Apply the secondary rule set to requests with the cookie

The second rule reads the `Cookie` header. When two rules that carry _Set WAF_ match one request, the later rule's rule set and mode apply, so keep this rule below the first one. To create it in Azion Console:

<DocSteps>
  <DocStep title="Select Rule">

  On the **Rules Engine** tab, start a second rule.

  </DocStep>
  <DocStep title="Name the rule">

  Enter a name. For example: `Apply storefront-cookie`.

  </DocStep>
  <DocStep title="Set the criterion">

  In the **Criteria** section, select the `Header Cookie` variable, the _matches_ operator, and your cookie as the argument. For example: `partner-access=b7c1f2e4`. The _matches_ operator reads the argument as a regular expression.

  </DocStep>
  <DocStep title="Add the Set WAF behavior">

  In the **Behaviors** section, select **Set WAF**, then select the secondary rule set and _Blocking_ as the mode.

  </DocStep>
  <DocStep title="Save the rule" />
</DocSteps>

A request that carries the cookie is scored against the secondary rule set: rule `1005` no longer scores its `Cookie` header, and every other internal rule still scores it. A request without the cookie is scored against the primary rule set. The rules propagate across Azion's distributed infrastructure before requests show them. For more information, refer to [Propagation](/en/documentation/platform/firewall/how-it-works/#propagation).
