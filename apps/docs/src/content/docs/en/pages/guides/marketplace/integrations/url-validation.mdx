You install the URL Validation integration from Azion Marketplace and run it on a [Firewall](/en/documentation/platform/firewall/), from Azion Console. The integration scans URLs with the IPQualityScore Malicious URL Scanner API to detect malware, phishing links, suspicious domains, parked domains, and spam. The API runs over 20 data point checks per request and uses machine learning models to classify threats, including zero-day phishing links and newly registered domains. On each request, the function reads the URL from the query string, the request body, or a header, queries IPQualityScore, and then blocks the request, drops it, or adds a header to signal the result.

Five objects have to exist before a request is scanned: the installed function, a firewall carrying the **Functions** module, a function instance holding the arguments, a Rules Engine rule with the **Run Function** behavior, and a workload deployment bound to the firewall. Each section below creates one of them.

---

## Prerequisites

- An Azion account. To sign in, refer to [How to access Azion Console](/en/documentation/guides/platform/account-and-billing/how-to-access-azion-console/).
- An application served by a [workload](/en/documentation/platform/workloads/), whose deployment you bind to the firewall in the last section.
- An [IPQualityScore account](https://www.ipqualityscore.com/create-account). After you create it, get your API key from the IPQualityScore dashboard.
- The [Azion CLI](/en/documentation/devtools/cli/) installed and authorized, for the last section.
- Turning on a product or a module can generate usage costs. For more information, refer to [Pricing](/en/documentation/fundamentals/pricing/).

## Install the integration

The function is installed once per account. To install it:

<DocSteps>
  <DocStep title="Open Marketplace">

  Access [Azion Console](https://console.azion.com/) > **Marketplace**.

  </DocStep>
  <DocStep title="Find the integration">

  Enter `URL Validation` in the **Search on Marketplace** field, then select the integration's card. Browsing the cards and the categories reaches the same page.

  </DocStep>
  <DocStep title="Select Install" />
</DocSteps>

The card shows `Successfully installed!` and `Latest version installed!`, and the function appears in the **Function** list of the **Create Instance** drawer.

## Create the firewall

The firewall is where the function is instanced and where the rule that runs it lives. To create one:

<DocSteps>
  <DocStep title="Open the Firewalls page">

  Access [Azion Console](https://console.azion.com/) > **Firewalls**, then create a firewall.

  </DocStep>
  <DocStep title="Name the firewall">

  In the **General** section, enter a **Name**. For example: `url-validation-firewall`.

  </DocStep>
  <DocStep title="Turn on the Functions module">

  In the **Modules** section, turn on the **Functions** switch.

  </DocStep>
  <DocStep title="Save the firewall" />
</DocSteps>

The firewall shows a **Functions Instances** tab while the **Functions** module stays on. To use an existing firewall instead, turn on its **Functions** module and save it. For every setting on this form, refer to [Set a firewall's main settings](/en/documentation/guides/application-security/firewall-and-waf/firewall-configure-main-settings/).

## Create the function instance

The instance holds your IPQualityScore API key, where the URL comes from, and what to do with a risky one. To create it:

<DocSteps>
  <DocStep title="Open the Functions Instances tab">

  In **Firewalls**, select your firewall, then select the **Functions Instances** tab.

  </DocStep>
  <DocStep title="Select + Function">

  A firewall that has no instance shows the same action as **Function Instance**. The **Create Instance** drawer opens.

  </DocStep>
  <DocStep title="Name the instance">

  In **Name**, enter a name. For example: `url-validation`.

  </DocStep>
  <DocStep title="Select the installed function">

  In **Function**, select the URL Validation function. The list holds only the functions that run on a firewall.

  </DocStep>
  <DocStep title="Enter the arguments">

  In **Arguments**, the editor is prefilled with the integration's default arguments in JSON. Enter your values, as the next section describes.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

The instance is listed in the **Functions Instances** tab.

### Arguments

The instance takes your API key, the source of the URL, and the action:

```json
{
  "api_key": "YourIPQSAPIKey",
  "fast": true,
  "get_data_from": "querystring",
  "data_name": "url",
  "when_score_above": 85,
  "execute": "deny"
}
```

| Variable | Required | Description |
| ---- | ---- | ---- |
| `api_key` | Yes | Your IPQualityScore API key |
| `fast` | No | Turns on fast validation mode. When `true`, the API skips some forensic checks for lower latency. Recommended: `true`. Default: `false` |
| `get_data_from` | Yes | Where the function reads the URL. Accepted values: `querystring`, `body`, `header` |
| `data_name` | Yes | The name of the query string parameter, body field, or header that holds the URL to validate |
| `when_score_above` | No | The risk score threshold (0–100) that triggers the action in `execute`. A risk score ≥ 85 indicates suspected phishing or malware, and a score of 100 confirms malicious activity. If you do not set it, the function takes no action |
| `execute` | No | The action when the score exceeds `when_score_above`. Accepted values: `deny`, `drop`, `add_header` |

Each `execute` value does the following:

| Value | Behavior |
| ---- | ---- |
| `deny` | Runs the **Deny** behavior, which returns a `403 Forbidden` response |
| `drop` | Runs the **Drop** behavior, which closes the connection without a response |
| `add_header` | Adds the `ipqs-limit-score-reached` header to the request and lets the request continue. Use it to handle the result in Rules Engine or at the origin |

:::note
The key data points the IPQualityScore API returns are `risk_score`, `phishing`, `malware`, `suspicious`, `parking`, and `spamming`. The API runs over 20 checks per request. For every field, refer to the [IPQualityScore Malicious URL Scanner API documentation](https://www.ipqualityscore.com/documentation/malicious-url-scanner-api/overview).
:::

## Create the rule

The instance scans nothing until a rule runs it. A [Rules Engine for Firewall](/en/documentation/platform/firewall/rules-engine/) rule selects the requests that reach the instance, through a **Run Function** behavior. To create the rule:

<DocSteps>
  <DocStep title="Open the Rules Engine tab">

  In **Firewalls**, select your firewall, then select the **Rules Engine** tab.

  </DocStep>
  <DocStep title="Select + Rule" />
  <DocStep title="Name the rule">

  In **Name**, enter a name. For example: `Run URL Validation`.

  </DocStep>
  <DocStep title="Set the criterion">

  In the **Criteria** section, select the requests that trigger the URL validation check. For example: if `Host` _matches_ `yourdomain.com`.

  </DocStep>
  <DocStep title="Add the Run Function behavior">

  In the **Behaviors** section, select **Run Function**, then select the instance by the name you gave it.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

The firewall runs the instance on every request that matches the criterion.

---

## Bind the firewall to the workload

The binding is on the workload's deployment, so create a deployment that names both the application and the firewall:

```bash
azion create workload-deployment --workload-id <workload-id> --name <deployment-name> \
  --application-id <application-id> --firewall-id <firewall-id> --strategy-type default \
  --active true --current true
```

The command prints the id of the new deployment:

```text
Created Workload Deployment with ID 325379
```

Requests to the workload's domain reach the firewall, and the rule runs the URL Validation instance on each one that matches.
