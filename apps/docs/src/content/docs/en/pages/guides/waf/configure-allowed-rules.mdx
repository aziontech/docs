You can create a [Web Application Firewall (WAF)](/en/documentation/platform/firewall/waf/) exception, which takes one part of a request out of the scoring of one internal rule, from Azion Console, the Azion CLI, or the API. To turn many matched requests into exceptions at once, refer to [Tune a WAF rule set](/en/documentation/guides/application-security/firewall-and-waf/tune-waf/).

## Create the exception

An exception names the internal rule it exempts, the path it covers, and at least one condition that names the part of the request. Azion Console calls an exception an allowed rule, on the **Allowed Rules** tab of the rule set. For every field and all fifteen match zones, refer to [WAF Exceptions](/en/documentation/platform/firewall/waf/custom-allowed-rules/#fields).

The example clears one false positive. An API at `/api/v1/data` reads a `filter` query string parameter whose values carry an apostrophe:

```text
GET /api/v1/data?filter=name%20LIKE%20%27test%27
```

Internal rule `1013` matches the apostrophe, and a rule set with every family at `medium` refuses the request with `400`.

The comparison is set once for the whole exception: `regex` reads the path and the condition as regular expressions, and `contains`, the default, does not.

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

To create the exception in Azion Console:

<DocSteps>
  <DocStep title="Open the WAF Rules page">

  Access [Azion Console](https://console.azion.com/) > **WAF Rules**.

  </DocStep>
  <DocStep title="Select the rule set that scores the request" />
  <DocStep title="Select the Allowed Rules tab" />
  <DocStep title="Select Allowed Rule" />
  <DocStep title="Select the rule to exempt">

  In **Rule ID**, select the rule that produced the false positive. For this example, rule `1013`.

  </DocStep>
  <DocStep title="Record why the request is allowed">

  In **Description**, enter what the exception is for. For example: `Allow apostrophes in the data API filter`.

  </DocStep>
  <DocStep title="Restrict the exception to one path">

  In **Path**, enter `/api/v1/data`.

  </DocStep>
  <DocStep title="Name the part of the request">

  In **Condition**, select _Specific Query String Value_, then enter `filter`, the name of the parameter, in the **Value** field.

  </DocStep>
  <DocStep title="Choose the comparison">

  Leave the **Active** switch of the **Regex** section off for `contains`, or turn it on for `regex`.

  </DocStep>
  <DocStep title="Save the exception" />
</DocSteps>

The exception appears on the **Allowed Rules** tab, in a row with **Rule ID**, **Description**, **Path**, **Conditions**, **Status**, **Last Editor**, and **Last Modified**.

</Fragment>

<Fragment slot="panel.cli">

### CLI

The Azion CLI reads the exception from a file. The `--conditions` flag sends an empty array on any value, and the API refuses it with `400` and `10049 Ensure this field has at least 1 elements.` To create the exception with the Azion CLI:

<DocSteps>
  <DocStep title="Write the exception to a file">

  Save the following as `exception.json`:

  ```json
  {
    "rule_id": 1013,
    "name": "Allow apostrophes in the data API filter",
    "path": "/api/v1/data",
    "operator": "contains",
    "active": true,
    "conditions": [
      { "match": "specific_query_string_value", "value": "filter" }
    ]
  }
  ```

  </DocStep>
  <DocStep title="Create the exception">

  Replace `<waf-id>` with the ID of your rule set:

  ```bash
  azion create waf-exceptions --waf-id <waf-id> --file exception.json
  ```

  </DocStep>
  <DocStep title="Read the output">

  The command prints the ID of the exception:

  ```text
  Created WAF Exception with ID <exception-id>
  ```

  </DocStep>
</DocSteps>

Record the ID. The next section reads the exception back with it.

</Fragment>

<Fragment slot="panel.api">

### API

To create the exception with the API:

<DocSteps>
  <DocStep title="Send the create request">

  Replace `<waf-id>` with the ID of your rule set and `[TOKEN VALUE]` with your personal token:

  ```bash
  curl --request POST \
    --url https://api.azion.com/v4/workspace/wafs/<waf-id>/exceptions \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: application/json' \
    --data '{
    "rule_id": 1013,
    "name": "Allow apostrophes in the data API filter",
    "path": "/api/v1/data",
    "operator": "contains",
    "active": true,
    "conditions": [
      { "match": "specific_query_string_value", "value": "filter" }
    ]
  }'
  ```

  </DocStep>
  <DocStep title="Read the response">

  The API answers `202`, and `"state": "pending"` means the exception is still propagating:

  ```json
  {
    "state": "pending",
    "data": {
      "id": 123456,
      "rule_id": 1013,
      "name": "Allow apostrophes in the data API filter",
      "path": "/api/v1/data",
      "conditions": [
        { "match": "specific_query_string_value", "value": "filter" }
      ],
      "operator": "contains",
      "active": true,
      "last_editor": "user@example.com",
      "last_modified": "2026-01-01T12:00:00.000000Z"
    }
  }
  ```

  </DocStep>
</DocSteps>

Record the `id`. The next section reads the exception back with it. Of the six fields of the body, only `name` and `conditions` are required: `rule_id` defaults to `0`, which stands for all rules, `operator` to `contains`, and `active` to `true`.

</Fragment>

</Tabs>

The exception exempts rule `1013` on the value of `filter` at `/api/v1/data`, and the rule keeps scoring every other parameter and path. It propagates across Azion's distributed infrastructure before requests show it, so a request refused right after the create has broken nothing. Wait, then send it again.

:::caution
Two shapes did not clear the match in the observed runs. A _Specific Query String Name_ condition with `filter` left the value of `filter` scored, and a **Path** that held only the start of the request path did not cover the request. Set **Path** to the exact path of the request, or leave it empty to cover every path.
:::

## Confirm what the exception covers

:::caution
A key that the condition shape does not carry is dropped, not refused. A condition sent as `{"match": "any_http_header_value", "name": "cookie"}` is accepted with `202` and reads back as `{"match": "any_http_header_value"}`. The exception then covers every request header instead of one, and the response does not say so.
:::

To catch a dropped key, read the exception back and compare its `conditions` with the ones you sent.

<Fragment slot="panel.cli">

### CLI

`azion describe waf-exceptions` prints the stored exception. Read it rather than `azion list waf-exceptions`, whose **RULE ID** column does not print the rule. To read the exception back with the Azion CLI:

<DocSteps>
  <DocStep title="Describe the exception">

  Replace `<waf-id>` and `<exception-id>` with your IDs:

  ```bash
  azion describe waf-exceptions --waf-id <waf-id> --exception-id <exception-id> --format json
  ```

  </DocStep>
  <DocStep title="Compare the conditions with what you sent">

  The command prints the exception with its keys in alphabetical order:

  ```json
  {
   "active": true,
   "conditions": [
    {
     "match": "specific_query_string_value",
     "value": "filter"
    }
   ],
   "id": 123457,
   "last_editor": "user@example.com",
   "last_modified": "2026-01-01T12:00:00.000000Z",
   "name": "Allow apostrophes in the data API filter",
   "operator": "contains",
   "path": "/api/v1/data",
   "rule_id": 1013
  }
  ```

  </DocStep>
</DocSteps>

The stored condition carries the `value` key. A stored condition that holds `match` alone covers every query string parameter.

</Fragment>
