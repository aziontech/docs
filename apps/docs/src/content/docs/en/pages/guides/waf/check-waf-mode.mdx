You can read and change the mode in which a [Firewall](/en/documentation/platform/firewall/) applies a [Web Application Firewall (WAF)](/en/documentation/platform/firewall/waf/) rule set, from Azion Console or the API. The mode belongs to the _Set WAF_ behavior of a rule, not to the rule set, so one rule set can run in _Logging_ on one rule and in _Blocking_ on another. To apply a rule set for the first time, refer to [Create and apply a WAF rule set](/en/documentation/guides/application-security/firewall-and-waf/create-waf-rule-set/).

## Check the mode

A Firewall holds several rules, and the mode sits on the rule that carries _Set WAF_.

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

To read the mode in Azion Console:

<DocSteps>
  <DocStep title="Open the Rules Engine tab of the Firewall">

  Access [Azion Console](https://console.azion.com/) > **Firewalls**, select the Firewall, then go to the **Rules Engine** tab.

  </DocStep>
  <DocStep title="Select the rule that applies the rule set">

  Its **Behaviors** section carries **Set WAF**.

  </DocStep>
  <DocStep title="Read the mode">

  Beside the rule set, the **Set WAF** behavior shows _Logging_ or _Blocking_.

  </DocStep>
</DocSteps>

The Firewall applies the rule set in that mode to every request the rule matches.

</Fragment>

<Fragment slot="panel.api">

### API

To read the mode with the API:

<DocSteps>
  <DocStep title="List the rules of the Firewall">

  Replace `<firewall-id>` with the ID of your Firewall, and `[TOKEN VALUE]` with your personal token:

  ```bash
  curl --request GET \
    --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]'
  ```

  </DocStep>
  <DocStep title="Find the set_waf behavior">

  The API answers `200`. The rule that applies the rule set carries this behavior:

  ```json
  "behaviors": [
    { "type": "set_waf", "attributes": { "waf_id": 12345, "mode": "blocking" } }
  ]
  ```

  </DocStep>
</DocSteps>

`mode` reads `logging` or `blocking`, which Azion Console shows as _Logging_ and _Blocking_. Record the `id` of the rule to change its mode.

</Fragment>

</Tabs>

## Change the mode

`mode` takes `logging` or `blocking`. In _Logging_, WAF records what the rule set flags and serves the request; in _Blocking_, it refuses the request with `400`. For what each mode does, refer to [Scoring and modes](/en/documentation/platform/firewall/waf/scoring-and-modes/#modes).

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

To change the mode in Azion Console:

<DocSteps>
  <DocStep title="Open the rule">

  Open the rule as in [Check the mode](#check-the-mode).

  </DocStep>
  <DocStep title="Select the new mode on the Set WAF behavior">

  Select _Logging_ or _Blocking_.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

</Fragment>

<Fragment slot="panel.api">

### API

A `PATCH` replaces the whole `behaviors` array of the rule and keeps its criteria, so send every behavior the rule carries. To change the mode with a `PATCH`:

<DocSteps>
  <DocStep title="Send the change">

  Replace `<firewall-id>` and `<rule-id>` with your IDs, and `waf_id` with the ID of your rule set:

  ```bash
  curl --request PATCH \
    --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules/<rule-id> \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: application/json' \
    --data '{
    "behaviors": [
      {
        "type": "set_waf",
        "attributes": {
          "waf_id": 12345,
          "mode": "blocking"
        }
      }
    ]
  }'
  ```

  </DocStep>
  <DocStep title="Read the response">

  The API answers `202`, with `"state": "pending"` and the whole rule, carrying the new mode:

  ```json
  "behaviors": [{ "type": "set_waf", "attributes": { "waf_id": 12345, "mode": "blocking" } }]
  ```

  </DocStep>
</DocSteps>

A `PUT` replaces the whole rule instead, so its body carries the name and the criteria too. A `PUT` without `criteria` is refused with `10059 Required Field` on `/data/criteria`. To change the mode with a `PUT`:

<DocSteps>
  <DocStep title="Write the whole rule to a file">

  Save the rule as `rule.json`, with `mode` set to the new value:

  ```json
  {
    "name": "Apply storefront-waf",
    "active": true,
    "criteria": [
      [
        {
          "conditional": "if",
          "variable": "${request_uri}",
          "operator": "starts_with",
          "argument": "/"
        }
      ]
    ],
    "behaviors": [
      {
        "type": "set_waf",
        "attributes": {
          "waf_id": 12345,
          "mode": "blocking"
        }
      }
    ]
  }
  ```

  </DocStep>
  <DocStep title="Send the replacement">

  ```bash
  curl --request PUT \
    --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules/<rule-id> \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: application/json' \
    --data @rule.json
  ```

  </DocStep>
  <DocStep title="Read the response">

  The API answers `202`, with `"state": "pending"` and the rule as stored:

  ```text
  {"state":"pending","data":{"id":<rule-id>,"name":"Apply storefront-waf",…,"behaviors":[{"type":"set_waf","attributes":{"waf_id":12345,"mode":"blocking"}}],"description":"","order":<order>}}
  ```

  </DocStep>
</DocSteps>

A `set_waf` behavior with no `mode` is refused with `10059 Required Field` on `/data/behaviors/0/attributes/mode`. Any other value is refused too. Real-Time Events records a request scored in _Logging_ with `wafLearning` set to `1`, but the API refuses `learning` as a mode:

```json
{
  "errors": [
    {
      "code": "10039",
      "title": "Invalid Choice",
      "detail": "\"learning\" is not a valid choice.",
      "status": "400",
      "source": { "pointer": "/data/behaviors/0/attributes/mode" }
    }
  ]
}
```

</Fragment>

</Tabs>

After the change to _Blocking_, a request the rule set flags receives `400` instead of reaching your Application. The new mode propagates before requests show it, and answers can alternate between the two modes meanwhile. In one observed change, the first `400` came 323 seconds after the save, and one later request was still served. For more information, refer to [Propagation](/en/documentation/platform/firewall/how-it-works/#propagation).
