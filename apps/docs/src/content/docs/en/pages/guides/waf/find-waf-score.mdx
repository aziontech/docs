You can read which internal rules matched a request that [Web Application Firewall (WAF)](/en/documentation/platform/firewall/waf/) refused, and what each threat family scored, from Real-Time Events in Azion Console or the GraphQL API. For how a score decides a block, refer to [Scoring and modes](/en/documentation/platform/firewall/waf/scoring-and-modes/#scoring-and-sensitivity).

## Capture the request ID

A refused request receives `400` and never reaches your origin. No header of that response names WAF, the internal rule, or the score, so the request ID is the value that finds the event. To capture it:

1. Send an injection-shaped request to your Workload:

   ```bash
   curl -i "https://<your-workload-domain>/?q=1%27%20OR%20%271%27%3D%271"
   ```

   WAF refuses the request:

   ```text
   HTTP/2 400
   server: nginx
   content-type: text/html
   x-azion-request-id: 0123456789abcdef0123456789abcdef
   x-azion-edge-location: <location>
   ```

2. Record the value of `x-azion-request-id`.

The body is Azion's default error page, headed **Bad Request**. A visitor who reports a refusal can read the same value in the **Request ID** row of its **Error Details** block.

## Find the event

[Real-Time Events](/en/documentation/platform/real-time-events/) holds one row per request, and the row carries the WAF decision.

<Fragment slot="panel.console">

### Console

To open the event in Azion Console:

<DocSteps>
  <DocStep title="Open Real-Time Events">

  Access [Azion Console](https://console.azion.com/) > **Real-Time Events**.

  </DocStep>
  <DocStep title="Select the HTTP Requests tab" />
  <DocStep title="Set a time range that contains the request" />
  <DocStep title="Filter on the request ID">

  In the search field, filter on the request ID you recorded.

  </DocStep>
  <DocStep title="Select the request in the results list" />
</DocSteps>

The event opens with its WAF fields, among them **WAF Block** and **WAF Learning**.

</Fragment>

<Fragment slot="panel.api">

### API

To read the event with the GraphQL API:

<DocSteps>
  <DocStep title="Write the query">

  Save the following as `waf-event.json`, with your request ID in `requestIdEq` and a time window around the request in `tsGte` and `tsLt`:

  ```json
  {
    "query": "query { workloadEvents(limit: 3, filter: { tsGte: \"2026-01-01T11:55:00\", tsLt: \"2026-01-01T12:05:00\", requestIdEq: \"0123456789abcdef0123456789abcdef\" }) { ts requestId host requestUri status upstreamStatus wafBlock wafMatch wafLearning wafScore wafAttackFamily wafAttackAction wafEvheaders wafTotalBlocked wafTotalProcessed } }"
  }
  ```

  </DocStep>
  <DocStep title="Send the query">

  Replace `[TOKEN VALUE]` with your personal token:

  ```bash
  curl --request POST \
    --url https://api.azion.com/v4/events/graphql \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: application/json' \
    --data @waf-event.json
  ```

  </DocStep>
  <DocStep title="Read the event">

  The API answers `200`, and the row carries the decision:

  ```json
  {
    "ts": "2026-01-01T12:00:00Z",
    "requestId": "0123456789abcdef0123456789abcdef",
    "host": "<your-workload-domain>",
    "requestUri": "/?q=1%27%20OR%20%271%27%3D%271",
    "status": 400,
    "upstreamStatus": 0,
    "wafBlock": "1",
    "wafMatch": "0:1009:ARGS:q,1:1013:ARGS:q",
    "wafLearning": "0",
    "wafScore": "0:$SQL:18,1:$XSS:32",
    "wafAttackFamily": "$SQL,$XSS",
    "wafAttackAction": "$BLOCK",
    "wafEvheaders": "<base64>",
    "wafTotalBlocked": 0,
    "wafTotalProcessed": 0
  }
  ```

  </DocStep>
</DocSteps>

`wafEvheaders` is base64. Decoded, it carries the headers of the refused request.

:::note
The endpoint is `/v4/events/graphql`, and the dataset is `workloadEvents`. The same query sent to `https://api.azion.com/events/graphql` answers `204` with an empty body, and no `wafEvents` dataset exists. The WAF fields of `workloadEvents` are camelCase: `wafBlock`, not `waf_block`.
:::

## Read the match and the score

`wafMatch` and `wafScore` carry the decision. Each is a string with one entry per match, separated by commas, and each reads `-` on a request that matched no internal rule. To read them:

1. Read `wafMatch`, shaped `<index>:<ruleId>:<zone>:<varName>`. In `0:1009:ARGS:q,1:1013:ARGS:q`, the internal rules `1009` and `1013` each matched the `q` argument, in the `ARGS` zone. For what each rule ID detects, refer to [WAF Rule Sets](/en/documentation/platform/firewall/waf/rules-set/#internal-rules).
2. Read `wafScore`, shaped `<index>:$<family>:<score>`, with one score per threat family. In `0:$SQL:18,1:$XSS:32`, the SQL injection family scores `18` and the cross-site scripting family scores `32`. A family blocks when its score reaches the threshold of its sensitivity level. For the thresholds, refer to [WAF Rule Sets](/en/documentation/platform/firewall/waf/rules-set/#sensitivity-levels).
3. Read `wafAttackAction` to tell a refusal from a logged decision. It reads `$BLOCK` when WAF refused the request, and `$LEARNING-BLOCK` when a rule in _Logging_ mode recorded the decision and served the request.

`wafBlock` reads `1` in both modes when the rule set flags the request, and `wafLearning` reads `1` in _Logging_ mode only. `wafAttackFamily` lists the families that scored, such as `$SQL,$XSS`. Azion Console shows these fields under labels such as **WAF Block** and **WAF Learning**.

`wafTotalProcessed` and `wafTotalBlocked` read `0` on the row of a refused request, so they say nothing about a refusal.
