You install the JWT integration from Azion Marketplace and run it on a [Firewall](/en/documentation/platform/firewall/), from Azion Console. Access tokens control access to online resources, such as APIs and media archives, and JSON Web Tokens (JWTs) simplify this control, although a JWT can be larger than a session ID and affect network speed. The integration validates each token on the firewall, before the request reaches your infrastructure, without a call to an authenticator server. You grant and revoke privileges with KIDs and secrets, and you set expiration dates.

Five objects have to exist before a request is validated: the installed function, a firewall carrying the **Functions** module, a function instance holding the arguments, a Rules Engine rule with the **Run Function** behavior, and a workload deployment bound to the firewall. Each section below creates one of them.

---

## Prerequisites

- An Azion account. To sign in, refer to [How to access Azion Console](/en/documentation/guides/platform/account-and-billing/how-to-access-azion-console/).
- An application served by a [workload](/en/documentation/platform/workloads/), whose deployment you bind to the firewall in the last section.
- The [Azion CLI](/en/documentation/devtools/cli/) installed and authorized, for the last section.
- Turning on a product or a module can generate usage costs. For more information, refer to [Pricing](/en/documentation/fundamentals/pricing/).

## Install the integration

The function is installed once per account. To install it:

<DocSteps>
  <DocStep title="Open Marketplace">

  Access [Azion Console](https://console.azion.com/) > **Marketplace**.

  </DocStep>
  <DocStep title="Find the integration">

  Enter `JWT` in the **Search on Marketplace** field, then select the integration's card. Browsing the cards and the categories reaches the same page.

  </DocStep>
  <DocStep title="Select Install" />
</DocSteps>

The card shows `Successfully installed!` and `Latest version installed!`, and the function appears in the **Function** list of the **Create Instance** drawer.

---

## Create the firewall

The firewall is where the function is instanced and where the rule that runs it lives. To create one:

<DocSteps>
  <DocStep title="Open the Firewalls page">

  Access [Azion Console](https://console.azion.com/) > **Firewalls**, then create a firewall.

  </DocStep>
  <DocStep title="Name the firewall">

  In the **General** section, enter a **Name**. For example: `jwt-firewall`.

  </DocStep>
  <DocStep title="Turn on the Functions module">

  In the **Modules** section, turn on the **Functions** switch.

  </DocStep>
  <DocStep title="Save the firewall" />
</DocSteps>

The firewall shows a **Functions Instances** tab while the **Functions** module stays on. To use an existing firewall instead, turn on its **Functions** module and save it. For every setting on this form, refer to [Set a firewall's main settings](/en/documentation/guides/application-security/firewall-and-waf/firewall-configure-main-settings/).

## Create the function instance

The instance holds the KIDs and secrets that the function accepts. To create it:

<DocSteps>
  <DocStep title="Open the Functions Instances tab">

  In **Firewalls**, select your firewall, then select the **Functions Instances** tab.

  </DocStep>
  <DocStep title="Select + Function">

  A firewall that has no instance shows the same action as **Function Instance**. The **Create Instance** drawer opens.

  </DocStep>
  <DocStep title="Name the instance">

  In **Name**, enter a name. For example: `jwt`.

  </DocStep>
  <DocStep title="Select the installed function">

  In **Function**, select the JWT function. The list holds only the functions that run on a firewall.

  </DocStep>
  <DocStep title="Enter the arguments">

  In **Arguments**, the editor is prefilled with the integration's default arguments in JSON. Enter your KIDs, as the next section describes.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

The instance is listed in the **Functions Instances** tab.

### Arguments

The editor loads an example of KIDs, like the one below:

```json
[{
  "kids": {
    "4546D4AA7F62F01A833A7ABE354030E7": "D6CB2342E44EFB6DD628276F36DA2359",
    "D6CB2342E44EFB6DD628276F36DA2359": "60BD8ED7A768E8BD6925BEB0A691AADB",
    "60BD8ED7A768E8BD6925BEB0A691AADB": "4546D4AA7F62F01A833A7ABE354030E7"
  }
}]
```

## Create the rule

The instance validates nothing until a rule runs it. A [Rules Engine for Firewall](/en/documentation/platform/firewall/rules-engine/) rule selects the requests that reach the instance, through a **Run Function** behavior. To create the rule:

<DocSteps>
  <DocStep title="Open the Rules Engine tab">

  In **Firewalls**, select your firewall, then select the **Rules Engine** tab.

  </DocStep>
  <DocStep title="Select + Rule" />
  <DocStep title="Name the rule">

  In **Name**, enter a name. For example: `Run JWT`.

  </DocStep>
  <DocStep title="Set the criterion">

  In the **Criteria** section, select the domains that run the integration. For example: if `Host` _matches_ `yourdomain.com`.

  </DocStep>
  <DocStep title="Add the Run Function behavior">

  In the **Behaviors** section, select **Run Function**, then select the instance by the name you gave it.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

The firewall runs the instance on every request to the domain in the criterion.

## Bind the firewall to the workload

The binding is on the workload's deployment, so create a deployment that names both the application and the firewall:

```bash
azion create workload-deployment --workload-id <workload-id> --name <deployment-name> \
  --application-id <application-id> --firewall-id <firewall-id> --strategy-type default \
  --active true --current true
```

The command prints the id of the new deployment:

```text
Created Workload Deployment with ID 123456
```

Requests to the workload's domain reach the firewall, and the rule runs the JWT instance on each one.

## Run the instance on an API path

An API checks the token on the path every API route starts with, so a request without a valid token is refused before it reaches the API origin. The token travels in the request's `Authorization` header, in the Bearer scheme. The example instances the function as `api-jwt`, with the key ID and secret key pairs your token issuer signs with, and runs it on `/v1/` of `api.example.com`. Replace each value with your own.

To instance the JWT function:

<DocSteps>
  <DocStep title="Open the Functions Instances tab">

  Access [Azion Console](https://console.azion.com/) > **Firewalls**, select the firewall, then go to the **Functions Instances** tab.

  </DocStep>
  <DocStep title="Select + Function Instance" />
  <DocStep title="Name the instance">

  Enter `api-jwt`.

  </DocStep>
  <DocStep title="Select JWT in the function list" />
  <DocStep title="Enter the key pairs">

  In the **Arguments** tab, replace the example with your pairs, each key ID mapped to its secret key:

  ```json
  [{ "kids": { "<key-id>": "<secret-key>" } }]
  ```

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

To run it on the API paths:

<DocSteps>
  <DocStep title="Go to the Rules Engine tab" />
  <DocStep title="Select + Rule" />
  <DocStep title="Name the rule">

  Enter `api - check token`.

  </DocStep>
  <DocStep title="Match the API paths">

  In the **Criteria** section, select `Request Uri`, _starts with_, and `/v1/`.

  </DocStep>
  <DocStep title="Add the Run Function behavior">

  In the **Behaviors** section, select **Run Function**, then `api-jwt`.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

A request to `/v1/` with an invalid token receives `400` or `401`, depending on the error. A route your API serves without a token needs its own path outside `/v1/`, or a criterion that excludes it from this rule.

To confirm the check, send a request with no `Authorization` header:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://api.example.com/v1/orders
```

The command prints `400` or `401`. The same request with a valid `Authorization: Bearer <token>` header reaches the API.

The [Protect public APIs from abuse](/en/documentation/use-cases/secure-applications-and-networks/protect-public-apis-from-abuse/) use case uses the values of this example.

These checks confirm the [Protect public APIs from abuse](/en/documentation/use-cases/secure-applications-and-networks/protect-public-apis-from-abuse/) use case.
