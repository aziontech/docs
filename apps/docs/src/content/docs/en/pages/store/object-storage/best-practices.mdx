Most of what goes wrong with stored objects is decided before anything is uploaded. A key that cannot be replaced safely and a content type nobody set are cheap to fix at the start. So are a bucket that anyone can delete from and a credential that reaches every bucket in the account. Each one is expensive to change once an audience depends on it.

The practices below cover, in order: the access level, versioned keys, the content type, the prefix, the S3 credential, the delivery path, and deletions.

---

## Give a bucket the lowest access level the Application needs

Set `workloads_access` to `read_only` unless a Function has to write objects during a request, and to `restricted` when no Application should serve the bucket at all.

The level decides what a Connector and a Function of your Applications can do with the objects. The Azion API and the S3 protocol are outside it: a deployment pipeline writes to a `read_only` bucket with a token or a `writeFiles` credential. On a `read_write` bucket, a Connector deletes an object on any `DELETE` request that reaches it. Point no Connector at a bucket that a Function writes to.

<Code client:visible lang="bash" code={`curl --request POST \\
\x20 --url https://api.azion.com/v4/workspace/storage/buckets \\
\x20 --header 'Accept: application/json' \\
\x20 --header 'Authorization: Token [TOKEN VALUE]' \\
\x20 --header 'Content-Type: application/json' \\
\x20 --data '{
\x20 "name": "site-assets-ro",
\x20 "workloads_access": "read_only"
}'`} />

A `201` response returns the bucket with `workloads_access` set to `read_only`.

The cost is that a level change takes up to about 90 seconds to reach the Connector and the Function, as [Access levels](/en/documentation/platform/object-storage/how-it-works/#access-levels) explains. Azion Console cannot set a bucket back to `restricted` once it is open to Workloads, while the Azion API can. Start low and raise the level when a Function needs the write. To check a bucket's level, `azion list storage bucket` shows it in the WORKLOADS ACCESS column.

## Version an object's name instead of replacing it in place

Give an object a key that changes when its content changes, and upload the new content under the new key.

An upload to a key in use replaces the object that the Azion API returns, and no setting turns versioning on. Through the S3 protocol, an earlier version stays readable by version ID for a period you cannot set, so a rollback cannot rely on it. Readers of the key get the new content at once, from the Azion API and from an Application with its default settings. During a deployment that replaces several objects one by one, readers see a mix of old and new until the last one lands.

```text
assets/app.4f2a9c.js
assets/app.9b71e0.js
assets/styles.4f2a9c.css
```

A key that carries a build identifier lets both versions exist while a deployment runs, and a rollback points back at the previous key. A long cache lifetime is also safe, because the key never serves different content. The cost is that old keys accumulate, so a deployment that versions keys also needs a step that removes the ones nothing references.

## Set the Content-Type header on every upload

Send the `Content-Type` header on every upload request rather than relying on detection.

The content type is fixed at upload and returned on every read. Without the header, an upload through the Azion API gets the type from the key's extension. Text under a `.png` key is stored as `image/png`. `curl --data-binary` with no `Content-Type` header sends `application/x-www-form-urlencoded`, and Object Storage stores and serves that type. An object stored with the wrong content type keeps serving it until the object is written again, and a browser handed the wrong type may download a page instead of rendering it.

<Code client:visible lang="bash" code={`curl --request POST \\
\x20 --url https://api.azion.com/v4/workspace/storage/buckets/site-assets-ro/objects/assets/app.4f2a9c.js \\
\x20 --header 'Accept: application/json' \\
\x20 --header 'Authorization: Token [TOKEN VALUE]' \\
\x20 --header 'Content-Type: application/javascript' \\
\x20 --data-binary '@./dist/app.4f2a9c.js'`} />

A `201` response confirms the key:

```json
{
  "state": "executed",
  "data": {
    "object_key": "assets/app.4f2a9c.js"
  }
}
```

The `Storage-Content-Type` header the API accepts does not set the stored type, so a script that sends it instead of `Content-Type` silently stores the detected type. To check the stored type, read the object: the `content-type` header of the response carries it.

## Choose a prefix that matches what the Application serves

Lay keys out so that one prefix holds exactly what one Connector should serve.

A Connector of type `storage` asks its bucket for the key made of its prefix, when it has one, followed by the request path. When the layout matches, one Connector exposes one set of objects and nothing else. When it does not, either the Connector exposes more than intended or the same bucket needs several Connectors and rules.

```text
public/index.html
public/assets/app.4f2a9c.js
internal/reports/2026-q3.csv
```

A Connector with the prefix `public` serves `public/index.html` at `/index.html`, because it puts the prefix before every request path. Without a prefix, a Connector reaches every key, and a request for `/` lists them, as [Object Storage limits](/en/documentation/platform/object-storage/limits/#scope) explains. The cost is that changing a prefix later rewrites every object under it, one copy and one delete per object. To check the layout, request `/internal/reports/2026-q3.csv` through the Application: the Connector asks for `public/internal/reports/2026-q3.csv` and returns `404`.

## Scope an S3 credential to the buckets and capabilities it needs

Name the buckets in the `buckets` array and grant only the capabilities the client uses.

A credential created without `buckets` reaches every bucket in the account, and so does one sent with a singular `bucket`, which the API ignores. A credential cannot change after it is created: `PATCH` and `PUT` return `405`. So a credential that is too broad is replaced by a new one. `writeFiles` also allows `DeleteObject`, and `deleteFiles` alone allows no operation, as [Capabilities](/en/documentation/platform/object-storage/s3-compatibility/#capabilities) shows.

<Code client:visible lang="bash" code={`curl --request POST \\
\x20 --url https://api.azion.com/v4/workspace/storage/credentials \\
\x20 --header 'Accept: application/json' \\
\x20 --header 'Authorization: Token [TOKEN VALUE]' \\
\x20 --header 'Content-Type: application/json' \\
\x20 --data '{
\x20 "name": "ci-upload",
\x20 "capabilities": ["listFiles", "readFiles", "writeFiles"],
\x20 "buckets": ["site-assets-ro"],
\x20 "expiration_date": "2027-01-31T23:59:59Z"
}'`} />

A `201` response returns the credential with its `access_key` and `secret_key`, and no later response carries the secret key. Check `buckets` in it: an empty list means the credential reaches every bucket.

Setting `expiration_date` bounds the damage of a leaked key without anyone having to remember to revoke it. Past that date, the S3 endpoint refuses the key with `403` `InvalidAccessKeyId`. The cost is a new credential before the date, because an expiration cannot be extended, so set the date where you provision the credential.

## Serve objects to end users through an Application

Serve the bucket from an Application rule that sets a Connector or runs a Function, and keep end users off the S3 endpoint.

The [Terms of Service](/en/documentation/agreements/tos/) say that objects should reach end users through an Application that uses Connectors. They also subject direct access to objects, outside an Application, to rate limits. A pre-signed URL handed to a browser is direct access, because the S3 endpoint delivers the object to whoever holds the URL. Serving through an Application applies the rules the Application already has, such as a redirect of `/` that hides the bucket listing.

The cost is the setup: an Application serves nothing until a rule sets a Connector or runs a Function. Keep the S3 endpoint for uploading, listing, and removing objects.

---

## Plan deletions around the grace period

Treat a delete as staged rather than immediate, and do not build a flow that creates a bucket, empties it, and deletes it in one pass.

The Azion API stops listing and serving a deleted object at once, although the S3 protocol can still read it by its version ID. The object is removed permanently after a 24-hour grace period, and until then the bucket it was in cannot be deleted. So an automated teardown that empties a bucket and deletes it right away fails, while a bucket that never held an object is deleted straight away.

Delete the Connectors that reference the bucket first: the Azion API refuses to delete a referenced bucket with `409` `17016`.

Reusing one long-lived bucket, or accepting that teardown finishes the next day, both avoid the failure. The cost of reuse is that the bucket's name stays taken, which matters because names are unique across every Azion account.
