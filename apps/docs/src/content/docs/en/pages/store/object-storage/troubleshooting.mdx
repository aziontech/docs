This page lists the symptoms of buckets and objects in [Object Storage](/en/documentation/platform/object-storage/), each with its cause and fix. Azion API responses come first, then an object an Application does not serve, then two Azion CLI commands.

---

## A bucket cannot be deleted and the API returns 17006

A `DELETE` on the bucket answers HTTP `400`, with the title `Cannot Delete Non Empty Bucket` and the detail `Unable to delete a non-empty bucket. Additionally, objects deleted within the last 24 hours are also taken into consideration.`

Two conditions block the deletion, and the detail names both. A bucket that holds one object cannot be deleted. A bucket emptied within the last 24 hours cannot be deleted either, because Object Storage removes a deleted object permanently only after a 24-hour grace period. A bucket that never held an object deletes at once.

- **Empty the bucket**: list the keys with `GET /buckets/{bucket_name}/objects`, then send one `DELETE` per key. For the operations, refer to [Buckets and objects](/en/documentation/platform/object-storage/buckets-and-objects/).
- **Wait out the grace period**: send the `DELETE` again 24 hours after the last object was removed.
- **Delete with the Azion CLI**: refer to [A forced delete with the Azion CLI leaves the bucket in place](/en/documentation/platform/object-storage/troubleshooting/#a-forced-delete-with-the-azion-cli-leaves-the-bucket-in-place).

The `DELETE` then answers HTTP `200` with `state` set to `executed`, and the bucket leaves `GET /buckets`.

## A bucket cannot be deleted and the API returns 17016

A `DELETE` on the bucket answers HTTP `409`, with the title `Cannot Delete Referenced Bucket` and the detail `Cannot delete a bucket referenced by another resource. References: <connector-name> (id: <connector-id>)`.

A [Connector](/en/documentation/platform/connectors/) of type `storage` still references the bucket, so the API refuses the deletion. The detail and `meta.references` name that Connector and its ID.

- **Free the Connector from its rules**: in each Application rule that sets the Connector the detail names, set another Connector or delete the rule. The API refuses to delete a Connector that a rule still sets, with `28000`.
- **Delete the Connector**: for the errors a Connector returns, refer to [Connector settings](/en/documentation/platform/connectors/settings/#errors).
- **Delete the bucket again**: send the same `DELETE` once no Connector references the bucket.

Once no Connector references the bucket, the `DELETE` answers HTTP `200` with `state` set to `executed`. A bucket that holds objects, or lost one within the last 24 hours, answers `17006` instead.

## A bucket name is refused and the API returns 17000, 17001, or 17002

A `POST /buckets` answers HTTP `400` under one of three titles, and `source.pointer` names `/data/name`.

`Bucket Already Exists` means that your account or another one already holds the name. A bucket name is unique across every Azion account, and the detail reads `Bucket name '<name>' is already in use.`

`Bucket Name Not Available` means the name begins or ends with a reserved string. The reserved prefixes are `azion`, `xn--`, `sthree-`, and `amzn-s3-demo-`, and the suffixes are `-s3alias` and `--ol-s3`. `Invalid Bucket Name` means the name has an underscore (`_`), an uppercase letter, or a hyphen at either end.

- **`17000`, `Bucket Already Exists`**: send another name. A name that carries your project or account as a prefix collides less often than a generic one.
- **`17001`, `Bucket Name Not Available`**: remove the reserved prefix or suffix from the name.
- **`17002`, `Invalid Bucket Name`**: remove each underscore, write the letters in lowercase, and start and end the name with a letter or a number.
- **Check the name against the other rules**: a name has 6 to 63 characters of lowercase letters, numbers, and hyphens. Outside that length, the API answers `10048` `Min Length` or `10046` `Max Length`. For each bound, refer to [Object Storage limits](/en/documentation/platform/object-storage/limits/).

The create request then answers HTTP `201` with `state` set to `executed`, and the response carries the bucket.

## The access level is refused and the API returns 10059 or 10039

A `POST /buckets` answers HTTP `400` with the title `Required Field` under code `10059`, or the title `Invalid Choice` under code `10039`. In both cases `source.pointer` names `/data/workloads_access`.

`workloads_access` is required on create, and it accepts exactly three values: `read_only`, `read_write`, and `restricted`. `10059` means the field is absent from the body. A body that sends `edge_access` produces the same error, because the API does not read `edge_access` and the create schema does not store an unknown field. `10039` means the value sits outside the three: a body carrying `private` answers `"private" is not a valid choice.`

- **Name the field `workloads_access`**: the Azion API and the `@aziontech/storage` library take that name, and the Azion CLI takes the flag `--workloads-access`. None of them takes `edge_access`.
- **Replace `private` with `restricted`**: `restricted` closes the bucket to a Connector and a Function of your Applications. The Azion API and the S3 protocol still read and write it.
- **Check which level the bucket needs**: for what each value permits, refer to [Access levels](/en/documentation/platform/object-storage/how-it-works/#access-levels).

The create request then answers HTTP `201`, and reading the bucket back shows `workloads_access` with the value you sent.

## An object is served with the wrong content type

A download of the object returns a `Content-Type` the object was not uploaded with. An image is served as `text/plain`, a JSON body as `application/octet-stream`, or a file sent with `curl` as `application/x-www-form-urlencoded`.

The stored content type comes from the `Content-Type` header of the upload request. Without a `Content-Type`, an upload through the Azion API gets its type from the extension of the key. A `.txt` key gets `text/plain`, and a key with no extension gets `application/octet-stream`, whatever its content.

When the command sets no `Content-Type` header, `curl --data-binary` adds its own, `application/x-www-form-urlencoded`, and Object Storage stores that value. The API specification documents a `Storage-Content-Type` header, and Object Storage ignores it. A request that sets only that header stores a detected type, not the one you named.

- **Upload the object again with `Content-Type`**: the header sets the stored type, and a `POST` to a key that already exists replaces the object and answers `201`.
- **Drop `Storage-Content-Type` from the request**: the header changes nothing, and it hides the missing `Content-Type`.
- **Read the type back**: `GET /buckets/{bucket_name}/objects/{object_key}` returns the object with the type it holds.

Every later request for the object then returns the type you sent. For the upload operations, refer to [Buckets and objects](/en/documentation/platform/object-storage/buckets-and-objects/).

## A PUT to an object key returns 17013

A `PUT` on `/buckets/{bucket_name}/objects/{object_key}` answers HTTP `404`, with the title `Object Does Not Exist`. The bucket exists and the request body is valid.

`PUT` maps to `update_object_key`, which replaces an object that is already stored. It never creates one. `POST` maps to `create_object_key`, which is the operation that creates the key, including every prefix inside it: a `POST` to `objects/folder/sub/data.json` needs no prior step.

- **`POST` the key first**: the create answers `201` with `state` set to `executed` and `data.object_key` naming the key.
- **Keep `PUT` for replacements**: once the key exists, `PUT` answers `200` or `202`.
- **Or `POST` every time**: a `POST` to a key that already exists replaces the object and answers `201`, so one operation covers both cases.

The object is then stored under the key, and `GET /buckets/{bucket_name}/objects` returns it.

## A list request returns no bucket although the bucket exists

`GET /buckets` with `name` set to part of a bucket name answers `200` with `count` as `0` and an empty `results` array. The `bucket` filter returns nothing for any value, including an exact name.

`name` matches the whole bucket name and ignores case, although the API specification describes it as a partial match. The `bucket` filter returns no record at all. `search` is the parameter that matches part of a name, and `workloads_access` filters correctly.

- **Match part of a name with `search`**: `GET /buckets?search=my-bucket` returns every bucket whose name contains `my-bucket`.
- **Use `name` only with the whole name**: `GET /buckets?name=my-bucket-ro` returns that one bucket.
- **Do not filter with `bucket`**: it returns no record, so an empty response proves nothing about the account.
- **Page through the list instead of filtering**: a page holds 10 buckets unless you set `page_size`, which accepts up to 100. `page` moves through the pages.

The response then carries the bucket in `results`, and `count` states how many buckets matched.

## An object is missing from the Application that serves the bucket

The bucket lists the object key, but the Application that serves the bucket does not return the object.

This entry covers a bucket served through a [Connector](/en/documentation/platform/connectors/) of type `storage` that an Application rule sets. The Connector asks the bucket for the request path, preceded by the Connector's prefix when it has one. For example, with the prefix `assets`, a request for `/logo.svg` reads `assets/logo.svg`, and a request for `/assets/logo.svg` reads `assets/assets/logo.svg`. A key the bucket does not hold answers `404` with a `NoSuchKey` XML body.

- **Compare the object key with the Connector's prefix**: request the path that follows the prefix in the key, such as `/logo.svg` for `assets/logo.svg`. The Connector puts its prefix before the request path, so `/assets/logo.svg` asks for `assets/assets/logo.svg` and gets `404`.
- **Confirm a rule sets the Connector**: without a rule that sets it, no request reaches the Connector.
- **Check the access level of the bucket**: a `restricted` bucket answers `502` through a Connector, while `read_only` and `read_write` buckets serve their objects.
- **For the whole chain, refer to [Use a bucket as an application origin](/en/documentation/guides/application-development/data/use-bucket-as-origin/)**: it carries the Connector fields and the rule.

A request that matches the rule then returns the object from the bucket.

## A forced delete with the Azion CLI leaves the bucket in place

`azion delete storage bucket --name <bucket> --force` prints `Delete all objects from bucket` and `Deleting objects...`, then removes the objects. The bucket is still in the output of `azion list storage bucket`, and some objects can remain in it.

A bucket cannot be deleted while it holds objects, or for 24 hours after its last object is removed: the API refuses it with `17006`. The command cannot finish the delete inside that window.

- **Check what is left**: `azion list storage object --bucket-name <bucket>` lists the objects the command did not remove. Remove each one with `azion delete storage object --bucket-name <bucket> --object-key <key>`, which prints `Object <key> was deleted successfully`.
- **Delete the bucket after the grace period**: 24 hours after the last object was removed, run `azion delete storage bucket --name <bucket>`.

A delete that succeeds prints `Bucket <bucket> was deleted successfully`, and the bucket leaves the list.

:::note
With Azion CLI 4.26.2, the command can stop after `Deleting objects...` and leave some objects in the bucket. Azion CLI 4.23.0 printed `Bucket deletion was scheduled successfully` at the end.
:::

## The Azion CLI reports no such file or directory for a file that exists

`azion create storage object --source` fails on a path you can read. From the working directory `/tmp`, `--source /tmp/os-cli.txt` answers `Error: open /tmp/tmp/os-cli.txt: no such file or directory`, and the file is there.

The command prepends the working directory to the value of `--source`, even when the value is an absolute path. The directory then appears twice in the path the command opens.

- **Pass a relative path**: from the directory that holds the file, `--source os-cli.txt` reaches it.
- **Run the command from the directory that holds the file**: the relative path is then the file name alone.
- **Upload through the API when a script needs an absolute path**: `POST /buckets/{bucket_name}/objects/{object_key}` takes the file as the request body.

The command then prints `Object created successfully`. For the storage commands and their flags, refer to [Azion CLI storage](/en/documentation/devtools/cli/resources/storage/).

:::note
The CLI behavior in this section matches Azion CLI 4.26.2.
:::
