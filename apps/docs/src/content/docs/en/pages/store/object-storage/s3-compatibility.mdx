[Object Storage](/en/documentation/platform/object-storage/) answers S3 requests on its own endpoint, so a tool, an SDK, or a library that speaks the S3 protocol reaches the same buckets and the same objects the Azion API v4 reaches. What changes is the credential: the API v4 carries a personal token, and the S3 endpoint carries a request signed with Signature Version 4 (SigV4) using an access key and a secret key. This page lists the credential that holds that key pair, the capabilities it grants, the connection settings, and the S3 operations Azion supports. For the steps that configure a client, refer to [Use S3-compatible tools with Object Storage](/en/documentation/guides/application-development/data/use-s3-compatible-tools-with-object-storage/).

---

## Connection settings

An S3 client needs the endpoint, the region, and the key pair of a credential.

| Setting | Value |
| --- | --- |
| Endpoint | `s3.us-east-005.azionstorage.net` |
| Region | `us-east-005` |
| Access key | The `access_key` the credential returns |
| Secret key | The `secret_key` the credential returns |

The endpoint does not validate the region in the signature, so a request signed for another region, such as `us-east-1`, also succeeds. Set `us-east-005`, the region in the endpoint's host name.

A client that builds its own host names takes the DNS-style template `%(bucket).s3.us-east-005.azionstorage.net`.

Both address forms reach the same object. Virtual-host style carries the bucket in the host name, and path style carries it in the first path segment:

```text
my-bucket-ro.s3.us-east-005.azionstorage.net/file.txt
s3.us-east-005.azionstorage.net/my-bucket-ro/file.txt
```

Anyone who holds a presigned URL for `GetObject` reads the object through the endpoint, with no other authentication. The [Terms of Service](/en/documentation/agreements/tos/) say that delivery to end users should go through an Application that uses Connectors. They also subject direct access to objects, outside an Application, to rate limits. To serve objects to your users, use an [Application](/en/documentation/platform/applications/) whose rule sets a [Connector](/en/documentation/platform/connectors/) of type `storage`, which routes requests to the bucket.

## Credentials

A credential holds the key pair an S3 client signs with, the operations that key pair may run, and the buckets it may reach. Create one through the Azion API v4 at `https://api.azion.com/v4/workspace/storage/credentials`, which this page documents, or in Azion Console.

In Azion Console: **Credentials** › **Object Storage**, or the **Credentials** tab of a bucket. Azion Console requires at least one bucket and an expiration date, which the API leaves optional.

A credential is independent of the bucket's access level. `workloads_access` decides only what a Connector and a [Function](/en/documentation/platform/functions/) of your Applications can do with the objects. A credential that carries `writeFiles` writes to a bucket at every level, `restricted` included. For the access levels, refer to [Buckets and objects](/en/documentation/platform/object-storage/buckets-and-objects/#access-levels).

| Field | Type | Required | Default | Description |
| --- | --- | --- | --- | --- |
| `name` | string | Yes | — | The name of the credential: letters, numbers, and hyphens |
| `capabilities` | array of strings | Yes | — | The operations the credential may run, from the six values under [Capabilities](#capabilities) |
| `buckets` | array of bucket names | No | `[]`, every bucket in the account | The buckets the credential reaches |
| `expiration_date` | date-time, UTC ISO 8601 | No | `null` | When the credential expires. It must be later than the creation date |

:::caution
`buckets` is plural, it takes an array, and it is the field that scopes a credential. A create request that omits it, or that sends `bucket` in the singular, produces a credential that reaches every bucket in the account. The response then carries `"buckets": []`.
:::

A credential cannot change after it is created: a `PATCH` or a `PUT` on it is refused with `405` `10007`. To change its capabilities, its buckets, or its expiration date, create another credential and delete the old one.

### Create a credential

Create the credential with the personal token of the account that owns the buckets:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/storage/credentials \
  --header 'Accept: application/json' \
  --header 'Authorization: Token [TOKEN VALUE]' \
  --header 'Content-Type: application/json' \
  --data '{
  "name": "my-credential",
  "capabilities": ["listFiles", "readFiles", "writeFiles", "deleteFiles", "listAllBucketNames", "listBuckets"],
  "buckets": ["my-bucket-ro"],
  "expiration_date": "2026-12-31T23:59:59Z"
}'
```

The response carries `201` and the credential, with both keys:

```json
{
  "state": "executed",
  "data": {
    "id": 1236,
    "name": "my-credential",
    "access_key": "[ACCESS KEY]",
    "secret_key": "[SECRET KEY]",
    "capabilities": [
      "listAllBucketNames",
      "listBuckets",
      "listFiles",
      "readFiles",
      "writeFiles",
      "deleteFiles"
    ],
    "buckets": ["my-bucket-ro"],
    "expiration_date": "2026-12-31T23:59:59Z",
    "last_editor": "user@example.com",
    "created_at": "2026-01-01T12:03:16.829681Z",
    "last_modified": "2026-01-01T12:03:16.829695Z"
  }
}
```

`secret_key` is returned by this response and by no other call. Store it when the credential is created; to replace a secret key that was not stored, create another credential.

### List credentials

```bash
curl --request GET \
  --url https://api.azion.com/v4/workspace/storage/credentials \
  --header 'Accept: application/json' \
  --header 'Authorization: Token [TOKEN VALUE]'
```

The response is paginated:

```json
{
  "count": 1,
  "total_pages": 1,
  "page": 1,
  "page_size": 10,
  "next": null,
  "previous": null,
  "results": [
    {
      "id": 1236,
      "name": "ci-upload",
      "access_key": "[ACCESS KEY]",
      "capabilities": ["listFiles", "readFiles", "writeFiles"],
      "buckets": ["my-bucket-ro"],
      "expiration_date": "2027-01-31T23:59:59Z",
      "created_at": "2026-01-01T12:03:16.829681Z",
      "last_modified": "2026-01-01T12:03:16.829695Z",
      "last_editor": "user@example.com"
    }
  ]
}
```

To retrieve one credential, send `GET` to `https://api.azion.com/v4/workspace/storage/credentials/<credential-id>`. The response carries the same fields under `data`, without `secret_key`.

No call after the create request returns `secret_key`. Replace a lost secret key by creating another credential and deleting the old one.

### Delete a credential

Delete a credential by the `id` the create response returned:

```bash
curl --request DELETE \
  --url https://api.azion.com/v4/workspace/storage/credentials/<credential-id> \
  --header 'Accept: application/json' \
  --header 'Authorization: Token [TOKEN VALUE]'
```

The response carries `200` and `{"state": "executed"}`. From then on, a request signed with its key pair receives `403`.

## Capabilities

A capability names the S3 operations a credential allows. The `capabilities` array accepts these six values and no others, and a value outside the six returns `17008`. The last column lists what each capability allows on its own, on a bucket in the credential's scope:

| Capability | In Azion Console | S3 operations it allows on its own |
| --- | --- | --- |
| `listFiles` | List Files | ListObjectsV2 |
| `readFiles` | Read Files | GetObject, HeadObject |
| `writeFiles` | Write Files | PutObject, CreateMultipartUpload, DeleteObject |
| `deleteFiles` | Delete Files | None |
| `listAllBucketNames` | List All Bucket Names | ListBuckets |
| `listBuckets` | List Buckets | HeadBucket |

`writeFiles` also deletes, because it allows `DeleteObject`. `deleteFiles` on its own allows no operation, not even `DeleteObject`, although the API accepts a credential that carries only `deleteFiles`. No capability on its own allows `CopyObject`, and a credential with all six allows every operation under [Supported operations](#supported-operations).

For a key that does not exist, the status depends on the capabilities, as [Errors](#errors) states.

:::caution
A credential with `listAllBucketNames` lists every bucket name in the account with `ListBuckets`, even when `buckets` scopes it to one bucket.
:::

## Supported operations

Azion supports the sixteen S3 operations below, and a credential with all six capabilities allows each of them. The [Terms of Service](/en/documentation/agreements/tos/) assign these operations to billing classes, and [Pricing](/en/documentation/fundamentals/pricing/#object-storage) carries the rates.

The last column carries the [s3cmd](https://s3tools.org/s3cmd) form of each operation, as an example of how a client expresses it.

| Operation | What it does | s3cmd command |
| --- | --- | --- |
| ListBuckets | Lists the buckets in the account | `s3cmd ls` |
| HeadBucket | Checks a bucket: `200`, `404` when it does not exist, `403` outside the scope | `s3cmd info s3://BUCKET` |
| ListMultipartUploads | Lists the multipart uploads in progress in a bucket | `s3cmd multipart s3://BUCKET` |
| ListObjects | Lists the objects in a bucket, sorted by key | `s3cmd ls s3://BUCKET` |
| ListObjectsV2 | Lists the objects in a bucket and pages with a continuation token | `s3cmd ls s3://BUCKET` |
| CopyObject | Copies an object that is already stored | `s3cmd cp s3://BUCKET/OBJECT1 s3://BUCKET/OBJECT2` |
| GetObject | Returns an object, or a byte range of it with `Range` | `s3cmd get s3://BUCKET/OBJECT LOCAL_FILE` |
| HeadObject | Returns the metadata of an object without the object itself | `s3cmd info s3://BUCKET/OBJECT` |
| DeleteObject | Removes one object from a bucket | `s3cmd del s3://BUCKET/OBJECT` |
| DeleteObjects | Removes several objects in one request, with the keys in the XML body | `s3cmd del s3://BUCKET/PREFIX --recursive` |
| AbortMultipartUpload | Ends a multipart upload without assembling it | `s3cmd abortmp s3://BUCKET/OBJECT Id` |
| CompleteMultipartUpload | Assembles the uploaded parts into the object | Called by `s3cmd put` |
| CreateMultipartUpload | Starts a multipart upload and returns the `uploadId` that groups its parts | Called by `s3cmd put` |
| ListParts | Lists the parts uploaded for one multipart upload | `s3cmd listmp s3://BUCKET/OBJECT Id` |
| PutObject | Uploads an object | `s3cmd put FILE s3://BUCKET/OBJECT` |
| UploadPart | Uploads one part of a multipart upload | Called by `s3cmd put` |

Both listing operations page: a response that does not hold every key sets `IsTruncated` to true. `ListObjectsV2` also returns a `NextContinuationToken`, which the next request sends as the `continuation-token` query parameter. With `Delimiter=/`, a listing returns the keys at the root and one `CommonPrefixes` entry per prefix, such as `assets/`.

The six multipart operations carry one large upload in parts. `CreateMultipartUpload` opens the upload, `UploadPart` sends each part, `CompleteMultipartUpload` assembles them, and `AbortMultipartUpload` ends an upload that is not finished; `ListParts` and `ListMultipartUploads` report what is in progress. A client that splits large files calls them from its own upload command, so they are rarely called directly.

Beyond the sixteen, the endpoint answers these operations as follows:

| Operation | Answer |
| --- | --- |
| ListObjectVersions | Lists the earlier versions of a key and the deleted objects |
| GetObject with a version ID | Returns that version, including the version of a deleted object |
| CreateBucket, DeleteBucket | `403` `AccessDenied` |
| GetBucketLocation, GetBucketVersioning, PutBucketVersioning | `403` `AccessDenied` |
| GetBucketLifecycleConfiguration, PutBucketLifecycleConfiguration | `403` `AccessDenied` |
| PutObjectAcl | `501` `NotImplemented` |
| PutObject with `If-None-Match: *` | `501` `NotImplemented` |

An earlier version stays for a period you cannot set, as [Object Storage limits](/en/documentation/platform/object-storage/limits/#scope) states. Create and delete buckets through the Azion API, Azion Console, the Azion CLI, or the Terraform Provider.

### Response status

A signed request to the endpoint returns these statuses:

| Operation | Signed request | Status |
| --- | --- | --- |
| ListBuckets | `GET /` | `200` |
| ListObjectsV2 | `GET /<bucket>?list-type=2` | `200` |
| PutObject | `PUT /<bucket>/<key>` | `200` |
| GetObject | `GET /<bucket>/<key>` | `200` |
| HeadObject | `HEAD /<bucket>/<key>` | `200` |
| DeleteObject | `DELETE /<bucket>/<key>` | `204` |

The two listing operations answer in XML, as the S3 protocol defines.

## Authentication

A request to `s3.us-east-005.azionstorage.net` is signed with Signature Version 4, from the credential's `access_key` and `secret_key`. The signature also names a region, which the endpoint does not validate, as [Connection settings](#connection-settings) states. An S3 client signs each request once it holds the connection settings. A request with no signature is refused with `401` and the code `UnauthorizedAccess`.

This is not the authentication the Azion API v4 uses. A call to `https://api.azion.com/v4/workspace/storage` carries a [personal token](/en/documentation/guides/platform/account-and-billing/personal-tokens/) in an `Authorization` header, and what the call may do comes from the account's permissions. A signed S3 request carries no token, and what it may do comes from the credential's `capabilities` and its `buckets` scope.

The two meet in one place: creating, listing, and deleting a credential are API v4 calls, so they carry the personal token. Everything the S3 endpoint answers is signed with the key pair that the create call returned.

## Errors

A credential request that is rejected returns the error envelope every Object Storage API response uses. For the other codes it can return, refer to [Buckets and objects](/en/documentation/platform/object-storage/buckets-and-objects/#errors).

| Code | Title | Status | Cause |
| --- | --- | --- | --- |
| `10007` | `Method Not Allowed` | 405 | A `PATCH` or a `PUT` targets a credential, which cannot change |
| `10059` | `Required Field` | 400 | `name` or `capabilities` is missing from a create request |
| `17007` | `Invalid Credential Name` | 400 | `name` carries a character other than a letter, a number, or a hyphen |
| `17008` | `Not Allowed Capabilities` | 400 | `capabilities` carries a value outside the six. `meta.allowed_capabilities` lists them |
| `17009` | `Expiration Before Creation` | 400 | `expiration_date` is in the past |

The `17007` entry's `detail` reads `Names are limited to 100 alphanumeric characters and can contain hyphen, numbers and letters.`

The S3 endpoint answers in the error format of the S3 protocol, with these statuses and codes:

| Status | Code | Cause |
| --- | --- | --- |
| `401` | `UnauthorizedAccess` | The request carries no signature |
| `403` | `AccessDenied` | The credential lacks the capability or the bucket, or the endpoint refuses the operation |
| `403` | `InvalidAccessKeyId` | The credential expired or was deleted |
| `404` | `NoSuchKey` | The key does not exist, for a credential with all six capabilities |
| `501` | `NotImplemented` | The endpoint does not implement the operation, or a header it carries |

For a key that does not exist, a credential with only one capability receives `403` instead of `404`, whichever capability it is.
