An [Application](/en/documentation/platform/applications/) processes the requests received by your [Workloads](/en/documentation/platform/workloads/): it runs its request and response [rules](/en/documentation/platform/applications/rules-engine/) on each request.

Each Platform Resource turned on in the Application adds bounds of its own. [Cache](/en/documentation/platform/applications/cache/) bounds [cache settings](/en/documentation/platform/applications/cache/cache-settings/) and the objects it stores, and [Real-Time Purge](/en/documentation/platform/applications/cache/real-time-purge/) bounds purge requests. [Application Accelerator](/en/documentation/platform/applications/application-accelerator/) moves the floor of the cache time to live (TTL), and [Image Processor](/en/documentation/platform/applications/image-processor/) bounds the size, width, and height of one image. This page states each bound and the answer a call receives where the API refuses it.

A Platform Resource that you turn on can add costs that depend on usage, and a service plan includes an amount of usage before a rate applies. That amount is a billing quantity: passing it changes what the account is charged rather than what the call returns. [Azion pricing](https://www.azion.com/en/pricing/) lists the plans and the usage each one includes. For the rates, refer to [Pricing](/en/documentation/fundamentals/pricing/#applications).

## Scope

These boundaries hold for every Application, whichever Platform Resources are turned on in it. The boundaries of each nested Platform Resource open its own section of this page.

- **Phases**: every rule belongs to one of two phases, which you choose when you create the rule and cannot change later. The Request Phase acts on the request before a response exists, and the Response Phase acts on the response that the user receives. Only Request Phase rules can choose the origin and the cache setting. [Rules Engine for Applications](/en/documentation/platform/applications/rules-engine/#phases) lists the variables and behaviors of each phase and the Platform Resource that each one needs.
- **Origins**: an Application reaches each origin through a [Connector](/en/documentation/platform/connectors/) that a rule sets, so two rules with two Connectors can route `/api/` to one server and every other path to another. The origin behind a Connector can be a web server in your infrastructure, a cloud service, or an [Object Storage](/en/documentation/platform/object-storage/) bucket, as [Use a bucket as an application origin](/en/documentation/guides/application-development/data/use-bucket-as-origin/) shows. With [Load Balancer](/en/documentation/platform/connectors/load-balancer/) enabled, one Connector of the `http` type can spread traffic across several origins. Connectors replace the origins that earlier versions of Applications configured on the Application.
- **Functions**: a [Function Instance](/en/documentation/platform/applications/functions-instances/) belongs to one Application, and it runs only when a rule with _Run Function_ invokes it. Functions starts on in a new Application, in its `modules.functions.enabled` field in the API. Only Functions written in Lua run in the Response Phase, as the Function Instance form in Azion Console states: `Only Lua functions can be used in the Response phase.` For the steps to add your first Function, refer to [Instantiate a function on an application](/en/documentation/guides/application-development/getting-started/instantiate-functions/).
- **Devices**: a [device group](/en/documentation/platform/applications/device-groups/) is a name and a regular expression that the Application compares with the `User-Agent` header of each request. Both uses of a group need Application Accelerator on: a rule tests the group through `${device_group}`, and a cache setting can keep one copy per group. [Applications best practices](/en/documentation/platform/applications/best-practices/#match-a-device-group-on-the-words-that-only-that-device-sends) shows how to write an expression that matches only the devices you mean.
- **WebSocket**: Azion turns [WebSocket Proxy](/en/documentation/platform/applications/websocket/) on for an account only on request, and [Support guidelines](/en/documentation/support/) explains how to ask. A WebSocket connection opens with the `Upgrade: websocket` and `Connection: upgrade` headers. Azion recycles the keepalive connections on its servers approximately every 15 minutes, so an active connection that needs more time can be terminated. When a WebSocket connection closes this way, your client code has to detect the closed connection and open it again.
- **Large files**: the same keepalive cycle can end a long transfer, and either of two options lets each transfer finish before the connection is recycled. With `modules.cache.large_file_cache.enabled` set to `true` in a cache setting, Cache stores the file in fragments, as [Cache settings](/en/documentation/platform/applications/cache/cache-settings/#cache) shows. The other option, compression, shrinks the file, as [Compress application responses with gzip](/en/documentation/guides/application-performance/delivery-optimization/gzip-compression/) shows.
- **Workloads**: a Workload holds the domains, protocols, and certificates that serve the Application, so you configure delivery on the Workload, not on the Application. _Redirect HTTP to HTTPS_ works only when the Workload has HTTPS. When the Connector receives a 4xx or 5xx response from your origin, the client sees the error page of the custom page set that the Workload's deployment sets, in [Custom Pages](/en/documentation/platform/custom-pages/). To request an Application on your own domain from one device before you change its DNS records, refer to [Test an application through the hosts file](/en/documentation/guides/application-development/getting-started/stage-applications-through-hosts-file/).

## Applications, rules, and connections

These bounds apply to every Application, whichever Platform Resources are turned on in it. They cover the rules in its Rules Engine, the [Debug Rules](/en/documentation/platform/applications/main-settings/#debug-rules) log, and the connections it keeps open.

### Default limits

Seven bounds apply to every Application.

| Scope | Limit |
| --- | --- |
| Rules in one Application, request and response phases together | 200 rules |
| Criteria groups per rule | 1 to 5 groups |
| Criteria per group | 1 to 10 criteria |
| Behaviors per rule | 1 to 10 behaviors |
| Behavior argument | 1,600 characters |
| Debug Rules log size | 1.5 kB |
| WebSocket connection time | 15 minutes |

Three further bounds apply to names: an Application's name takes 1 to 100 characters, a device group's name takes 1 to 250, and a device group's `user_agent` expression takes 1 to 512.

The 200 rules are one total that the request phase and the response phase share. For example, an Application can carry 150 request rules and 50 response rules, but not 200 of each.

## Cache

Cache bounds a cache setting and an object it stores, and Real-Time Purge bounds a purge request. The API validates the TTL bounds on every cache setting, and past a bound that it checks, the call returns HTTP `400` with an error code and a title. [Tiered Cache](/en/documentation/platform/applications/cache/tiered-cache/) changes two bounds of a cache setting: the lowest TTL it takes and the cache behavior it allows.

For the rates of Cache, refer to [Pricing](/en/documentation/fundamentals/pricing/#cache). To query the data that Tiered Cache transferred, refer to [Query usage data from Tiered Cache](/en/documentation/guides/platform/observability/query-tiered-cache-usage-data-with-graphql/).

### Scope

These boundaries hold for Cache in every Application, from any interface.

- **Always on**: Cache is on in every Application, and the API refuses `false` in its `modules.cache.enabled` field with error `31001`. In Azion Console, the **Cache** switch of **Main Settings** is locked on, with the note `Automatically enabled in all accounts.` A new Application has no cache settings and no rules, so Cache stores copies only once a rule with _Set Cache Policy_ applies a cache setting.
- **Expired copies**: with stale cache turned on in `modules.cache.stale_cache.enabled` of a cache setting, Azion may serve an expired copy when it cannot confirm the copy with the origin, and the response then reports `STALE`. A setting created through Azion API or Azion CLI has stale cache off, while Azion Console turns it on for a new setting, as [Cache settings](/en/documentation/platform/applications/cache/cache-settings/#cache) shows. For when an old page is better than an error, refer to [Applications best practices](/en/documentation/platform/applications/best-practices/#cache).
- **Large files**: Large File Optimization is off in a new cache setting, and a cache setting turns it on in `modules.cache.large_file_cache.enabled`. Each fragment of a large file is fetched when a user reaches it and stored under a key of its own, so a purge of the file has to name every fragment or use a wildcard.
- **Tiered Cache**: [Tiered Cache](/en/documentation/platform/applications/cache/tiered-cache/) adds a second cache layer between the data center that answers a request and the origin, and it requires the `override` behavior and a minimum TTL. Each cache setting turns it on in its `modules.cache.tiered_cache.enabled` field, and every plan includes it. A _Bypass Cache_ rule acts on Azion's cache only, so the Tiered Cache layer keeps caching objects for the Max Age of the cache setting.
- **Keys and variation**: Azion builds the default [cache key](/en/documentation/platform/applications/cache/cache-keys/) from the scheme, the host, and the path, so one path is one stored object, and the query string stays out of the key. [Application Accelerator](/en/documentation/platform/applications/application-accelerator/) lets a cache setting keep a separate copy for each value of a query-string argument, a cookie, the device group, or the method. [Image Processor](/en/documentation/platform/applications/image-processor/) adds the format of a converted image to the key.
- **Purge**: [Real-Time Purge](/en/documentation/platform/applications/cache/real-time-purge/) queues a purge after you confirm it, because the result takes time to propagate, and the purge history lists the purge once it completes. A copy that varies by cookie, device group, or image format survives a URL purge, and a cache key or wildcard purge reaches it.
- **Code**: Cache cannot run code, so code that reads and writes cached entries runs in a [Function](/en/documentation/platform/functions/) and calls [Cache API](/en/documentation/devtools/runtime/api-reference/cache/).

### Cache settings

Each bound in this table applies to one cache setting, from any interface that writes it. The Scope column names the API field and, where one exists, the Console label. The Past the limit column carries the code and the title of the `400` answer. The error titles keep earlier names: `Edge Cache` stands for Cache, and `Module` stands for a Platform Resource turned on in the Application.

| Scope | Limit | Past the limit |
| --- | --- | --- |
| Cache TTL minimum, **Max Age** (`modules.cache.max_age`) | 60 seconds; 0 seconds with Application Accelerator on the Application | Error `21021`, `Edge Cache Max Age Lower Than The Minimum Allowed By Application's Application Accelerator Module`, with `meta.min_value` set to `60`. |
| Cache TTL minimum with Tiered Cache on | 3 seconds, with Application Accelerator on; without it, the 60-second minimum holds | Error `21020`, `Edge Cache Max Age Lower Than The Minimum Allowed By The Tiered Cache Module`, with `meta.min_value` set to `3`. |
| Cache TTL maximum | 31,536,000 seconds, one year | Error `10068`, `Max Value`, with the detail `Ensure this value is less than or equal to 31536000.` |
| Cache behavior with Tiered Cache on (`modules.cache.behavior`) | `override` only | Error `21001`, `It's Not Possible To Use This Edge Cache Behavior.` |
| Browser cache TTL (`browser_cache.max_age`) | 0 to 31,536,000 seconds | Error `10068`, `Max Value`. |
| Cache setting name, **Name** (`name`) | 250 characters | Error `10046`, `Max Length`, with the detail `Ensure this field has no more than 250 characters.` |

One further bound applies to a cache setting: its `cache_vary_by_method` array takes at most 2 values, `post` and `options`.

With `modules.cache.stale_cache.enabled` set to `true` in a cache setting, Cache can serve an expired copy of an object for a limited window. Under the `honor` behavior, the window is the value of the origin's `stale-while-revalidate=<ttl>` directive. Under `override`, or when the origin omits the directive, the window is 300 seconds.

### Cached objects

Two bounds apply to an object that Cache stores: its size, and the size of each fragment of a large file stored in pieces. The API checks the fragment size on every cache setting.

| Scope | Limit | Past the limit |
| --- | --- | --- |
| Fragment size of a large file (`modules.cache.large_file_cache.offset`) | 1,024 kB per fragment, fixed | Error `10068`, `Max Value`, with the detail `Ensure this value is less than or equal to 1024.` |

A single object in cache takes up to 10 GB.

### Real-Time Purge

Each bound in this table applies to a purge request, from any interface that sends one. The Past the limit column carries what the API returns past the bound.

| Scope | Limit | Past the limit |
| --- | --- | --- |
| Objects in one URL or cache key purge request | 50 objects | Error `10065`, `List Field Max Length`, with the detail `Ensure this field has no more than 50 elements.` |
| Wildcards in one purge request | 1 wildcard | Error `10065`, `List Field Max Length`, with the detail `Ensure this field has no more than 1 elements.` |

A URL or a cache key in a purge takes up to 4,096 characters.

Six more bounds set the rate of purge requests, the length of a wildcard, and how much purge history Azion keeps.

| Scope | Limit |
| --- | --- |
| URL and cache key purge requests per client | 200 requests, 50 objects each |
| Objects purged by URL and cache key every 60 seconds | 10,000 objects |
| Wildcard purge requests per day, in a 24-hour interval | 2,000 requests |
| Wildcard length | 256 characters |
| Requests kept in the purge history | 1,000,000 requests |
| Time a request stays in the purge history | 6 months |

## Application Accelerator

Application Accelerator changes one bound of a cache setting: the shortest time Cache holds an object. The Max Age of a cache setting, its `modules.cache.max_age` field, sets in seconds how long Cache holds an object. The field takes an integer from 0 to 31,536,000 and refuses any value outside that range. Whether Application Accelerator and Tiered Cache are on decides how low inside the range a cache setting goes.

For the rates of Application Accelerator, refer to [Pricing](/en/documentation/fundamentals/pricing/#application-accelerator).

### Scope

These boundaries hold for Application Accelerator in every Application, from any interface.

- **One Application at a time**: Application Accelerator is off in a new Application, and it belongs to the Application, so one Application can have it on while another has it off. Turning it on leaves traffic as it was: the variation controls of a cache setting start at `ignore`, and a cache setting reaches a request only through a [Set Cache Policy](/en/documentation/platform/applications/rules-engine/#set-cache-policy) rule. [Main Settings](/en/documentation/platform/applications/main-settings/#platform-resources) shows where to turn it on in Azion Console and the API.
- **All or none**: an Application takes every capability that Application Accelerator unlocks, or none of them. They are cache variation, the caching of `POST` and `OPTIONS` responses, a lower floor for the Max Age, the `${request_uri}` and `${device_group}` variables, and the Rules Engine behaviors that [Application Accelerator settings](/en/documentation/platform/applications/application-accelerator/settings/) lists.
- **Methods**: an Application passes `POST`, `PUT`, `PATCH`, `DELETE`, and `OPTIONS` requests to the origin with or without Application Accelerator. Of those methods, Application Accelerator makes only the `POST` and `OPTIONS` responses cacheable. A `POST` reports `-` in `x-cache` until the `cache_vary_by_method` field of the cache setting carries `post`.
- **Variation size**: each distinct value of a varied input is a separate cached object. A cookie unique to each visitor gives every visitor a copy, so the number of objects grows with the audience instead of with the content. An allowlist and sorting, the `sort_enabled` field, bound that number, as [Cache variation](/en/documentation/platform/applications/application-accelerator/cache-variation/#the-cost-of-a-variation) explains. For the practices, refer to [Applications best practices](/en/documentation/platform/applications/best-practices/#application-accelerator).
- **Purges**: copies that vary by cookie or device group survive a URL purge, and a cache key purge or a wildcard purge that ends the key with `@@*` reaches them. Copies that vary by query string are the exception: a URL purge reaches them when it sends the arguments in the order they were presented, or in alphabetical order with `sort_enabled` on. For the purge types, refer to [Real-Time Purge](/en/documentation/platform/applications/cache/real-time-purge/#purge-content-that-varies).
- **Bypass Cache and a TTL of 0**: [Bypass Cache](/en/documentation/platform/applications/rules-engine/#bypass-cache) sends each request that its rule matches to the origin and keeps the response out of Azion's cache, but not out of the Tiered Cache layer of a cache setting that turns Tiered Cache on. A Max Age of 0 seconds keeps the request on the cache path, and every request still reaches the origin. [Bypass Cache and a TTL of 0](/en/documentation/platform/applications/application-accelerator/cache-variation/#bypass-cache-and-a-ttl-of-0) compares how the two handle a request.
- **Image Processor**: to vary the cache on the `ims` string of [Image Processor](/en/documentation/platform/applications/image-processor/), add `ims` to the query-string allowlist of the cache setting that serves images.

### Default limits

Each row names a cache TTL bound and the condition that puts it in force.

| Scope | Limit | Applies when |
| --- | --- | --- |
| Minimum cache TTL | 60 seconds | Application Accelerator is off in the Application, with Tiered Cache on or off. |
| Minimum cache TTL | 0 seconds | Application Accelerator is on, and Tiered Cache is off. |
| Minimum cache TTL | 3 seconds | Application Accelerator is on, and Tiered Cache is on. |
| Maximum cache TTL | 31,536,000 seconds, one year | Every cache setting, whichever Platform Resources are on. |

A Max Age lower than the minimum in force returns HTTP `400`. The error is `21021` while Application Accelerator is off, and `21020` while Application Accelerator and Tiered Cache are both on. A value higher than the maximum returns error `10068`. For the error titles, refer to [Cache settings](#cache-settings).

A request that Application Accelerator varies is still bounded by the Platform Resources that store the object and run code on it. Cache bounds the object itself: the size of one cached object, and the size of each fragment of a large file. For those values, refer to [Cached objects](#cached-objects).

A [Function](/en/documentation/platform/functions/) that the Application runs carries its own limits on its code and on each invocation. For those values, refer to [Functions limits](/en/documentation/platform/functions/limits/).

## Image Processor

Image Processor bounds a single image with three default limits: its size, its width, and its height.

For the rates of the Images metric, refer to [Pricing](/en/documentation/fundamentals/pricing/#image-processor). To query the number of images the account has processed, refer to [Query usage data from Image Processor](/en/documentation/guides/platform/observability/query-image-processor-usage-data-with-graphql/).

### Scope

These boundaries hold for Image Processor in every Application, from any interface.

- **One Application at a time**: Image Processor is off in a new Application, and each Application turns it on separately, in its `modules.image_processor.enabled` field in the API. Even when it is on, Image Processor processes only the requests that a rule with _Optimize Images_ matches. [Main Settings](/en/documentation/platform/applications/main-settings/#platform-resources) shows where to turn it on in Azion Console and the API.
- **Parameters it cannot parse**: an `ims` value that Image Processor cannot parse returns the source image untransformed. For the syntax that each operation accepts, refer to [URL parameters](/en/documentation/platform/applications/image-processor/url-parameters/).
- **Storage**: Image Processor returns each derived image without saving it as an asset of the account, and you cannot upload images to Image Processor. The cache holds the derived images, and the source image stays where it already lives. A workflow that needs to keep a transformed file saves the response itself.
- **Code**: [WASM Image Processor](/en/documentation/devtools/azion-lib/wasm-image-processor/) is a WebAssembly library that processes images inside a [Function](/en/documentation/platform/functions/). It runs in the code of that Function, separately from Image Processor and its settings, as [Where Image Processor stops](/en/documentation/platform/applications/image-processor/image-delivery/#where-image-processor-stops) explains.

### Default limits

An image takes at most 150 MB, 3,840 pixels of width, and 2,160 pixels of height.

Each `ims` parameter also accepts a range of values of its own. For the range of each parameter, refer to [URL parameters](/en/documentation/platform/applications/image-processor/url-parameters/).
