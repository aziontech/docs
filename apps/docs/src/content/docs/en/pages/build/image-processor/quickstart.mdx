This guide instructs you through requesting your first derived image from an Application. By the end you will have:

- [Image Processor](/en/documentation/platform/applications/image-processor/) turned on for one Application.
- A cache setting that stores each transformation as its own object.
- A [Rules Engine](/en/documentation/platform/applications/rules-engine/) rule that sends image requests to Image Processor.
- A resized image returned from a URL you wrote.

Three entities and one URL carry that result, in this order. The **Application** has Image Processor turned on. The **cache setting** belongs to the Application and makes the cache store two different transformations as two different objects. The **rule** belongs to the Application, matches image requests, and applies both the cache setting and the _Optimize Images_ behavior. The image URL then carries the transformation in its `ims` query string. A request that no rule matches is delivered unprocessed, so the rule is what makes the query string mean anything.

## Turn on Image Processor and Application Accelerator

Image Processor is a Platform Resource that is off in a new Application. This stage turns on two Platform Resources.

[Application Accelerator](/en/documentation/platform/applications/application-accelerator/) is the second for two reasons. The field that varies the cache by a query string belongs to it, and the cache setting uses that field. The rule in this guide also reads `${request_uri}`, and Azion refuses a rule that reads it while Application Accelerator is off. Processing an image does not require Application Accelerator, but caching each transformation separately does.

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

To turn on both Platform Resources in Azion Console:

<DocSteps>
  <DocStep title="Open the Application">

  Access [Azion Console](https://console.azion.com/) > **Applications** > **your Application**.

  </DocStep>
  <DocStep title="Go to the Main Settings tab" />
  <DocStep title="Turn on Image Processor">

  In the **Modules** section, turn on **Image Processor**, described as *Enable dynamic image editing options*.

  </DocStep>
  <DocStep title="Turn on Application Accelerator">

  The toggle is in the same section.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

The Application now has both Platform Resources turned on, and the _Optimize Images_ behavior is available to its rules.

</Fragment>

<Fragment slot="panel.cli">

### CLI

One command turns on both Platform Resources. Replace `<application_id>` with [your Application ID](/en/documentation/platform/applications/main-settings/#api):

<DocSteps>
  <DocStep title="Run the update command">

  <Code client:visible lang="bash" code={`azion update application --application-id <application_id> --image-processor true --application-accelerator true`} />

  </DocStep>
  <DocStep title="Read the output">

  The command confirms the Application it changed:

  ```text
  Updated Application with ID <application_id>
  ```

  </DocStep>
</DocSteps>

The Application now has both Platform Resources turned on, and the _Optimize Images_ behavior is available to its rules.

</Fragment>

<Fragment slot="panel.api">

### API

One request turns on both Platform Resources. Replace `[TOKEN VALUE]` with your personal token and `<application_id>` with [your Application ID](/en/documentation/platform/applications/main-settings/#api):

<DocSteps>
  <DocStep title="Send the update request">

  <Code client:visible lang="bash" code={`curl --request PATCH \\
    --url https://api.azion.com/v4/workspace/applications/<application_id> \\
    --header 'Accept: application/json' \\
    --header 'Authorization: Token [TOKEN VALUE]' \\
    --header 'Content-Type: application/json' \\
    --data '{
    "modules": {
      "application_accelerator": { "enabled": true },
      "image_processor": { "enabled": true }
    }
}'`} />

  </DocStep>
  <DocStep title="Read the response">

  A `202` carries `"state": "pending"`, because the change is still propagating. The `modules` object of the response echoes every switch of the Application, including the ones you left alone:

  ```json
  {
    "cache": { "enabled": true },
    "functions": { "enabled": false },
    "application_accelerator": { "enabled": true },
    "image_processor": { "enabled": true }
  }
  ```

  </DocStep>
</DocSteps>

The Application now has both Platform Resources turned on, and the _Optimize Images_ behavior is available to its rules.

</Fragment>

</Tabs>

## Create a cache setting that varies on the ims query string

Without this step, the cache cannot tell one transformation from another. It may answer a request for a 400-pixel image with a 200-pixel one.

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

To create the cache setting in Azion Console:

<DocSteps>
  <DocStep title="Open the Application">

  Access [Azion Console](https://console.azion.com/) > **Applications** > **your Application**.

  </DocStep>
  <DocStep title="Go to the Cache Settings tab" />
  <DocStep title="Select + Cache" />
  <DocStep title="Name the cache setting">

  In **Name**, enter `images`.

  </DocStep>
  <DocStep title="Set Cache Behavior to Override cache behavior">

  In the **Cache** section, set **Cache Behavior** to _Override cache behavior_.

  </DocStep>
  <DocStep title="Set the maximum age">

  In the **Cache** section, in **Max Age**, enter `31536000`.

  </DocStep>
  <DocStep title="Expand Cache vary by Query String">

  The panel is in the **Application Accelerator** section.

  </DocStep>
  <DocStep title="Set Behavior to Allowlist" />
  <DocStep title="Add the ims field">

  In **Fields**, enter `ims`.

  </DocStep>
  <DocStep title="Turn on Sort" />
  <DocStep title="Select Save" />
</DocSteps>

The Application now has a cache setting that stores one object per distinct `ims` value.

</Fragment>

<Fragment slot="panel.cli">

### CLI

The Azion CLI command sends the whole body from a file, because no create flag sets the cache `max_age` or `sort_enabled`.

<DocSteps>
  <DocStep title="Write the cache setting to a file">

  Save the following as `cache-setting.json`:

  <Code client:visible lang="json" code={`{
    "name": "images",
    "browser_cache": { "behavior": "honor" },
    "modules": {
      "cache": { "behavior": "override", "max_age": 31536000 },
      "application_accelerator": {
        "cache_vary_by_querystring": {
          "behavior": "allowlist",
          "fields": ["ims"],
          "sort_enabled": true
        }
      }
    }
}`} />

  `31536000` seconds is the ceiling of `max_age`, which suits images because they change rarely.

  </DocStep>
  <DocStep title="Create the cache setting">

  Replace `<application_id>` with [your Application ID](/en/documentation/platform/applications/main-settings/#api):

  <Code client:visible lang="bash" code={`azion create cache-setting --application-id <application_id> --file cache-setting.json`} />

  The command prints the id of the new cache setting:

  ```text
  Created Cache Settings configuration with ID 123464
  ```

  </DocStep>
  <DocStep title="Read the cache setting back">

  <Code client:visible lang="bash" code={`azion describe cache-setting --application-id <application_id> --cache-setting-id 123464 --format json`} />

  The output reports the `ims` allowlist and the maximum age the file set.

  </DocStep>
</DocSteps>

The Application now has a cache setting that stores one object per distinct `ims` value. Record the id the command printed, because the rule applies it. For every flag the command accepts, refer to [Azion CLI cache-setting](/en/documentation/devtools/cli/resources/cache-setting/).

</Fragment>

<Fragment slot="panel.api">

### API

One request carries the cache behavior and the query string allowlist together.

<DocSteps>
  <DocStep title="Send the create request">

  Replace `<application_id>` with [your Application ID](/en/documentation/platform/applications/main-settings/#api):

  <Code client:visible lang="bash" code={`curl --request POST \\
    --url https://api.azion.com/v4/workspace/applications/<application_id>/cache_settings \\
    --header 'Accept: application/json' \\
    --header 'Authorization: Token [TOKEN VALUE]' \\
    --header 'Content-Type: application/json' \\
    --data '{
    "name": "images",
    "browser_cache": { "behavior": "honor" },
    "modules": {
      "cache": { "behavior": "override", "max_age": 31536000 },
      "application_accelerator": {
        "cache_vary_by_querystring": {
          "behavior": "allowlist",
          "fields": ["ims"],
          "sort_enabled": true
        }
      }
    }
}'`} />

  `31536000` seconds is the ceiling of `max_age`, which suits images because they change rarely.

  </DocStep>
  <DocStep title="Read the response">

  A `201` carries `"state": "executed"` and the cache setting it created. The response brings `modules.cache.max_age` back as `31536000` and echoes `cache_vary_by_querystring` exactly as you sent it.

  Record `data.id`, such as `123463`, because the rule applies it.

  </DocStep>
</DocSteps>

The Application now has a cache setting that stores one object per distinct `ims` value.

</Fragment>

</Tabs>

For the rest of the fields a cache setting carries, including how long an object stays cached, refer to [Cache settings](/en/documentation/platform/applications/cache/cache-settings/).

## Create a rule that sends image requests to Image Processor

The rule is what turns the query string into a transformation. It matches requests for image paths, applies the cache setting you created, and carries the _Optimize Images_ behavior.

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

To create the rule in Azion Console:

<DocSteps>
  <DocStep title="Open the Application">

  Access [Azion Console](https://console.azion.com/) > **Applications** > **your Application**.

  </DocStep>
  <DocStep title="Go to the Rules Engine tab" />
  <DocStep title="Select + Rule" />
  <DocStep title="Name the rule">

  In **Name**, enter `Optimize images`.

  </DocStep>
  <DocStep title="Select Request Phase" />
  <DocStep title="Select the variable">

  In the criteria, select `${request_uri}`.

  </DocStep>
  <DocStep title="Select the operator matches" />
  <DocStep title="Enter the argument">

  Enter `\.(jpg|jpeg|gif|bmp|png|ico|webp|avif)`.

  </DocStep>
  <DocStep title="Add the Set Cache Policy behavior">

  In the behaviors, select **Set Cache Policy**, then choose the `images` cache setting.

  </DocStep>
  <DocStep title="Select Add Behavior" />
  <DocStep title="Select Optimize Images" />
  <DocStep title="Select Save" />
</DocSteps>

Every request for a path with one of those extensions now gets the `images` cache setting and the _Optimize Images_ behavior. Image Processor transforms the image when its URL carries `ims`.

</Fragment>

<Fragment slot="panel.cli">

### CLI

The criteria carry `${request_uri}`, which a shell expands, and the argument carries backslashes, so the rule goes in a file.

<DocSteps>
  <DocStep title="Write the rule to a file">

  Save the following as `rule.json`, with the id of your cache setting in the `set_cache_policy` behavior:

  <Code client:visible lang="json" code={`{
    "name": "Optimize images",
    "description": "Apply the cache setting and optimize images",
    "active": true,
    "criteria": [
      [
        {
          "conditional": "if",
          "variable": "\${request_uri}",
          "operator": "matches",
          "argument": "\\\\.(jpg|jpeg|gif|bmp|png|ico|webp|avif)"
        }
      ]
    ],
    "behaviors": [
      { "type": "set_cache_policy", "attributes": { "value": 123464 } },
      { "type": "optimize_images" }
    ]
}`} />

  One rule carries both behaviors, and `optimize_images` takes no attributes.

  </DocStep>
  <DocStep title="Create the rule">

  <Code client:visible lang="bash" code={`azion create rules-engine --application-id <application_id> --phase request --file rule.json`} />

  The command prints the id of the new rule:

  ```text
  Created Rules Engine with ID 234571
  ```

  </DocStep>
</DocSteps>

Every request for a path with one of those extensions now gets the `images` cache setting and the _Optimize Images_ behavior. Image Processor transforms the image when its URL carries `ims`.

</Fragment>

<Fragment slot="panel.api">

### API

The criteria carry `${request_uri}`, which a shell expands, and the argument carries backslashes, so the body is sent from a file.

<DocSteps>
  <DocStep title="Write the rule to a file">

  Save the following as `rule.json`, with the id of your cache setting in the `set_cache_policy` behavior:

  <Code client:visible lang="json" code={`{
    "name": "Optimize images",
    "description": "Apply the cache setting and optimize images",
    "active": true,
    "criteria": [
      [
        {
          "conditional": "if",
          "variable": "\${request_uri}",
          "operator": "matches",
          "argument": "\\\\.(jpg|jpeg|gif|bmp|png|ico|webp|avif)"
        }
      ]
    ],
    "behaviors": [
      { "type": "set_cache_policy", "attributes": { "value": 123463 } },
      { "type": "optimize_images" }
    ]
}`} />

  One rule carries both behaviors, and `optimize_images` takes no attributes.

  </DocStep>
  <DocStep title="Send the create request">

  <Code client:visible lang="bash" code={`curl --request POST \\
    --url https://api.azion.com/v4/workspace/applications/<application_id>/request_rules \\
    --header 'Accept: application/json' \\
    --header 'Authorization: Token [TOKEN VALUE]' \\
    --header 'Content-Type: application/json' \\
    --data @rule.json`} />

  </DocStep>
  <DocStep title="Read the response">

  A `202` carries `"state": "pending"`, because the rule is still propagating. It echoes the criteria and both behaviors, and it carries the `order` the rule holds among the rules of the Application.

  </DocStep>
</DocSteps>

Every request for a path with one of those extensions now gets the `images` cache setting and the _Optimize Images_ behavior. Image Processor transforms the image when its URL carries `ims`.

</Fragment>

</Tabs>

:::note
This part is optional. An **Add Request Header** behavior with `Accept: image/webp` on the same rule makes the automatic conversion deliver WEBP to every request the rule matches, including one whose browser asked for PNG. Add it only when every client of those paths displays WEBP. In the Azion CLI and the API, it is a behavior of type `add_request_header`, whose `attributes` carry `"value": "Accept: image/webp"`. For the behavior's fields, refer to [Image Processor settings](/en/documentation/platform/applications/image-processor/settings/).
:::

## Request a derived image

Ask for a width and see the response change.

Request one of your images with an `ims` query string, replacing the host and the path with your own:

<Code client:visible lang="bash" code={`curl -s -o /dev/null -w "%{http_code} %{content_type} %{size_download} bytes\\n" \\
    -H "Accept: image/webp,image/*" \\
    "https://www.example.com/images/photo.jpg?ims=400x"`} />

The response reports its status, its type, and its size:

```text
200 image/webp 8312 bytes
```

Request the same image with no query string and compare the size. The resized response is smaller when the source image is wider than 400 pixels. Both responses can carry a different format from the file on your origin, because Image Processor converts images for browsers that accept another format, such as WEBP.

To confirm that Image Processor handled the response rather than the origin, read the headers:

<Code client:visible lang="bash" code={`curl -sI -H "Accept: image/webp" "https://www.example.com/images/photo.jpg?ims=400x"`} />

A processed response carries `x-ims: Enabled` and the size of the source image before the transformation:

```text
HTTP/2 200
content-type: image/webp
x-ims: Enabled
x-original-image-size: 484156
```

You now have an Application that transforms images on request, and a URL that describes the transformation.
