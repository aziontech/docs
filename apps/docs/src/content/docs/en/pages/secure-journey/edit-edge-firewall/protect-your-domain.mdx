You can set an existing [Firewall](/en/documentation/platform/firewall/) on a [Workload](/en/documentation/platform/workloads/) from Azion Console or the [Azion CLI](/en/documentation/devtools/cli/), so that it inspects the requests to the domains of the Workload. To create a Firewall, add its first rule, and set it in one pass, refer to [Firewall quickstart](/en/documentation/platform/firewall/quickstart/).

## Set the Firewall on the Workload

A Firewall has no domain of its own: the deployment of the Workload sets the Firewall, and the Workload record holds no Firewall field. A deployment carries three settings: its Application, its Firewall, and its [custom page set](/en/documentation/platform/custom-pages/settings/). The Application and the custom page set stay the ones the Workload uses today, so the Firewall is the only setting that changes. Until a deployment sets the Firewall, its rules see no request to the Workload.

A Workload holds one deployment, so you change the deployment it has. A second deployment is refused with `The maximum number of deployments allowed per workload is 1.` For every field of the deployment, refer to [Workload settings](/en/documentation/platform/workloads/settings/#deployment).

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

To set the Firewall in Azion Console:

<DocSteps>
  <DocStep title="Open the Workloads page">

  Access [Azion Console](https://console.azion.com/) > **Workloads**.

  </DocStep>
  <DocStep title="Open the Workload">

  Select the Workload whose requests the Firewall inspects. Its edit form opens.

  </DocStep>
  <DocStep title="Select your Firewall">

  In the **Deployment Settings** section, select your Firewall in the **Firewall** field. In a Workload with no Firewall, the field reads _Select a Firewall_.

  **Application** and **Custom Page** keep the values the Workload serves today.

  </DocStep>
  <DocStep title="Save the Workload">

  Select **Save**.

  </DocStep>
</DocSteps>

After the save, the deployment of the Workload sets your Firewall.

</Fragment>

<Fragment slot="panel.cli">

### CLI

The Azion CLI has no command that updates a deployment, and your Workload already has one. To set the Firewall, follow the Console panel.

On a Workload with no deployment yet, pass `--firewall-id` to `azion create workload-deployment` when you create the deployment. In a project that declares the Workload in `azion.config.js`, set the Firewall in `strategy.attributes.firewall` of its [`deployments`](/en/documentation/devtools/cli/azion-config-js/#workload-deployments) entry, then run `azion deploy`. For every flag, refer to [Azion CLI workload-deployment](/en/documentation/devtools/cli/resources/workload-deployment/).

</Fragment>

</Tabs>

## Set the Firewall on a v3 domain

An account on API v3 has [Domains](/en/documentation/platform/workloads/domains/) in place of Workloads, and sets the Firewall in the settings of each domain. To find out which model your account runs on, refer to [Verify your account migration](/en/documentation/guides/application-security/access-and-compliance/verify-account-migration/).

To set a Firewall on a domain in Azion Console:

<DocSteps>
  <DocStep title="Open the domain">

  Access [Azion Console](https://console.azion.com/) > **Domains** > **the domain whose requests the Firewall inspects**.

  </DocStep>
  <DocStep title="Choose the Firewall">

  In the **Settings** section, open the **Firewall** selector and choose the Firewall.

  </DocStep>
  <DocStep title="Save the domain">

  Select **Save**.

  </DocStep>
</DocSteps>

The Firewall then inspects the requests of that domain. The confirmation check reads the response of a request, whichever model served it.

## Confirm that the Firewall applies its rules

The check is the same for every interface. It needs a rule of the Firewall whose answer you can recognize. This section uses a rule that denies every path that starts with `/deny-test`, such as the one in [Create a Firewall rule](/en/documentation/guides/application-security/firewall-and-waf/work-with-rules-engine/).

The rules of the Firewall can take several minutes to reach the Workload after its deployment sets the Firewall, and no duration is guaranteed. Until then, requests reach your Application as before, and while the change propagates, answers to the same request alternate between the old result and the new one. Repeat the request until it returns `403`. For more information, refer to [How Firewall works](/en/documentation/platform/firewall/how-it-works/#propagation).

Send a request to the denied path. Replace `<your-domain>` with a domain the Workload serves, such as its Workload domain of the form `<id>.map.azionedge.net`:

```bash
curl -i https://<your-domain>/deny-test
```

The Firewall refuses the request with `403`. This excerpt of the response leaves out its long `content-security-policy` header:

```text
HTTP/2 403
server: nginx
date: Thu, 01 Jan 2026 12:00:00 GMT
content-type: text/html; charset=utf-8
x-content-type-options: nosniff
x-azion-request-id: 0123456789abcdef0123456789abcdef
x-azion-edge-location: <edge-location>
alt-svc: h3=":443"; ma=86400
```

The body is Azion's default error page, headed Forbidden, and it shows your IP address and the request ID. No response header identifies the Firewall or the rule behind the refusal. Paths that no rule matches still reach your Application.

If `/deny-test` keeps reaching your Application after the change has had several minutes to propagate, refer to [Troubleshoot Firewall](/en/documentation/platform/firewall/troubleshooting/#a-firewall-does-not-act-on-a-workloads-requests).
