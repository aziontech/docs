You can calibrate a [Bot Manager](/en/documentation/platform/firewall/bot-manager/) Function Instance from Azion Console, and read the report log it writes from Azion Console or the GraphQL API. For what each choice costs and how long to hold it, refer to [Best practices for Firewall](/en/documentation/platform/firewall/best-practices/#bot-manager).

The steps are the same for [Bot Manager Lite](/en/documentation/platform/firewall/bot-manager/bot-manager-lite/). Where the arguments of the two editions differ, the section names each one.

---

## Prerequisites

- A Bot Manager Function Instance on a Firewall, run by a [Rules Engine for Firewall](/en/documentation/platform/firewall/rules-engine/) rule. For more information, refer to [Bot Manager quickstart](/en/documentation/platform/firewall/bot-manager/quickstart/).
- Access to Azion Console. To sign in, refer to [How to access Azion Console](/en/documentation/guides/platform/account-and-billing/how-to-access-azion-console/).
- A personal token, for the query that reads the report log. For more information, refer to [Personal Tokens](/en/documentation/fundamentals/personal-tokens/).
- To score addresses against a reputation list, the ID of each [Network List](/en/documentation/platform/firewall/network-shield/network-lists/) you want to use.

## Turn the logging up

A report line is the only record of how one request scored. The Function writes a line only for the requests that `internal_logs` selects, and the argument ships at `0`. Raise it to `2` so that every request produces a line, including one that scores `0`. Set `action` to `allow` so that a request at or above the threshold is scored and still served:

```json
{
  "threshold": 30,
  "action": "allow",
  "internal_logs": 2,
  "log_tag": "bot-calibration",
  "log_headers": [
    "accept",
    "accept-encoding",
    "accept-language",
    "content-type",
    "host",
    "referer",
    "user-agent",
    "x-forwarded-for",
    "x-request-id"
  ]
}
```

| Argument | What it does in the observation window |
| --- | --- |
| `action` | At `allow`, a request at or above the threshold continues to the Application |
| `internal_logs` | At `2`, the Function writes a line for every request. The value is a number: the API stores the string `"2"` as sent, and Bot Manager Lite reads a value it does not recognize as `0` |
| `log_tag` | The tag the line prefix carries, which separates the lines of one Function Instance from the lines of another |
| `log_headers` | The request headers the Function writes into the line. The nine above are the shipped default |

:::caution
The API checks that the arguments are a JSON object or array, and it checks no key. A misspelled key such as `thresold` is stored and read back as typed, the API and the Azion CLI raise no error, and `threshold` stays absent from the Function Instance. To see what the Function does without it, refer to [Threshold](/en/documentation/platform/firewall/bot-manager/arguments/#threshold).
:::

To replace the arguments of the Function Instance in Azion Console:

<DocSteps>
  <DocStep title="Open the Firewall that runs the Function Instance">

  Access [Azion Console](https://console.azion.com/) > **Firewalls**, then select that Firewall.

  </DocStep>
  <DocStep title="Select the Functions Instances tab" />
  <DocStep title="Open the Function Instance">

  Select the Bot Manager Function Instance you want to calibrate.

  </DocStep>
  <DocStep title="Replace the arguments">

  In the **Arguments** section, enter the object. Bot Manager Lite carries no argument schema, so the section holds a JSON editor and builds no form from it.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

The Function Instance scores every request the rule sends it and refuses none of them. A change to the arguments of a Function Instance takes up to a few minutes to reach Azion's distributed infrastructure, and no duration is guaranteed. While it spreads, answers to the same request alternate between the earlier configuration and the new one. For more information, refer to [Propagation](/en/documentation/platform/firewall/how-it-works/#propagation).

Change one argument at a time, so that each reading describes one change. Return `action` to the value you run in production once the lines answer your question.

## Read the report log in Real-Time Events

[Real-Time Events](/en/documentation/platform/real-time-events/) serves each report line as a record of the `functionConsoleEvents` dataset. Azion Console has no Bot Manager column of its own, so the JSON object of a line arrives whole and not split into columns.

To read the lines in Azion Console:

<DocSteps>
  <DocStep title="Open Real-Time Events">

  Access [Azion Console](https://console.azion.com/) > **Real-Time Events**.

  </DocStep>
  <DocStep title="Select the Functions Console tab">

  The tab shows a **Time** column and a **Log Body** column.

  </DocStep>
  <DocStep title="Narrow the period to your observation window" />
  <DocStep title="Read the lines whose prefix carries your log_tag" />
</DocSteps>

To read the same records with the API, send the following query to `https://api.azion.com/v4/events/graphql` with an `Authorization: Token [TOKEN VALUE]` header and a `tsRange` covering the window:

```graphql
{
  functionConsoleEvents(
    limit: 200
    filter: { tsRange: { begin: "2026-01-01T11:30:00", end: "2026-01-01T13:00:00" } }
    orderBy: [ts_ASC]
  ) {
    ts
    line
    level
    lineSource
    functionId
    configurationId
  }
}
```

The query answers `200` and returns one record per line the Function wrote. `line` carries the whole report line. `functionId` is the ID of the installed Function, not of its Function Instance. `configurationId` is the ID of the Workload the request arrived on, not of the Firewall.

A line opens with the prefix `[Bot-Protection][<log_tag>] Report:` and continues as one JSON object:

```text
[Bot-Protection][bot-calibration] Report:  {"request_id":"0123456789abcdef0123456789abcdef","remote_addr":"203.0.113.42","fingerprint":"ge20cn020000_000000000000_000000000000_000000000000","host":"<your-workload-domain>","http_user_agent":"","request_uri":"/","geoip_country":"DE","geoip_region":"HE","asn":"64496","score":28,"bot_category":"Bad Bot Signatures, Malicious Intent detected","classified":"legitimate","action":"allow","matched_rules":[1,10,18,19,20]}
```

Four values carry the calibration. `score` is the total the Function calculated, `matched_rules` names the rules that produced it, `action` is what the Function applied, and `classified` is the verdict it reached. In the line above the score is `28` under a threshold of `30`, so `action` reads `allow` and `classified` reads `legitimate`. Under a threshold that `28` reaches, the same request reads `bad bot` and meets the configured action.

`bot_category` is a comma-joined list of the categories of the rules that matched, so a line classified `legitimate` can still name bad-bot categories. For every field a line carries and the four values `classified` takes, refer to [Logs](/en/documentation/platform/firewall/bot-manager/logs/#fields).

The two Real-Time Metrics datasets that the Bot Manager dashboards read count requests by classification, action, mode, host, geography, and URL, and neither carries a score. Read a score distribution from the report log. For the counts, refer to [Query Bot Manager data with GraphQL](/en/documentation/guides/platform/observability/query-bot-manager-data-with-graphql/), [Query the top URLs bots reach with GraphQL](/en/documentation/guides/platform/observability/query-bot-manager-breakdown-data-with-graphql/), and [Real-Time Metrics](/en/documentation/platform/real-time-metrics/secure-dashboards/#bot-manager).

## Set the threshold from the scores you read

`threshold` is the score at which `action` applies. The value comes from the distribution in your own report log: the clients you recognize cluster at the low end, automated clients cluster higher, and the threshold goes in the gap between the two.

To set the threshold:

<DocSteps>
  <DocStep title="Collect the scores of the window">

  Read `score` on the lines the window produced, and separate the requests you recognize from the ones you do not.

  </DocStep>
  <DocStep title="Pick a value in the gap">

  Set it above the scores of the traffic you recognize, and at or below the scores of the traffic you do not.

  </DocStep>
  <DocStep title="Apply the threshold and the action">

  Replace the arguments of the Function Instance with the new `threshold` and the `action` that a request at or above it meets.

  </DocStep>
  <DocStep title="Wait for the change to propagate">

  A change to the arguments takes up to a few minutes, and answers alternate meanwhile.

  </DocStep>
  <DocStep title="Read the lines nearest the threshold">

  Read the lines classified `legitimate` whose score sits just below it. Those requests are one matched rule away from the action.

  </DocStep>
</DocSteps>

The Function Instance applies the action to the traffic at or above the threshold, and the lines below it name the requests that came closest. Repeat the loop: lower the threshold while automated traffic still passes, and raise it when requests you recognize are refused.

:::caution
`classified` is computed against the threshold in force, not against the score alone. Raising a threshold relabels traffic as well as stopping the action, so record the threshold beside any classification count you compare across two periods. `score` and `matched_rules` describe the request and do not move.
:::

## Take a rule out of the scoring

A score is the sum of the increments of the rules a request matched. `matched_rules` carries the IDs of those rules, and `score` carries the total. Add an ID to the arguments only after it appears in your own lines.

To stop a rule from raising a score:

<DocSteps>
  <DocStep title="Find the lines you did not expect">

  Read the lines classified `legitimate` whose score sits at or near the threshold, and the lines that carry requests you recognize.

  </DocStep>
  <DocStep title="Read the rule IDs off those lines">

  `matched_rules` carries the IDs of the rules each request matched. Compare several lines, so that one request does not settle it.

  </DocStep>
  <DocStep title="Add the IDs to the arguments">

  On Bot Manager Lite, add them to `disabled_rules`. On Bot Manager, add them to `disabled_static_rules`. Both are arrays.

  </DocStep>
  <DocStep title="Wait for the change to propagate, then read the lines again" />
</DocSteps>

The requests that matched the rule score lower by its increment. On Bot Manager Lite, the Function no longer processes a rule in `disabled_rules`. On Bot Manager, a rule in `disabled_static_rules` still runs, and each match lands in the `disabled_matched_rules` field of the line. A rule taken out of the scoring is out of it for every request the Function Instance scores.

For both arguments and the types they take, refer to [Disabled rules](/en/documentation/platform/firewall/bot-manager/arguments/#disabled-rules).

## Score an address against a reputation Network List

`reputation_network_lists` takes an array of Network List IDs. The Function checks the address of every request it scores against each list, and raises the score once for each list the address is found in. Azion maintains lists of its own: Network List `2` is _Azion IP Tor Exit Nodes_, a list of IP addresses. A list you build yourself is named the same way, by its ID.

On Bot Manager Lite the argument ships empty, and a match is rule `14`, worth 6 points for each list. On Bot Manager the argument defaults to the Azion-maintained Network Lists of the account. Six points do not reach the threshold of `30` that Bot Manager Lite ships, so a listed address meets the action only when other rules match as well.

To score addresses against a list:

<DocSteps>
  <DocStep title="Replace the arguments with the list IDs">

  Replace the arguments of the Function Instance, as in [Turn the logging up](#turn-the-logging-up), with an object that names the lists:

  ```json
  {
    "threshold": 30,
    "action": "allow",
    "internal_logs": 2,
    "reputation_network_lists": [2],
    "log_tag": "bot-reputation"
  }
  ```

  </DocStep>
  <DocStep title="Wait for the change to propagate" />
  <DocStep title="Read the lines of the listed addresses">

  On Bot Manager Lite, a line whose address is on a list carries rule `14` in `matched_rules`, and its `score` is 6 points higher for each list.

  </DocStep>
</DocSteps>

The Function Instance checks every address the rule sends it against the lists you named. For every rule Bot Manager Lite runs and what each one adds, refer to [Bot Manager Lite](/en/documentation/platform/firewall/bot-manager/bot-manager-lite/#rules).

## Raise the dynamic rules tolerance

Bot Manager documents a dynamic rules method that scores a request against the Application's own traffic baseline. `dynamic_rules_tolerance` sets how strict that comparison is. The documented values are `soft`, `medium`, and `hard`, and `soft` is the documented default. Bot Manager Lite does not carry the method.

Move one step at a time. A tolerance change re-scores every request the Function Instance sees, so each step needs an observation window of its own. Two steps taken together produce their false positives together, and nothing in the lines says which step produced them.

To raise the tolerance one step:

<DocSteps>
  <DocStep title="Replace the arguments with the next tolerance">

  Replace the arguments of the Function Instance, as in [Turn the logging up](#turn-the-logging-up). Set `dynamic_rules_tolerance` one step up and `dynamic_rules_logs_enabled` to `true`, which writes the debugging logs of the method:

  ```json
  {
    "threshold": 18,
    "action": "deny",
    "dynamic_rules_tolerance": "medium",
    "dynamic_rules_logs_enabled": true,
    "log_tag": "tolerance-medium"
  }
  ```

  </DocStep>
  <DocStep title="Wait for the change to propagate" />
  <DocStep title="Read the lines of the window">

  Compare the requests you recognize against the previous window, and look for new refusals.

  </DocStep>
  <DocStep title="Turn the debugging logs off">

  When the window closes, set `dynamic_rules_logs_enabled` to `false`, because of the volume it adds to the log.

  </DocStep>
</DocSteps>

The Function Instance compares every request against the baseline at the new tolerance. For the four arguments the method takes, refer to [Dynamic rules](/en/documentation/platform/firewall/bot-manager/arguments/#dynamic-rules).

## Keep a copy of the report log

Report lines surface in Real-Time Events, and the platform ages that data out. A copy in a destination of your own lasts as long as you keep it, beside the records of the Application those requests reached. [Data Stream](/en/documentation/platform/data-stream/) forwards the report lines from the _Functions_ data source to an endpoint you configure.

To keep a copy:

<DocSteps>
  <DocStep title="Create a stream on the Functions data source">

  In the stream, select _Functions_ as the data source and _Functions Event Collector_ as the template, then select your endpoint. For the full procedure, refer to [Debug functions with Data Stream](/en/documentation/guides/platform/observability/debugging-functions-data-stream/).

  </DocStep>
  <DocStep title="Lower internal_logs when the window closes">

  At `2`, every request produces a line, and that is the volume the stream carries.

  </DocStep>
</DocSteps>

The endpoint receives the lines the Function writes, in the format of the template. For the endpoints a stream writes to, refer to [Endpoints](/en/documentation/platform/data-stream/endpoints/).
