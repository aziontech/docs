You can create a [Web Application Firewall (WAF)](/en/documentation/platform/firewall/waf/) rule set, and apply it to the requests of a [Firewall](/en/documentation/platform/firewall/), from Azion Console, the Azion CLI, or the API. For a first run that fixes every option and ends in a blocked request, refer to [WAF quickstart](/en/documentation/platform/firewall/waf/quickstart/).

## Create the rule set

A rule set carries up to eight threat families, each with its own sensitivity. Every family opens at `medium`, the level to start from before your traffic shows a reason to raise one. For what each family detects and what each level changes, refer to [WAF Rule Sets](/en/documentation/platform/firewall/waf/rules-set/#threat-families).

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

The form lists all eight families, so you set every sensitivity in one place. To create the rule set in Azion Console:

<DocSteps>
  <DocStep title="Open the WAF Rules page">

  Access [Azion Console](https://console.azion.com/) > **WAF Rules**.

  </DocStep>
  <DocStep title="Select WAF Rule" />
  <DocStep title="Name the rule set">

  In the **General** section, enter a **Name**. For example: `checkout-waf`.

  </DocStep>
  <DocStep title="Set the sensitivity of each threat family">

  The **Threat Type Configuration** section lists eight families, each at _Sensitivity Medium_. For example, set **SQL Injection** to _Sensitivity High_, or leave every family at _Sensitivity Medium_.

  </DocStep>
  <DocStep title="Keep the Active switch turned on" />
  <DocStep title="Save the rule set" />
</DocSteps>

The rule set appears in **WAF Rules**. It scores no request until a rule of a Firewall applies it.

</Fragment>

<Fragment slot="panel.cli">

### CLI

`--thresholds` takes comma-separated `threat=sensitivity` pairs. To create the rule set with the Azion CLI:

<DocSteps>
  <DocStep title="Run the create command">

  ```bash
  azion create waf --name "checkout-waf" --active true --rulesets 1 \
    --thresholds "sql_injection=medium,cross_site_scripting=medium,directory_traversal=medium,evading_tricks=medium,file_upload=medium,identified_attack=medium,remote_file_inclusion=medium,unwanted_access=medium"
  ```

  </DocStep>
  <DocStep title="Read the output">

  The command prints the ID of the rule set:

  ```text
  Created WAF with ID <waf-id>
  ```

  </DocStep>
</DocSteps>

The rule set is active, on ruleset `1`, with every family at the sensitivity you sent. Record the ID: the rule in the next section uses it.

A create that sends only `--name` also gives a complete rule set: active, on ruleset `1`, with engine version `2021-Q3`, engine type `score`, and all eight families at `medium`.

</Fragment>

<Fragment slot="panel.api">

### API

Each entry of `thresholds` sets one threat family and its sensitivity. To create the rule set with the API:

<DocSteps>
  <DocStep title="Send the create request">

  Replace `[TOKEN VALUE]` with your personal token:

  ```bash
  curl --request POST \
    --url https://api.azion.com/v4/workspace/wafs \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: application/json' \
    --data '{
    "name": "checkout-waf",
    "active": true,
    "engine_settings": {
      "engine_version": "2021-Q3",
      "type": "score",
      "attributes": {
        "rulesets": [1],
        "thresholds": [
          { "threat": "cross_site_scripting", "sensitivity": "medium" },
          { "threat": "directory_traversal", "sensitivity": "medium" },
          { "threat": "evading_tricks", "sensitivity": "medium" },
          { "threat": "file_upload", "sensitivity": "medium" },
          { "threat": "identified_attack", "sensitivity": "medium" },
          { "threat": "remote_file_inclusion", "sensitivity": "medium" },
          { "threat": "sql_injection", "sensitivity": "medium" },
          { "threat": "unwanted_access", "sensitivity": "medium" }
        ]
      }
    }
  }'
  ```

  </DocStep>
  <DocStep title="Read the response">

  The API answers `202`, and `"state": "pending"` means the rule set is still propagating:

  ```json
  {
    "state": "pending",
    "data": {
      "id": 12349,
      "active": true,
      "name": "checkout-waf",
      "last_editor": "user@example.com",
      "last_modified": "2026-01-01T12:00:00.000000Z",
      "product_version": "1.0",
      "engine_settings": {
        "engine_version": "2021-Q3",
        "type": "score",
        "attributes": {
          "rulesets": [1],
          "thresholds": [
            { "threat": "cross_site_scripting", "sensitivity": "medium" },
            { "threat": "directory_traversal", "sensitivity": "medium" },
            { "threat": "evading_tricks", "sensitivity": "medium" },
            { "threat": "file_upload", "sensitivity": "medium" },
            { "threat": "identified_attack", "sensitivity": "medium" },
            { "threat": "remote_file_inclusion", "sensitivity": "medium" },
            { "threat": "sql_injection", "sensitivity": "medium" },
            { "threat": "unwanted_access", "sensitivity": "medium" }
          ]
        }
      },
      "version_id": null,
      "version_state": null,
      "is_versioned": false,
      "version": null
    }
  }
  ```

  </DocStep>
</DocSteps>

Record the `id`. The rule in the next section uses it.

:::note
A `thresholds` array with fewer than eight entries is accepted, and the rule set then carries only the families you sent. A repeated `threat` is refused with `500` and `10067 Internal Server Error`.
:::

</Fragment>

</Tabs>

In the [Protect web applications from OWASP Top 10 and zero-day attacks](/en/documentation/use-cases/secure-applications-and-networks/protect-web-applications-from-owasp-top-10-and-zero-day-attacks/) use case, this section takes these values:

| Setting | Value |
| --- | --- |
| Rule set | `webapp-waf`, every threat family at _Sensitivity Medium_ |

In the [Protect public APIs from abuse](/en/documentation/use-cases/secure-applications-and-networks/protect-public-apis-from-abuse/) use case, this section takes these values:

| Setting | Value |
| --- | --- |
| Rule set | `api-waf`, every threat family at _Sensitivity Medium_ |

In the [Block account takeover on login and checkout flows](/en/documentation/use-cases/secure-applications-and-networks/block-account-takeover-on-login-and-checkout-flows/) use case, this section takes these values:

| Setting | Value |
| --- | --- |
| Rule set | `auth-waf`, every threat family at _Sensitivity Medium_ |

## Apply the rule set to every request

A rule of [Rules Engine for Firewall](/en/documentation/platform/firewall/rules-engine/) selects requests with its criteria, and its _Set WAF_ behavior applies one rule set in one mode. A rule carries at most one _Set WAF_ behavior. The mode is required: `logging` records what the rule set flags and serves the request, and `blocking` refuses the request with `400`.

:::caution
A criterion on `${request_args}` matches only a request that carries a query string. A `POST` with its fields in the body and no query string then skips the rule set and reaches your Application unscored. Key the criterion on `${request_uri}` instead.
:::

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

To apply the rule set to every request in Azion Console:

<DocSteps>
  <DocStep title="Open the Firewall">

  Access [Azion Console](https://console.azion.com/) > **Firewalls**, then select the Firewall.

  </DocStep>
  <DocStep title="Select the Rules Engine tab" />
  <DocStep title="Select Rule" />
  <DocStep title="Name the rule">

  Enter a name. For example: `Apply checkout-waf`.

  </DocStep>
  <DocStep title="Set the criterion">

  In the **Criteria** section, select the `Request Uri` variable, the _starts with_ operator, and `/` as the argument.

  </DocStep>
  <DocStep title="Add the Set WAF behavior">

  In the **Behaviors** section, select **Set WAF**, then select `checkout-waf` as the rule set and _Blocking_ as the mode.

  </DocStep>
  <DocStep title="Save the rule" />
</DocSteps>

</Fragment>

<Fragment slot="panel.cli">

### CLI

`azion create firewall-rule` reads the rule from `--file`, so the behavior and the mode travel in the JSON. To apply the rule set with the Azion CLI:

<DocSteps>
  <DocStep title="Write the rule to a file">

  Save the following as `fw-rule.json`, with the ID of your rule set in `waf_id`:

  ```json
  {
    "name": "Apply checkout-waf",
    "active": true,
    "description": "",
    "criteria": [
      [
        {
          "conditional": "if",
          "variable": "${request_uri}",
          "operator": "starts_with",
          "argument": "/"
        }
      ]
    ],
    "behaviors": [
      {
        "type": "set_waf",
        "attributes": {
          "waf_id": 12350,
          "mode": "blocking"
        }
      }
    ]
  }
  ```

  </DocStep>
  <DocStep title="Create the rule">

  Replace `<firewall-id>` with the ID of your Firewall:

  ```bash
  azion create firewall-rule --firewall-id <firewall-id> --file fw-rule.json
  ```

  </DocStep>
  <DocStep title="Read the output">

  The command prints the ID of the rule:

  ```text
  Created Firewall Rule with ID <rule-id>
  ```

  </DocStep>
</DocSteps>

</Fragment>

<Fragment slot="panel.api">

### API

A shell expands `${request_uri}` in a double-quoted string, so the body travels in a file. To apply the rule set with the API:

<DocSteps>
  <DocStep title="Write the rule to a file">

  Save the following as `rule.json`, with the ID of your rule set in `waf_id`:

  ```json
  {
    "name": "Apply checkout-waf",
    "active": true,
    "criteria": [
      [
        {
          "conditional": "if",
          "variable": "${request_uri}",
          "operator": "starts_with",
          "argument": "/"
        }
      ]
    ],
    "behaviors": [
      {
        "type": "set_waf",
        "attributes": {
          "waf_id": 12349,
          "mode": "blocking"
        }
      }
    ]
  }
  ```

  </DocStep>
  <DocStep title="Send the create request">

  Replace `<firewall-id>` with the ID of your Firewall:

  ```bash
  curl --request POST \
    --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: application/json' \
    --data @rule.json
  ```

  </DocStep>
  <DocStep title="Read the response">

  The API answers `202` with the rule and two fields it adds, `description` and `order`:

  ```json
  {
    "state": "pending",
    "data": {
      "id": 123456,
      "name": "Apply checkout-waf",
      "last_editor": "user@example.com",
      "last_modified": "2026-01-01T12:00:00.000000Z",
      "created_at": "2026-01-01T12:00:00.000000Z",
      "active": true,
      "criteria": [
        [
          {
            "conditional": "if",
            "variable": "${request_uri}",
            "operator": "starts_with",
            "argument": "/"
          }
        ]
      ],
      "behaviors": [
        {
          "type": "set_waf",
          "attributes": {
            "waf_id": 12349,
            "mode": "blocking"
          }
        }
      ],
      "description": "",
      "order": 1
    }
  }
  ```

  </DocStep>
</DocSteps>

A `set_waf` behavior with no `mode` is refused with `400`:

```json
{"errors":[{"code":"10059","title":"Required Field","detail":"This field is required.","status":"400","source":{"pointer":"/data/behaviors/0/attributes/mode"}}]}
```

`mode` takes `logging` or `blocking`. Any other value is refused with `400` and `10039 Invalid Choice`, and a second `set_waf` behavior in one rule with `25011 Duplicated Behavior`.

</Fragment>

</Tabs>

The Firewall applies the rule set to every request of the Workloads whose deployment sets it, and refuses with `400` a request the rule set blocks. A new rule propagates across Azion's distributed infrastructure before requests show it. For more information, refer to [Propagation](/en/documentation/platform/firewall/how-it-works/#propagation).

## Apply a rule set to selected paths in Logging

A rule can apply a rule set only to the paths that need it, such as a login form, in _Logging_ mode. You then read what the rule set flags on your own traffic before it refuses anything. The rule matches the paths, not the query string, because a form posts its fields in the body.

The example applies `auth-waf` to `/login`, `/signup`, and `/checkout`. Replace each value with your own.

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

### Console

To apply the rule set to the three paths in Azion Console:

<DocSteps>
  <DocStep title="Open the Rules Engine tab of the Firewall">

  Access [Azion Console](https://console.azion.com/) > **Firewalls**, select the Firewall, then go to the **Rules Engine** tab.

  </DocStep>
  <DocStep title="Select Rule" />
  <DocStep title="Name the rule">

  Enter `auth - apply auth-waf`.

  </DocStep>
  <DocStep title="Match the three paths">

  In the **Criteria** section, select `Request Uri`, _starts with_, and `/login`. Add two criteria joined by **Or**: `/signup` and `/checkout`.

  </DocStep>
  <DocStep title="Add the Set WAF behavior">

  In the **Behaviors** section, select **Set WAF**, then `auth-waf` and _Logging_.

  </DocStep>
  <DocStep title="Save the rule" />
</DocSteps>

</Fragment>

<Fragment slot="panel.cli">

### CLI

To apply the rule set to the three paths with the Azion CLI:

<DocSteps>
  <DocStep title="Write the rule to a file">

  Save the following as `auth-rule.json`, with the ID of your rule set in `waf_id`:

  ```json
  {
    "name": "auth - apply auth-waf",
    "active": true,
    "criteria": [
      [
        { "variable": "${request_uri}", "conditional": "if", "operator": "starts_with", "argument": "/login" },
        { "variable": "${request_uri}", "conditional": "or", "operator": "starts_with", "argument": "/signup" },
        { "variable": "${request_uri}", "conditional": "or", "operator": "starts_with", "argument": "/checkout" }
      ]
    ],
    "behaviors": [{ "type": "set_waf", "attributes": { "waf_id": 12351, "mode": "logging" } }]
  }
  ```

  </DocStep>
  <DocStep title="Create the rule">

  ```bash
  azion create firewall-rule --firewall-id <firewall-id> --file auth-rule.json
  ```

  The command prints `Created Firewall Rule with ID <rule-id>`.

  </DocStep>
</DocSteps>

</Fragment>

<Fragment slot="panel.api">

### API

To apply the rule set to the three paths with the API:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules \
  --header 'Authorization: Token [TOKEN VALUE]' \
  --header 'Content-Type: application/json' \
  --data '{
  "name": "auth - apply auth-waf",
  "active": true,
  "criteria": [
    [
      { "variable": "${request_uri}", "conditional": "if", "operator": "starts_with", "argument": "/login" },
      { "variable": "${request_uri}", "conditional": "or", "operator": "starts_with", "argument": "/signup" },
      { "variable": "${request_uri}", "conditional": "or", "operator": "starts_with", "argument": "/checkout" }
    ]
  ],
  "behaviors": [{ "type": "set_waf", "attributes": { "waf_id": 12351, "mode": "logging" } }]
}'
```

The API answers `202` with a `state` of `pending` and the rule as it was stored.

</Fragment>
</Tabs>

The rule set scores the requests to the three paths and records what it would block, with `wafLearning` set to `1` and `wafAttackAction` set to `$LEARNING-BLOCK` in Real-Time Events. Move the rule to _Blocking_ once the last 3 days of [Tuning](/en/documentation/guides/application-security/firewall-and-waf/tune-waf/) hold no request that should have been served. For the switch, refer to [Change the mode](/en/documentation/guides/application-security/firewall-and-waf/how-to-check-your-waf-mode/#change-the-mode).

To confirm that the rule scores the paths, send an injection-shaped query string to one of them:

```bash
curl -i "https://www.example.com/login?q=1%27%20OR%20%271%27%3D%271"
```

In _Logging_ mode, the request reaches your Application. After the switch to _Blocking_, the same request receives:

```text
HTTP/2 400
```

The `x-azion-request-id` header of the response finds the WAF record of the request. For the lookup, refer to [Find the WAF score of a blocked request](/en/documentation/guides/application-security/firewall-and-waf/how-to-find-waf-score/).

In the [Protect web applications from OWASP Top 10 and zero-day attacks](/en/documentation/use-cases/secure-applications-and-networks/protect-web-applications-from-owasp-top-10-and-zero-day-attacks/) use case, this section takes these values:

| Setting | Value |
| --- | --- |
| Rule | `webapp - apply webapp-waf` |
| Criterion | `Request Uri` _starts with_ `/` |
| Behavior | **Set WAF** with `webapp-waf`, in _Logging_, sent in the API as `"mode": "logging"` |

The rule set scores every request that the use case's network rule lets through, and records what it would block. To read those records and turn a false positive into an exception, refer to [Tune a WAF rule set](/en/documentation/guides/application-security/firewall-and-waf/tune-waf/).

In the [Protect public APIs from abuse](/en/documentation/use-cases/secure-applications-and-networks/protect-public-apis-from-abuse/) use case, this section takes these values:

| Setting | Value |
| --- | --- |
| Rule | `api - apply api-waf` |
| Criterion | `Request Uri` _starts with_ `/v1/` |
| Behavior | **Set WAF** with `api-waf`, in _Logging_, sent in the API as `"mode": "logging"` |

The rule set scores every request to `/v1/` against `api-waf`, and records what it would block.

The [Block account takeover on login and checkout flows](/en/documentation/use-cases/secure-applications-and-networks/block-account-takeover-on-login-and-checkout-flows/) use case uses the values of this example.

In the [Protect web applications from OWASP Top 10 and zero-day attacks](/en/documentation/use-cases/secure-applications-and-networks/protect-web-applications-from-owasp-top-10-and-zero-day-attacks/) use case, expect:

- **WAF scores an attack pattern.** From an address that is not listed, a request with an injection-shaped query string, `https://www.example.com/?q=1%27%20OR%20%271%27%3D%271`, is answered as usual in _Logging_, and receives `HTTP/2 400` after the switch to _Blocking_. The `x-azion-request-id` header of the response finds the request in the `workloadEvents` dataset of Real-Time Events, where `wafMatch` names the internal rules that matched, `1009` and `1013` for this query string. For the lookup, refer to [Find the WAF score of a blocked request](/en/documentation/guides/application-security/firewall-and-waf/how-to-find-waf-score/).

In the [Protect public APIs from abuse](/en/documentation/use-cases/secure-applications-and-networks/protect-public-apis-from-abuse/) use case, expect:

- **WAF scores an attack pattern.** With a valid token, a request with an injection-shaped query string, `https://api.example.com/v1/orders?q=1%27%20OR%20%271%27%3D%271`, is answered as usual in _Logging_, and receives `HTTP/2 400` after the switch to _Blocking_. Its `x-azion-request-id` finds the record in Real-Time Events.

In the [Block account takeover on login and checkout flows](/en/documentation/use-cases/secure-applications-and-networks/block-account-takeover-on-login-and-checkout-flows/) use case, expect:

- **WAF scores attacks on `/v1/`.** A request to `/v1/` with an injection-shaped query string is answered as usual in _Logging_, and receives `HTTP/2 400` after the switch to _Blocking_. Its `x-azion-request-id` finds the record in Real-Time Events.

In the [Prepare regulated web applications for security audits](/en/documentation/use-cases/secure-applications-and-networks/prepare-regulated-web-applications-for-security-audits/) use case, expect:

- **Attack patterns are filtered.** Send `https://www.example.com/?q=1%27%20OR%20%271%27%3D%271`. With the WAF rule in _Blocking_, the response is `400`.
