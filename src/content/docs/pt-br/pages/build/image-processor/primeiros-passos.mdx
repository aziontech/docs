Este guia conduz você pela requisição da sua primeira imagem derivada a partir de uma aplicação. Ao final, você terá:

- Image Processor ativado em uma aplicação.
- Um cache setting que armazena cada transformação como um objeto próprio.
- Uma regra do Rules Engine que envia requisições de imagem para o módulo.
- Uma imagem redimensionada retornada a partir de uma URL que você escreveu.

Quatro objetos produzem esse resultado, e cada um está ligado ao anterior. A **aplicação** carrega o switch do módulo. O **cache setting** pertence à aplicação e decide que duas transformações diferentes são dois objetos diferentes em cache. A **regra** pertence à aplicação, corresponde a requisições de imagem e aplica tanto o cache setting quanto o behavior **Optimize Images**. A URL da imagem carrega então a transformação na própria query string `ims`. Uma requisição que nenhuma regra corresponde é entregue sem processamento, então é a regra que dá sentido à query string.

---

## Pré-requisitos

- Uma [conta Azion](/pt-br/documentacao/fundamentos/criar-uma-conta/).
- Uma aplicação que já entrega imagens a partir de uma origem. Para criar uma, consulte [Criar uma aplicação](/pt-br/documentacao/guias/desenvolvimento-de-aplicacoes/primeiros-passos/criar-uma-aplicacao/).
- O path de uma imagem que a aplicação serve, para que você possa requisitá-la ao final.

---

## 1. Ative Image Processor

O módulo é um switch na aplicação, e fica desativado até você configurá-lo.

<DocSteps>
  <DocStep title="Abra a aplicação">

  Acesse [Azion Console](/pt-br/documentacao/guias/plataforma/conta-e-billing/como-acessar-o-azion-console/) > **Applications** e selecione a aplicação que entrega suas imagens.

  </DocStep>
  <DocStep title="Vá para a aba Main Settings" />
  <DocStep title="Ative Image Processor">

  Na seção **Modules**, ative **Image Processor**, descrito como *Enable dynamic image editing options*.

  </DocStep>
  <DocStep title="Ative Application Accelerator">

  O switch fica na mesma seção.

  </DocStep>
  <DocStep title="Selecione Save" />
</DocSteps>

**Application Accelerator** está nesta lista por um motivo: o campo que varia o cache por uma query string pertence a ele, e o passo 2 usa esse campo. Processar uma imagem não exige o módulo, mas armazenar cada transformação separadamente em cache exige.

A aplicação agora carrega os dois módulos, e o behavior **Optimize Images** fica disponível para as suas regras.

---

## 2. Crie um cache setting que varia pela query string ims

Sem esta etapa, o cache não consegue diferenciar uma transformação de outra, e pode responder a uma requisição de imagem de 400 pixels com uma de 200 pixels.

<DocSteps>
  <DocStep title="Vá para a aba Cache Settings" />
  <DocStep title="Selecione + Cache" />
  <DocStep title="Nomeie a cache setting">

  Em **Name**, digite `images`.

  </DocStep>
  <DocStep title="Expanda Cache vary by Query String">

  O painel fica na seção **Application Accelerator**.

  </DocStep>
  <DocStep title="Defina Behavior como Allowlist" />
  <DocStep title="Adicione o campo ims">

  Em **Fields**, digite `ims`.

  </DocStep>
  <DocStep title="Selecione Save" />
</DocSteps>

A aplicação agora tem um cache setting que armazena um objeto por valor distinto de `ims`. Para o restante dos campos que um cache setting carrega, incluindo por quanto tempo um objeto permanece em cache, consulte [Cache Settings](/pt-br/documentacao/build/cache/cache-settings/).

---

## 3. Crie uma regra que envia as requisições de imagem para o módulo

A regra é o que converte a query string em uma transformação.

<DocSteps>
  <DocStep title="Vá para a aba Rules Engine" />
  <DocStep title="Selecione + Rule" />
  <DocStep title="Nomeie a regra">

  Em **Name**, digite `Optimize images`.

  </DocStep>
  <DocStep title="Selecione Request Phase" />
  <DocStep title="Selecione a variável">

  Nos critérios, selecione `${request_uri}`.

  </DocStep>
  <DocStep title="Selecione o operador matches" />
  <DocStep title="Digite o argumento">

  Digite `\.(jpg|jpeg|gif|bmp|png|ico|webp|avif)`.

  </DocStep>
  <DocStep title="Adicione o behavior Set Cache Policy">

  Nos behaviors, selecione **Set Cache Policy** e escolha o cache setting `images`.

  </DocStep>
  <DocStep title="Selecione Add Behavior" />
  <DocStep title="Selecione Optimize Images" />
  <DocStep title="Selecione Save" />
</DocSteps>

Toda requisição para um path terminado em uma dessas extensões agora alcança Image Processor, carrega o cache setting `images` e é processada quando a URL dela pede uma transformação.

---

## 4. Requisite uma imagem derivada

Peça uma largura e veja a resposta mudar.

Requisite uma das suas imagens com uma query string `ims`, substituindo o host e o path pelos seus próprios:

```bash
curl -s -o /dev/null -w "%{http_code} %{content_type} %{size_download} bytes\n" \
  -H "Accept: image/webp,image/*" \
  "https://www.example.com/images/photo.jpg?ims=400x"
```

A resposta informa o status, o tipo e o tamanho dela:

```text
200 image/webp 8312 bytes
```

Requisite a mesma imagem sem query string e compare o tamanho. A resposta processada é menor, e também pode carregar um formato diferente do arquivo na sua origem, porque Image Processor entrega WEBP para os navegadores que o aceitam.

Para confirmar que foi o módulo, e não a origem, que processou a resposta, leia os headers:

```bash
curl -sI -H "Accept: image/webp" "https://www.example.com/images/photo.jpg?ims=400x"
```

Uma resposta processada carrega `x-ims: Enabled` e o tamanho da imagem de origem antes da transformação:

```text
HTTP/2 200
content-type: image/webp
x-ims: Enabled
x-original-image-size: 484156
```

Agora você tem uma aplicação que transforma imagens sob demanda, e uma URL que descreve a transformação.

:::tip[dica]
Mantenha `ims=` como o último parâmetro na URL. Uma requisição que carrega outro parâmetro de query string depois dele pode retornar um erro `504`.
:::
