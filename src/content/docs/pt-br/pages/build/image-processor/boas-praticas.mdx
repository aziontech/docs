Uma solicitação de imagem transformada pode retornar um arquivo mais pesado do que a página precisa, uma imagem recortada de uma forma que ninguém pretendia, ou um erro que remonta à posição de um parâmetro na URL. Um cache que não consegue diferenciar uma transformação de outra pode entregar a um visitante a versão errada de uma imagem, ou contar a mesma transformação mais de uma vez contra um limite de uso.

[Image Processor](/pt-br/documentacao/build/image-processor/) lê cada um desses fatores a partir da própria solicitação e da cache setting ao redor dela. As práticas abaixo definem o valor de qualidade a solicitar, escolhem `fit-in` em vez de um redimensionamento simples quando a proporção importa, e colocam `ims` por último na query string. Elas também cobrem o header que uma conversão de formato exige, o campo que lista `ims` no allowlist de uma cache setting, e por quanto tempo vale a pena manter uma imagem derivada em cache.

---

## Defina a qualidade em 85

O filtro de qualidade define o quanto o Image Processor comprime uma imagem derivada, equilibrando tamanho de arquivo e fidelidade visual. `?ims=filters:quality(85)` solicita o valor que a Azion documenta como o que otimiza o arquivo sem perda perceptível de qualidade visual.

Um valor mais baixo reduz ainda mais o arquivo, e a perda se torna visível na imagem entregue. Um valor mais alto adiciona tamanho de arquivo que quem visualiza não consegue perceber, porque a diferença visível já parou de existir abaixo dele. Solicite qualidade 85 para as imagens derivadas que uma página entrega, e só se afaste desse valor quando uma imagem precisar parecer mais nítida ou ser transferida com tamanho menor do que esse.

Para o intervalo completo de valores que o argumento aceita, consulte [Parâmetros de URL](/pt-br/documentacao/build/image-processor/parametros-de-url/).

---

## Use fit-in quando a proporção importa

Um redimensionamento escrito como `?ims=WidthxHeight` ajusta a imagem derivada a uma caixa exata, e o Image Processor pode recortá-la automaticamente para chegar a esse resultado. Quando as proporções solicitadas não correspondem à origem, o recorte é centralizado e ocorre ao longo do eixo que ultrapassa o limite, o que pode remover parte do assunto que a solicitação pretendia manter.

`?ims=fit-in/WidthxHeight` ajusta a imagem dentro da mesma caixa, mas preserva a proporção. O Image Processor nunca amplia a origem para preencher a caixa: a imagem derivada para no primeiro limite que atinge, então ela pode ficar aquém da largura ou da altura totais.

`?ims=400x400` recorta automaticamente uma fotografia em modo paisagem para preencher o quadrado exatamente. `?ims=fit-in/400x400` mantém a mesma fotografia inteira dentro do quadrado, mais curta de um lado em vez de recortada. Use o redimensionamento simples quando um layout precisa que a caixa seja preenchida exatamente, e `fit-in` quando a imagem não pode perder uma borda.

Para o restante das formas de redimensionamento, consulte [Parâmetros de URL](/pt-br/documentacao/build/image-processor/parametros-de-url/).

## Coloque ims por último na query string

O Image Processor espera que o parâmetro `ims` seja o último na query string de uma solicitação. Quando outro parâmetro vem depois dele, a solicitação pode retornar um erro `504`.

`example.com/image.jpeg?ts=1234&ims=1000x1000` coloca `ims` por último, e a solicitação é válida. `example.com/image.jpeg?ims=1000x1000&ts=1234` coloca outro parâmetro depois dele, e essa solicitação pode retornar um `504`.

Adicione todos os outros parâmetros da query string antes de `ims`, nunca depois, incluindo um timestamp de cache-busting ou um valor de rastreamento anexado por outro sistema.

## Envie um header Accept ao converter para WEBP ou AVIF

Converter a imagem derivada para WEBP ou AVIF depende de um header. `filters:format(webp)` ou `filters:format(avif)` na string `ims` exige que a solicitação também carregue `Accept: image/webp` ou `Accept: image/avif`.

O behavior **Add Request Header** do [Rules Engine](/pt-br/documentacao/plataforma/applications/rules-engine/) adiciona esse header dentro da **Request Phase**, para que a conversão não dependa do cliente ter enviado esse header. Esta é a estrutura desse behavior em uma regra configurada para solicitar WEBP:

```json
{
  "type": "add_request_header",
  "attributes": {
    "value": "Accept: image/webp"
  }
}
```

Corresponda o valor ao formato para o qual a string `ims` converte: `Accept: image/avif` para uma regra que converte para AVIF. Para os critérios que restringem uma regra a solicitações de imagem, consulte [Configurações](/pt-br/documentacao/build/image-processor/configuracoes/).

## Liste ims no allowlist da cache setting

Uma cache setting sem `ims` como chave não diferencia uma imagem derivada de outra: duas solicitações que constroem transformações diferentes a partir da mesma imagem de origem podem compartilhar uma única resposta em cache, e um visitante pode receber qualquer transformação que já esteja armazenada.

Adicionar `ims` ao allowlist de `cache_vary_by_querystring` faz o cache usar esse parâmetro como chave, para que cada transformação tenha sua própria cópia armazenada:

```json
{
  "modules": {
    "application_accelerator": {
      "cache_vary_by_querystring": {
        "behavior": "allowlist",
        "fields": ["ims"]
      }
    }
  }
}
```

No Azion Console, os mesmos campos são **Behavior**, **Fields** e **Sort**, na seção **Application Accelerator** de uma cache setting. `cache_vary_by_querystring` fica em `modules.application_accelerator`, então variar o cache por `ims` exige o módulo [Application Accelerator](/pt-br/documentacao/build/application-accelerator/). Processar uma imagem não exige.

Para o restante dos campos que uma cache setting carrega, consulte [Configurações](/pt-br/documentacao/build/image-processor/configuracoes/).

## Mantenha as imagens derivadas em cache por muito tempo

Toda transformação que o Image Processor realiza conta para o medidor mensal de Images, seja ela um redimensionamento, um recorte, uma conversão de formato ou a aplicação de um filtro. Uma solicitação para a qual o cache já tem uma resposta não chega novamente ao Image Processor, então ela não soma nada a essa contagem.

Defina a idade máxima da cache setting para uma imagem derivada com a maior duração que o conteúdo de origem pode tolerar. Cada solicitação que o cache responde sozinho é uma imagem a menos contada contra a cota mensal do plano, e uma imagem de origem que muda raramente pode manter suas versões derivadas em cache por muito tempo sem ficar desatualizada. Uma duração de cache curta força o Image Processor a reconstruir a mesma transformação em um ritmo que não tem relação com o fato de a imagem de origem ter mudado ou não.

A duração é o `max_age` da cache setting, dentro do módulo `cache`. Defina-o na cache setting que a regra de imagens aplica:

```json
{
  "modules": {
    "cache": {
      "behavior": "override",
      "max_age": <segundos_que_o_conteudo_de_origem_pode_tolerar>
    }
  }
}
```

O teto que esse campo aceita está em [Cache Settings](/pt-br/documentacao/build/cache/cache-settings/). Para saber o que conta contra o medidor de Images e o que não conta, consulte [Como funciona o Image Processor](/pt-br/documentacao/build/image-processor/como-funciona/).
