Um cache que varia pelo atributo errado é pior do que um cache que não varia. Cada valor distinto do atributo pelo qual ele varia se torna mais um objeto armazenado. Um atributo que não altera a resposta, portanto, divide uma única resposta em cache em cópias que atendem, cada uma, menos requisições. Essa escolha também decide o quanto será difícil purgar o conteúdo depois.

As práticas abaixo mantêm uma variação presa a algo que altera a resposta e mantêm visível o custo dessa variação. Os mecanismos por trás delas estão em [Como Application Accelerator funciona](/pt-br/documentacao/build/application-accelerator/como-funciona/), os nomes dos campos e os padrões estão em [Configurações do Application Accelerator](/pt-br/documentacao/build/application-accelerator/configuracoes/) e os tetos estão em [Limites](/pt-br/documentacao/build/application-accelerator/limites/).

Cada exemplo desta página é um fragmento de um cache setting, como Azion API o recebe. As seções seguem a ordem em que as decisões aparecem: quais atributos entram na cache key, como a ordem dos argumentos é tratada e as duas decisões que os cookies impõem. As três últimas tratam de quando um cache TTL de 0 segundos substitui Bypass Cache, do que Tiered Cache faz com essa regra e de como um purge alcança conteúdo que varia.

## Nomeie os atributos que alteram a resposta

O campo `behavior` de uma variação de cache decide quanto de uma requisição entra na cache key. O modo `all` deixa entrar na key todos os argumentos de query string que chegam, inclusive os que a aplicação nunca lê. Um argumento de campanha acrescentado a um link compartilhado passa a produzir um objeto em cache próprio, que guarda a mesma resposta do objeto sem ele.

O modo `allowlist` varia apenas pelos argumentos que você nomeia. Um argumento que ninguém nomeou não pode criar um segundo objeto, então o número de cópias armazenadas continua preso ao conteúdo, e não ao tráfego. Nomeie os argumentos de que a resposta depende e deixe o resto fora da key.

Esta é a variação por query string de um cache setting, com dois argumentos nomeados:

```json
{
  "modules": {
    "application_accelerator": {
      "cache_vary_by_querystring": {
        "behavior": "allowlist",
        "fields": ["category", "page"]
      }
    }
  }
}
```

O custo é que a lista é sua para manter. Um argumento que passa a alterar a resposta precisa ser adicionado a ela. Até que seja, requisições que diferem apenas por esse argumento compartilham um único objeto em cache. Para o que cada variação acrescenta a uma cache key, consulte [Como Application Accelerator funciona](/pt-br/documentacao/build/application-accelerator/como-funciona/).

## Ative a ordenação da query string

A ordenação da query string decide se a ordem dos argumentos altera a cache key. Sem ela, os argumentos nomeados entram na key na ordem em que o cliente os enviou. Dois clientes que enviam os mesmos argumentos em ordens diferentes passam a criar dois objetos para uma única resposta, e cada objeto atende metade das requisições que poderia atender.

O campo `sort_enabled` da variação por query string elimina essa duplicação ao agrupar as variações sob uma única key, em ordem alfabética. Esta é a mesma variação com a ordenação ativada:

```json
{
  "modules": {
    "application_accelerator": {
      "cache_vary_by_querystring": {
        "behavior": "allowlist",
        "fields": ["category", "page"],
        "sort_enabled": true
      }
    }
  }
}
```

A ordenação tem uma consequência no momento do purge. Um purge por URL alcança uma variação por query string apenas quando os argumentos chegam na ordem em que foram apresentados, e com a ordenação ativada essa ordem é alfabética. Para os tipos de purge que alcançam uma variação, consulte [Real-Time Purge](/pt-br/documentacao/build/cache/real-time-purge/#purge-de-application-accelerator).

## Varie o cache pelos cookies que segmentam o conteúdo

Uma requisição carrega todos os cookies que o navegador guarda para o domínio, e a maioria deles não altera a resposta. Identificadores de analytics e flags de consentimento chegam na mesma requisição que o cookie que a aplicação de fato lê. O modo `all` deixa todos eles entrarem na cache key, então as cópias armazenadas se multiplicam com os cookies, e não com o conteúdo.

O modo `allowlist` varia a key pelos cookies que você lista e ignora todos os demais. É o que segmenta conteúdo por perfil de usuário, ou por qualquer outro agrupamento que a aplicação mantenha. Azion recomenda esse modo quando os cookies gerenciam sessões de usuário.

Esta é a variação por cookie de um cache setting, com um cookie nomeado:

```json
{
  "modules": {
    "application_accelerator": {
      "cache_vary_by_cookies": {
        "behavior": "allowlist",
        "cookie_names": ["session_id"]
      }
    }
  }
}
```

Um cookie com um valor distinto por visitante produz um objeto armazenado por visitante, o que torna a lista uma decisão sobre cardinalidade tanto quanto sobre correção. Para os passos que configuram uma variação por cookie, consulte [Configurar Advanced Cache Key](/pt-br/documentacao/guias/performance-e-confiabilidade/cache-e-purge/advanced-cache-key/).

## Mantenha cookies de sessão privados fora de uma resposta encaminhada

O behavior [Forward Cookies](/pt-br/documentacao/plataforma/applications/rules-engine/#forward-cookies) envia aos usuários o header `Set-Cookie` da origem, inclusive em um cache hit. Cookies de sessão podem estar entre os cookies que esse header carrega. Uma regra que encaminha cookies, portanto, encaminha também os privados, a menos que o cache setting daquele path diga o contrário.

Para impedir que cookies de sessão privados cheguem aos usuários, liste-os no modo `denylist` da variação por cookie:

```json
{
  "modules": {
    "application_accelerator": {
      "cache_vary_by_cookies": {
        "behavior": "denylist",
        "cookie_names": ["session_id"]
      }
    }
  }
}
```

Esta é uma pergunta diferente de quais cookies segmentam o conteúdo, e as duas respostas não compartilham um campo: um cache setting carrega um único behavior de cookie. O cache setting aplicado ao path onde **Forward Cookies** é executado é o que carrega a denylist. Para os passos que criam esse cache setting e o vinculam à regra, consulte [Configurar políticas de cache](/pt-br/documentacao/guias/performance-e-confiabilidade/cache-e-purge/cache-settings/).

## Defina um cache TTL de 0 segundos onde a resposta pode ser compartilhada

Um cache TTL de 0 segundos e o behavior [Bypass Cache](/pt-br/documentacao/plataforma/applications/rules-engine/#bypass-cache) mantêm o usuário fora de uma cópia armazenada, e diferem no que chega à origem. Bypass Cache envia todas as requisições à origem, então cada requisição pode receber o próprio conteúdo. Um `modules.cache.max_age` de 0 segundos mantém a requisição no caminho do cache. Requisições paralelas por um mesmo objeto chegam à origem como uma única requisição, e um objeto inalterado não é transferido de novo.

Defina o TTL como 0 segundos onde conteúdo dinâmico pode ser entregue de forma idêntica a todos que o requisitam no mesmo momento. Reserve Bypass Cache para os paths onde duas requisições simultâneas precisam receber respostas diferentes. Cada opção abre mão do que a outra preserva, e não existe configuração que preserve as duas.

Nenhuma das opções é absoluta em todas as camadas de cache. Bypass Cache age na camada de cache, e uma aplicação com cache settings de Tiered Cache ativos continua armazenando em cache na camada tiered, independentemente da regra. A opção de definir um TTL de 0 segundos existe apenas enquanto Application Accelerator está ativado, porque é o módulo que remove o cache TTL mínimo. Para os dois lados dessa escolha, consulte [Como Application Accelerator funciona](/pt-br/documentacao/build/application-accelerator/como-funciona/).

## Verifique Tiered Cache antes de confiar em Bypass Cache

O behavior [Bypass Cache](/pt-br/documentacao/plataforma/applications/rules-engine/#bypass-cache) impede que Azion armazene em cache a resposta da origem, e [Tiered Cache](/pt-br/documentacao/build/cache/tiered-cache/) é uma segunda camada de cache atrás dessa. Tiered Cache não suporta bypass de cache. Uma aplicação com cache settings de Tiered Cache ativos continua armazenando em cache na camada tiered pelo TTL mínimo dela, mesmo com uma regra Bypass Cache configurada.

Confirme quais módulos de cache a aplicação carrega antes de uma regra Bypass Cache virar a resposta a um requisito de atualidade do conteúdo. Uma regra que parece correta na camada de cache não descreve o que a camada tiered faz, e nada na própria regra registra essa diferença. O sintoma, quando isso passa despercebido, é conteúdo ainda entregue a partir do cache depois que a regra está no ar.

Onde o requisito é que nenhuma camada guarde uma cópia, Tiered Cache entra na decisão, e não depois dela. Para o TTL mínimo que essa camada mantém, consulte [Tiered Cache](/pt-br/documentacao/build/cache/tiered-cache/).

## Planeje o purge quando planejar a variação

Um purge encontra um objeto pela cache key, então as variações que você configura são os objetos que um purge precisa alcançar. Um purge por URL monta essa key apenas a partir da URL, e a variação de conteúdo não participa disso. Variações baseadas em cookies ou em device groups não expiram com ele, e as cópias delas permanecem no cache.

Dois tipos de purge alcançam essas variações. Um purge por cache key nomeia cada variação individualmente. Um purge por wildcard, em vez disso, termina a cache key com uma de duas formas:

```text
@@*
?*
```

`@@*` é o final para variações por cookie e para objetos `POST` ou `OPTIONS` em cache. `?*` é o final para variações por query string. Uma variação por query string também pode ser purgada por URL, desde que os argumentos sejam enviados na ordem em que a cache key os guarda.

Decida isso enquanto escolhe por qual atributo variar, e não depois. Uma variação com muitos valores distintos é cara de purgar tanto quanto de armazenar, porque cada valor é mais um objeto que o purge precisa alcançar. Para os tipos de purge e os passos para executar cada um, consulte [Real-Time Purge](/pt-br/documentacao/build/cache/real-time-purge/#purge-de-application-accelerator).
