Application Accelerator altera o que uma cache key contém, quais métodos HTTP uma aplicação armazena em cache e quais behaviors do Rules Engine uma regra pode usar. Cada sintoma abaixo é algo que você observa no cache ou na interface, e cada seção o nomeia, apresenta a causa e indica a correção. Para o mecanismo por trás deles, consulte [Como Application Accelerator funciona](/pt-br/documentacao/build/application-accelerator/como-funciona/).

---

## Nenhum status de cache em uma requisição POST

Você envia uma requisição `POST` para um path coberto por um cache setting, e o status de cache dessa requisição é `-` em vez de `HIT` ou `MISS`. Uma requisição que carrega o header `Pragma: azion-debug-cache` retorna o status no header de resposta `X-Cache`.

Um status de cache `-` significa que o conteúdo está impedido de ser armazenado em cache. Uma requisição `POST` cujo cache setting não tem o cache para `POST` ativado se enquadra nesse caso, e o status não é registrado. Uma aplicação armazena `GET` e `HEAD` em cache nativamente, e armazena uma resposta `POST` ou `OPTIONS` apenas quando Application Accelerator está ativado e o cache setting nomeia o método.

- **Ative o módulo**: o switch **Application Accelerator**, na aba **Main Settings** da aplicação, condiciona o cache dos dois métodos. Para o campo que cada interface define, consulte [Configurações do Application Accelerator](/pt-br/documentacao/build/application-accelerator/configuracoes/).
- **Nomeie o método no cache setting**: na seção **Application Accelerator** do cache setting, abra **Cache vary by Method** e selecione **POST**. Na Azion API, `cache_vary_by_method` carrega `post`.
- **Siga o procedimento**: os passos para as duas interfaces estão em [Cache de respostas POST e OPTIONS](/pt-br/documentacao/guias/performance-e-confiabilidade/cache-e-purge/cache-de-respostas-post-e-options/).

A próxima requisição `POST` para esse path carrega um status de cache em vez de `-`, e o objeto armazenado em cache recebe uma key que termina com o hash MD5 do corpo da requisição.

## Variações por cookie e por device group sobrevivem a um purge

Você faz o purge da URL de um objeto que varia, e as requisições que carregam o cookie ou o device group que produziu uma variação continuam sendo atendidas pelo cache.

Um purge por URL converte cada URL que recebe em uma cache key sem considerar a variação de conteúdo. As variações por cookie, por device group e outras são objetos separados em cache, e a URL não descreve as keys delas. Essas cópias, portanto, não expiram com um purge por URL, por mais vezes que você o execute.

- **Faça purge por cache key**: nomeie cada variação do objeto individualmente, de modo que o purge alcance a key que a mantém.
- **Faça purge por wildcard**: encerre a cache key com `@@*`, que alcança toda variação que acrescenta o separador `@@`.

Os dois procedimentos pertencem a Real-Time Purge. Para os passos, consulte [Purge de Application Accelerator](/pt-br/documentacao/build/cache/real-time-purge/#purge-de-application-accelerator).

As variações que você nomeou deixam de ser atendidas pelo cache, e a próxima requisição por cada uma delas alcança a origem.

## Um purge por URL não alcança uma variação por query string

Você faz o purge de uma URL que carrega argumentos de query string, e o objeto que varia por esses argumentos continua sendo entregue pelo cache.

As variações por query string podem ser purgadas por URL, porque a query string faz parte da URL. A correspondência depende da ordem dos argumentos. Um purge por URL alcança o objeto apenas quando os argumentos são enviados na ordem em que foram apresentados. Quando o switch **Sort** de **Cache vary by Query String** está ativado, a cache key mantém os argumentos em ordem alfabética, então o purge também precisa nomeá-los nessa ordem.

- **Respeite a ordem que a key mantém**: envie os argumentos na ordem em que foram apresentados, ou em ordem alfabética quando a ordenação está ativada.
- **Nomeie apenas os argumentos presentes na key**: um purge por URL alcança o objeto quando carrega os argumentos pelos quais a cache key varia.
- **Faça purge por wildcard**: encerre a URL com `?*`, que alcança toda variação de query string desse path.

Para os tipos de purge e os passos de cada um, consulte [Real-Time Purge](/pt-br/documentacao/build/cache/real-time-purge/).

O purge expira o objeto cuja cache key mantém esses argumentos, nessa ordem.

## Um behavior ou uma variável ausente no Rules Engine

Você adiciona uma regra na aba **Rules Engine** de uma aplicação, e um behavior que você espera não aparece na lista. **Bypass Cache**, **Forward Cookies** e **Rewrite Request** são três dos behaviors afetados. A variável `${device_group}` também não aparece nos criteria.

Enquanto Application Accelerator está desativado nessa aplicação, Rules Engine oferece apenas parte das variáveis e dos behaviors para uma regra. Sete behaviors e a variável `${device_group}` exigem o módulo.

Para ativar o módulo:

<DocSteps>
  <DocStep title="Abra a página de Applications">

  Acesse [Azion Console](https://console.azion.com/) > **Applications**.

  </DocStep>
  <DocStep title="Selecione a aplicação que executa a regra" />
  <DocStep title="Vá para a aba Main Settings" />
  <DocStep title="Ative o módulo">

  Na seção **Modules**, ative **Application Accelerator**.

  </DocStep>
  <DocStep title="Selecione Save" />
</DocSteps>

Os sete behaviors condicionados ao módulo passam a aparecer na lista de behaviors de uma regra, e os criteria de uma regra aceitam `${device_group}`. Para saber quais behaviors o módulo condiciona e em que fase cada um é executado, consulte [Configurações do Application Accelerator](/pt-br/documentacao/build/application-accelerator/configuracoes/).

**Run Function** é a exceção, porque exige [Functions](/pt-br/documentacao/build/functions/) além deste módulo. Para esse caso, consulte [Solução de problemas de Functions](/pt-br/documentacao/build/functions/solucao-de-problemas/).

## Conteúdo entregue pelo cache com Bypass Cache configurado

Uma regra aplica o behavior **Bypass Cache**, um dos behaviors condicionados a Application Accelerator, e as requisições para esse path continuam sendo atendidas pelo cache.

Tiered Cache não suporta bypass cache. Uma regra **Bypass Cache** impede que Azion armazene a resposta da origem na camada de cache. Uma aplicação cujos cache settings têm Tiered Cache ativado continua armazenando em cache nessa segunda camada, pelo TTL mínimo que essa camada aceita. Esse mínimo é de 3 segundos.

É assim que os dois recursos se comportam em conjunto, portanto nenhuma configuração na regra corrige isso. O que você observa é a camada do Tiered Cache atendendo a requisição, e não uma regra **Bypass Cache** que deixou de ser aplicada. Para o que essa camada armazena em cache e as configurações que a governam, consulte [Tiered Cache](/pt-br/documentacao/build/cache/tiered-cache/).
