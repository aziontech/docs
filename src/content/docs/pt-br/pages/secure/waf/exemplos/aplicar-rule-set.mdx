Um rule set não pontua nada até que uma regra do [Rules Engine for Firewall](/pt-br/documentacao/plataforma/firewall/rules-engine/) o nomeie. A regra abaixo corresponde a toda requisição que o firewall recebe e a entrega a um rule set em modo blocking. Recorra a ela na primeira vez que você colocar um rule set no caminho, e sempre que precisar do critério que não pula nenhuma requisição.

<DocSteps>
  <DocStep title="Abra o firewall vinculado ao seu workload">

  Acesse o [Azion Console](https://console.azion.com/) > **Firewalls** e selecione esse firewall.

  </DocStep>
  <DocStep title="Selecione a aba Rules Engine" />
  <DocStep title="Selecione + Rule" />
  <DocStep title="Nomeie a regra">

  Informe `Apply storefront-waf` como o nome.

  </DocStep>
  <DocStep title="Defina o critério">

  Na seção **Criteria**, selecione a variável `Request Uri`, o operador _starts with_ e `/` como argumento.

  </DocStep>
  <DocStep title="Adicione o behavior Set WAF">

  Na seção **Behaviors**, selecione **Set WAF** e então `storefront-waf` como o rule set e _Blocking_ como o modo.

  </DocStep>
  <DocStep title="Salve a regra" />
</DocSteps>

Para a mesma regra com as famílias de ameaças e o modo em aberto, consulte [Crie e aplique um WAF rule set](/pt-br/documentacao/guias/seguranca-de-aplicacoes/firewall-e-waf/criar-waf-rule-set/).

<Fragment slot="panel.cli">

Salve a regra como `rule.json`, com o id do seu rule set em `waf_id`:

```json
{
  "name": "Apply storefront-waf",
  "active": true,
  "criteria": [
    [
      {
        "conditional": "if",
        "variable": "${request_uri}",
        "operator": "starts_with",
        "argument": "/"
      }
    ]
  ],
  "behaviors": [
    {
      "type": "set_waf",
      "attributes": {
        "waf_id": 21717,
        "mode": "blocking"
      }
    }
  ]
}
```

O Azion CLI aceita o mesmo arquivo:

```bash
azion create firewall-rule --firewall-id <firewall-id> --file rule.json
```

```text
Created Firewall Rule with ID 131733
```

<Fragment slot="panel.api">

Salve a regra como `rule.json`, com o id do seu rule set em `waf_id`:

```json
{
  "name": "Apply storefront-waf",
  "active": true,
  "criteria": [
    [
      {
        "conditional": "if",
        "variable": "${request_uri}",
        "operator": "starts_with",
        "argument": "/"
      }
    ]
  ],
  "behaviors": [
    {
      "type": "set_waf",
      "attributes": {
        "waf_id": 21717,
        "mode": "blocking"
      }
    }
  ]
}
```

Envie-a para o firewall que serve o seu workload:

```bash
curl --request POST \
  --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules \
  --header 'Accept: application/json' \
  --header 'Authorization: Token [TOKEN VALUE]' \
  --header 'Content-Type: application/json' \
  --data @rule.json
```

A API responde `202` e retorna a regra com duas chaves que ela atribuiu: um `description` vazio e a `order` que a regra ocupa entre as regras daquele firewall.

## Como funciona

`criteria` é uma lista de listas, e `mode` é obrigatório no behavior. Um behavior `set_waf` enviado sem ele é recusado com `400` e o erro `10059 Required Field`, apontando para `/data/behaviors/0/attributes/mode`. Uma regra carrega no máximo um behavior `Set WAF`, então uma regra fixa um rule set e um modo para as requisições com que ela corresponde.

Baseie o critério em `${request_uri}`, não na query string. Um critério de `${request_args}` com o operator `matches` e um argument de `.*` parece uma correspondência com tudo e não é: uma variável vazia não corresponde, então essa regra pula toda requisição que não carrega query string, incluindo um `POST` cujo payload está inteiramente no corpo. Duas requisições POST idênticas provaram isso, uma enviada para `/?x=1` e bloqueada, a outra enviada para `/` e entregue.
