O objeto abaixo está a um valor de distância de uma instância que não recusa nada: `action` lê `deny`, então [Bot Manager Lite](/pt-br/documentacao/secure/bot-manager/bot-manager-lite/) responde `403` a uma requisição cuja pontuação atinge o threshold, em vez de entregá-la. Recorra a ele depois que uma janela de observação mostrar o que o seu próprio tráfego pontua e você quiser que o threshold tenha efeito.

```json
{
  "threshold": 30,
  "action": "deny",
  "internal_logs": 2,
  "log_tag": "storefront-bots"
}
```

`30` é o threshold que Bot Manager Lite traz, e nesse valor um navegador não é recusado: Azion enviou uma requisição com um user agent do Chrome, `Accept`, `Accept-Language`, `Accept-Encoding`, quatro headers `Sec-Fetch-*` e `Upgrade-Insecure-Requests` contra esta mesma configuração, e ela chegou à aplicação. `internal_logs` em `2` mantém uma linha de report para toda requisição, então uma recusa deixa atrás de si um registro da pontuação. Para todos os argumentos que uma instância aceita, consulte [Argumentos](/pt-br/documentacao/secure/bot-manager/argumentos/#campos).

:::caution[Atenção]
O objeto não é validado. Uma chave que a função não reconhece é aceita, armazenada e exibida de volta exatamente como foi digitada, enquanto a função roda com o próprio padrão. Uma instância cujo `action` está escrito errado parece configurada para recusar e não recusa nada.
:::

```bash

```

curl --request POST \

  "active": true,

A chamada responde `202` e retorna a instância como a plataforma a armazenou:

```json
{
  "state": "pending",
  "data": {
    "id": 15842,

    "azion_form": {},

    "active": true
  }

```

`"state": "pending"` diz que a escrita foi aceita e ainda não chegou à infraestrutura distribuída da Azion. `"azion_form": {}` é o motivo pelo qual Azion Console renderiza um editor JSON para esta função em vez de um formulário.

## Como funciona

`action: deny` responde `HTTP 403` e entrega a página de erro padrão da Azion. Azion mediu isso contra um workload próprio: a resposta carrega `content-type: text/html`, um header `x-azion-request-id` e a página intitulada `Azion - Default error page`. Nada na resposta nomeia Bot Manager, então a linha de report é onde você confirma qual instância recusou a requisição e quanto ela pontuou.

Esse `403` é a resposta que a ação deny produz, e não é o conjunto completo de respostas que um cliente pode receber de um firewall rodando Bot Manager. Um cliente que não apresenta uma sessão válida recebe, em vez disso, uma resposta de corpo vazio, com os dois cookies de sessão que a função define, e um cliente que não roda JavaScript nem guarda cookies permanece nessa resposta: um consumidor de API, um health check ou um monitor nunca chega a um `403` e também nunca chega à aplicação. Para ver como isso aparece e o que fazer a respeito, consulte [Solucionar problemas de Bot Manager](/pt-br/documentacao/secure/bot-manager/solucao-de-problemas/).

Espere cerca de dois minutos antes de tirar qualquer conclusão de uma resposta. Azion trocou uma instância de `allow` para `deny` e consultou o workload a cada 15 segundos: as sete primeiras tentativas foram entregues e a oitava foi recusada. Vale conhecer mais dois valores antes de alterar este objeto. Em um `threshold` de `0` toda requisição está no threshold ou acima dele, então a ação configurada dispara em todas, o que com `deny` recusa toda requisição que a regra corresponde. E, como nada valida o objeto, `deny` só está em vigor enquanto a chave que o carrega estiver escrita corretamente: Azion enviou vinte e uma chaves a uma instância, uma delas sem significado, e todas as vinte e uma foram armazenadas e devolvidas byte a byte, sem erro em lugar nenhum.
