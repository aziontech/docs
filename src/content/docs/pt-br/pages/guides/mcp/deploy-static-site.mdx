Você pode fazer o deploy de um site estático na Azion pedindo a um agente de código conectado ao [MCP server da Azion](/pt-br/documentacao/devtools/mcp/) que siga o guia de deploy do servidor. O servidor retorna apenas o texto do guia. O deploy é feito pelos comandos da [Azion CLI](/pt-br/documentacao/devtools/cli/) que o guia indica, na pasta do seu projeto. Para fazer o deploy sem um agente, consulte [Primeiros passos com a Azion CLI](/pt-br/documentacao/devtools/cli/primeiros-passos/).

---

## Pré-requisitos

- Um projeto de site estático, como uma pasta de arquivos HTML, CSS e JavaScript, ou um projeto criado com um framework.
- Um agente de código conectado ao MCP server. Para conectar um, consulte [Primeiros passos com o MCP server](/pt-br/documentacao/devtools/mcp/configuracao/).
- Uma conta da Azion e um [personal token](/pt-br/documentacao/fundamentos/personal-tokens/) para a Azion CLI. O guia instala a CLI quando ela não está instalada.

---

## Faça o deploy do site com o seu agente

O MCP server traz o deploy como quatro guias, os recursos em `azion://static-site/deploy/`. O agente segue esses guias em ordem, e o relatório de cada etapa é a entrada da etapa seguinte. Para fazer o deploy do site:

<DocSteps>
  <DocStep title="Peça ao seu agente que faça o deploy do site">

  Abra o agente na pasta do seu projeto e descreva o site e o objetivo. Por exemplo:

  ```text
  Tenho um site estático com arquivos HTML, CSS e JavaScript. Me ajude a fazer o deploy na Azion.
  ```

  Um cliente que suporta recursos MCP lê os quatro recursos. Um cliente sem suporte a recursos chama a ferramenta `deploy_azion_static_site` com `action` definido como `deploy`, que retorna as quatro etapas. Com `action` definido como `help`, a ferramenta lista as URIs dos recursos.

  </DocStep>
  <DocStep title="Revise a análise do projeto">

  Em `deploy/step-0-preparation`, o agente lê o projeto e escreve um relatório de prontidão para o deploy. O relatório informa o framework, o gerenciador de pacotes, o ponto de entrada, o preset e se o projeto é novo ou já está vinculado à Azion. Ele também informa se o site é estático ou precisa de ajustes, e se a Azion CLI está instalada e autenticada.

  O agente detecta o framework pelos arquivos de configuração dele e o gerenciador de pacotes pelo arquivo de lock. Ele procura um arquivo `azion/azion.json` ou `azion.config.*` existente e código do lado do servidor. Ele verifica a CLI com `azion --version` e a autenticação com `azion whoami`. Esta etapa não instala nada e não altera nenhum arquivo.

  </DocStep>
  <DocStep title="Revise a configuração do projeto">

  Em `deploy/step-1-configuration`, o agente configura a CLI e vincula o projeto. Quando a CLI não está instalada, a etapa faz a instalação. Quando a CLI não está autenticada, a etapa executa `azion -t` com um personal token, ou `azion login`.

  Um projeto novo é vinculado com `azion link --name <project-name> --preset <your-preset> --auto --package-manager <your-package-manager>`. Um projeto existente é atualizado com `azion sync`, depois que você confirma a atualização. Em seguida, o agente testa o build com `azion build --preset <your-preset> --entry <your-entry-file>`. Quando o build falha com um erro de módulo, a etapa adiciona `"type": "module"` ao `package.json` e tenta de novo. Quando falha com um erro de ponto de entrada, a etapa verifica se o arquivo de entrada existe e tenta outros caminhos.

  A etapa termina com um projeto vinculado, um build bem-sucedido e um arquivo `azion.config.js`.

  </DocStep>
  <DocStep title="Revise o deploy">

  Em `deploy/step-2-execute`, o agente faz o deploy do projeto com `azion deploy --no-prompt --auto --local --debug`. Para ter mais controle sobre cada fase, a etapa executa `azion build --preset <your-preset> --entry <your-entry-file>` e depois `azion deploy --auto --debug --local --skip-build`. A etapa verifica se a pasta `.edge/storage` contém os arquivos estáticos antes de continuar.

  Da saída do deploy, o agente obtém o nome da application, o ID da application e a URL de produção, no formato `xxxxxxxxx.map.azionedge.net`. O nome e o ID também estão em `azion/azion.json` e na saída de `azion list application`. A etapa informa que o primeiro deploy em produção pode levar até 10 minutos para propagar, e testa a URL a cada 2 minutos até ela responder.

  Para testar, o agente resolve a URL de produção com `nslookup`, `host` ou `dig`. Em seguida, envia `curl -H "Host: <production-url>" -I http://<ip>/` para esse endereço IP e repete a requisição com `-H "Pragma: azion-debug-cache"` para ler os headers de cache. Quando um teste falha, a etapa verifica os logs com `azion logs http`.

  </DocStep>
  <DocStep title="Revise o relatório de teste">

  Em `deploy/step-3-basic-test`, o agente requisita a página inicial e os assets principais, como CSS, JavaScript e imagens, pelo mesmo endereço IP e header `Host`. Ele executa a verificação de cache duas ou três vezes, porque a primeira requisição pode ser um miss. O relatório marca o acesso ao site, o carregamento dos assets e os headers de cache como OK ou NOT OK.

  Quando um teste é NOT OK, a etapa verifica os logs com `azion logs http --tail`. Ela também verifica o diretório de saída do build em `azion.config.js` e confirma que todos os assets estáticos fizeram parte do deploy.

  </DocStep>
</DocSteps>

O agente termina com o relatório de teste e a URL de produção do site. A URL `map.azionedge.net` serve para testes e é o destino do registro DNS `CNAME` que aponta o seu próprio domínio para o site. Uma alteração posterior no site exige outro `azion deploy`. Para cada flag do comando de deploy, consulte [Azion CLI deploy](/pt-br/documentacao/devtools/cli/deploy/). Para os headers de cache que o teste lê, consulte [Teste o comportamento do cache com o MCP server](/pt-br/documentacao/guias/performance-e-confiabilidade/cache-e-purge/testar-cache-com-mcp/). Para os logs, consulte [Azion CLI logs](/pt-br/documentacao/devtools/cli/logs/).

## Presets de framework que o guia detecta

Em `deploy/step-0-preparation`, o agente escolhe o preset a partir do framework do projeto. O guia indica estes presets: `angular`, `astro`, `docusaurus`, `eleventy`, `emscripten`, `gatsby`, `hexo`, `html`, `hugo`, `javascript`, `jekyll`, `next`, `nuxt`, `opennextjs`, `preact`, `qwik`, `react`, `rustwasm`, `stencil`, `svelte`, `typescript`, `vitepress`, `vue` e `vuepress`.

O preset é o valor que o agente passa para `--preset` em `azion link` e `azion build`. Para os frameworks que cada preset suporta, consulte [Compatibilidade com frameworks](/pt-br/documentacao/devtools/runtime/frameworks/compatibilidade-frameworks/). Para o comando `link` e as flags dele, consulte [Azion CLI link](/pt-br/documentacao/devtools/cli/link-comando/).

## Faça o deploy de uma aplicação Next.js com ISR

Incremental Static Regeneration (ISR) é um recurso do Next.js. Para pedir um deploy de Next.js com ISR, descreva o objetivo ao seu agente. Por exemplo:

```text
Faça deploy da minha app Next.js com Incremental Static Regeneration
```

O agente orienta você nestas etapas:

1. Verificar se o Next.js está no seu projeto.
2. Configurar o `azion.config.js` para suportar ISR.
3. Configurar os cache settings.
4. Fazer o deploy com essas configurações.
5. Fornecer queries de monitoramento para a performance do ISR.

Para escrever as queries de monitoramento com o MCP server, consulte [Gere queries GraphQL com o MCP server](/pt-br/documentacao/guias/plataforma/observabilidade/gerar-queries-graphql-com-mcp/).

## Configure os ambientes de staging e produção

Para manter um ambiente de staging separado da produção, descreva os dois ambientes ao seu agente. Por exemplo:

```text
Configure ambientes de staging e produção para minha aplicação
```

O agente ajuda você nestas tarefas:

- Criar applications separadas.
- Configurar variáveis de ambiente.
- Configurar pipelines de deploy.
- Implementar o roteamento de domínios.
