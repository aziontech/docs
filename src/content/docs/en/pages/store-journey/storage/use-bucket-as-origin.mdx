You serve the objects of an [Object Storage](/en/documentation/store/object-storage/) bucket to the internet by pairing a connector with a Rules Engine rule on an [application](/en/documentation/platform/applications/). A request to the domain of the [workload](/en/documentation/platform/workloads/) then returns the object stored under the matching key.

An account that has not migrated to API v4 builds the same delivery path through Origins instead. For more information, refer to [Verify Your Account Migration to API v4](/en/documentation/guides/application-security/access-and-compliance/verify-account-migration/), [Connectors](/en/documentation/platform/connectors/), and [Origins](/en/documentation/platform/connectors/origins/).

---

## Prerequisites

- A bucket with `workloads_access` set to `read_only` or `read_write`. A `restricted` bucket cannot back an application. For more information, refer to [Create a bucket](/en/documentation/guides/application-development/data/create-and-modify-bucket/).
- An [application](/en/documentation/platform/applications/), and a [workload](/en/documentation/platform/workloads/) that carries the domain the application answers on.
- A [personal token](/en/documentation/guides/platform/account-and-billing/personal-tokens/), for the API procedures.
- Access to Azion Console, for the Console procedures. For more information, refer to [Access Azion Console](/en/documentation/guides/platform/account-and-billing/how-to-access-azion-console/).

:::caution
A bucket set to `read_write` and served by an application can be modified by anyone who reaches it, by a request that overwrites an object. Serve static content from a `read_only` bucket, and put a function in front of the bucket when a path has to accept writes. For more information, refer to [Best practices](/en/documentation/store/object-storage/best-practices/).
:::

## Upload the objects to serve

The connector serves what the bucket already holds, so the objects go in first. This example serves a page of two objects, both stored under the `src` prefix of a bucket named `app-origin`:

```text
src/index.html
src/styles/style.css
```

To create the two files and store them:

<DocSteps>
  <DocStep title="Create the HTML file">

  In a local `src` directory, create `index.html`, which links the stylesheet by a relative path:

  ```html
  <!DOCTYPE html>
  <html lang="en">
  <head>
      <meta charset="UTF-8">
      <meta name="viewport" content="width=device-width, initial-scale=1.0">
      <title>Document</title>
      <link rel="stylesheet" href="styles/style.css">
  </head>
  <body>
      <h1>Hello world!</h1>
      <p>I am an object from a bucket.</p>
  </body>
  </html>
  ```

  </DocStep>
  <DocStep title="Create the stylesheet">

  In a `styles` directory inside `src`, create `style.css`, the file the page links to:

  ```css
  body {
    background-color: black;
  }

  h1,
  p {
    color: white;
  }
  ```

  </DocStep>
  <DocStep title="Upload the HTML file">

  The object key is the path the file keeps inside the bucket, and `Content-Type` sets the type the object is stored and served with:

  ```bash
  curl --request POST \
    --url https://api.azion.com/v4/workspace/storage/buckets/app-origin/objects/src/index.html \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: text/html' \
    --data-binary '@./src/index.html'
  ```

  The response carries the key the object is stored under:

  ```json
  {
    "state": "executed",
    "data": {
      "object_key": "src/index.html"
    }
  }
  ```

  </DocStep>
  <DocStep title="Upload the stylesheet">

  ```bash
  curl --request POST \
    --url https://api.azion.com/v4/workspace/storage/buckets/app-origin/objects/src/styles/style.css \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: text/css' \
    --data-binary '@./src/styles/style.css'
  ```

  The response carries the key of the second object:

  ```json
  {
    "state": "executed",
    "data": {
      "object_key": "src/styles/style.css"
    }
  }
  ```

  </DocStep>
</DocSteps>

The bucket holds the two objects, and the `src/` segment of each key is part of the key rather than a folder. Azion Console and the Azion CLI store the same objects. For more information, refer to [Upload and download objects](/en/documentation/guides/application-development/data/upload-and-download-objects-from-bucket/).

## Create the connector

A connector of type Object Storage names the bucket an application reads from and the prefix inside it. The prefix decides where the application path starts: with the prefix `/src`, the object stored under `src/index.html` answers at `/index.html`, and `src/styles/style.css` answers at `/styles/style.css`.

### Azion Console

To create the connector:

<DocSteps>
  <DocStep title="Open the connector list">

  Access [Azion Console](https://console.azion.com/) > **Connectors**, and start a new connector.

  </DocStep>
  <DocStep title="Name the connector">

  In **General**, enter a name that identifies what the connector serves.

  </DocStep>
  <DocStep title="Select the connector type">

  In **Connector Type**, select _Object Storage_.

  </DocStep>
  <DocStep title="Select the bucket">

  In **Connection Options**, select your bucket in **Bucket**. The selector lists the buckets of your account and carries a search field.

  </DocStep>
  <DocStep title="Set the prefix">

  In **Connection Options**, enter `/src` in **Prefix**, the prefix the objects were uploaded under.

  </DocStep>
  <DocStep title="Activate the connector">

  Set **Status** to _Active_.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

The connector reads from the bucket and the prefix you set.

### The API

Send a `POST` request to the connectors endpoint. The `type` field is the string `storage`, and `attributes` carries the bucket and the prefix. To create the connector:

<DocSteps>
  <DocStep title="Send the create request">

  ```bash
  curl --request POST \
    --url https://api.azion.com/v4/workspace/connectors \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: application/json' \
    --data '{
    "name": "object storage connector",
    "active": true,
    "type": "storage",
    "attributes": {
      "bucket": "app-origin",
      "prefix": "/src"
    }
  }'
  ```

  </DocStep>
  <DocStep title="Read the response">

  A `201` carries the connector Azion stored:

  ```json
  {
    "state": "executed",
    "data": {
      "id": "<connector_id>",
      "name": "object storage connector",
      "last_editor": "user@example.com",
      "last_modified": "2026-09-17T22:34:31.009649Z",
      "active": true,
      "product_version": "1.0",
      "type": "storage",
      "attributes": {
        "bucket": "app-origin",
        "prefix": "/src"
      }
    }
  }
  ```

  </DocStep>
</DocSteps>

Copy the value of `data.id`. The Rules Engine rule addresses the connector by it.

## Route requests to the connector

A connector serves nothing until a Rules Engine rule sends requests to it. The rule runs in the **Request Phase** of the application, matches the paths the bucket answers, and sets the connector on each matching request.

### Azion Console

The behavior is **Set Connector**, and a criteria of `${uri}` starting with `/` sends the whole application to the bucket. To route the requests:

<DocSteps>
  <DocStep title="Open the rules of the application">

  Access [Azion Console](https://console.azion.com/) > **Applications** > your application, then go to the **Rules Engine** tab.

  </DocStep>
  <DocStep title="Open a request rule">

  Edit the default rule, or add a rule in the **Request Phase**.

  </DocStep>
  <DocStep title="Match the paths to serve">

  In **Criteria**, set the criteria to `If ${uri} starts with /`.

  </DocStep>
  <DocStep title="Set the connector">

  In **Behavior**, select the **Set Connector** behavior, then select the connector you created.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

The rule sends every matching request to the bucket. The change takes some time to propagate before the domain answers with the objects.

### The API

Send a `POST` request to the request rules of the application. The behavior type is `set_connector`, and it carries the connector identifier in `value`. To route the requests:

<DocSteps>
  <DocStep title="Send the create request">

  Replace `<application_id>` with the identifier of your application, and `<connector_id>` with the identifier of the connector:

  ```bash
  curl --request POST \
    --url https://api.azion.com/v4/workspace/applications/<application_id>/request_rules \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: application/json' \
    --data '{
    "name": "serve the bucket",
    "active": true,
    "criteria": [
      [
        {
          "conditional": "if",
          "variable": "${uri}",
          "operator": "starts_with",
          "argument": "/"
        }
      ]
    ],
    "behaviors": [
      {
        "type": "set_connector",
        "attributes": {
          "value": "<connector_id>"
        }
      }
    ]
  }'
  ```

  </DocStep>
  <DocStep title="Read the response">

  The response returns the rule, with `state` set to `pending`:

  ```json
  {
    "state": "pending",
    "data": {
      "id": "<rule_id>",
      "name": "serve the bucket",
      "active": true,
      "criteria": [
        [
          {
            "conditional": "if",
            "variable": "${uri}",
            "operator": "starts_with",
            "argument": "/"
          }
        ]
      ],
      "behaviors": [
        {
          "type": "set_connector",
          "attributes": {
            "value": "<connector_id>"
          }
        }
      ],
      "description": "",
      "order": 1,
      "last_editor": "user@example.com",
      "last_modified": "2025-07-25T19:29:30.684210Z"
    }
  }
  ```

  </DocStep>
</DocSteps>

The rule is created in the **Request Phase** of the application. The change takes some time to propagate before the domain answers with the objects.

## Verify the setup

A request to the domain of the workload returns the object the connector maps to the path. A workload carries a domain in the format `xxxxxxxxxxx.azionedge.net`.

To confirm the delivery path:

<DocSteps>
  <DocStep title="Request the page">

  Replace `<workload-domain>` with the domain your workload carries:

  ```bash
  curl https://<workload-domain>/index.html
  ```

  </DocStep>
  <DocStep title="Read the response">

  The response body is the object stored under `src/index.html`, which the `/src` prefix maps to `/index.html`. It carries the heading and the paragraph of the page:

  ```html
  <h1>Hello world!</h1>
  <p>I am an object from a bucket.</p>
  ```

  </DocStep>
  <DocStep title="Open the page in a browser">

  Go to the same address. The browser renders the page with the stylesheet applied, which it loads from `/styles/style.css` under the same prefix.

  </DocStep>
</DocSteps>

The application serves the bucket. A request that does not return the object yet is a change that has not propagated: wait, send it again, and look for another cause only after that.
