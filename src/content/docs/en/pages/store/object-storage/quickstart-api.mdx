This guide instructs you through storing your first object in [Object Storage](/en/documentation/store/object-storage/), using the Azion API. By the end you will have:

- Your first bucket, created with `workloads_access` set to `read_only`.
- An object stored in that bucket, addressed by its key.
- The object listed and read back, which confirms the upload.

Prefer Azion Console? Refer to [Object Storage quickstart using Azion Console](/en/documentation/store/object-storage/quickstart/).

A bucket is not a public folder: an object you upload answers no request from the internet until an application is pointed at it. The result rests on three objects, in this order. The **bucket** is the top-level container for objects, and buckets do not nest. Each **object** inside it is a file, its key, and its content type. The key addresses the object: a `/` in a key is part of the key, not a folder. A **connector** of type Object Storage, paired with a Rules Engine rule on an [application](/en/documentation/platform/applications/), is what sends a request to the bucket. This guide creates the first two and stops there.

---

## Prerequisites

- A [personal token](/en/documentation/guides/platform/account-and-billing/personal-tokens/). Every request on this page sends it in the `Authorization` header.
- Permission to create buckets and objects in your account. For more information, refer to [Teams Permissions](/en/documentation/fundamentals/teams-permissions/).
- `curl`, or another client that sends HTTP requests.
- A file on your machine to upload, such as an image.

---

## 1. Create a bucket

A bucket holds the objects you upload. This one is created with `read_only`, the access level for content the Azion platform serves without changing it.

Bucket names are unique across every Azion account, so a short generic name is likely to be taken. A name is 6 to 63 characters, uses letters, numbers, and the hyphen, and never begins with `azion`.

<DocSteps>
  <DocStep title="Send the create request">

  Replace `[TOKEN VALUE]` with your personal token, and `my-first-bucket` with a name of your own:

  ```bash
  curl --request POST \
    --url https://api.azion.com/v4/workspace/storage/buckets \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: application/json' \
    --data '{
    "name": "my-first-bucket",
    "workloads_access": "read_only"
  }'
  ```

  </DocStep>
  <DocStep title="Read the response">

  A `201` carries the bucket:

  ```json
  {
    "state": "executed",
    "data": {
      "name": "my-first-bucket",
      "workloads_access": "read_only",
      "last_editor": "user@example.com",
      "last_modified": "2026-09-17T22:39:45.442763+00:00",
      "product_version": "1.0"
    }
  }
  ```

  A `400` with the code `17000` means the name is already in use, in your account or another. Choose a different one and send the request again.

  </DocStep>
</DocSteps>

The bucket exists and holds no objects.

## 2. Upload an object

The upload names the bucket and the key in the path, and sends the file as the body. There is no create-then-write sequence: the object exists when the request succeeds.

<DocSteps>
  <DocStep title="Send the upload request">

  Replace the key and the file path with your own. Set `Content-Type` to the type of your file, because the stored value is the one this header carries:

  ```bash
  curl --request POST \
    --url https://api.azion.com/v4/workspace/storage/buckets/my-first-bucket/objects/images/logo.png \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: image/png' \
    --data-binary '@./logo.png'
  ```

  </DocStep>
  <DocStep title="Read the response">

  A `201` carries the key the object is stored under:

  ```json
  {
    "state": "executed",
    "data": {
      "object_key": "images/logo.png"
    }
  }
  ```

  </DocStep>
</DocSteps>

The object is stored. The `images/` segment is part of the key, not a folder that had to exist first.

---

## 3. Confirm the object is stored

Two requests confirm the upload: one lists the bucket, and one reads the object back.

<DocSteps>
  <DocStep title="List the objects in the bucket">

  ```bash
  curl --request GET \
    --url https://api.azion.com/v4/workspace/storage/buckets/my-first-bucket/objects \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]'
  ```

  The response lists the key, when it was last modified, its size in bytes, and whether the entry is a prefix:

  ```json
  {
    "continuation_token": null,
    "results": [
      {
        "key": "images/logo.png",
        "last_modified": "2026-09-17T22:40:32.054000Z",
        "size": 5364,
        "is_folder": false
      }
    ]
  }
  ```

  </DocStep>
  <DocStep title="Download the object">

  Read the object back into a local file, and confirm the content type Azion stored:

  ```bash
  curl --request GET \
    --url https://api.azion.com/v4/workspace/storage/buckets/my-first-bucket/objects/images/logo.png \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --output ./logo-downloaded.png --dump-header -
  ```

  The response headers carry `HTTP/2 200` and the `content-type` the upload set, and the file is written to `./logo-downloaded.png`.

  </DocStep>
</DocSteps>

The object is stored under its key and reads back with the content type you set. It is reachable through the Azion API, the Azion CLI, and the S3 protocol, and not yet from the internet.
