A project on Vercel spreads its behavior across build settings, routing files, server functions, stored files, configuration data, security rules, and a production domain. Moving it means recreating each of these on Azion and confirming that the project answers correctly before the domain changes.

On Azion, an [application](/en/documentation/platform/applications/) and its rules take over delivery and routing. [Functions](/en/documentation/platform/functions/) runs the server code. [Object Storage](/en/documentation/platform/object-storage/) holds files, and [KV Store](/en/documentation/platform/kv-store/) holds configuration data. [Firewall](/en/documentation/platform/firewall/) filters traffic, a [workload](/en/documentation/platform/workloads/) serves the domain, and [Real-Time Metrics](/en/documentation/platform/real-time-metrics/) and [Real-Time Events](/en/documentation/platform/real-time-events/) show what happens to each request. Routes, redirects, headers, variables, functions, files, and security policies move with focused changes.

Each stage of this guide moves one layer, in the order a migration runs: inventory, deployment, code and rules, data, security, monitoring, and the domain. When near-zero downtime is not a requirement, migrate in phases with maintenance windows. Writes stop during each step, so the data needs no parallel synchronization.

## Inventory the Vercel project

Move one project first. Choose one that is meaningful enough to test the whole path and small enough to move quickly. A good first project carries one production-like domain, a few routes, redirects, and headers, one function, one Blob dependency, one Edge Config dependency, and one analytics workflow. Use it to document the process, then move the next projects in the same order.

Before you create anything on Azion, list what the project uses:

- Projects, teams, production deployments, and preview deployments.
- Build commands, output directories, framework presets, and install commands.
- `vercel.json`, the framework configuration, middleware, and route definitions.
- Environment variables for production, preview, and development.
- API routes, server actions, functions, and Fluid Compute workloads.
- Redirects, rewrites, headers, cache behavior, and image optimization settings.
- Domains, DNS records, nameservers, and the status of each certificate.
- Blob stores, Edge Config stores, feature flags, and experiments.
- Firewall rules, WAF controls, bot protections, deployment access controls, and SSO dependencies.
- Observability dashboards, analytics, alerts, log workflows, and Marketplace integrations.

Each item in the list maps to a stage of this guide. The table in Map each Vercel feature to Azion names the destination of each one.

## Deploy the project on Azion

On Azion, a Vercel project becomes an application, and a workload serves that application on a domain. Vercel keeps the build configuration in `vercel.json`, the framework configuration, and the project settings. Azion keeps it in [`azion.config.js`](/en/documentation/devtools/cli/azion-config-js/) and in the settings of the application.

Azion Console [imports a project from a GitHub repository](/en/documentation/guides/application-development/automation/import-an-existing-project-from-github/) through the Azion GitHub App, which you authorize for that repository. The Azion CLI [deploys a project](/en/documentation/devtools/cli/deploy/) from your machine. Both detect the framework and set the build settings, and `azion.config.js` overrides the preset Azion detects. For the commands that install the CLI, sign in, run the project locally, deploy, read logs, and roll back, refer to [Azion CLI](/en/documentation/devtools/cli/).

Keep the first deployment small. Prove that one representative project builds and runs on Azion before you move functions, domains, Blob stores, Edge Config values, firewall policies, dashboards, or AI integrations. To build the same chain one resource at a time, refer to [Applications quickstart](/en/documentation/platform/applications/quickstart/).

The deployment answers on a workload domain that Azion assigns under `map.azionedge.net`. Before you move any production domain, send a request to the root path, with that domain in place of `<your-workload-domain>`:

```bash
curl -i https://<your-workload-domain>/
```

The response carries the status, the headers, and the body the project returns for `/`. Send the same request to each critical route, such as a health path of the API:

```bash
curl -i https://<your-workload-domain>/api/health
```

A new workload domain can take about 11 minutes to serve its first deployment. Until then, repeat the request.

If the build fails on Azion, compare the framework preset, the install command, and the output directory with the Vercel project. Check `azion.config.js`, the package scripts, and the build output.

## Move environment variables

Environment variables hold API keys, database credentials, authentication secrets, third-party endpoints, AI provider tokens, feature flags, and per-environment settings. A variable that does not reach Azion breaks the project at run time, even when the deployment succeeds.

Collect every variable from these places before you change any code:

- The environment settings of the Vercel project.
- Variables managed through the Vercel CLI.
- Framework `.env` files used for local development.
- AI provider keys and model gateway settings.
- Blob tokens and storage credentials.
- Edge Config IDs, tokens, and keys.
- CI/CD environment settings.
- Runtime configuration in the source code.

[Recreate each variable on Azion](/en/documentation/guides/application-development/automation/work-with-variables/). For the interfaces that create, list, and change a variable, refer to [Environment variables](/en/documentation/platform/functions/environment-variables/).

Then change the code that reads the variables. A function on Azion reads a variable with `Azion.env.get()`:

```javascript
// Before: Vercel / Node.js
const apiKey = process.env.API_KEY;
const aiApiKey = process.env.AI_API_KEY;

// After: Azion Functions
const apiKey = Azion.env.get('API_KEY');
const aiApiKey = Azion.env.get('AI_API_KEY');
```

Configuration data that Vercel keeps in Edge Config moves to KV Store instead, as Move Edge Config data to KV Store shows.

:::caution
Keep secrets in approved systems, and limit access to the processes that need them. Never copy a secret into local notes, tickets, chat messages, or temporary documents.
:::

If a function reports a variable as not found, confirm that the variable exists on Azion and that the code reads it with `Azion.env.get()`.

## Move API routes and server functions

Vercel Functions and Fluid Compute often carry the most critical logic of a project: API routes, server actions, webhooks, authentication, personalization, AI orchestration, and calls to backend services. On Azion, this code runs in Functions. A function holds the code, a function instance runs it on an application, and a rule decides which requests reach it. Code that read Vercel Blob or Edge Config reads Object Storage or KV Store instead.

A Vercel handler receives `req` and `res`. A function on Azion exports a `fetch` handler that takes a standard `Request` and returns a `Response`:

```javascript
// Before: Vercel API route style
export default async function handler(req, res) {
  const body = req.body;

  res.status(200).json({
    message: 'Hello',
    data: body
  });
}

// After: Azion Functions
export default {
  async fetch(request) {
    const body = await request.json();

    return new Response(JSON.stringify({ message: 'Hello', data: body }), {
      status: 200,
      headers: { 'Content-Type': 'application/json' }
    });
  }
};
```

Vercel routes a request to a function by its file path, such as `app/api/users/[id]/route.ts` or `pages/api/users/[id].ts`. On Azion, a rule routes it. This rule sends `GET` requests for `/api/users/<id>` to a function instance:

```json
{
  "name": "GET /api/users/:id",
  "active": true,
  "criteria": [
    [
      { "variable": "${uri}", "conditional": "if", "operator": "matches", "argument": "^/api/users/([^/]+)$" },
      { "variable": "${request_method}", "conditional": "and", "operator": "is_equal", "argument": "GET" }
    ]
  ],
  "behaviors": [
    { "type": "run_function", "attributes": { "value": <function-instance-id> } }
  ]
}
```

The `run_function` behavior takes the ID of the function instance, not of the function. It requires [Application Accelerator](/en/documentation/platform/applications/application-accelerator/settings/) and Functions on the application. For more information, refer to [Run Function](/en/documentation/platform/applications/rules-engine/#run-function).

## Move AI routes

AI routes on Vercel combine application code, model calls, streaming responses, tool calls, provider routing, usage tracking, and observability. On Azion, a function calls the model, through AI Inference or an external provider. Provider credentials become environment variables, and Real-Time Events, Real-Time Metrics, and Data Stream take over the observability.

| Concern | On Vercel | On Azion |
| --- | --- | --- |
| Model access | AI Gateway and provider integrations | [AI Inference models](/en/documentation/platform/ai-inference/models/), or an external provider called from a function |
| SDK | AI SDK | Azion AI Client and standard JavaScript APIs |
| Streaming | Framework and SDK streaming responses | Functions with Web APIs and streaming responses |
| Observability | AI Gateway and Observability | Real-Time Events, Real-Time Metrics, and Data Stream |
| Routing and fallbacks | AI Gateway | Functions with provider routing logic |

This function forwards the request body to a model provider and returns the provider's response. It reads the provider key from an environment variable:

```javascript
export default {
  async fetch(request) {
    const prompt = await request.text();

    const response = await fetch('https://ai-provider.example.com/v1/chat/completions', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'Authorization': 'Bearer ' + Azion.env.get('AI_API_KEY')
      },
      body: JSON.stringify({ prompt })
    });

    return response;
  }
};
```

To move an AI route:

1. List the models, the providers, the routes, and the fallback behavior.
2. Move the provider credentials to environment variables.
3. Decide, per route, whether inference runs on AI Inference or on an external provider.
4. Recreate each AI route as a function.
5. Route a path to each function with a rule.
6. Rebuild the observability with Real-Time Events, Real-Time Metrics, and Data Stream.
7. Check streaming responses, timeouts, and error handling.

The function is deployed and routed like any other function. For the commands, refer to Move API routes and server functions on this page.

## Recreate redirects, rewrites, and headers

Routing on Vercel comes from framework routes, middleware, `vercel.json`, project settings, and CDN behavior. On Azion, Rules Engine for Applications holds redirects, rewrites, headers, connector selection, cache behavior, and changes to requests and responses. Each rule pairs criteria with behaviors, and it runs in the Request Phase or the Response Phase.

This `vercel.json` entry sends every path under `/old-blog/` to the same path under `/blog/`, permanently:

```json
{
  "redirects": [
    {
      "source": "/old-blog/:path*",
      "destination": "/blog/:path*",
      "permanent": true
    }
  ]
}
```

On Azion, the rule matches the old path with a regular expression and captures the rest of it. The `capture_match_groups` behavior stores the capture as `%{capture[1]}`, and `redirect_to_301` sends the user to the new path:

```json
{
  "name": "old-blog-redirect",
  "active": true,
  "criteria": [
    [
      { "variable": "${uri}", "conditional": "if", "operator": "matches", "argument": "^/old-blog/(.*)$" }
    ]
  ],
  "behaviors": [
    {
      "type": "capture_match_groups",
      "attributes": { "captured_array": "capture", "subject": "${uri}", "regex": "^/old-blog/(.*)$" }
    },
    { "type": "redirect_to_301", "attributes": { "value": "/blog/%{capture[1]}" } }
  ]
}
```

`capture_match_groups` requires Application Accelerator on the application. For every argument of both behaviors, refer to [Capture Match Groups](/en/documentation/platform/applications/rules-engine/#capture-match-groups) and [Redirect To](/en/documentation/platform/applications/rules-engine/#redirect-to).

Response headers go in a Response Phase rule. In the Azion configuration file of the project, this rule adds two security headers to every response:

```typescript
import type { AzionConfig } from 'azion/config';

const config: AzionConfig = {
  applications: [{
    name: 'my-app',
    rules: {
      response: [{
        name: 'Security Headers',
        active: true,
        criteria: [{
          variable: 'uri',
          conditional: 'if',
          operator: 'starts_with',
          argument: '/'
        }],
        behavior: {
          addResponseHeader: [
            'X-Frame-Options: SAMEORIGIN',
            'X-Content-Type-Options: nosniff'
          ]
        }
      }]
    }
  }]
};

export default config;
```

Recreate the rest of the routing in the same way:

- Convert each Vercel route pattern to Rules Engine criteria and regular expressions.
- Move simple redirects to rules.
- Move simple response headers to Response Phase rules.
- Use Functions for dynamic rewrites, authentication, signed URLs, and external lookups.
- Check trailing slashes, locale prefixes, and canonical paths.
- Compare cache headers and the redirects that search ranking depends on before the cutover.

If a redirect or a rewrite behaves differently than on Vercel, test the capture groups and check the criteria that each Vercel pattern became.

## Recreate cache behavior

A Vercel project can combine CDN caching, framework cache settings, dynamic rendering, static generation, and route-level behavior. On Azion, a [cache setting](/en/documentation/platform/applications/cache/cache-settings/) holds how long an object stays cached, and a rule applies it to the paths you choose. A cache setting belongs to one application, so every call that creates or changes one names the application.

| Concern | On Vercel | On Azion |
| --- | --- | --- |
| Cache configuration | Framework cache behavior, CDN settings, and headers | Cache settings, applied by rules |
| Cache key | Platform and framework behavior | The variations of [Cache variation](/en/documentation/platform/applications/application-accelerator/cache-variation/), which need Application Accelerator |
| Purge | Redeploys and cache invalidation | [Real-Time Purge](/en/documentation/platform/applications/cache/real-time-purge/), by URL, cache key, or wildcard |
| Stale content | Framework and CDN controls | The **Stale cache** switch of a cache setting |
| Fewer requests to the origin | The managed CDN | [Tiered Cache](/en/documentation/platform/applications/cache/tiered-cache/) and [Origin Shield](/en/documentation/platform/connectors/origin-shield/) |

Without Application Accelerator on the application, a **Max Age** below 60 seconds is refused with `21021`. For every field of a cache setting, refer to [Cache settings](/en/documentation/platform/applications/cache/cache-settings/).

### Purge cached content

On Vercel, a redeploy invalidates the cache. On Azion, Real-Time Purge removes objects before their TTL ends, by URL, by cache key, or by one wildcard expression. A wildcard purge takes one expression per request. A URL purge for a domain outside your account is refused with `400` and code `30003`.

## Serve optimized images

Vercel transforms images through URLs that the framework generates. On Azion, Image Processor transforms an image when a request carries the `ims` query-string parameter, and it resizes, crops, fits, and converts formats. The source image comes from an HTTP origin or from Object Storage, and the application delivers the derived image.

The first line in this pair is one framework-generated image URL. The pattern varies by framework. The second line asks Image Processor for the same image, 1,200 pixels wide:

```text
/_next/image?url=%2Fhero.jpg&w=1200&q=75
/hero.jpg?ims=1200x
```

A resize takes these forms in `ims`:

| Syntax | What it does | Example |
| --- | --- | --- |
| `?ims=WxH` | Resizes to a width and a height | `?ims=400x300` |
| `?ims=Wx` | Resizes to a width, and calculates the height | `?ims=400x` |
| `?ims=xH` | Resizes to a height, and calculates the width | `?ims=x300` |

For crop, fit, fill, quality, and format conversion, refer to [Image Processor URL parameters](/en/documentation/platform/applications/image-processor/url-parameters/). Image Processor picks the output format from the `Accept` header of the client, and serves WebP to a browser that accepts it.

  </DocStep>
  <DocStep title="Select the Main Settings tab" />
  <DocStep title="Turn on Image Processor">

  In **Modules**, turn on **Image Processor**.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

Image Processor is on, and the rules of the application can use the **Optimize Images** behavior.

Each transformation also needs its own cache entry, so `ims` goes in the cache key of the cache setting that serves images. To add the rule and the cache key, refer to [Image Processor quickstart](/en/documentation/platform/applications/image-processor/quickstart/). For the same setup on an application that already serves traffic, refer to [Configure Image Processor on an application](/en/documentation/guides/application-performance/delivery-optimization/process-images/).

Request a few representative image URLs before the cutover. If images come back untransformed, check that Image Processor is on and that every image URL carries `ims`.

## Move Blob files to Object Storage

Vercel Blob holds files such as images, documents, videos, and user uploads. Object Storage holds them as objects in buckets, and it is S3 compatible: S3 tools, the API, the CLI, and the Runtime API all reach it. Object management goes through the S3 endpoint `s3.us-east-005.azionstorage.net`. A private file that Vercel protects with a token or a URL pattern relies on bucket and object permissions, and on application logic, on Azion.

Code that writes with the Blob SDK switches to an S3-compatible client:

```javascript
// Before: Vercel Blob pattern
import { put } from '@vercel/blob';

const blob = await put('avatar.png', file, {
  access: 'public'
});

// After: S3-compatible Object Storage client
import { S3Client, PutObjectCommand } from '@aws-sdk/client-s3';

const client = new S3Client({
  region: 'us-east-005',
  endpoint: 'https://s3.us-east-005.azionstorage.net',
  credentials: {
    accessKeyId: Azion.env.get('AZION_ACCESS_KEY'),
    secretAccessKey: Azion.env.get('AZION_SECRET_KEY')
  }
});

await client.send(new PutObjectCommand({
  Bucket: 'my-bucket',
  Key: 'avatar.png',
  Body: file
}));
```

[S3-compatible tools](/en/documentation/guides/application-development/data/use-s3-compatible-tools-with-object-storage/) such as `s3cmd`, `rclone`, or the AWS CLI copy objects in bulk. For the S3 operations Object Storage accepts and the `s3cmd` form of each, refer to [S3 compatibility](/en/documentation/platform/object-storage/s3-compatibility/).

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.cli">

To [create a bucket](/en/documentation/guides/application-development/data/create-and-modify-bucket/) and [upload a file](/en/documentation/guides/application-development/data/upload-and-download-objects-from-bucket/) with the Azion CLI, create the bucket first. `read_only` lets workloads read its objects:

```bash
azion create storage bucket --name <your-bucket-name> --workloads-access read_only
```

```text

```

Upload a file, with its key in the bucket:

```bash
azion create storage object --bucket-name <your-bucket-name> --object-key images/logo.png --source ./logo.png
```

```text
Object created successfully
```

Pass a relative path in `--source`. With an absolute path, the CLI prepends the working directory and cannot open the file.

List the objects of the bucket:

```bash
azion list storage object --bucket-name <your-bucket-name> --details
```

The command prints a table with the `KEY`, `LAST MODIFIED`, and `SIZE` columns, and the uploaded object is in it.

</Fragment>

<Fragment slot="panel.api">

To [create a bucket](/en/documentation/guides/application-development/data/create-and-modify-bucket/) and [upload a file](/en/documentation/guides/application-development/data/upload-and-download-objects-from-bucket/) with the API, create the bucket first. `read_only` lets workloads read its objects:

```bash

  --header 'Accept: application/json' \

```

The API answers `201` with `state` set to `executed`. Upload a file, with its key in the path and its media type as the `Content-Type` header:

```bash

  --header 'Authorization: Token [TOKEN VALUE]' \

```

The API answers `201`, and `data.object_key` holds `images/logo.png`. List the objects of the bucket:

```bash

  --header 'Accept: application/json' \
  --header 'Authorization: Token [TOKEN VALUE]'
```

The API answers `200`. Each entry in `results` carries the object's `key`, `last_modified`, `size`, and `is_folder`.

</Fragment>

</Tabs>

Serve the objects to users through the application and a [connector](/en/documentation/platform/connectors/), so requests pass through cache, security rules, and your production domain. For the steps, refer to [Use a bucket as an application origin](/en/documentation/guides/application-development/data/use-bucket-as-origin/).

If files are missing after the move, the export or the import was incomplete. Export the files again, then check the object keys and the bucket permissions.

## Move Edge Config data to KV Store

Edge Config often holds feature flags, experiments, redirects, configuration, and data the project reads often. KV Store keeps key-value pairs in [namespaces](/en/documentation/platform/kv-store/namespaces/), and functions read them through [`Azion.KV`](/en/documentation/devtools/runtime/api-reference/kv-store/). It covers the same uses, plus lightweight state.

Code that reads Edge Config [opens a KV Store namespace](/en/documentation/guides/application-development/data/manage-with-functions/) instead:

```javascript
// Before: Vercel Edge Config
import { get } from '@vercel/edge-config';

const checkoutEnabled = await get('feature:checkout');

// After: Azion KV Store
const kv = await Azion.KV.open('my-namespace');

const checkoutEnabled = await kv.get('feature:checkout');
```

Then move the data:

3. Document what the code does when a key is missing.
4. Check the value encoding and the JSON serialization.
5. Test the read paths before production traffic moves.
6. Rebuild the flag and experiment workflows that rely on Vercel tooling.

If Edge Config data is missing after the move, recreate the keys, check the namespace names, and test the default values.

## Protect the application

Vercel Firewall, WAF, Bot Management, BotID, Platform Security, and Advanced Deployment Protection move to Firewall and the Products enabled on it. The workload deploys the firewall alongside the application, and the firewall filters malicious traffic. In Azion Console, the **Deployment Settings** of the workload select its **Firewall**.

| Concern | On Vercel | On Azion |
| --- | --- | --- |
| Managed WAF | WAF protections | [WAF rule sets](/en/documentation/platform/firewall/waf/rules-set/) |
| Custom traffic rules | Firewall rules | Rules Engine for Firewall |
| IP controls and trusted IPs | IP blocks and allowlists | Network Lists |
| Rate limiting | Firewall rate controls | Rules Engine for Firewall and Functions |
| Actions | Block, challenge, redirect, and allow | Allow, deny, drop, redirect, custom HTML, and hold connection |
| Infrastructure protection | Platform Security | DDoS Protection, Network Shield, and Firewall |
| Bot controls | Bot Management and BotID | Bot Manager, Bot Manager Lite, and function logic where needed |
| Password or authentication gates | Advanced Deployment Protection | Functions and firewall rules |

To move the protection:

1. Create a firewall, or select an existing one.
2. Turn on WAF rule sets where the project needs them. For the steps, refer to [WAF quickstart](/en/documentation/platform/firewall/waf/quickstart/).
3. Recreate the custom rules in Rules Engine for Firewall. For the steps, refer to [Create a firewall rule](/en/documentation/guides/application-security/firewall-and-waf/work-with-rules-engine/).
4. Create network lists for IP allowlists and denylists.
5. Turn on bot protection where the project needs it. For the steps, refer to [Bot Manager quickstart](/en/documentation/platform/firewall/bot-manager/quickstart/).
6. Associate the firewall with the workload, in its **Deployment Settings**.

A deployment protection rule on Vercel becomes a firewall rule that denies requests outside an approved network. For example, a rule can deny requests to `/admin`, or to paths that start with `/preview/`, unless the client address is in a network list that holds `10.0.0.0/8`. For the variables and operators such a rule takes, refer to [Rules Engine for Firewall](/en/documentation/platform/firewall/rules-engine/).

Run WAF changes in a monitoring mode before they block requests. Compare the false positives, the rules that trigger most, the bypass requirements, and the exceptions the application needs, then enforce. If a firewall rule blocks valid users, go back to monitoring, compare the events, and tune the criteria.

## Rebuild monitoring

Vercel Observability, Speed Insights, and Web Analytics move to the Observe Products, so production visibility, troubleshooting, and compliance reporting continue after the cutover. Retention depends on the Product and, for exported data, on the destination.

Real-Time Metrics shows dashboards for the traffic of the application, and it answers queries through a GraphQL API. It tracks these metrics:

- **Requests**: total requests, requests by status code, and requests by HTTP method.
- **Performance**: response time, upstream header time, and origin response time.
- **Bandwidth**: data transferred, and data saved by cache.
- **Cache**: hit ratio, miss ratio, and expired objects.
- **Errors**: `4xx` errors, `5xx` errors, and origin errors.

Real-Time Events holds [the detailed logs of each request](/en/documentation/guides/platform/observability/understand-logs/), for investigation. Its datasets cover requests, functions, WAF, DNS, and image processing, among others. You query them in Azion Console, filtered by time range, or [through the GraphQL API](/en/documentation/guides/platform/observability/investigate-requests-graphql-api/).

Edge Pulse measures real-user performance, as Speed Insights does on Vercel. Data Stream [sends logs to external tools](/en/documentation/platform/data-stream/first-steps/) for security, analytics, storage, and compliance work. [A stream](/en/documentation/guides/platform/observability/use-data-stream/) reads a source, such as Applications or WAF, formats each record with a template, and delivers it to a destination with that destination's credentials. Data Stream delivers to these destinations:

- **Cloud storage**: Amazon S3, Azure Blob Storage, and Azion Object Storage.
- **Monitoring**: Datadog, Splunk, Elasticsearch, and Azure Monitor.
- **Streaming**: AWS Kinesis Data Firehose and Apache Kafka.
- **Analytics**: Google BigQuery.
- **Security**: IBM QRadar.
- **Custom**: an HTTP webhook, or a standard HTTP or HTTPS `POST`.

Integrations from the Vercel Marketplace move to the Azion Marketplace, or to a Data Stream destination.

To move the monitoring:

1. List the Core Web Vitals, the page-level reports, and the analytics dashboards you use.
2. Decide which dashboards move to Edge Pulse, to Real-Time Metrics, or to an external BI tool.
3. Recreate custom event tracking where the project needs it.
4. Check the privacy and consent requirements.
5. After the cutover, compare the user experience metrics with the Vercel baseline.

If analytics show a gap after the cutover, a Vercel analytics dependency was not replaced. Configure Edge Pulse, Real-Time Metrics, Real-Time Events, and Data Stream before production traffic moves.

## Point the domain to Azion

The domain moves last, as a planned cutover, because it affects users, search ranking, brand trust, and availability. The workload, the DNS records, and the certificate can all be ready before production traffic switches.

There are two ways to point a domain at Azion:

| Strategy | Use it for | DNS control |
| --- | --- | --- |
| CNAME | A subdomain you want to move quickly | Your DNS provider stays |
| Nameserver | Full DNS control, and apex domains | DNS moves to Edge DNS |

To move the domain:

1. Create the certificate first, so the domain answers over HTTPS as soon as it resolves to Azion. Azion issues free Let's Encrypt certificates and renews them automatically.
2. [Add the domain to the workload](/en/documentation/guides/application-development/getting-started/create-azion-custom-domain/) that serves the application. For more information, refer to [Domains](/en/documentation/platform/workloads/domains/).
3. Point the domain at Azion, with one of the two strategies.

For the CNAME strategy, point the subdomain at the workload domain. Your DNS provider keeps the rest of the zone:

```text
www CNAME <your-workload-domain>
```

For the nameserver strategy, set the domain's nameservers to Edge DNS. Azion then answers for the whole zone, which an apex domain requires:

```text
ns1.aziondns.net
ns2.aziondns.com
ns3.aziondns.org
```

:::caution
Before production traffic switches, confirm that the certificate is active, the domain belongs to the right workload, and the DNS records are ready. Test the critical routes and the redirects, and set up the monitoring you need after the cutover.
:::

Once the record resolves, send a request to the domain, with it in place of `<your-domain>`:

```bash
curl -i https://<your-domain>/
```

The response comes from the application, with the status and headers it returns for `/`. If the certificate is not active, check the certificate status and its association with the workload before you change DNS.
