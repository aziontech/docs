You can describe a [Rules Engine](/en/documentation/platform/applications/rules-engine/) rule in plain language to a coding agent connected to the [Azion MCP server](/en/documentation/devtools/mcp/) and get a rule proposal back. The server creates no rule: you review the proposal and create the rule yourself. To create a rule without an agent, refer to [Create an application rule](/en/documentation/guides/application-development/getting-started/work-with-rules-engine/).

---

## Prerequisites

- A coding agent connected to the MCP server. To connect one, refer to [MCP server quickstart](/en/documentation/devtools/mcp/configuration/).
- An application to add the rule to, or a firewall for a [Rules Engine for Firewall](/en/documentation/platform/firewall/rules-engine/) rule.

---

## Ask your agent for a rule proposal

The MCP server turns a goal into a rule proposal with the `create_rules_engine` tool. The tool asks a language model for the rule, so the proposal can differ between calls. It does not use your token and creates nothing in your account. To get a proposal that adds security headers:

<DocSteps>
  <DocStep title="Describe the rule to your agent">

  Give the agent the goal, and say whether the rule is for an application or a firewall. For example: `Create Rules Engine rules to add security headers including HSTS, X-Frame-Options, and CSP for my application.`

  </DocStep>
  <DocStep title="Check the arguments of the tool call">

  The agent calls `create_rules_engine` with your goal in `query` and the kind of rule in `useCase`. Use `edge_application` for an application rule and `edge_firewall` for a firewall rule. Only `useCase` is required, but the tool builds the rule from `query`.

  </DocStep>
  <DocStep title="Read the proposal">

  The tool returns JSON text. Inside `data`, the proposal carries the `criteria`, `behaviors`, and `phase` of the rule, and an `explanation`.

  </DocStep>
</DocSteps>

The tool returns a proposal such as:

```json
{
  "success": true,
  "data": {
    "criteria": [
      {
        "logic": null,
        "criteria": [
          {
            "variable": "${request_uri}",
            "operator": "matches",
            "argument": ".*"
          }
        ]
      }
    ],
    "behaviors": [
      {
        "type": "Add_response_header",
        "args": "Strict-Transport-Security: max-age=31536000; includeSubDomains"
      },
      {
        "type": "Add_response_header",
        "args": "X-Frame-Options: DENY"
      },
      {
        "type": "Add_response_header",
        "args": "Content-Security-Policy: default-src 'self'"
      }
    ],
    "phase": "RESPONSE",
    "explanation": "This rule adds the HSTS, X-Frame-Options, and Content-Security-Policy headers to all responses. Adjust the CSP value as needed for your application's requirements."
  }
}
```

The proposal adds three `Add_response_header` behaviors in the `RESPONSE` phase, one per header. Its criterion matches `${request_uri}` against `.*`, so the rule acts on every request. `${request_uri}` requires [Application Accelerator](/en/documentation/platform/applications/application-accelerator/settings/) on the application. Without it, match `${uri}` instead, as [Variables](/en/documentation/platform/applications/rules-engine/#variables) explains. Adjust the `Content-Security-Policy` value to your application, as the `explanation` says. The rule does not exist until you apply the proposal.

## Review a cache proposal

A proposal can depend on objects that do not exist yet, or need changes before it does what you asked. For the goal `Configure Rules Engine to cache static assets for 1 year and API responses for 5 minutes.`, the tool returns a proposal such as:

```json
{
  "success": true,
  "data": {
    "criteria": [
      {
        "logic": "OR",
        "criteria": [
          {
            "variable": "${uri}",
            "operator": "matches",
            "argument": ".*\\.(jpg|jpeg|png|gif|css|js|svg|woff|woff2|ttf|eot|ico|mp4|webm|ogg|mp3|wav|pdf|zip|tar|gz|rar|7z)$"
          },
          {
            "variable": "${uri}",
            "operator": "starts with",
            "argument": "/api/"
          }
        ]
      }
    ],
    "behaviors": [
      {
        "type": "Set_cache_policy",
        "args": "StaticAssetsCachePolicy"
      },
      {
        "type": "Set_cache_policy",
        "args": "ApiCachePolicy"
      }
    ],
    "phase": "RESPONSE",
    "explanation": "You need to create two cache policies in Azion: one named 'StaticAssetsCachePolicy' with a TTL of 1 year for static assets, and another named 'ApiCachePolicy' with a TTL of 5 minutes for API responses. The rules engine will apply the appropriate cache policy based on the URI pattern. For more details on creating cache policies, refer to the Azion documentation."
  }
}
```

Before you apply this proposal, make three changes:

- Create the cache settings first. Each `Set_cache_policy` behavior names a cache policy that the `explanation` asks you to create. In Applications, the object this behavior applies is a cache setting, which holds the TTL. Create one with a 1-year TTL and one with a 5-minute TTL. For the procedure, refer to [Create a cache setting](/en/documentation/guides/application-performance/cache-and-purge/tune-cache-settings/).
- Split the rule in two. The proposal joins the static-asset criterion and the `/api/` criterion with `OR`, so both behaviors apply to both kinds of request. Create one rule per criterion, each with its own cache setting. For how criteria combine, refer to [Conditionals](/en/documentation/platform/applications/rules-engine/#conditionals).
- Create both rules in the Request Phase. The proposal names `RESPONSE`, but _Set Cache Policy_ runs only in the Request Phase, as [Set Cache Policy](/en/documentation/platform/applications/rules-engine/#set-cache-policy) states.

## Apply the proposal

The proposal is not an API request body, so you translate it into the rule fields of the Rules Engine. In the API and the Azion CLI, a behavior `type` is lowercase, such as `add_response_header` or `set_cache_policy`, and its argument goes in `attributes.value`. For `set_cache_policy`, the value is the ID of the cache setting. Each criterion carries a `conditional` (`if`, `and`, or `or`), and its `operator` is one of the [Operators](/en/documentation/platform/applications/rules-engine/#operators), such as `starts_with`.

To create the rule in Azion Console, follow [Create an application rule](/en/documentation/guides/application-development/getting-started/work-with-rules-engine/). To create it with the API, refer to the [API](/en/documentation/platform/applications/rules-engine/#api) section of Rules Engine for Applications. To create it from a JSON file with the CLI, refer to [Azion CLI rules-engine](/en/documentation/devtools/cli/resources/rules-engine/). For a firewall rule, refer to [Rules Engine for Firewall](/en/documentation/platform/firewall/rules-engine/).

The rule appears in the **Rules Engine** tab of the application, in the list of its phase. If the agent finds no `create_rules_engine` tool, refer to [Troubleshoot the MCP server](/en/documentation/devtools/mcp/troubleshooting/).
