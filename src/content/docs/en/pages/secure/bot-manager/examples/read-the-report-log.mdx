A scored request leaves a report line behind it, carrying the score, the rules that produced it, and the verdict the function reached. The query below reads those lines from the `functionConsoleEvents` dataset, which is the route Azion verified. Reach for it whenever you want the scores your own traffic produces, whether or not anything is being refused yet.

Send the query to `https://api.azion.com/v4/events/graphql` with an `Authorization: Token [TOKEN VALUE]` header and a `tsRange` covering the window you care about:

```graphql
{
  functionConsoleEvents(
    limit: 200
    filter: { tsRange: { begin: "2026-09-21T11:30:00", end: "2026-09-21T13:00:00" } }
    orderBy: [ts_ASC]
  ) {
    ts
    line
    level
    lineSource
    functionId
    configurationId
  }
}
```

The response is `200`, with one record for each line the function wrote. `level` reads `LOG` and `lineSource` reads `CONSOLE` on a Bot Manager record. `functionId` is the id of the installed function, and `configurationId` is the id of the workload the request arrived on, not the id of the firewall that ran the instance.

`line` carries the whole report line: a prefix, then one JSON object.

```text
[Bot-Protection][storefront-bots] Report:  {"request_id":"f377c02e9b8c032ee3d426dc187d24b5","remote_addr":"203.0.113.42","fingerprint":"ge20cn020000_236f06e2e1da_aea9e0ce93d5_5311f4c13046","host":"<your-workload-domain>","http_user_agent":"","request_uri":"/","geoip_country":"BR","geoip_region":"PE","asn":"264046","score":28,"bot_category":"Bad Bot Signatures, Malicious Intent detected","classified":"legitimate","action":"allow","matched_rules":[1,10,18,19,20]}
```

Four values answer what the instance did with the request. `score` is the number the function reached, `matched_rules` holds the rules that produced it, `action` is what the function applied at the threshold in force, and `classified` is the verdict it recorded. For every field a line carries, refer to [Logs](/en/documentation/secure/bot-manager/logs/#fields).

## How it works

The second bracket of the prefix carries the `log_tag` from the instance's arguments, not the host. The host is a field inside the object, and `log_tag` is not: it appears in the prefix alone, which is what makes it the way to tell one instance's lines from another's. `functionId` will not do that job, because every instance of the installed function shares it. Give each instance a tag of its own before you go looking for its lines.

A line exists only for a request the instance's `internal_logs` value covers. At `2` the function writes one for every request, including one that scores `0`, which is the value an observation window wants. The verdict in the line moves with the threshold as well: `classified` is relative to the threshold in force rather than a property of the request, and Azion measured the same score of `28`, from the same matched rules, reading `legitimate` under a threshold of `30` and `bad bot` under a threshold that `28` reaches.

Two values in a record are read wrong more often than the rest. `configurationId` is the workload id, so a filter built around a firewall id returns nothing at all rather than an error. And `geoip_country` is a country code, `BR` rather than `Brazil`, while `fingerprint` is four underscore-separated segments rather than a hash of any length.
