The object below is one value away from an instance that refuses nothing: `action` reads `deny`, so [Bot Manager Lite](/en/documentation/secure/bot-manager/bot-manager-lite/) answers `403` to a request whose score reaches the threshold instead of serving it. Reach for it once an observation window has shown you what your own traffic scores and you want the threshold to have an effect.

```json
{
  "threshold": 30,
  "action": "deny",
  "internal_logs": 2,
  "log_tag": "storefront-bots"
}
```

`30` is the threshold Bot Manager Lite ships, and at that value a browser is not refused: Azion sent one request carrying a Chrome user agent, `Accept`, `Accept-Language`, `Accept-Encoding`, four `Sec-Fetch-*` headers and `Upgrade-Insecure-Requests` against this exact configuration, and it reached the application. `internal_logs` at `2` keeps a report line for every request, so a refusal leaves a record of the score behind it. For every argument an instance accepts, refer to [Arguments](/en/documentation/secure/bot-manager/arguments/#fields).

:::caution
The object is not validated. A key the function does not recognize is accepted, stored, and displayed back exactly as typed, while the function runs on its own default. An instance whose `action` is misspelled looks configured to refuse and refuses nothing.
:::

Save the object as `bmargs.json`:

The `--args` flag of `azion create firewall-instance` takes the path to that file, and no inline JSON:

```bash
azion create firewall-instance --name bot-manager-lite --firewall-id <firewall-id> \
  --function-id <function-id> --args bmargs.json --active true
```

```bash
  "name": "bot-manager-lite",

  "active": true,

```

The call answers `202` and returns the instance as the platform stored it:

## How it works

`action: deny` answers `HTTP 403` and serves Azion's default error page. Azion measured it against a workload of its own: the response carries `content-type: text/html`, an `x-azion-request-id` header, and the page titled `Azion - Default error page`. Nothing about the answer names Bot Manager, so the report line is where you confirm which instance refused the request and what it scored.

That `403` is the answer the deny action produces, and it is not the whole set of answers a client can receive from a firewall running Bot Manager. A client presenting no valid session receives an empty-bodied response instead, carrying the two session cookies the function sets, and a client that neither runs JavaScript nor keeps cookies stays on that answer: an API consumer, a health check, or a monitor never reaches a `403` and never reaches the application either. For what that looks like and what to do about it, refer to [Troubleshoot Bot Manager](/en/documentation/secure/bot-manager/troubleshooting/).

Wait about two minutes before you read anything into a response. Azion switched one instance from `allow` to `deny` and polled the workload every 15 seconds; the first seven attempts were served and the eighth was refused. Two more values are worth knowing before you change this object. At a `threshold` of `0` every request is at or above the threshold, so the configured action fires on all of them, which with `deny` refuses every request the rule matches. And because nothing validates the object, `deny` is in force only while the key that carries it is spelled correctly: Azion sent one instance twenty-one keys, one of them meaningless, and all twenty-one were stored and read back byte for byte with no error anywhere.
