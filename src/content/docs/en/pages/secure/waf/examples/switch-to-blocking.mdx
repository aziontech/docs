The mode belongs to the `Set WAF` behavior, not to the rule set. `Logging` scores a request, records what matched, and serves it; `Blocking` refuses it with `400`. Reach for this when a rule set has run long enough in `Logging` for you to read what it matched, and you are ready for it to start refusing requests.

Send the rule again with `mode` set to `blocking`. A `PUT` to `/v4/workspace/firewalls/<firewall-id>/request_rules/<rule-id>` replaces the rule, so the body carries the criteria too:

```json
{
  "name": "Apply storefront-waf",
  "active": true,
  "criteria": [
    [
      {
        "conditional": "if",
        "variable": "${request_uri}",
        "operator": "starts_with",
        "argument": "/"
      }
    ]
  ],
  "behaviors": [
    {
      "type": "set_waf",
      "attributes": {
        "waf_id": 21717,
        "mode": "blocking"
      }
    }
  ]
}
```

In Azion Console, open the firewall, select the **Rules Engine** tab and the rule, and set the mode on its **Set WAF** behavior to _Blocking_.

## How it works

`mode` takes `logging` or `blocking` and nothing else. A body carrying `"mode": "learning"` is refused with `400` and the error `10039 Invalid Choice`, pointing at `/data/behaviors/0/attributes/mode`; a body with no `mode` at all is refused with `10059 Required Field` at the same pointer.

Because the mode sits on the behavior, the same rule set can run in `logging` on one rule and in `blocking` on another. That is how you move one path at a time: keep the rule set unchanged, and switch the rules that apply it one by one. A change takes several minutes to reach Azion's distributed infrastructure, and requests alternate between the old and new behavior while it arrives.
