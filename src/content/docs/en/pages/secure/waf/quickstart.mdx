This guide instructs you through scoring your first request against [Web Application Firewall (WAF)](/en/documentation/secure/waf/).

- Create a rule set that carries eight threat families at `medium` sensitivity.
- Apply that rule set to a firewall with a `Set WAF` behavior in blocking mode.
- Send an injection-shaped request and read the refusal.

Four objects put a request under inspection, and each one links to the next:

1. The **rule set** holds the threat families and the sensitivity chosen for each.
2. The **firewall** carries the WAF module, and the **workload** serving your application is bound to that firewall.
3. The **Rules Engine rule** on that firewall carries a `Set WAF` behavior, which names the rule set and the mode.
4. The **request** is what WAF then scores against the rule set.

A rule set inspects nothing on its own. Until a Rules Engine rule names it, no request is scored.

- An Azion account. To create one, refer to [How to create an account on Azion](/en/documentation/fundamentals/creating-account/).

## 1. Create the WAF rule set

The rule set holds what to detect. It carries eight threat families, and each family has a sensitivity level that fixes the score at which it blocks. Every family starts at `medium`, which is the level this guide uses.

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

To create the rule set in Azion Console:

<DocSteps>
  <DocStep title="Open the WAF Rules page">

  Access [Azion Console](https://console.azion.com/) > **Edge Libraries** > **WAF Rules**.

  </DocStep>
  <DocStep title="Select + WAF Rule" />
  <DocStep title="Name the rule set">

  In the **General** section, enter a **Name**. For example: `storefront-waf`.

  </DocStep>
  <DocStep title="Leave every family at its default sensitivity">

  The **Threat Type Configuration** section lists eight threat families. Each one opens on _Sensitivity Medium_.

  </DocStep>
  <DocStep title="Keep the Active switch turned on" />
  <DocStep title="Save the rule set" />
</DocSteps>

The rule set appears in **WAF Rules**, which lists its **Threat Type Configuration**, **Status**, **Last Editor**, and **Last Modified**.

</Fragment>

<Fragment slot="panel.cli">

The Azion CLI creates a complete rule set from a name alone. To create it:

<DocSteps>
  <DocStep title="Run the create command">

  ```bash
  azion create waf --name "storefront-waf"
  ```

  </DocStep>
  <DocStep title="Read the output">

  The command prints the id of the new rule set:

  ```text
  Created WAF with ID 21719
  ```

  </DocStep>
</DocSteps>

The rule set is active, it runs on ruleset `1`, and it carries all eight threat families at `medium`. Record the id. Stage 2 passes it to the rule.

</Fragment>

## 2. Apply the rule set with a Rules Engine rule

A [Rules Engine for Firewall](/en/documentation/platform/firewall/rules-engine/) rule selects requests by its own criteria. Its `Set WAF` behavior then names one rule set and one mode. The rule below applies your rule set to every request the firewall receives.

The mode is required, and it belongs to the behavior rather than to the rule set. `Blocking` refuses a request whose score reaches a threshold. `Logging` records the same request and serves it. This guide uses `Blocking`.

:::caution
Key the criterion on the request URI, never on the query string. A criterion such as `${request_args}` `matches` `.*` does not match a request without a query string. It silently skips every `POST` whose payload sits in the body.
:::

<Tabs client:visible sharedStore="interface">

<Fragment slot="panel.console">

To apply the rule set in Azion Console:

<DocSteps>
  <DocStep title="Open the firewall bound to your workload">

  Still in Azion Console, go to **Firewalls** and select that firewall.

  </DocStep>
  <DocStep title="Select the Rules Engine tab" />
  <DocStep title="Select + Rule" />
  <DocStep title="Name the rule">

  Enter a name for the rule. For example: `Apply storefront-waf`.

  </DocStep>
  <DocStep title="Set the criterion">

  In the **Criteria** section, select the `Request URI` variable, the _starts with_ comparison operator, and `/` as the argument.

  </DocStep>
  <DocStep title="Add the Set WAF behavior">

  In the **Behaviors** section, select **Set WAF**, then select the rule set you created.

  </DocStep>
  <DocStep title="Select Blocking as the mode" />
  <DocStep title="Save the rule" />
</DocSteps>

The firewall now scores every request it receives against the rule set. A rule carries at most one `Set WAF` behavior.

</Fragment>

<Fragment slot="panel.cli">

`azion create firewall-rule` reads the whole rule from a JSON file. It has no flag for a behavior or a mode.

<DocSteps>
  <DocStep title="Write the rule to a file">

  Save the following as `fw-rule.json`, with the id of your rule set in `waf_id`:

  ```json
  {
    "name": "Apply storefront-waf",
    "active": true,
    "description": "",
    "criteria": [
      [
        {
          "conditional": "if",
          "variable": "${request_uri}",
          "operator": "starts_with",
          "argument": "/"
        }
      ]
    ],
    "behaviors": [
      {
        "type": "set_waf",
        "attributes": {
          "waf_id": 21717,
          "mode": "blocking"
        }
      }
    ]
  }
  ```

  </DocStep>
  <DocStep title="Create the rule">

  Replace `<firewall-id>` with the id of your firewall:

  ```bash
  azion create firewall-rule --firewall-id <firewall-id> --file fw-rule.json
  ```

  </DocStep>
  <DocStep title="Read the output">

  The command prints the id of the new rule:

  ```text
  Created Firewall Rule with ID 131733
  ```

  </DocStep>
</DocSteps>

The firewall now scores every request it receives against the rule set.

</Fragment>

<Fragment slot="panel.api">

The criteria carry `${request_uri}`, so the body is sent from a file.

<DocSteps>
  <DocStep title="Write the rule to a file">

  Save the following as `rule.json`, with the id of your rule set in `waf_id`:

  ```json
  {
    "name": "Apply storefront-waf",
    "active": true,
    "criteria": [
      [
        {
          "conditional": "if",
          "variable": "${request_uri}",
          "operator": "starts_with",
          "argument": "/"
        }
      ]
    ],
    "behaviors": [
      {
        "type": "set_waf",
        "attributes": {
          "waf_id": 21717,
          "mode": "blocking"
        }
      }
    ]
  }
  ```

  </DocStep>
  <DocStep title="Send the create request">

  Replace `<firewall-id>` with the id of your firewall:

  ```bash
  curl --request POST \
    --url https://api.azion.com/v4/workspace/firewalls/<firewall-id>/request_rules \
    --header 'Accept: application/json' \
    --header 'Authorization: Token [TOKEN VALUE]' \
    --header 'Content-Type: application/json' \
    --data @rule.json
  ```

  </DocStep>
  <DocStep title="Read the response">

  A `202` carries the rule, with the `order` it holds among the rules of the firewall:

  ```json
  {
    "state": "pending",
    "data": {
      "id": 131732,
      "name": "Apply storefront-waf",
      "last_editor": "user@example.com",
      "last_modified": "2026-09-20T15:53:29.020679Z",
      "created_at": "2026-09-20T15:53:29.020695Z",
      "active": true,
      "criteria": [
        [
          {
            "conditional": "if",
            "variable": "${request_uri}",
            "operator": "starts_with",
            "argument": "/"
          }
        ]
      ],
      "behaviors": [
        {
          "type": "set_waf",
          "attributes": {
            "waf_id": 21717,
            "mode": "blocking"
          }
        }
      ],
      "description": "",
      "order": 1
    }
  }
  ```

  </DocStep>
</DocSteps>

A body that omits `mode` is refused with `400` and the error `10059 Required Field`, pointing at `/data/behaviors/0/attributes/mode`.

## 3. Verify that WAF blocks a request

The check is the same whichever interface built the rule. Your workload answers on a domain of the form `<id>.map.azionedge.net`, written below as `<your-workload-domain>`.

A new binding takes time to reach Azion's distributed infrastructure. Expect close to six minutes before the rule takes effect. The domain then answers inconsistently for several minutes, while the change arrives in different places. A request that still returns the earlier response has broken nothing: wait, then send it again.

Send a clean request first:

```bash
curl -i https://<your-workload-domain>/
```

The request is not scored as a threat and reaches the application, which answers it:

```text
HTTP/2 200
```

Your own application decides that status. What matters is that the request is not refused.

Now send an injection-shaped request, carrying `1' OR '1'='1` in the query string:

```bash
curl -i "https://<your-workload-domain>/?q=1%27%20OR%20%271%27%3D%271"
```

WAF refuses it:

```text
HTTP/2 400
content-type: text/html
x-azion-request-id: 1123d5bf29651faaaaf6e09dbafcc4e3
```

The body is Azion's default error page, headed **Bad Request**. Nothing in the response names WAF, the rule that matched, or the score. Record `x-azion-request-id`: that value finds the request in [Real-Time Events](/en/documentation/observe/real-time-events/).

That request tripped the internal rules `1009` and `1013`, both on the `q` argument. It scored under the SQL injection and cross-site scripting families. Your rule set is now scoring traffic.
