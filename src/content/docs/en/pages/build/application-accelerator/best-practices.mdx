A cache that varies by the wrong attribute is worse than one that does not vary at all. Every distinct value of the attribute it varies by becomes another stored object. An attribute that does not change the response therefore splits one cached answer into copies that each serve fewer requests. That choice also decides how hard the content is to purge later.

The practices below keep a variation tied to something that changes the response, and keep the cost of that variation visible. The mechanisms behind them are on [How Application Accelerator works](/en/documentation/build/application-accelerator/how-it-works/), the field names and defaults are on [Application Accelerator settings](/en/documentation/build/application-accelerator/settings/), and the ceilings are on [Limits](/en/documentation/build/application-accelerator/limits/).

Every specimen on this page is a fragment of one cache setting, as Azion API receives it. The sections follow the order in which the decisions arise: which attributes enter the cache key, how argument order is handled, and the two decisions cookies force. The last three cover when a cache TTL of 0 seconds replaces Bypass Cache, what Tiered Cache does to that rule, and how a purge reaches content that varies.

---

## Name the attributes that change the response

The `behavior` field of a cache variation decides how much of a request enters the cache key. The `all` behavior lets every query string argument that arrives into the key, including the ones the application never reads. A campaign argument appended to a shared link then produces a cached object of its own, holding the same response as the object without it.

The `allowlist` behavior varies only by the arguments you name. An argument nobody named cannot create a second object, so the number of stored copies stays tied to the content rather than to the traffic. Name the arguments the response depends on, and leave the rest out of the key.

This is the query string variation of a cache setting, with two arguments named:

```json
{
  "modules": {
    "application_accelerator": {
      "cache_vary_by_querystring": {
        "behavior": "allowlist",
        "fields": ["category", "page"]
      }
    }
  }
}
```

The cost is that the list is yours to maintain. An argument that starts changing the response has to be added to it. Until it is, requests that differ only by that argument share one cached object. For what each variation adds to a cache key, refer to [How Application Accelerator works](/en/documentation/build/application-accelerator/how-it-works/).

## Turn on query string sorting

Query string sorting decides whether the order of the arguments changes the cache key. Without it, the named arguments enter the key in the order the client submitted them. Two clients that send the same arguments in different orders then create two objects for one response, and each object serves half the requests it could.

The `sort_enabled` field of the query string variation removes that duplication by grouping the variations under one key, ordered alphabetically. This is the same variation with sorting on:

```json
{
  "modules": {
    "application_accelerator": {
      "cache_vary_by_querystring": {
        "behavior": "allowlist",
        "fields": ["category", "page"],
        "sort_enabled": true
      }
    }
  }
}
```

Sorting has one consequence at purge time. A URL purge reaches a query string variation only when the arguments arrive in the order they were presented, and with sorting on that order is alphabetical. For the purge types that reach a variation, refer to [Real-Time Purge](/en/documentation/build/cache/real-time-purge/#purge-content-that-varies).

## Vary the cache by the cookies that segment content

A request carries every cookie the browser holds for the domain, and most of them do not change the response. Analytics identifiers and consent flags arrive on the same request as the cookie the application actually reads. The `all` behavior lets all of them into the cache key, so the stored copies multiply with the cookies rather than with the content.

The `allowlist` behavior varies the key by the cookies you list and ignores every other cookie. That is what segments content by user profile, or by any other grouping the application maintains. Azion recommends it when cookies manage user sessions.

This is the cookie variation of a cache setting, with one cookie named:

```json
{
  "modules": {
    "application_accelerator": {
      "cache_vary_by_cookies": {
        "behavior": "allowlist",
        "cookie_names": ["session_id"]
      }
    }
  }
}
```

A cookie with a distinct value per visitor produces one stored object per visitor, which makes the list a decision about cardinality as much as about correctness. For the steps that configure a cookie variation, refer to [Configure Advanced Cache Key](/en/documentation/guides/application-performance/cache-and-purge/advanced-cache-key/).

## Keep private session cookies out of a forwarded response

The [Forward Cookies](/en/documentation/platform/applications/rules-engine/#forward-cookies) behavior sends the origin's `Set-Cookie` header to users even on a cache hit. Session cookies can be among the cookies that header carries. A rule that forwards cookies therefore forwards the private ones too, unless the cache setting on that path says otherwise.

To keep private session cookies from reaching users, list them in the `denylist` behavior of the cookie variation:

```json
{
  "modules": {
    "application_accelerator": {
      "cache_vary_by_cookies": {
        "behavior": "denylist",
        "cookie_names": ["session_id"]
      }
    }
  }
}
```

This is a different question from which cookies segment the content, and the two answers do not share a field: a cache setting carries one cookie behavior. The setting applied to the path where **Forward Cookies** runs is the one that carries the denylist. For the steps that create that setting and attach it to the rule, refer to [Configure cache policies](/en/documentation/guides/application-performance/cache-and-purge/cache-settings/).

## Set a cache TTL of 0 seconds where the answer can be shared

A cache TTL of 0 seconds and the [Bypass Cache](/en/documentation/platform/applications/rules-engine/#bypass-cache) behavior both keep a user off a stored copy, and they differ in what reaches the origin. Bypass Cache sends every request to the origin, so each request can receive its own content. A `modules.cache.max_age` of 0 seconds keeps the request on the cache path. Parallel requests for one object reach the origin as a single request, and an unchanged object is not transferred again.

Set the TTL to 0 seconds where dynamic content can be delivered identically to everyone requesting it at the same moment. Reserve Bypass Cache for the paths where two simultaneous requests have to receive different answers. Each option gives up what the other keeps, and there is no configuration that keeps both.

Neither option is absolute across cache layers. Bypass Cache acts on the cache layer, and an application with active Tiered Cache settings keeps caching in the tiered layer regardless of the rule. The option to set a TTL of 0 seconds exists only while Application Accelerator is on, because the module is what removes the minimum cache TTL. For the trade in full, refer to [How Application Accelerator works](/en/documentation/build/application-accelerator/how-it-works/).

## Check Tiered Cache before relying on Bypass Cache

The [Bypass Cache](/en/documentation/platform/applications/rules-engine/#bypass-cache) behavior stops Azion from caching the origin response, and [Tiered Cache](/en/documentation/build/cache/tiered-cache/) is a second cache layer behind that one. Tiered Cache does not support bypass cache. An application with active Tiered Cache settings keeps caching in the tiered layer for its minimum TTL, even with a Bypass Cache rule configured.

Confirm which cache modules the application carries before a Bypass Cache rule becomes the answer to a freshness requirement. A rule that reads as correct on the cache layer does not describe what the tiered layer does, and nothing in the rule itself records the difference. The symptom, when this is missed, is content still served from cache after the rule is in place.

Where the requirement is that no layer holds a copy, Tiered Cache belongs in the decision rather than after it. For the minimum TTL that layer keeps, refer to [Tiered Cache](/en/documentation/build/cache/tiered-cache/).

## Plan the purge when you plan the variation

A purge finds an object by its cache key, so the variations you configure are the objects a purge has to reach. A URL purge builds that key from the URL alone, and content variation plays no part in it. Variations based on cookies or device groups do not expire with it, and their copies stay in the cache.

Two purge types do reach them. A cache key purge names each variation individually. A wildcard purge ends the cache key with one of two forms instead:

```text
@@*
?*
```

`@@*` is the ending for cookie variations and for cached `POST` or `OPTIONS` objects. `?*` is the ending for query string variations. A query string variation can also be purged by URL, as long as the arguments are sent in the order the cache key holds them.

Decide this while you choose what to vary by, not after. A variation with many distinct values is expensive to purge as well as to store, because every value is another object the purge has to reach. For the purge types and the steps to run each one, refer to [Real-Time Purge](/en/documentation/build/cache/real-time-purge/#purge-content-that-varies).
