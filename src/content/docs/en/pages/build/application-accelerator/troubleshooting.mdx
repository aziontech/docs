Application Accelerator changes what a cache key contains, which HTTP methods an application caches, and which Rules Engine behaviors a rule can use. Every symptom below is something you observe in the cache or in the interface, and each section names it, gives its cause, and states the fix. For the mechanism behind them, refer to [How Application Accelerator works](/en/documentation/build/application-accelerator/how-it-works/).

---

## No cache status on a POST request

You send a `POST` request to a path that a cache setting covers, and the cache status of that request is `-` rather than `HIT` or `MISS`. A request carrying the `Pragma: azion-debug-cache` header returns the status in the `X-Cache` response header.

A cache status of `-` means the content is restricted from caching. A `POST` request whose cache setting does not have caching for `POST` turned on falls into that case, and the status is not logged. An application caches `GET` and `HEAD` natively, and it caches a `POST` or `OPTIONS` response only when Application Accelerator is on and the cache setting names the method.

- **Turn on the module**: the **Application Accelerator** switch on the **Main Settings** tab of the application gates caching for both methods. For the field each interface sets, refer to [Application Accelerator settings](/en/documentation/build/application-accelerator/settings/).
- **Name the method on the cache setting**: in the **Application Accelerator** section of the cache setting, open **Cache vary by Method** and select **POST**. In the Azion API, `cache_vary_by_method` carries `post`.
- **Follow the procedure**: the steps for both interfaces are in [Cache POST and OPTIONS responses](/en/documentation/guides/application-performance/cache-and-purge/cache-post-and-options-responses/).

The next `POST` request to that path carries a cache status instead of `-`, and its cached object takes a key that ends with the MD5 hash of the request body.

## Cookie and device group variations survive a purge

You purge the URL of an object that varies, and requests carrying the cookie or the device group that produced a variation are still answered from cache.

A URL purge converts each URL it receives into a cache key without considering content variation. Variations based on cookies, device groups, and others are separate cached objects, and the URL does not describe their keys. Those copies therefore do not expire with a URL purge, however many times you run it.

- **Purge by cache key**: name each variation of the object individually, so the purge addresses the key that holds it.
- **Purge with a wildcard**: end the cache key with `@@*`, which reaches every variation that appends the `@@` separator.

Real-Time Purge owns both procedures. For the steps, refer to [Application Accelerator purge](/en/documentation/build/cache/real-time-purge/#application-accelerator-purge).

The variations you named stop answering from cache, and the next request for each one reaches the origin.

---

## A URL purge misses a query string variation

You purge a URL that carries query string arguments, and the object that varies by those arguments is still served from cache.

Query string variations can be purged by URL, because the query string is part of the URL. The match depends on the order of the arguments. A URL purge reaches the object only when the arguments are sent in the order they were presented. Where the **Sort** toggle of **Cache vary by Query String** is on, the cache key holds the arguments in alphabetical order, so the purge has to name them in that order too.

- **Match the order the key holds**: send the arguments in the order they were presented, or in alphabetical order where sorting is on.
- **Name only the arguments in the key**: a URL purge reaches the object when it carries the arguments the cache key varies by.
- **Purge with a wildcard**: end the URL with `?*`, which reaches every query string variation of that path.

For the purge types and the steps for each one, refer to [Real-Time Purge](/en/documentation/build/cache/real-time-purge/).

The purge expires the object whose cache key holds those arguments, in that order.

## A behavior or a variable is missing from Rules Engine

You add a rule in the **Rules Engine** tab of an application, and a behavior you expect is absent from the list. **Bypass Cache**, **Forward Cookies**, and **Rewrite Request** are three of the behaviors this affects. The `${device_group}` variable is also missing from the criteria.

While Application Accelerator is off on that application, Rules Engine offers only some of its variables and behaviors for a rule. Seven behaviors and the `${device_group}` variable require the module.

To turn the module on:

<DocSteps>
  <DocStep title="Open the Applications page">

  Access [Azion Console](https://console.azion.com/) > **Applications**.

  </DocStep>
  <DocStep title="Select the application that runs the rule" />
  <DocStep title="Go to the Main Settings tab" />
  <DocStep title="Turn on the module">

  In the **Modules** section, turn on **Application Accelerator**.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

The seven gated behaviors appear in the behaviors list of a rule, and rule criteria accept `${device_group}`. For which behaviors the module gates and in which phase each one runs, refer to [Application Accelerator settings](/en/documentation/build/application-accelerator/settings/).

**Run Function** is the exception, because it requires [Functions](/en/documentation/build/functions/) as well as this module. For that case, refer to [Functions troubleshooting](/en/documentation/build/functions/troubleshooting/).

## Content served from cache with Bypass Cache configured

A rule applies the **Bypass Cache** behavior, one of the behaviors Application Accelerator gates, and requests for that path are still answered from cache.

Tiered Cache does not support bypass cache. A **Bypass Cache** rule stops Azion from caching the origin response in the cache layer. An application whose cache settings have Tiered Cache turned on keeps caching in that second layer, for the minimum TTL that layer accepts. That minimum is 3 seconds.

This is how the two features behave together, so no setting on the rule corrects it. What you observe is the tiered layer answering the request, rather than a **Bypass Cache** rule that failed to apply. For what that layer caches and the settings that govern it, refer to [Tiered Cache](/en/documentation/build/cache/tiered-cache/).
