This guide instructs you through requesting your first derived image from an application. By the end you will have:

- Image Processor turned on for one application.
- A cache setting that stores each transformation as its own object.
- A Rules Engine rule that sends image requests to the module.
- A resized image returned from a URL you wrote.

Four objects carry that result, and each one is linked to the one before it. The **application** holds the module switch. The **cache setting** belongs to the application and decides that two different transformations are two different cached objects. The **rule** belongs to the application, matches image requests, and applies both the cache setting and the **Optimize Images** behavior. The image URL then carries the transformation in its `ims` query string. A request that no rule matches is delivered unprocessed, so the rule is what makes the query string mean anything.

---

## Prerequisites

- An [Azion account](/en/documentation/fundamentals/creating-account/).
- An application that already delivers images from an origin. To create one, refer to [Build an application](/en/documentation/guides/application-development/getting-started/build-an-application/).
- The path of one image the application serves, so you can request it at the end.

---

## 1. Turn on Image Processor

The module is a switch on the application, and it is off until you set it.

<DocSteps>
  <DocStep title="Open the application">

  Access [Azion Console](/en/documentation/guides/platform/account-and-billing/how-to-access-azion-console/) > **Applications**, then select the application that delivers your images.

  </DocStep>
  <DocStep title="Go to the Main Settings tab" />
  <DocStep title="Turn on Image Processor">

  In the **Modules** section, turn on **Image Processor**, described as *Enable dynamic image editing options*.

  </DocStep>
  <DocStep title="Turn on Application Accelerator">

  The toggle is in the same section.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

**Application Accelerator** is on this list for one reason: the field that varies the cache by a query string belongs to it, and step 2 uses that field. Processing an image does not require the module, but caching each transformation separately does.

The application now carries both modules, and the **Optimize Images** behavior becomes available to its rules.

---

## 2. Create a cache setting that varies on the ims query string

Without this step the cache cannot tell one transformation from another, and it may answer a request for a 400 pixel image with a 200 pixel one.

<DocSteps>
  <DocStep title="Go to the Cache Settings tab" />
  <DocStep title="Select + Cache" />
  <DocStep title="Name the cache setting">

  In **Name**, enter `images`.

  </DocStep>
  <DocStep title="Expand Cache vary by Query String">

  The panel is in the **Application Accelerator** section.

  </DocStep>
  <DocStep title="Set Behavior to Allowlist" />
  <DocStep title="Add the ims field">

  In **Fields**, enter `ims`.

  </DocStep>
  <DocStep title="Select Save" />
</DocSteps>

The application now has a cache setting that stores one object per distinct `ims` value. For the rest of the fields a cache setting carries, including how long an object stays cached, refer to [Cache Settings](/en/documentation/build/cache/cache-settings/).

---

## 3. Create a rule that sends image requests to the module

The rule is what turns the query string into a transformation.

<DocSteps>
  <DocStep title="Go to the Rules Engine tab" />
  <DocStep title="Select + Rule" />
  <DocStep title="Name the rule">

  In **Name**, enter `Optimize images`.

  </DocStep>
  <DocStep title="Select Request Phase" />
  <DocStep title="Select the variable">

  In the criteria, select `${request_uri}`.

  </DocStep>
  <DocStep title="Select the operator matches" />
  <DocStep title="Enter the argument">

  Enter `\.(jpg|jpeg|gif|bmp|png|ico|webp|avif)`.

  </DocStep>
  <DocStep title="Add the Set Cache Policy behavior">

  In the behaviors, select **Set Cache Policy**, then choose the `images` cache setting.

  </DocStep>
  <DocStep title="Select Add Behavior" />
  <DocStep title="Select Optimize Images" />
  <DocStep title="Select Save" />
</DocSteps>

Every request for a path ending in one of those extensions now reaches Image Processor, carries the `images` cache setting, and is processed when its URL asks for a transformation.

---

## 4. Request a derived image

Ask for a width and see the response change.

Request one of your images with an `ims` query string, replacing the host and the path with your own:

```bash
curl -s -o /dev/null -w "%{http_code} %{content_type} %{size_download} bytes\n" \
  -H "Accept: image/webp,image/*" \
  "https://www.example.com/images/photo.jpg?ims=400x"
```

The response reports its status, its type, and its size:

```text
200 image/webp 8312 bytes
```

Request the same image with no query string and compare the size. The processed response is smaller, and it may also carry a different format from the file on your origin, because Image Processor delivers WEBP to the browsers that accept it.

To confirm the module handled the response rather than the origin, read the headers:

```bash
curl -sI -H "Accept: image/webp" "https://www.example.com/images/photo.jpg?ims=400x"
```

A processed response carries `x-ims: Enabled` and the size of the source image before the transformation:

```text
HTTP/2 200
content-type: image/webp
x-ims: Enabled
x-original-image-size: 484156
```

You now have an application that transforms images on request, and a URL that describes the transformation.

:::tip
Keep `ims=` as the last parameter in the URL. A request that carries another query string parameter after it may return a `504` error.
:::
