This page fixes symptoms you observe in [Image Processor](/en/documentation/build/image-processor/): a `504` error, an image that ignores its `ims` query string, a conversion or a rotation that does not apply, and an Images meter that climbs faster than the requests you send. Each section is self-contained, and you can read them in any order.

---

## A `504` error on a request whose `ims` is not the last parameter

You request an image whose URL carries `ims=` followed by another query string parameter, and the response is a `504` error.

The `ims=` parameter must be the last parameter in the URL. When another parameter follows it, the request may return a `504` error, though a request with a later parameter does not always fail this way.

- **Move `ims` to the end**: place every other query string parameter before `ims=`, as in `example.com/image.jpeg?ts=1234&ims=1000x1000`, rather than after it. For the full grammar `ims` accepts, refer to [URL parameters](/en/documentation/build/image-processor/url-parameters/).

The request returns the derived image instead of a `504` error.

---

## The image is delivered unprocessed, and the `ims` query string is ignored

You request an image with a valid `ims` query string, and the response returns the source image unchanged, with no resize, crop, or filter applied.

A transformation does not run because an `ims` query string is present. It runs because a [Rules Engine](/en/documentation/platform/applications/rules-engine/) rule matched the request and applied the **Optimize Images** behavior. A request that no rule matches is delivered unprocessed, `ims` and all.

- **Check the rule's criteria**: open the rule in the **Rules Engine** tab of the application and confirm its criterion matches the request, such as `${request_uri}` or `${uri}` with the `matches` operator against an argument like `\.(jpg|jpeg|gif|bmp|png|ico|webp|avif)`.
- **Confirm the behavior is present**: the rule's **Request Phase** must apply the **Optimize Images** behavior. For the behavior's fields, refer to [Image Processor settings](/en/documentation/build/image-processor/settings/).
- **Follow the procedure**: the steps for building the rule are in [Configure Image Processor](/en/documentation/guides/application-performance/delivery-optimization/process-images/).

The next request that matches the rule returns a derived image, and the response carries `x-ims: Enabled`.

---

## The image is not converted to WEBP or AVIF

You request a format conversion to WEBP or AVIF, and the response is not delivered in that format.

Converting to WEBP or AVIF requires the request to carry an `Accept` header naming the format: `Accept: image/webp` or `Accept: image/avif`. A request that does not carry that header does not receive the converted format.

- **Add the header with a rule**: add the **Add Request Header** behavior to the rule's **Request Phase**, with its value set to `Accept: image/webp` or `Accept: image/avif`. For the behavior's fields, refer to [Image Processor settings](/en/documentation/build/image-processor/settings/).

The next matching request receives the image in the requested format.

---

## Every request for the same derived image is processed again, and the Images meter climbs

You request the same image with the same `ims` query string more than once, and each request counts as a processed image against the account's Images meter instead of being served from cache.

The cache key for a derived image carries the `ims` query string, but varying the cache on a query string is an [Application Accelerator](/en/documentation/build/application-accelerator/) field: `cache_vary_by_querystring` lives under `modules.application_accelerator` in a cache setting. Varying the cache on `ims` requires that module; processing an image does not. While `ims` is absent from that field, the cache does not tell one derived image from another, and Image Processor runs again on each request.

- **List `ims` in the query-string allowlist**: in the **Application Accelerator** section of the cache setting, set **Behavior** to _Allowlist_ and add `ims` under **Fields**. For the field descriptions, refer to [Image Processor settings](/en/documentation/build/image-processor/settings/).

A repeated request for the same `ims` value returns from cache, and only the request that built that derived image counts against the Images meter.

---

## A resize larger than the original does not enlarge the image

You request `fit-in/WidthxHeight`, or a width or height larger than the source image, and the derived image is not larger than the original.

This is how the resize behaves, not a fault. `fit-in` never enlarges an image: when the requested area is larger than the image dimensions, the image keeps its original size. Outside `fit-in`, a request for a resolution larger than the original renders at the highest possible resolution the source supports.

The derived image renders at the size of the source image, or at the largest size the requested box can hold. For the rest of the resize grammar, refer to [URL parameters](/en/documentation/build/image-processor/url-parameters/).

---

## A rotation value has no effect

You set `?ims=filters:rotate(Angle)` to a value outside `0`, `90`, `180`, `270`, and `360`, and the derived image is not rotated.

Rotation accepts only those five values. A value outside that list does not rotate the image.

- **Use one of the five accepted values**: `0`, `90`, `180`, `270`, or `360`. For the full syntax, refer to [URL parameters](/en/documentation/build/image-processor/url-parameters/).

The image rotates to the left by the requested angle.
