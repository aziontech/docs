A request for a transformed image can return a file heavier than the page needs, an image cropped in a way nobody intended, or an error that traces back to where one parameter sits in the URL. A cache that cannot tell one transformation from another can serve a visitor the wrong version of an image, or count the same transformation against a usage limit more than once.

[Image Processor](/en/documentation/build/image-processor/) reads each of these from the request itself and from the cache setting around it. The practices below set the quality value to request, choose `fit-in` over a plain resize where the aspect ratio matters, and place `ims` last in the query string. They also cover the header a format conversion needs, the field that lists `ims` in a cache setting's allowlist, and how long a derived image is worth keeping in cache.

---

## Set quality to 85

The quality filter sets how much Image Processor compresses a derived image, trading file size against visual fidelity. `?ims=filters:quality(85)` requests the value Azion documents as optimizing the file with no noticeable loss of visual quality.

A lower value shrinks the file further, and the loss becomes visible in the delivered image. A higher value adds file size a viewer cannot see, because the visible difference already stopped below it. Request quality 85 for the derived images a page serves, and move off it only when one image needs to look sharper or transfer smaller than that.

For the full range the argument accepts, refer to [URL parameters](/en/documentation/build/image-processor/url-parameters/).

---

## Use fit-in when the aspect ratio matters

A resize written as `?ims=WidthxHeight` fits the derived image to an exact box, and Image Processor may autocrop it to get there. When the requested proportions do not match the source, the crop is centered and runs along whichever axis overflows, which can remove part of the subject the request meant to keep.

`?ims=fit-in/WidthxHeight` fits the image inside the same box instead, with the aspect ratio preserved. Image Processor never enlarges the source to reach the box: the derived image stops at whichever bound it reaches first, so it can land short of the full width or height.

`?ims=400x400` autocrops a landscape photograph to fill the square exactly. `?ims=fit-in/400x400` keeps the same photograph whole inside the square, shorter on one side instead of cropped. Use the plain resize when a layout needs the box filled exactly, and `fit-in` when the image cannot lose an edge.

For the rest of the resize forms, refer to [URL parameters](/en/documentation/build/image-processor/url-parameters/).

---

## Put ims last in the query string

Image Processor expects the `ims` parameter to be the last one in a request's query string. When another parameter follows it, the request may return a `504` error.

`example.com/image.jpeg?ts=1234&ims=1000x1000` places `ims` last, and the request is valid. `example.com/image.jpeg?ims=1000x1000&ts=1234` places another parameter after it, and that request may return a `504`.

Add every other query string parameter before `ims`, not after it, including a cache-busting timestamp or a tracking value appended by another system.

---

## Send an Accept header when you convert to WEBP or AVIF

Converting the derived image to WEBP or AVIF depends on a header. `filters:format(webp)` or `filters:format(avif)` in the `ims` string requires the request to also carry `Accept: image/webp` or `Accept: image/avif`.

The **Add Request Header** behavior of [Rules Engine](/en/documentation/platform/applications/rules-engine/) adds that header inside the **Request Phase**, so the conversion does not depend on whether the client sent it. This is the shape of that behavior in a rule set to request WEBP:

```json
{
  "type": "add_request_header",
  "attributes": {
    "value": "Accept: image/webp"
  }
}
```

Match the value to the format the `ims` string converts to: `Accept: image/avif` for a rule that converts to AVIF. For the criteria that scope a rule to image requests, refer to [Settings](/en/documentation/build/image-processor/settings/).

## List ims in the cache setting's allowlist

A cache setting keyed without `ims` does not distinguish one derived image from another: two requests that build different transformations from the same source image can share one cached response, and a visitor can receive whichever transformation is already stored.

Adding `ims` to the `cache_vary_by_querystring` allowlist keys the cache by that parameter instead, so each transformation gets its own stored copy:

```json
{
  "modules": {
    "application_accelerator": {
      "cache_vary_by_querystring": {
        "behavior": "allowlist",
        "fields": ["ims"]
      }
    }
  }
}
```

In Azion Console, the same fields are **Behavior**, **Fields**, and **Sort**, under the **Application Accelerator** section of a cache setting. `cache_vary_by_querystring` lives under `modules.application_accelerator`, so varying the cache on `ims` requires the [Application Accelerator](/en/documentation/build/application-accelerator/) module. Processing an image does not require it.

For the rest of the fields a cache setting carries, refer to [Settings](/en/documentation/build/image-processor/settings/).

---

## Cache derived images for a long time

Every transformation Image Processor performs counts toward the monthly Images meter, whether it resizes, crops, converts a format, or applies a filter. A request the cache already holds an answer for does not reach Image Processor again, so it adds nothing to that count.

Set the cache setting's maximum age for a derived image to the longest duration the source content can tolerate. Every request the cache answers on its own is one fewer image counted against the plan's monthly allowance, and a source image that changes rarely can hold its derived versions in cache for a long time without going stale. A short cache duration forces Image Processor to rebuild the same transformation on a schedule unrelated to whether the source image changed.

The duration is the cache setting's `max_age`, under the `cache` module. Set it on the cache setting the image rule applies:

```json
{
  "modules": {
    "cache": {
      "behavior": "override",
      "max_age": <seconds_the_source_content_can_tolerate>
    }
  }
}
```

The ceiling that field accepts is on [Cache Settings](/en/documentation/build/cache/cache-settings/). For what counts against the Images meter and what does not, refer to [How Image Processor works](/en/documentation/build/image-processor/how-it-works/).
